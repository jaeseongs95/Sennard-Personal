# Golden cases: the external contract of the server

This table is the case list of the golden tests in `java/sennard-personal/src/test/java/io/github/jaeseongs95/sennard/serverit/golden`
(`ToolsListGoldenTest`, `ToolGoldenTest`, `HookGoldenTest`; the comparison is `Golden.java`). The files are in this directory:
`list/`, `tools/`, `hooks/`. They were written from the server as it is at 6.0.0 (commit e0e1bdd6) and are the completion criterion of every
later change to how the server is built: the answers must stay the same, and a difference needs a reason that the change is meant to make it.

188 cases: 5 protocol (L), 98 tool (T: every tool has at least one success and one error it really gives), 9 shared
refusals (X), 76 hooks (H: the 38 recorded bodies each alone, `H-<os>-<host>-<event>`, and the same 38 as the course of one session per OS and host,
`H-seq-<os>-<host>-<step>-<event>`, because most of a hook's answer depends on what the earlier events left). 247 normalization rules (one per JSON pointer of one case, below).

## Running

- Compare (default): `cd <repo>/java && ./gradlew --no-daemon --console=plain :sennard-personal:test --tests 'io.github.jaeseongs95.sennard.serverit.golden.*'`.
  A difference fails with the case ID and the JSON pointer of the first difference, for example `case T-start_workflow-ok: first difference at /body/result/content/0/text/data/runId`.
- Rewrite: the same with `-Dsennard.golden.update=true`. Only this writes files. Rewrite only for a change that is meant to alter the contract, and say so in the commit.
- `theTableListsExactlyTheseCases` of each class fails when a row has no case or a case has no row.

## What a case is

- Each case sends the bytes a host sends to the assembled server (real PostgreSQL, the stand-ins `ToolServerSupport` names), under its own session
  (the identifier is a name-based UUID of the case ID, so it is the same on every run). The server is started once per class.
- A tool case may first make calls of its own to reach its state; only its last call is the golden answer.
- Standard answer: the HTTP status, the Content-Type and the whole JSON-RPC body. For a tool, `content[0].text` is parsed, so every member of the
  `api-result.v1` envelope (`schemaVersion`, `ok`, `data`, `error{code,message,messageKey,params,details}`), `isError` and `_meta` is compared.
  Every tool but `codex_hook` answers with this envelope, `run_skill_check` and `get_background_job` among them (`data` holds the check's `{exitCode, value}`, `{jobRef, state}` or the job; a refused call is an `error`).
  `codex_hook` answers the hook's own JSON, because Codex's hook runner reads the text of the result as the hook's answer; `ToolEnvelopeServerTest` holds every other tool of `tools/list` to the envelope.
- The tool cases use the recorded Windows Codex `_meta` (`hook-fixtures`, `mcp-meta-fixtures`) on every OS, so they are the same on Linux.
  The hook cases use the recording of their own OS (`H-windows-*`, `H-linux-*`), so there is one golden per OS recording.
- Objects are compared by member name, not by order (the server builds some objects from `Map.of`, whose order differs between JVMs); arrays by position.
  The files are written with members in name order. `L-tools_list` is the exception: its exact bytes are the golden.
- The language is English (`Locale.US` for the run; the server's message locale is `en`).

## Normalization

Only what changes from run to run or from machine to machine is replaced, and only at the JSON pointer written in the row of its case.
No rule ignores a field, a type or a whole string. A pointer of a `T-` or `X-` row is relative to the envelope
(`/body/result/content/0/text`); a pointer that starts with `/body` is absolute (the `H-` rows). A value that does not have the form its rule names is left as it is,
so the comparison shows it. Syntax of a rule: `` `pointer` ~ `regex` → `placeholder` `` replaces the parts of the string that match; without `~` the whole value is replaced.

| Placeholder | Stands for | Why it differs |
| --- | --- | --- |
| `<TIME>` | an ISO-8601 time, whole value or inside a text | the clock of the run |
| `<UUID>` | a random UUID inside an identifier (`task-`, `root-`, `run-task-<uuid>-n`, `lease-`, `prop-`, a message, job, upload or attachment id) | generated per run. For a run id the rule takes the counter after the UUID too (`run-task-<uuid>-n` becomes `run-task-<UUID>`): the counter counts the runs the server has made so far, so it moves whenever a case that makes a run is added or removed, and no other case may be shaken by that |
| `<DIGEST>` | `sha256:` and 64 hex | a digest of a value that holds a generated id, a time or a path |
| `<HMAC>` | `hmac-sha256:` and 64 hex | keyed with this server's random secret |
| `<TOKEN>` | a state, integrity, restore, plan or session token | derived from generated values or the secret |
| `{WS}` | the workspace folder of the golden tests, `build/golden-ws/<uuid>` | random folder; native and slash forms, case-insensitive, the rest of the path with slashes |
| `{PROFILE}` | the folder the two background-job cases read, a new folder under the OS temporary directory (outside any checkout, so the baseline capture refuses it the same way on every machine) | random name, OS-specific temporary directory |
| `{REPO}` | this checkout's root | where the checkout is; the rest of the path with slashes |
| `{ADMIN_PORT}` | the admin page's port in `adminUrl` and in the message that names it | a free port per run |

## Kept as it is, on purpose

- `serverInfo.version` and `currentVersion` are checked against `release/version.json` before normalization. The skill cases (`get_skill_inventory`,
  `classify_skills`, `record_skill_selection`) read this repository's `skills/`, and the SessionStart and PreInvocation hook answers carry its skill
  list (and the path of `skills/orchestrator/references/intake.md`), so a change to a skill file changes them.
- The inputs of the tool cases are those of the tool tests (`ToolContractServerTest`, `ContinuityMessagingToolContractTest`, `WorkflowToolsServerTest`,
  `ToolRulesServerTest`) where one exists; the ones without are written in the row.
- Odd answers are kept: `T-claim_workflow_attempt-root_not_found` (no argument is answered `RUN_NOT_FOUND` for the root, not `INVALID_INPUT`),
  and `X-convert-update_session_status-summary` (a number for a string is `INVALID_INPUT` without `ARGUMENT_CONVERSION_FAILED`).
