# Contributing

This guide is for people who modify Sennard itself. The repository working rules (structure and responsibilities, the vendor-independence principle, branches, and the distribution contract) are defined authoritatively in [AGENTS.md](AGENTS.md) (Korean), and this document summarizes the order for preparing and submitting changes.

**Outside contributions are not accepted.** Sennard is licensed under AGPL-3.0-or-later and its copyright holder also licenses it commercially, so the project does not accept pull requests or other code contributions from outside the project, and no contributor license agreement is offered. Issues and private security reports remain welcome. This guide describes the working rules for the maintainer and the agents the maintainer directs.



- **Vendor independence:** Shared skills, contracts, MCP tools, and the runtime do not assume a specific AI product or host API. Host-specific hooks, identity observation, wake-ups, and distribution formats are kept only within adapter or overlay boundaries. Whichever host, model, or actor (main session or subagent) runs it, the same code must reach the same decision.
- **Testing on three hosts:** Every change, including a small fix for a single defect, is investigated and actually tested on all three hosts: Claude Code, Codex, and Antigravity. Hosts that could not be tested are reported as unverified.
- **Keeping changes small:** Divide changes into small units based on one skill or one common contract boundary. Before broadening the responsibility of a specialist skill or making it overlap with another skill, explain the effect on orchestrator routing, contracts, and existing standalone invocations. Separate formatting cleanup unrelated to the implementation into its own change.

## Change Procedure

1. Create a work branch following gitflow. `main` holds only released versions, and `develop` is the integration branch for the next version. Create `feature/<task-name>` from `develop` for a new feature or fix, and merge it into `develop`. A release is prepared on `release/<version>` created from `develop`, which receives only the version number, the release notes, and pre-release fixes; it is merged into `main`, tagged, and then merged back into `develop`. An urgent fix to a released version is made on `hotfix/<version>` created from `main` and merged into both `main` and `develop`. If the user specifies a branch name, use that name. Work branches named `codex/`, `claude/`, or `gemini/` that were created before this rule remain as they are until they are merged.
2. Check the repository structure and conventions in [Architecture](docs/contributing/architecture.md) and [Development Reference](docs/contributing/development.md).
3. Include tests with the change. Each skill has normal, boundary, and expected-failure cases. Which tests run in CI and which run on the test server is described in [Testing and CI](docs/contributing/testing-and-ci.md).
4. If generated artifacts (`claude-plugin/`, hook definition files) contain the source, regenerate them and commit them together. [Generated Artifacts](docs/contributing/development.md#generated-files)
5. Every Java source file and every SQL migration script starts with the SPDX license header (three comment lines, see [ADDITIONAL-TERMS.md](ADDITIONAL-TERMS.md)). Run `./gradlew spotlessApply` from `java/` to add it; `spotlessCheck` runs under `check` and fails on a file without it.
6. Run the verification commands below.
7. Write commits as imperative Conventional Commits, such as `feat: add acceptance evidence validator` and `docs: define skill boundaries`.

```bash
cd java
./gradlew test --continue
cd ..
git diff --check
```

The full verification order and the role of each command are described in [Development Reference](docs/contributing/development.md#development-environment-and-verification-commands).

## Running the Tests

The full JUnit suite runs on a developer machine with `./gradlew` from `java/` and nothing else; no wrapper script is needed.

- **Gradle's own JVM:** `./gradlew` needs a JDK 17 or later to start, found through `JAVA_HOME` or the `PATH`. The build compiles and tests with JDK 25, which Gradle selects as a toolchain: an installed JDK 25 is found automatically (`JAVA_HOME`, the JVM running Gradle, the usual install folders), and a machine that has none downloads it through the foojay toolchain resolver declared in `java/settings.gradle.kts`. The download needs network access to `plugins.gradle.org` once (the plugin) and to the foojay API and the JDK vendor's site when a JDK is downloaded; the dependencies come from Maven Central. To use a JDK that is installed in a non-standard folder, list it in the user's own `gradle.properties` (`<GRADLE_USER_HOME>/gradle.properties`, not in this repository): `org.gradle.java.installations.paths=<folder of the JDK>`.
- **Isolation:** every test JVM (every `Test` task) starts without the variables of the agent session that runs Gradle (`SENNARD*`, `CLAUDE*`, `CODEX*`, `GEMINI*`, `ANTHROPIC*`, `OPENAI*`), so a test cannot reach that session's MCP server or relay. Its home and temporary folders (`user.home`, `java.io.tmpdir`, `HOME`, `USERPROFILE`, `TEMP`, `TMP`, `TMPDIR`) and the product's own places (`SENNARD_INSTALL_ROOT`, `SENNARD_STATE_DIR`, which the child JVMs of a test inherit; they do not inherit `user.home`) are folders under the module's `build/isolated/<task>/`, so no test reaches the real profile. `TestIsolationTest` in `sennard-protocol` checks this.
- **Memory and parallel execution:** the build states no heap, no processor count and no worker count of its own: the build's JVM, the number of tasks that run at the same time (`org.gradle.workers.max`) and the heap of a test JVM are Gradle's defaults, and a test JVM sees all processors. `org.gradle.parallel=true` runs the modules side by side. A machine that wants others states them itself, in its own `<GRADLE_USER_HOME>/gradle.properties` or on the command line: `org.gradle.jvmargs`, `org.gradle.workers.max`, and for the test JVMs `-Psennard.test.heap=<size>`, `-Psennard.test.cpus=<n>` and `-Psennard.test.childHeap=<size>` (the heap of the JVMs that tests start; without it they get the heap of the test JVM). A machine on which several builds run at once and must stay within one memory limit can switch the heap ledger on with `sennard.heap.ledger=true` and `sennard.build.heapLimitMiB=<MiB>` (no default, no upper bound): each build then reserves its daemon, and each running `Test` or `JavaExec` task its heap, in a ledger folder shared by the builds (`sennard.heap.ledgerDir`, the Gradle user home's `sennard-heap-ledger` when not given), and a task waits while the reservations are over the limit (`sennard.heap.maxWaitMinutes`, 60). The `Test`, `JavaExec` and `Exec` tasks of one build run one at a time with the ledger on: they share a Gradle build service that allows one user (`maxParallelUsages = 1`), so Gradle's scheduler holds a sibling back before it starts, and a task does not wait for a sibling inside a worker place (that left a build without a place for the task that held the reservation); only the wait for the reservations of other builds is the ledger's. The tests of `java/build-logic` run in `sennard-repo-tools` for the same reason. The ledger's wiring is the Java class `SennardBuildLogicPlugin` of `java/build-logic` (not a script plugin, whose class loader is isolated from the plugins of the root script), and `HeapLedgerBuildTest` (`sennard-repo-tools`) runs small builds with that plugin through Gradle TestKit: with the ledger on and `--max-workers=2`, three `Test` tasks whose reservations together are over the limit must finish. The performance measurements `perfBaseline` stay at one JVM; they include the five-round measurement of the session start on a real installation (`HookStartsServerProcessTest`), which `test` leaves out, while `test` keeps the case that runs one such start and asserts that the server it started answers. Run `./gradlew :sennard-personal:perfBaseline` for them (it needs the database named below).
- **Gradle's own features:** the daemon is on (CI uses `--no-daemon`, as a runner is used once), the build cache (`org.gradle.caching`) takes compilation, resources and jars from an earlier build of the same inputs, and the configuration cache (`org.gradle.configuration-cache`) keeps the configuration for the next build. A `Test` task is never taken from the build cache: a test run is run again. Do not add `--rerun-tasks` (it compiles everything again); to run the tests of a module again without that, use `./gradlew :<module>:test --rerun`, and `./gradlew :<module>:buildDependents` to check a module and the modules that depend on it.
- **Running at the same time:** the folders above belong to one working copy, so tests of two working copies (for example two `git worktree` folders) can run at the same time. Gradle's caches use file locking and may be shared by several builds, so the Gradle user home needs no separation. Do not run more full runs at once than the processors and memory of the machine allow: the connection timeout of the store is one second, and when more builds compete for the processors, tests that open a database connection or start a server fail on time and not on a defect. Check the available memory before starting a run.
- **The test database:** the tests that need the business schema (the classes and methods tagged `business-db`, in `sennard-store-pg`, `sennard-server` and `sennard-personal`) are not part of `test`. They are the task `businessDbTest` of each of those modules, and they run on one PostgreSQL database that you name (the tests run on PostgreSQL only). The JDBC driver is the user's in the product and so in the tests: the build copies the PostgreSQL driver (configuration `businessDbDrivers`) into `build/business-db-drivers`, which is the driver path of the tests, and `-Psennard.test.businessDb.driverPath=<jar or folder>` names another. Run: `./gradlew businessDbTest -Psennard.test.businessDb.url=<jdbc url> -Psennard.test.businessDb.user=<account> -Psennard.test.businessDb.passwordFile=<file>`. The build has no default database: when the task is requested and one of the three is missing, it fails before it starts anything; the tests are never skipped. The account is the one that owns the schema `sennard`, as the product connects with one account too. The test code reads the password from the first line of the password file and hands it to the JDBC driver as a property; it is never printed, logged or put on a command line. Every test class starts by dropping the schema `sennard` and migrating it again; nothing else in the database is touched. The database is one resource: the build lets one task use it at a time (a shared Gradle build service) and runs one test JVM for it, so run one build at a time against a database. **CI does not run them:** its workflows have no database and do not request `businessDbTest`; `test` and `build` leave the tagged tests out.
- **Results:** `java/<module>/build/test-results/test/*.xml` and the HTML report under `java/<module>/build/reports/tests/test/`.

## Third-Party Licenses

Sennard is distributed under AGPL-3.0-or-later with the additional terms in [ADDITIONAL-TERMS.md](ADDITIONAL-TERMS.md). The release jar holds the class path of `sennard-personal` (`runtimeClasspath`: the project modules, `sennard-hook-client` among them, and the libraries they use). Two checks guard what goes into it; both run in `java/` under `check`, and so under `build`:

- `./gradlew :sennard-personal:checkLicense` reads the license of every library of that class path from its POM (parent POMs included), normalizes the names, and fails when none of a library's licenses is in [`java/config/license/allowed-licenses.json`](java/config/license/allowed-licenses.json). A library with no license is not allowed either. The failure message lists each library with the license strings that were found. To allow a license that is acceptable under AGPL-3.0-or-later, add its normalized name to the allow-list; to allow one library only, add an entry with `moduleName` (and `moduleVersion`). A license that is spelled in a way the plugin does not recognize is mapped to a known one with a rule in [`java/config/license/license-normalizer-bundle.json`](java/config/license/license-normalizer-bundle.json) (`transformationRules`, in the format of the plugin's [default bundle](https://github.com/jk1/Gradle-License-Report/blob/master/src/main/resources/default-license-normalizer-bundle.json)). Licenses that are not compatible with AGPL-3.0-or-later (for example GPL-2.0-only, LGPL, or EPL-1.0 on their own) are not in the list; do not add them without a decision.
- `./gradlew :sennard-personal:generateThirdPartyNotices` rewrites [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) from the same report, and `./gradlew :sennard-personal:checkThirdPartyNotices` fails when the committed file is not current. Run the generation after a dependency changes and commit the file with the change. The release jar carries the file under `META-INF/`.

The report is made by the [Gradle-License-Report](https://github.com/jk1/Gradle-License-Report) plugin (Apache-2.0; its version is in `java/settings.gradle.kts`). Its tasks are not compatible with the configuration cache, so a build that runs them runs without that cache.

## Pull Requests

Pull requests from outside the project are not accepted. For the maintainer's own pull requests, state the purpose of the change, the affected skills and MCP paths, whether contracts or manifests change, the verification commands run and their results, and the hosts tested and not tested.

## Adding Skills and Providers

- Create a new specialist skill directly in the repository and update the lock with `:sennard-repo-tools:updateSourceLock`. [Adding Skills](docs/contributing/development.md#adding-a-skill)
- Name skill directories in `kebab-case` and match them to the frontmatter `name`. Specify the application conditions, exclusion conditions, inputs, outputs, and failure handling. Do not put specialist judgment in the orchestrator; add only the necessary connection rules.
- Register each added skill in `skills/registry.json` with its capability, phase, preconditions, required and generated artifacts, and risk gate.
- When adding a provider that overlaps an existing capability, record a different priority and a non-empty `selectionCriteria`. MCP prefers the provider with the higher priority and does not interpret the natural language of `selectionCriteria` at run time. If a different provider must be selected automatically depending on request conditions, declare a specific capability for each.
- When adding or deleting a skill, or changing its name, version, or role, update the skill tables in `README.md` and `README.ko.md` in the same change.

## Version Numbers and Releases

Compatible skill additions are classified as a plugin minor version, fixes to existing behavior as a patch, and changes that break contracts, skill names, or permission scopes as a major version. The version of each specialist skill is maintained separately from the plugin version. The location of release notes and the release procedure are described in [Release](docs/contributing/release.md).

## Security

Report vulnerabilities through the private reporting channel in the [Security Policy](SECURITY.md), not through public issues.
