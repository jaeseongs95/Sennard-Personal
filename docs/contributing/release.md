# Release

This document describes the version number, release notes, pre-release checks, and supply-chain metadata. A release (merging into main, tagging, a GitHub Release, and installation) is performed only with the explicit approval of the user.

A release follows the gitflow order. A `release/<version>` branch is created from `develop` and receives only the version number, the release notes, and pre-release fixes. When the pre-release checks pass, `release/<version>` is merged into `main`, the commit is tagged `v<version>`, and then `release/<version>` is merged back into `develop`. An urgent fix to a released version is made on `hotfix/<version>`, created from `main`, and merged into `main` and `develop`. The complete branch rules are in [AGENTS.md](../../AGENTS.md).

## Version Number

The version number follows SemVer. A change that breaks an existing contract, a skill name, the permission scope, or user settings is a major change, a compatible feature addition is a minor change, and a change that contains only fixes is a patch. The versions of the specialist skills themselves and the plugin version are managed separately.

The single source of the plugin's current version is `release/version.json`. `:sennard-repo-tools:syncReleaseMetadata` generates the current-version surfaces (the manifests, the marketplace, the two `release-version`, `release-install`, and `release-agy` markers in the README files, and the `release-version` marker in the [roadmap](roadmap.md)), and `:sennard-repo-tools:checkReleaseMetadata` fails on missing or duplicate markers and on drift. These commands do not create a tag, a GitHub Release, a marketplace installation, or a deployment.

The personal edition starts at `1.0.0` in [Sennard-Personal](https://github.com/jaeseongs95/Sennard-Personal). Create its tags, release notes and assets in that repository. Qualify the first personal release with a new installation and an empty business database. Repository URLs are not generated by `syncReleaseMetadata`: keep the marketplaces, source links, update tag-list API, annotated-tag URL prefix and update-notice links consistent with the personal repository.

## Release Notes

- Location: `docs/release-notes/release-notes-v<version>.md`. The first personal release is `docs/release-notes/release-notes-v1.0.0.md`. One file contains the English part first, followed by the Korean part. Earlier release notes are historical records.
- The body of the GitHub Release is created from this file.

  ```bash
  gh release create v<version> --notes-file docs/release-notes/release-notes-v<version>.md
  ```

- The content of the notes of a version that has already been released is not modified. If a document path changes and a relative link breaks, only the link target is corrected.
- The language, the section composition, and the order of the notes follow [Document Format](document-format.md).
- When a release is published, `.github/workflows/antigravity-package.yml` creates the Antigravity installation ZIP and uploads it to that release.
- When a release is published, `.github/workflows/server-package.yml` builds the one release jar and its `.sha256` file on one runner (`:sennard-personal:releaseJar`), checks the jar name against the tag and the checksum, and uploads both to that release only when the checks have passed. When it is run with `workflow_dispatch` without a tag, nothing is uploaded to a release and the result remains only as a run artifact. There is one runner and no OS matrix because the jar is the same file on every operating system.

## Pre-Release Checks

A release candidate must have the plugin manifests, the included skills, and the release jar all pointing to the same source state. If a contract or a skill has changed, the verification results that include that change are kept.

Two assets are attached to the GitHub Release: `sennard-<version>.jar` and `sennard-<version>.jar.sha256` (`:sennard-personal:releaseJar`). The user runs the jar with their own JDK 25; there are no archives per OS and no bundled runtime. The jar is reproducible (no file times, a fixed order of entries), so that the jar the workflow builds and the jar built on the maintainer's computer have the same SHA-256. Before the release is published, the two SHA-256 values are compared, and a difference stops the release.

Before a release, the following are confirmed.

- `./gradlew test --continue` in `java/` passes on JDK 25. The repository contract tests confirm that the skill metadata, the registry, the integrated checksums, and the generated files agree.
- `:sennard-repo-tools:checkReleaseMetadata` confirms that `release/version.json` agrees with all the current-version surfaces.
- `:sennard-repo-tools:publicExport -Ptool="check --ref HEAD"` passes the classification of the files to be exported and the check for private names.
- `git diff --check` reports no whitespace errors.
- The tests of `sennard-personal` confirm, on the designated business database, that existing runs, `revision`, the run ID sequence, and the plan signing key persist even after a server restart.
- The 24-hour cache of the update check, the retry after one hour following a failure, the notice shown once per version, and the non-blocking failure path are verified with fixtures.
- The current version of the release candidate is compared with the latest stable tag of the public repository, and it is confirmed that the update notification does not change installed files or marketplace settings.
- The quality evaluation status and the runtime activation status of the included skills are recorded separately in the public documents. A skill that has not passed the quality gate is deactivated by default; however, when the user has confirmed the current candidate and the remaining limitations and has explicitly approved an active release, the registry, the direct descriptor, and implicit invocation are activated consistently in the same release.
- It is confirmed that the `bootstrapExecution` of an orchestrated semantic workflow, the `executionRequirement` of each stage, and `StageResult.executionContext` are bound to the plan HMAC and the stored receipt, and that missing or under-provisioned execution is blocked with `BINDING_REQUIRED` and `BINDING_INVALID` respectively. It is also confirmed that an observation ID is consumed only once even after a server restart and concurrent database connections, and that a non-canonical base64url notation of an HMAC token with the same bytes is rejected by both the schema and the internal check. At the strict MCP claim, the guarded start, and the semantic stage boundaries, a plan without assurance is not allowed to proceed.
- A test confirms that a request is rejected with `BINDING_REQUIRED` when there is no caller observation and with `BINDING_INVALID` for a contradiction or a reuse error. Before a release, a new Claude Code session that leaves a transcript is started with the built plugin, and it is confirmed that one flow from `plan_workflow` through `open_convergence_root`, `claim_workflow_attempt`, `start_guarded_workflow`, and `record_stage_result` to `finalize_workflow` passes with the observed values, and that a `plan_workflow` called by a subagent is observed as the subagent actor.
- A test confirms that the `outputFile` of `record_stage_result` rejects a digest mismatch, a non-JSON attachment, a size above 16 MiB, and a missing or other session's attachment, and that it passes through the same checks as inline output and leaves only a reference in the receipt. With a real request that has stage output proportional to the size of the repository, a new Claude Code session is started and it is confirmed that the orchestrated run reaches finalize.
- A deactivated skill keeps a fail-closed instruction that does not run a provider or a script when invoked directly. For an active skill, it is confirmed that the states of the registry, the direct descriptor, `agents/openai.yaml`, and `SKILL.md` all agree.
- The user documents explain that the store keeps the full `WorkflowReceipt` and `StageResult` and the `core` and `evidenceRefs` of the direct continuity snapshot in plain text, the confirmation-based retention and deletion policy, the handling of the backup tables (`continuity_cleanup_backup`, `workflow_cleanup_backup`), and the OS access permission policy.

Before publication, the version, the change summary, the compatibility impact, and the known limitations are confirmed. If the database schema (the migration scripts) changes, compatibility is confirmed by starting the release candidate against a copy of the state folder of the previous version, and the recovery procedure is also recorded in the change summary. If a high-risk change is included, it is also confirmed that the target identifier and the verdict of the independent audit match the current release candidate.

Immediately before creating the public GitHub repository or pushing to it for the first time, the repository address and the visibility are confirmed again. After a release, it is confirmed that the `.codex-plugin/plugin.json` and `.agents/plugins/marketplace.json` of the tag point to the same version. In a clean Codex environment, after the marketplace is added, it is confirmed that all the specialist skills in the registry (23 as of 4.0.0) and the orchestrator are discovered, that the continuity MCP tools (such as `checkpoint_context`) appear in `tools/list`, and that deactivated skills are excluded from MCP routing. The MCP `tools/list`, representative planning, execution, and abort flows, and the explicit continuity tools are also checked. The installation check is performed on each of the three hosts, Claude Code, Codex, and Antigravity, and a host that could not be checked is recorded in the notes as unverified.

After the schema has been raised, reinstalling only the plugin does not roll it back. A version that changes the PostgreSQL schema states in its release notes how to revert.

## Skill Versions and Checksums

`skills/source-lock.json` fixes the version and the integrated checksum of each skill. All skills are managed directly in this monorepo. The repository contract tests cross-check the registry, the direct descriptors, the `SKILL.md` metadata, and the local checksums without a network, and when a skill is changed the checksum is updated with `:sennard-repo-tools:updateSourceLock`.
