# Execution Observation and Host Integration

Execution observation comes from the `execution` of the caller verified by the server (`VerifiedCaller`). The caller ingress of each host fills in that value from facts the host wrote, the common `HostAttestationProvider` determines eligibility through a trusted adapter, and `WorkflowService` enforces the binding of task, run, stage, and revision, and single consumption. An observation does not expire with time. Reuse is prevented permanently by the single-consumption record, and only an observation with a future timestamp is rejected. The `executionContext` JSON of a tool argument or a wished-for configuration value does not substitute for an observation. There is no signed token (`_hostAttestation`, `aghs1`, `aghs2`).

## Observation and Execution Eligibility

- `caller.execution` is `{model, effort, turnId, provenance}` or `{unavailable: reason}`. Only the tools that record an observation (`plan_workflow`, `record_stage_result`, `classify_skills`, `record_skill_selection`) consume it. Sennard has no execution floor.
- Two fields are both called `provenance`, and they answer different questions. `caller.execution.provenance` says where the model and the reasoning level came from (the host reported them). `recordedBy.provenance` of a stage result (`ObservedCaller`, `WorkflowCall.of`) says how the server came to know *who* recorded it: `HOST_OBSERVED` only for a subagent whose whole chain the host showed in the call; the main (root) session is `UNAVAILABLE` by design, because it may record on behalf of an agent the host never showed. So a main session whose model and effort were observed still records `recordedBy.provenance: UNAVAILABLE`; the observed execution is in the result's `execution`. The execution observation retains the physical actor and call ID for replay protection. The workflow and its evidence belong to the root session resolved through the [session tree](architecture.md#session-unit).
- `ExecutionAssurance.observe()` records the model and the reasoning level reported by the host exactly as reported. The reasoning level is any non-empty string (if there is no report or it is blank, it is `null` with the informational note `HOST_EFFORT_UNREPORTED`), and because the server does not know the model class, it is `null` with the informational note `MODEL_NOT_IN_CATALOG`; when the model came from the host's request record rather than from the line that issued the call, `MODEL_FROM_REQUEST_RECORD` is added last. There is no list of models or reasoning levels, no list of supported efforts, and no determination of a minimum effort.
- `observationId` is a hash of (host, sessionId, actor, callId). Even if the same host call is sent again, the second consumption is rejected by the workflow ledger. A host that gives a call no ID (agy) gets its call ID from the row its PreToolUse hook left (see the table below), so its observation exists only when that row is found; `HOST_CALL_ID_UNAVAILABLE` is the diagnosis of a call that has neither an ID nor such a row.

| Claude Code | The static header `Sennard-Host-Label: claude` in the manifest. The PreToolUse governance hook records the effort (`effort.level`) in an admission row, and the server retrieves that row once by `claudecode/toolUseId`. The PreToolUse hook does not report the model (the host gives a model only to SessionStart and the model-switch events), so the server reads it from the session's transcript, in this order: (1) the assistant line that issued the call (`message.model`; the observation rests on the call record); (2) if that line is not in the file, the request record (`type: api-request`) the host wrote for the request that produced the call (`params.model`, `params.output_config.effort`; the observation rests on the request record, and the context's `policyNotes` end with `MODEL_FROM_REQUEST_RECORD`). The adapter hands the common code a host-neutral basis of the observation (`SelfSession.Execution.Observed.Evidence`: `HOST_REPORT`, `CALL_RECORD`, `REQUEST_RECORD`), never a transcript-specific string. **When the lines are written.** Claude Code 2.1.330 queues the line of a request right after the response's headers arrive, and its writer drains the queue on a 100 ms timer (`HOST_QUEUE_FLUSH_INTERVAL`, read from the program); the hook path does not flush it, so a hook is not guaranteed to find the line of a request in the file. The host writes an assistant message that holds several tool calls only after its tools have finished, and the tool that asks for the observation is one of them, so such a call's line can never be waited for. So the server reads the file at once; only when none of the files that can hold the call's line (the session's own, and for a subagent also its own file and the files of the workflow runs) has it, and at least one of them could be read, it waits once (`REREAD_DELAY`, 250 ms, more than twice the flush interval), reads the file once more, and takes the line of the call if it is there now, otherwise the newest request of the same thread. A call whose line is in any one of those files at the first look waits for nothing, whatever the line says, and so does a look where no file could be read (nothing the host facts say shows that the transcript is being made); a subagent's call is looked for in its own file, so it does not wait for the session's file, which never holds its line. There is no waiting loop; the wait honours interruption. **Effort.** The effort the hook reported is the host's own value for this call (tied to it by `tool_use_id`) and is the effort when there is one, on both paths; what the record names is only the fallback when the hook reported none. The line that issued the call is tied to the call by its id, so it is not refused when it names another effort than the hook did (the hook's is taken; Claude Code 2.1.330 writes no effort on that line). A request record that names another effort is refused (`REQUEST_EFFORT_MISMATCH`), since nothing ties it to the call; one that names none, or the same, takes the hook's. **Which request.** The requests are read from the end of the file backwards and the first one of the caller's own thread is taken: for the main agent a request with `querySource: repl_main_thread` (also with an output style after a colon, `repl_main_thread:outputStyle:...`) or `sdk` and this session, for a subagent a request with `querySource: agent:...` or `hook_agent` and its own `agentId` (in the subagent's own file: `<session>/subagents/agent-<agentId>.jsonl`, or for a subagent of a workflow `<session>/subagents/workflows/<runId>/agent-<agentId>.jsonl`, looking one level of run folders deep and no deeper). A session or subagent id is made into a file name only when it is of `[A-Za-z0-9_-]+`, the form the host gives (`a` plus 16 hex digits, `wf_<8 hex>-<3 hex>-<n>` for a workflow subagent); another is refused (`CALLER_ID_INVALID`), and a transcript path that is not a path is refused (`TRANSCRIPT_PATH_INVALID`), neither raising an error. These values are how Claude Code 2.1.330 classifies its requests, read from the program; not every value has been seen in a transcript. A request of the other kind of thread is passed over. A request of the host's own side work (any other `querySource`: `compact`, `agent_summary`, `generate_session_title`, `auto_mode`, ...) is passed over too, and the caller's own request before it is taken; only when the lines read hold no request of any thread, only such side work, is the call refused. A line of another type that begins like a request (`api-request-resumed`) is not a request: what the host means by it is not confirmed, so it is passed over (a limit). The request record is not tied to the call: nothing the host writes names the `tool_use` id of the call in the request that produced it, so when the host has not yet written that request even after the wait, the newest request of the same thread, the one before it, is taken, and it differs from the right one only if the model or effort was switched between two requests of one turn (the hook's effort refuses a difference in effort). A main-thread request that carries an `agentId` or `isSidechain: true`, or a subagent's request without an `agentId`, is not the caller's. **A new turn.** A request is not the one that produced the call when a line of the same thread after it opens a new turn: the user's own input (a user line that is not `isMeta` and carries no tool result), the notice of a background task (a user line that begins with `<task-notification>`, whether or not it is marked `isMeta`), a compaction (a line that carries `logicalParentUuid`), or a conversation line with another `promptId` than the request's. The lines the host writes for a scheduled or loop wake-up and for a message of another session are not given by the host facts; they are recognised only when they are a user line that is not `isMeta` or carry another `promptId`, and otherwise are not (a limit). The result of an earlier tool of the same message after the request is not a sign of an ended answer, so it does not refuse the request. **Long and half-written lines.** A request line holds the request's body, so it can be longer than what is read of the end of the file (the last 2 MiB and 4000 lines). The one line that begins before that window is read once from its own beginning with a streaming parser that keeps only its marks, `params.model`, `params.output_config.effort` and the kinds of the blocks of `message.content`, and skips the rest without holding it; a line longer than 32 MiB is refused (`REQUEST_LINE_TOO_LARGE`), and when no request of the caller is in what was read and the file has older lines, the answer says so (`REQUEST_BEYOND_READ_LIMIT`). Only the last line of the file that holds `api-request` can be a request that is still being written (`REQUEST_THREAD_UNKNOWN`); an unreadable line in the middle is passed over. A folder of workflow runs that cannot be listed is told (`WORKFLOW_RUNS_UNLISTABLE`) and not taken for a folder with no run | If neither record is found, `BINDING_REQUIRED` with `details.observation.transcriptReason` (`MODEL_FIELD_MISSING`, `OTHER_THREAD`, `REQUEST_STALE`, `REQUEST_MODEL_MISSING`, `REQUEST_EFFORT_MISMATCH`, `REQUEST_SESSION_MISMATCH`, `REQUEST_THREAD_MISMATCH`, `REQUEST_ONLY_UNRECOGNIZED_SOURCES`, `REQUEST_THREAD_UNKNOWN`, `REQUEST_LINE_TOO_LARGE`, `REQUEST_BEYOND_READ_LIMIT`, `WORKFLOW_RUNS_UNLISTABLE`, `REQUEST_RECORD_NOT_FOUND`, `TRANSCRIPT_UNREADABLE`, `TRANSCRIPT_PATH_INVALID`, `TRANSCRIPT_PATH_MISSING`, `CALLER_ID_INVALID`, `CALL_ID_MISSING`), `waitedMs` (250 when the files were read once more, otherwise 0) and `linesSeen`; for `REQUEST_ONLY_UNRECOGNIZED_SOURCES` also `requestSource`, the newest `querySource` seen, cleaned to `[A-Za-z0-9_:.-]` and cut to 64 characters. `REQUEST_RECORD_NOT_FOUND` is what `CALL_LINE_NOT_FOUND` was called before this look included the request record. If the host label is absent or a value the adapter does not know, the host is handled as a host seen for the first time. Its trust level is `unavailable`, and the session is designated by `sessionRef` (issued by `open_session`).

The server does not decide a model class. It records `modelClass` as `null` and does not read a list of model names or a class mapping. Whatever reasoning level is reported is recorded as it is, and execution eligibility is not rejected on the basis of a model's supported list or a minimum. If there is no reasoning level, it is recorded as `reasoningEffort: null` and is not supplemented with the value of another model or turn.

## What the Transcript Observation Trusts

For Claude Code, the model and the request record are an observation that believes the transcript file the host wrote. It is not a defence against a principal that can write to that file on the same PC. Such a principal (the agent under observation included) can append a request record that the fallback takes: the look cannot tell a line the host wrote from one appended later, since nothing the host writes ties a request record to the call. The personal edition trusts the whole PC, so this threat is accepted and not blocked. The effort that the hook reports for the call limits it only in part: a forged request whose effort differs from the hook's is refused (`REQUEST_EFFORT_MISMATCH`), and one whose effort equals the hook's, with any model, is taken. A call whose own line is in the file is not affected by a forged request, because the line of the call is read first.

## Failure and Verification

If the caller cannot be observed, the result is `BINDING_REQUIRED` (`CALLER_PROVENANCE_UNAVAILABLE`); if the facts of the host contradict each other or there is an eligibility or reuse error, it is `BINDING_INVALID`. A call whose execution alone could not be observed keeps its identity and is still accepted, because Sennard has no execution floor (see below). Isolation from a process that writes to the DB with the same OS user's permissions or calls the MCP path of the server directly is not guaranteed.

The synthetic `_meta` of a unit fixture and the observation of an actually installed host are different verifications. The release and installation owner must confirm, on a real host (design 6.2), the observation and the completion of a guarded workflow separately.

## Basis and Scope of Stage Recommendations

A plan has no floor field for model class or reasoning level. Execution proceeds with whatever agent or model arrives, and whether the root or a subagent records, `record_stage_result` and `finalize_workflow` are not rejected because of the observed model class or reasoning level (including when not observed). A stage requirement has only `policyId`, `kind`, and `observationRequired` (a `deterministic` stage, determined only by the skill's checks, does not require an observation, and any other `semantic` stage does), and the observed values are only recorded. The observation itself (call binding, freshness, format) continues to be checked, and a wished-for value entered by the caller is not turned into an actual observation. Audit obligations, independence, and deliverable checks are enforced as before.

`constraints` of a TaskEnvelope is a string array, and the `gate` of a provider is an audit condition. There is no separate input contract that states an explicit model floor. A generated stage requirement is bound to the `taskDigest` and to the signature of the whole plan, and is recomputed from the task at claim time and compared. If the caller changes a signed value, it is rejected by the integrity check.
