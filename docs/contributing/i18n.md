# Sennard Internationalization (i18n) Design

## 1. Goals and Scope

Requirements:

- Sennard must support English, and where it does not, the feature must be added and a release published.
- The design must follow an i18n internationalization standard.
- The design must take into account the administration page that will later be attached to the MCP server.
- Internationalization must apply not only to the administration page but to every message that Sennard emits.

In 3.2.1, Sennard had no language setting (there are zero occurrences of locale handling in `mcp-server/src`, `runtime`, `scripts`, `hooks`, `claude-overlay`, and `antigravity-connector`; only `localeCompare` appears). Server errors and tool descriptions were in English, and some skills, intake guidance and hook messages used Korean.

The current admin page offers 한국어 / English. It uses the `sennard-admin-language` cookie first, then the browser's `Accept-Language` header, with English as the default.

### 1.1 Target: Every Sentence That Sennard Emits

| Surface | Location | Catalog domain (`locales/catalog.json`) | Recipient |
|---|---|---|---|
| MCP `instructions` | The `instructions` sentences of the server + the intake block of `skills/orchestrator/references/intake.md` | `instructions` | Agent |
| Tool descriptions and input field descriptions | The message keys of `@McpTool`, the `description` of `contracts/*.schema.json` | `tools`, `schema` | Agent |
| Tool results and error sentences | The message keys and `params` of errors that services throw | `server`, `workflow`, `services`, `continuity`, `peer` | Agent, user |
| Sentences shown again after storage | Labels kept in the store (stored as a key and `params`) | `workflowRecord` | Agent, administration page |
| Hook sentences | The host hook adapters (edit gate, workflow stage check, save check for each user input, work evidence for the current request) | `hooks`, `connector` | User screen, agent |
| Static sentences that the host reads directly | `statusMessage` of `hooks.json`, the description and `suggestedPrompts` of the plugin manifest, `marketplace.json` | None (original text as it is) | Host UI |
| Skills | `skills/*/SKILL.md` (including the frontmatter `description`), `references/`, `agents/openai.yaml` | None (original text as it is) | Agent |
| Skill check and report output | The `SkillCheck` implementations of the server | `skillScripts`, `skillTools`, `skillReports`, `skillChecks` (`*Ko` is the Korean original) | Agent, user |
| Engineering practices check output | The engineering-practices check of the server (`EngineeringPractices`) and the reading of deliverable files (`LocalFileFacts`) | `practices` | Agent, user |
| Administration page | `admin-page.html` and the state that the server emits | Section 9 | User |

### 1.2 What Is Not Translated

- Content written by a person or an agent: session message bodies, `goal`, `acceptanceCriteria`, result summaries, and the user's original text. Sennard stores this as it is and shows it as it is.
- Machine identifiers: error `code`, capability, skill names, tool names, schema field names, and status values. They are the same in every locale.
- The target language of the function of `korean-prose-editor`. Its explanatory and guidance sentences are translated, but the language it edits remains Korean.
- The repository maintains English and Korean editions of documents in `docs/` outside the runtime message catalog. The English entry point for users is `README.md`, which links to the Korean edition `README.ko.md`.
- stderr diagnostics. At present only a code and JSON are emitted. If a sentence is newly introduced, it goes through the catalog.

## 2. Standards Followed

| Area | Standard | How Sennard uses it |
|---|---|---|
| Language tag | BCP 47 (RFC 5646) | Every locale value. |
| Locale selection | RFC 4647 Lookup | The requested list is matched against the supported list from the front, and each tag is matched by removing one trailing subtag at a time (`en-US` to `en`). |
| Message syntax | `java.text.MessageFormat` | Only the placeholders `{name}` and `{n,number}` are used. Quoting follows the JDK rules (a single `'` is written `''`, and a literal `{` is written `'{'`). |
| Regional data | The JDK's locale data (CLDR) | The number format is determined by `MessageFormat` from the locale. |

The message executor is the JDK's `java.text.MessageFormat`, and there is no external library. Sentences are produced only through one Spring `MessageSource` bean (`CatalogMessageSource`) and `MessageSourceAccessor` (`message/Messages` in `sennard-server` converts a `MessageRef` into a sentence on top of them). `MessageFormat` reads only numbered arguments, so `CatalogPattern` converts the named arguments of the catalog into numbers the first time a message is used and passes them on.

A sentence that changes with a value (ICU's `select` and `plural`) is not written inside a pattern but is written as keys. If a sentence `K` has `{kind}`, then `K#kind=value` is one phrase for each value, and the phrase is chosen by the value of the argument (the name of an enum constant, a string, or the number of digits of an integer). If none matches, `K#kind=other` is used, and `other` must exist. A count is written in the same way with `K#count=0` and `K#count=other`, and English has no separate `one` phrase. Korean also has only a singular form. A phrase is a pattern that takes the same arguments. The locales are `en` and `ko`, and any other requested language is treated as `en`. To add a language, only the files under `locales/<language>/` are added.

## 3. Principles

1. **The machine contract is independent of language.** Every response that emits a sentence carries `code`, `messageKey`, and `params` together. `message` is for display. Agent instructions, tests, and the administration page decide by `code` and do not compare sentences.
2. **Store with key and params, render when emitting.** A stored error body holds `message` only as the sentence in the base locale (`en`), together with `messageKey` and `params`. Therefore the stored content and the digest do not vary with the language of the requester, and the administration page renders again from the key in the language of the viewer. The top-level `error` of a response is rendered again in the requested locale at the response boundary (`toolResult`). A stored body inside `data` (a receipt and the like) is left as it is to preserve the digest. An already stored Korean sentence (`LATE_ADOPTION_LABEL` and the like) is mapped from a known sentence to a key when it is read.
3. **There is one catalog.** The MCP tools, the hooks, the skill checks, the package build, and the administration page use the same `locales/`. No copy is kept for each surface.
4. **A release locale must have no missing keys.** CI enforces that the keys of the release locales (initially `ko` and `en`) are complete. The run-time fallback is only a safety net and is not a means of covering a missing translation.
5. **A translation is bound to the edition of the source.** The source digest is recorded for each translation entry. If the source changed while the translation stayed the same, CI fails.

## 4. Locale Determination

### 4.1 Per Process (MCP Server, Hook, CLI, Skill Scripts)

Sennard is deployed in three places. Each place may or may not be the same machine as the others.

| Deployment place | Where it runs | Sentences rendered here |
|---|---|---|
| (1) Host PC | The user's PC | Static package sentences |
| (2) Sennard/MCP service | The user's PC | Hook responses, `instructions`, tool descriptions, tool results and errors, skill check output, the administration page |
| (3) DBMS | Embedded in the service (local), or a remote server different from the service | Nothing is rendered |

It is not assumed that one deployment place reads the files of another.

#### (1) and (2) Locale of the Host PC and the Service: `MODEL_LOCALE` Alone

Sennard renders its model-facing catalog messages (hook guidance, MCP `instructions`, tool descriptions, tool results and errors, skill check output) using `MODEL_LOCALE` (`en`) from `server/message/Messages.java`. These are sentences that the model reads first and that cost tokens in every session, so the criterion is not the language but the number of tokens of each phrase. Comparing the 1,526 catalog entries one by one with o200k, English was shorter for 1,468, equal for 47, and Korean was shorter for 11, and for those 11 the English was shortened to at most the Korean length. Therefore the model-facing catalog is rendered in `en` alone. When a new phrase is added, both forms are measured and the one with fewer tokens is followed. The answer that the user sees is written by the agent in the user's language. The common intake block of `instructions` is a static sentence that is not rendered (4.2), so it remains in its original text (Korean). English would have 23% fewer tokens (1,594 against 2,116), but at 8,151 characters it exceeds the 4,096 characters at which Claude Code truncates instructions, so it was kept in Korean and shortened by moving overlapping clauses elsewhere. The skill descriptions are in English by the same criterion.

- The locale is not decided per place, so there is nothing to carry between (1) and (2). Whichever deployment place or instance renders, the result is the same.
- The service writes `MODEL_LOCALE` in `_meta["io.modelcontextprotocol/contentLanguage"]` of the response.
- The model locale is fixed. Signed `locale.set` records only participate in chain verification. The server rejects new `locale.set` records. See [the admin log contract](admin-log.md).
- The catalog keeps `ko` as it is (section 5). If a need arises to let the language be chosen again, only the locale argument that the rendering call receives has to change.

#### (3) DBMS

- No sentences are stored in the DB (principle 2). Only the key, the params, and the UTC time are stored. Therefore the result is the same wherever the DB is and whatever locale it is configured with.
- Error sentences of the DB server come out in the `lc_messages` language of that server. Sennard does not emit these sentences to the user as they are. It maps the SQLSTATE to a Sennard `code` and emits a catalog sentence.
- Identifier columns use `COLLATE "C"` so that sorting and comparison do not vary with the locale of the DB server. The sorting of sentences to be shown on a screen is done by the rendering side.

#### Deployment Places with Different Versions

The installed host plugin and local service can run different Sennard versions.

- The meaning and params of a released key are not changed. When a change is needed, a new key is created.
- A renderer that receives an unknown key does not fail. It uses the received `message` as it is, and if there is no `message`, it shows the `code` and the key.

#### Rendering State

- **Stateless rendering.** The locale is `MODEL_LOCALE` alone, and what rendering needs is only the catalog and the request. No table of per-request locales is kept in server memory.
- **The memory bound is the catalog size.** A message is compiled once when it is first used and kept. The bound is the number of locales used for rendering times the number of keys. Nothing is parsed per request, and rendering results are not cached. Therefore memory does not grow with the kinds of params.
- **Records are made by code.** Logs and metrics keep the `code`, the `messageKey`, and the locale instead of the rendered sentence. They are aggregated as the same event even when the language differs.
- **The administration page builds sentences in the browser.** The server sends the `admin.page.*` patterns of the request language (`Accept-Language`, `en` or `ko`, otherwise `en`) to the page as JSON (`AdminTexts`), and the screen builds sentences from the patterns and arguments. Only the sentences held by the HTML frame (the language, the title, and the guidance shown before the script) are drawn by the server. One sentence is one key, and the screen does not concatenate sentence fragments.

#### Users Who Are Not Familiar with Computers

The MCP service and the DBMS must be installable on a local PC, and this path is the default. The correct language must appear even for a user who has not touched any setting.

- The package is single, so no language is chosen at the installation step. An environment variable or a settings file is not required.
- Installation and connection failure guidance (failure to open the DB file, the service not running, a refused DB connection, and so on) is also a catalog sentence. It does not guess the cause. It states, in that language, the one next action that the user should take, and shows a `code` for support requests together with it.
- The business database is connected separately. The sentences of the connection and status screens also use this catalog.

### 4.2 Static Sentences and Run-Time Sentences

The host reads `skills/`, `hooks.json`, and the manifests of the plugin folder as they are. None of the three hosts (Claude Code, Codex, Antigravity) has a function for choosing a locale-specific variant of these files. Therefore the language of static sentences is decided by the original text of the single package, and the sentences rendered at run time are decided by `MODEL_LOCALE`. The intake block of the server `instructions` is read from the installed `skills/orchestrator/references/intake.md`, so it belongs to the static sentences (the current principle that it has the same origin as the skills is maintained).

### 4.3 Per Request

- MCP: the `acceptLanguage` of the request is not read (4.1). No locale argument is added to the tool input schema.
- Administration page: the screen appears in the language of the request (`Accept-Language`). English and Korean are supported, and any other language and a request that does not state a language get English. The language the user chose with the switch in the page header (cookie `sennard-admin-language`, `SennardLocaleResolver`) is followed before `Accept-Language`; it is not a signed setting ([admin-page.md](../user/admin-page.md)).

## 5. Catalog

### 5.1 Files

```text
locales/
  catalog.json            # release locales, the source locale of each domain
  en/server.json          # a file per domain; values are `MessageFormat` pattern strings (named arguments, phrases as `key#argument=value`)
  en/hooks.json
  en/cli.json
  en/manifest.json
  en/skill-scripts.json
  en/admin.json           # sentences shown by the administration page (`admin.` keys, the admin domain of `catalog.json`, source en). Screen sentences are `admin.page.<area>.<name>`, and screen sentences made by the server are `admin.jvm.*` and `admin.rootRelease.*`
  ko/...                  # same composition
  ko/translations.lock.json   # translation key -> sha256 of the source string
  en/translations.lock.json
```

- The reason for dividing into domains is that the administration page loads only the domains it needs and that translation review can be divided by surface.
- The source locale is written per domain in `catalog.json`. Server errors and tool descriptions that are currently written in English have the source `en`, and the hook sentences and intake guidance that were written and polished in Korean have the source `ko`. The source is not forced into one language. The purpose is to preserve the meaning of the current sentences and the polished result.

### 5.2 Keys

- Form: `<domain>.<area>.<name>`. Examples: `hooks.editGate.denied`, `server.tool.startWorkflow.description`, `server.error.INVALID_INPUT.startWorkflowRequiredArtifacts`.
- An error key is separate from the `code`, because one `code` is used by several sentences (for example, `INVALID_INPUT`).
- An input schema description is replaced at emission time without changing the file. The key is `server.schema.<$id>#<JSON Pointer>`. The source is the English `description` of the schema file. Therefore the engineering contract schemas locked by `CONTENT_LOCK.json` are not touched.

### 5.3 Format Safety

- `LocaleCatalogsTest` of `sennard-repo-tools` checks the key completeness and the translation review state of the release locales and the placeholder format.
- A function that emits a sentence (an error constructor, a hook response, a tool description registration) receives a `MessageRef { key, params }`.
- CI checks (no process is started):
  - For each release locale, the key set equals that of the source domain (zero missing keys and zero surplus keys).
  - Every value can be read by `CatalogPattern` (`MessageFormat`), and the set of placeholder names equals that of the source. `key#argument=value` has a sentence and its argument, and has `other`.
  - The source digest of `translations.lock.json` equals the current source (zero stale translations).
  - Tags are in canonical form.

## 6. Application by Surface

| Surface | Rendering time | Method |
|---|---|---|
| MCP `instructions` | Server start | The sentences before and after and the session message guidance use the `server` catalog with `MODEL_LOCALE`. The intake block is the installed `skills/orchestrator/references/intake.md` (4.2). |
| Tool descriptions and input field descriptions | Server start (`tools/list`) | The `server.tool.*` and `server.schema.*` keys are rendered with `MODEL_LOCALE` and emitted. |
| Tool results and errors | Per call | `WorkflowContractError(code, MessageRef, details)`. `messageKey` and `params` are added to the error body (an optional field is added in 4 places of the contract schemas), and the response boundary renders `message` with `MODEL_LOCALE` and writes `contentLanguage` in `_meta`. Existing fields are left as they are. |
| Sentences shown again after storage | When read | Storage is key and params. Known Korean sentences of existing rows are mapped to keys when read. |
| Hook sentences | Per hook call | The hook handler of the server renders a `MessageRef` and responds. |
| Static sentences (`statusMessage`, manifest) | Package build | The package is single and contains the original text as it is. |
| Skills | Package build | Section 7. |
| Skill checks | Per run | The `SkillCheck` implementation that handles `run_skill_check` renders inside the server. |
| Session messages | Per delivery | Only the envelope sentences (BEGIN/END warnings, ACK guidance) are from the catalog. The body is as it is. |
| Administration page | Per request | Section 9. |

## 7. Skill Translation and Locks

### 7.1 Layout

- `skills/` is left in its original text. The source locale of each skill is written in `skills/registry.json` (at present every skill is `ko`).
- Translations are placed at `locales/<tag>/skills/<skill>/<same relative path>`. The targets are sentence files such as `SKILL.md` (including the frontmatter `description`), `README.md`, `references/**/*.md`, `agents/openai.yaml`, and prompt templates. Non-sentence files such as scripts and JSON are not duplicated.
- The package contains the skill bodies in their original text. Translating skills requires testing all behavior again, so it was postponed as a follow-up task. If a translation becomes older than the source (7.2 `sourceChecksum`), CI fails.

### 7.2 Locks

| Lock | At present | What changes |
|---|---|---|
| `skills/source-lock.json` | `integratedChecksum` per skill folder | Adds `translations.<tag>.integratedChecksum` per locale and the `sourceChecksum` that the translation is based on. If the source changes, `sourceChecksum` no longer matches and CI fails. |
| `COMMON_POLICY_INVARIANTS` of `ClaudePlugin` | Comparison of Korean sentences | A set of invariant sentences per locale. |
| `claude-overlay/adaptations/*.json`, `antigravity-connector/adaptations/*.json` | Korean `find`/`replace` | An adaptation per locale. It is applied to the translated files. |

### 7.3 Semantic Review

Skills and tool descriptions are prompts that change agent behavior. For each translation, an independent reviewer confirms the correspondence in meaning with the source, and the review result is kept in the translation commit. Hash and structure checks do not prove that the meaning is preserved. Representative flows (the edit gate, starting and recording a workflow, the stage check) are run on a real host to see whether the behavior is the same.

## 8. Packages and Distribution

- There is one package per host: `claude-plugin/`, the Codex plugin at the repository root, and the agy zip. The plugin identifier is `sennard`.

## 9. Integration with the Administration Page

- The same `locales/` is used. Screen sentences are placed in the `admin` domain (`admin` of `locales/catalog.json`, `locales/en/admin.json`, `locales/ko/admin.json`).
- Every message object of the API is `{ code, messageKey, params, message, locale }`. The screen uses `message` as it is, or renders `messageKey` and `params` again in its own locale.
- Stored data holds only the key, the params, and the UTC ISO 8601 time. Date and number display is done by `Intl` in the negotiated locale.
- The administration page stores the language selected in the header in a cookie. Without a selection, it uses the request language.
- One screen sentence is one key. A phrase that varies with a value is written as `key#argument=value`, and sentence fragments are not concatenated in code. The screen file (`admin-page.html`) has no Korean text, and `AdminPageTextsTest` checks the keys that the page uses against the catalog.
- At first, no right-to-left language is among the release locales. The screen is built with CSS logical properties (`margin-inline-start` and the like) so that one can be added later.

## 10. Tests

- The catalog checks (5.3) and the type checks run in CI.
- The tests that compare Korean sentences as they are (about 153 files) are changed to compare `code` and `messageKey`. Only one representative sentence per surface is checked for its rendering result per locale.
- Locale fixation tests: whether rendering comes out in `MODEL_LOCALE` even when `SENNARD_LOCALE`, a signature record, or a request `_meta` is present, and whether a new `locale.set` is rejected.
- Package checks: `:sennard-repo-tools:checkClaudePlugin`, the agy bundle check, and the skill lock check.
- Real hosts: on the Linux test server, the packages are installed in Claude Code, Codex, and agy, and it is checked that `instructions`, the edit gate denial, and the stage check sentences come out in `MODEL_LOCALE` (English).

## 11. Phases

1. Foundation: `runtime/i18n` (locale determination, executor, catalog loading), `locales/catalog.json`, key type generation, CI checks.
2. Migration of run-time sentences: hooks, the sentences before and after `instructions`, session message guidance, tool descriptions and schema descriptions, about 463 error sites, stored sentences, the CLI, and skill scripts. Both `ko` and `en`.
3. Skill translation: `en` for the 23 distributed skills (15 agent correction skills and 8 specialist skills), per-locale locks and semantic review.
4. Packages: the single package build, the release workflow, the README.
5. Tests, real-host verification, and release.

Each phase is recorded as a Sennard workflow.
