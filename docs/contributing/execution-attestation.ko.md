# 실행 관측과 호스트 연결

실행 관측은 서버가 검증한 호출자(`VerifiedCaller`)의 `execution`에서 온다. 호스트별 caller ingress가 그 값을 호스트가 쓴 사실에서 채우고, 공통 `HostAttestationProvider`가 신뢰된 adapter로 자격을 판정하며, `WorkflowService`가 task/run/stage/revision 결속과 한 번 소비를 집행한다. 관측은 시간이 지나도 만료되지 않는다. 재사용은 한 번 소비 기록이 영구히 막고, 미래 시각의 관측만 거부한다. 도구 인자의 `executionContext` JSON이나 설정 희망값은 관측을 대신하지 않는다. 서명 token(`_hostAttestation`, `aghs1`·`aghs2`)은 없다.

## 관측과 실행 자격

- `caller.execution`은 `{model, effort, turnId, provenance}` 또는 `{unavailable: 사유}`다. 관측을 기록하는 도구(`plan_workflow`, `record_stage_result`, `classify_skills`, `record_skill_selection`)만 소비한다. 실행 하한은 없다.
- `provenance`라는 이름의 필드가 둘 있으며 서로 다른 것을 답합니다. `caller.execution.provenance`는 모델과 추론 강도가 어디서 왔는지(호스트가 보고했는지)를 말합니다. stage 결과의 `recordedBy.provenance`(`ObservedCaller`, `WorkflowCall.of`)는 서버가 *누가* 기록했는지를 어떻게 알게 되었는지를 말합니다. `HOST_OBSERVED`는 호스트가 호출에 사슬 전체를 보여 준 하위 에이전트일 때만이고, 메인(root) 세션은 호스트가 보여 주지 않은 에이전트를 대신해 기록할 수 있으므로 설계상 `UNAVAILABLE`입니다. 그래서 모델과 강도가 관측된 메인 세션도 `recordedBy.provenance: UNAVAILABLE`로 기록하며, 관측된 실행은 결과의 `execution`에 있습니다. 실행 관측에는 재사용을 방지하기 위해 실제 호출한 actor와 호출 ID를 유지합니다. 워크플로와 근거는 [세션 트리](architecture.ko.md#세션-단위)에서 확인한 메인 세션에 속합니다.
- `ExecutionAssurance.observe()`는 호스트가 보고한 모델과 추론 수준을 보고한 그대로 기록한다. 추론 수준은 비어 있지 않은 아무 문자열이며(보고가 없거나 공백이면 `null`과 참고 `HOST_EFFORT_UNREPORTED`), 모델 등급은 서버가 모르므로 `null`과 참고 `MODEL_NOT_IN_CATALOG`를 붙인다. 모델이 호출을 낸 줄이 아니라 호스트의 요청 기록에서 나왔으면 맨 뒤에 `MODEL_FROM_REQUEST_RECORD`를 더 붙인다. 모델·추론 수준의 목록, 지원 effort, 최소 effort 판정은 없다.
- `observationId`는 (host, sessionId, actor, callId)의 hash다. 같은 호스트 호출을 다시 보내도 두 번째 소비는 workflow 원장에서 거부된다. 호출에 ID를 주지 않는 호스트(agy)는 PreToolUse 훅이 남긴 행에서 호출 ID를 얻으므로(아래 표) 그 행을 찾았을 때만 관측이 생기며, `HOST_CALL_ID_UNAVAILABLE`은 ID도 그런 행도 없는 호출의 진단이다.

## 배포물의 연결

| 호스트 | 관측 출처 | 한계 |
| --- | --- | --- |
| Codex | `.mcp.json`의 정적 머리글 `Sennard-Host-Label: codex`. 서버가 `tools/call` `_meta`의 `x-codex-turn-metadata`(`model`, `reasoning_effort`, `turn_id`)와 `callId`를 읽는다. hook이 없다 | model이 없으면 `CODEX_EXECUTION_META_MISSING`. effort가 없으면 `reasoningEffort: null`로 관측한다. child도 자기 thread의 값을 쓴다 |
| Claude Code | manifest의 정적 머리글 `Sennard-Host-Label: claude`. PreToolUse governance hook이 effort(`effort.level`)를 admission 행에 기록하고, 서버가 `claudecode/toolUseId`로 그 행을 한 번 회수한다. PreToolUse hook은 model을 보고하지 않으므로(호스트는 model을 SessionStart와 모델 전환 이벤트에만 준다) 서버가 세션 transcript에서 다음 순서로 찾는다. (1) 호출을 낸 assistant 줄(`message.model`, 관측의 근거는 호출 기록). (2) 그 줄이 파일에 없으면, 호출을 낳은 요청을 보낼 때 호스트가 쓴 요청 기록(`type: api-request`)(`params.model`, `params.output_config.effort`, 관측의 근거는 요청 기록이며 맥락의 `policyNotes` 끝에 `MODEL_FROM_REQUEST_RECORD`가 붙는다). 어댑터는 공용 코드에 transcript 전용 문자열이 아니라 호스트 중립인 관측 근거(`SelfSession.Execution.Observed.Evidence`: `HOST_REPORT`, `CALL_RECORD`, `REQUEST_RECORD`)를 넘긴다. **줄이 쓰이는 때.** Claude Code 2.1.330은 요청의 줄을 응답 헤더가 도착한 직후 큐에 넣고, 기록기가 100 ms 타이머(`HOST_QUEUE_FLUSH_INTERVAL`, 프로그램에서 읽은 값)로 큐를 비우며, hook 경로는 큐를 비우지 않는다. 그래서 hook이 불릴 때 요청의 줄이 파일에 있다는 보장은 없다. 호스트는 도구 호출이 여럿인 assistant 메시지를 그 도구들이 끝난 뒤에야 쓰고, 관측을 요청하는 도구도 그중 하나이므로 그런 호출의 줄은 기다려도 나타나지 않는다. 그래서 서버는 파일을 먼저 한 번 읽고, 호출의 줄을 담을 수 있는 파일(세션 자신의 파일, 서브에이전트라면 자기 파일과 워크플로 실행 폴더의 파일도)이 어느 것에도 호출의 줄이 없고 그중 하나라도 읽을 수 있었을 때만 한 번(`REREAD_DELAY`, 250 ms, 큐를 비우는 간격의 두 배보다 길다) 기다린 뒤 파일을 다시 읽어, 호출의 줄이 생겼으면 그것을, 아니면 같은 스레드의 가장 새 요청을 쓴다. 호출의 줄이 그 파일 중 어느 하나에든 처음부터 있으면 줄이 무엇을 말하든 기다리지 않으며, 읽을 수 있는 파일이 하나도 없는 때도 기다리지 않는다(기록 파일이 만들어지는 중이라는 근거가 호스트 사실에 없다). 서브에이전트의 호출은 자기 파일에서 찾으므로 그 줄이 없는 세션 파일 때문에 기다리지 않는다. 기다림을 되풀이하는 반복은 없다. 기다림은 인터럽트를 따른다. **effort.** hook이 보고한 effort는 이 호출에 대한 호스트 자신의 값(`tool_use_id`로 묶임)이며 있으면 그것이 effort다. 두 경로 모두 그렇고, 기록이 적은 값은 hook이 보고하지 않았을 때의 대체일 뿐이다. 호출을 낸 줄은 id로 호출에 묶이므로 그 줄이 hook과 다른 effort를 적어도 거절하지 않고 hook의 값을 쓴다(Claude Code 2.1.330은 그 줄에 effort를 쓰지 않는다). 다른 effort를 적은 요청 기록은 호출에 묶이는 근거가 없으므로 거절하고(`REQUEST_EFFORT_MISMATCH`), effort가 없거나 같은 요청은 hook의 값을 쓴다. **어느 요청인가.** 요청은 파일 끝에서 거꾸로 읽어 호출자 자기 스레드의 첫 요청을 쓴다. 메인 에이전트는 `querySource: repl_main_thread`(콜론 뒤에 출력 스타일이 붙은 `repl_main_thread:outputStyle:...` 포함) 또는 `sdk`이고 이 세션인 요청, 서브에이전트는 `querySource: agent:...` 또는 `hook_agent`이고 자기 `agentId`가 있는 요청(서브에이전트 자신의 파일: `<session>/subagents/agent-<agentId>.jsonl`, 워크플로의 서브에이전트는 `<session>/subagents/workflows/<runId>/agent-<agentId>.jsonl`이며 실행 폴더 한 단계까지만 보고 그 아래는 찾지 않는다)이다. 세션 id와 서브에이전트 id는 호스트가 주는 형식 `[A-Za-z0-9_-]+`(`a`와 16자리 16진수, 워크플로 서브에이전트는 `wf_<8자리 16진수>-<3자리 16진수>-<n>`)일 때만 파일 이름이 되며, 다른 값은 거절하고(`CALLER_ID_INVALID`) 경로가 아닌 transcript 경로도 거절하며(`TRANSCRIPT_PATH_INVALID`) 어느 쪽도 오류를 일으키지 않는다. 이 값들은 Claude Code 2.1.330이 요청을 분류하는 방식을 프로그램에서 읽은 것이며, 모든 값을 기록에서 본 것은 아니다. 다른 종류 스레드의 요청은 건너뛴다. 호스트 자체 보조 작업의 요청(그 밖의 모든 `querySource`: `compact`, `agent_summary`, `generate_session_title`, `auto_mode` 등)도 건너뛰고 그 앞의 호출자 자기 요청을 쓴다. 읽은 줄에 어느 스레드의 요청도 없고 그런 보조 작업뿐일 때만 호출을 거절한다. 요청처럼 시작하지만 다른 종류인 줄(`api-request-resumed`)은 요청이 아니다. 호스트가 그 줄로 무엇을 뜻하는지는 확인되지 않았으므로 건너뛴다(한계). 요청 기록은 호출과 이어져 있지 않다. 호스트가 쓰는 어떤 값도 그 요청에 호출의 `tool_use` id를 적지 않으므로, 기다린 뒤에도 호스트가 그 요청을 아직 쓰지 않았으면 같은 스레드의 가장 새 요청, 곧 그 앞의 요청을 쓰며, 한 턴 안에서 두 요청 사이에 모델이나 effort가 바뀐 경우에만 맞는 요청과 다르다(effort의 차이는 hook의 값이 거절한다). `agentId`나 `isSidechain: true`가 있는 메인 스레드 요청, 또는 `agentId`가 없는 서브에이전트 요청은 호출자의 것이 아니다. **새 턴.** 요청 뒤에 같은 스레드에서 새 턴을 여는 줄이 있으면 그 요청은 이 호출을 낳은 요청이 아니다. 새 턴을 여는 줄은 사용자의 새 입력(`isMeta`가 아니고 도구 결과가 없는 user 줄), 백그라운드 작업의 알림(`<task-notification>`으로 시작하는 user 줄, `isMeta` 여부와 무관), 압축(`logicalParentUuid`가 있는 줄), 요청과 다른 `promptId`를 가진 대화 줄이다. 예약·반복 깨우기와 다른 세션 메시지가 기록에 남기는 줄의 형태는 호스트 사실 조사에 없으므로, `isMeta`가 아닌 user 줄이거나 다른 `promptId`를 가진 경우에만 알아보고 그렇지 않으면 알아보지 못한다(한계). 같은 메시지의 앞 도구 결과가 요청 뒤에 있는 것은 응답이 끝났다는 증거가 아니므로 요청을 거절하지 않는다. **긴 줄과 쓰는 중인 줄.** 요청 줄은 요청 본문을 담으므로 파일 끝에서 읽는 범위(마지막 2 MiB, 4000줄)보다 길 수 있다. 그 범위 앞에서 시작하는 한 줄은 자기 처음부터 스트리밍 파서로 한 번 읽어 줄의 표지, `params.model`, `params.output_config.effort`, `message.content` 블록의 종류만 남기고 나머지는 메모리에 올리지 않고 건너뛴다. 32 MiB보다 긴 줄은 거절하고(`REQUEST_LINE_TOO_LARGE`), 읽은 범위에 호출자의 요청이 없고 파일에 더 오래된 줄이 있으면 그 사실을 알린다(`REQUEST_BEYOND_READ_LIMIT`). 아직 쓰는 중인 요청일 수 있는 것은 `api-request`를 담은 파일의 마지막 줄뿐이며(`REQUEST_THREAD_UNKNOWN`), 중간의 읽을 수 없는 줄은 건너뛴다. 나열할 수 없는 워크플로 실행 폴더는 실행이 없는 폴더로 보지 않고 알린다(`WORKFLOW_RUNS_UNLISTABLE`) | 두 기록이 모두 없으면 `BINDING_REQUIRED`이고 `details.observation`에 `transcriptReason`(`MODEL_FIELD_MISSING`, `OTHER_THREAD`, `REQUEST_STALE`, `REQUEST_MODEL_MISSING`, `REQUEST_EFFORT_MISMATCH`, `REQUEST_SESSION_MISMATCH`, `REQUEST_THREAD_MISMATCH`, `REQUEST_ONLY_UNRECOGNIZED_SOURCES`, `REQUEST_THREAD_UNKNOWN`, `REQUEST_LINE_TOO_LARGE`, `REQUEST_BEYOND_READ_LIMIT`, `WORKFLOW_RUNS_UNLISTABLE`, `REQUEST_RECORD_NOT_FOUND`, `TRANSCRIPT_UNREADABLE`, `TRANSCRIPT_PATH_INVALID`, `TRANSCRIPT_PATH_MISSING`, `CALLER_ID_INVALID`, `CALL_ID_MISSING`)와 `waitedMs`(파일들을 다시 읽었으면 250, 아니면 0), `linesSeen`이 담기고, `REQUEST_ONLY_UNRECOGNIZED_SOURCES`이면 본 것 중 가장 새 `querySource`를 `[A-Za-z0-9_:.-]`로 거르고 64자로 자른 `requestSource`도 담긴다. `REQUEST_RECORD_NOT_FOUND`는 요청 기록까지 보기 전에 `CALL_LINE_NOT_FOUND`라 부르던 사유다. effort가 없으면 `reasoningEffort: null`로 관측한다. 최근 응답의 model은 추정하지 않는다. model은 호스트가 요청에 기록한 값이거나 호출을 낸 줄의 값이다. 앞선 수정을 위해 측정한 Claude Code 기록에서 메인 파일의 요청 기록은 모두 `querySource: repl_main_thread`이고 `agentId`가 없었으며, 서브에이전트 파일의 요청 기록은 모두 `querySource: agent:builtin:general-purpose`이고 `agentId`가 있었고 `sessionId`는 메인과 같았다 |
| Antigravity | `mcp_config.json`의 `Sennard-Host-Label: agy` 머리글로 어댑터를 선택합니다. MCP 호스트는 `_meta`에 대화, 루트, 하위 대화인 경우 부모를 전달합니다. 서버는 최근 30초 이내의 PreToolUse 관측 중 원래 대화, 도구, 정규화한 인자가 같은 관측을 가져옵니다. 훅은 호스트가 제공한 모델과 추론 수준도 기록합니다. | 도구 관측이 없거나 서로 충돌하면 `HOOK_OBSERVATION_UNMATCHED`로 결속 없이 응답합니다. 서로 다른 대화에서 동일한 도구 입력이 겹치면 관측이 만료될 때까지 어느 호출인지 확정할 수 없습니다. 한 대화가 같은 호출을 재시도하면 한 호출만 그 관측을 가져갑니다. |

호스트 이름표가 없거나 어댑터가 모르는 값이면 처음 보는 호스트로 처리한다. 신뢰 등급은 `unavailable`이며 `sessionRef`(`open_session`으로 발급)로 세션을 지정한다.

서버는 모델 등급을 정하지 않는다. `modelClass`는 `null`로 기록하고, 모델 이름 목록이나 등급 mapping을 읽지 않는다. 보고된 추론 수준은 무엇이든 그대로 기록하고, 모델의 지원 목록이나 minimum으로 실행 자격을 거부하지 않는다. 추론 수준이 없으면 `reasoningEffort: null`로 기록하고 다른 모델·턴의 값으로 보충하지 않는다.

## transcript 관측이 믿는 것

Claude Code의 모델과 요청 기록은 호스트가 쓴 transcript 파일을 믿는 관측이다. 같은 PC에서 그 파일에 쓸 수 있는 주체에 대한 방어가 아니다. 그런 주체(관측받는 에이전트 자신 포함)는 대체 경로가 받아들이는 요청 기록을 덧붙일 수 있고, 호스트가 쓰는 어떤 값도 요청 기록을 호출과 묶지 않으므로 호스트가 쓴 줄과 나중에 덧붙인 줄을 가릴 수 없다. 개인판은 PC 전체를 신뢰하므로 이 위협은 막지 않고 받아들인다. 훅이 그 호출에 보고한 effort가 일부만 걸러 낸다. effort가 훅의 값과 다른 위조 요청은 거절하고(`REQUEST_EFFORT_MISMATCH`), effort가 훅의 값과 같은 위조 요청은 모델이 무엇이든 받아들인다. 호출 자신의 줄이 파일에 있는 호출은 호출의 줄을 먼저 읽으므로 위조 요청의 영향을 받지 않는다.

## 실패와 검증

호출자를 관측하지 못하면 `BINDING_REQUIRED`(`CALLER_PROVENANCE_UNAVAILABLE`), 호스트 사실이 모순되거나 자격·재사용 오류면 `BINDING_INVALID`다. 실행만 관측하지 못한 호출은 신원을 유지한 채 그대로 받아들여진다. 실행 하한이 없기 때문이다(아래 참조). 같은 OS 사용자 권한으로 DB에 쓰거나 서버의 MCP 경로를 직접 호출하는 프로세스와의 격리는 보장하지 않는다.

단위 fixture의 synthetic `_meta`와 실제 설치 호스트의 관측은 서로 다른 검증이다. 릴리즈·설치 담당자는 실호스트(설계 6.2)에서 관측과 guarded workflow 완료를 따로 확인해야 한다.

## 단계 추천의 근거와 범위

계획에는 모델 등급·추론 수준의 하한 필드가 없다(모델 선택은 모델이 판단할 일이므로 하한 판정을 두지 않는다). 어떤 에이전트·모델이 와도 실행하며, 루트·하위 에이전트 어느 쪽이 기록하든 관측한 모델 등급·추론 수준(미관측 포함) 때문에 `record_stage_result`·`finalize_workflow`가 거부되지 않는다. 단계 요구는 `policyId`, `kind`, `observationRequired`만 가지며(스킬의 검사만으로 결정되는 `deterministic` 단계는 관측을 요구하지 않고, 그 밖의 `semantic` 단계는 요구한다), 관측값은 기록만 한다. 관측 자체(호출 결속·신선도·형식)는 계속 검사하고, caller가 입력한 희망값을 실제 관측으로 바꾸지 않는다. 감사 의무·독립성·산출물 검사는 그대로 집행한다.

TaskEnvelope의 `constraints`는 문자열 배열이고 provider의 `gate`는 감사 조건이다. 별도의 명시 모델 하한 입력 계약은 없다. 생성된 단계 요구는 `taskDigest`와 전체 계획 서명에 결속되고 claim 시 작업에서 다시 계산해 대조된다. caller가 서명된 값을 바꾸면 무결성 검사에서 거부한다.
