# Architecture

This repository distributes several specialist skills in one installable plugin. Even though the sources are in one repository, the execution responsibilities of the specialist skills are kept separate.

```text
plugin manifest
├── skills/orchestrator/       classification, ordering, input/output, result integration
├── skills/<specialist>/       specialist judgment and its result format
├── contracts/                 explicit contracts shared by several skills
└── java/                      resident server (MCP tools, hooks, admin page) and installation tools
```

The orchestrator does not hard-code skill names. It determines capability candidates from the skill descriptions exposed at installation, and queries only the `skillId`, capability, execution class, phase/order, priority, selection criteria, preconditions, and gates of the active providers with the orchestrator `query-registry` command of the MCP tool `run_skill_check`. The `--all` compact catalog is used only when the candidates cannot be identified. The query tool builds and sorts its result from the original `skills/registry.json` every time, so no separate copy of the catalog is kept. Providers are divided into `bootstrap`, `workflow`, and `recovery`. Bootstrap providers, which create the instruction scope, the repository conventions, and the task contract, run directly before `plan_workflow`. Ordinary workflow providers first satisfy artifact dependencies and use `phaseOrder` as a stable secondary sort key. Recovery providers are planned as a separate execution and are not mixed with the ordinary workflow. For a repeated failure, `recovery-strategy-selector` creates `RecoveryHandoff.v1` after `blocker-diagnostician` has confirmed the cause; the existing run remains immutable, and recovery runs only in a new `TaskEnvelope.v1` and a new workflow bound to the handoff.

When several providers offer the same capability, the one with the larger priority number is preferred. `selectionCriteria` are selection conditions and reasons for a person to review, and MCP does not interpret natural language. If automatic branching by condition is needed, register the providers under different, more specific capabilities. If priorities overlap for the same capability or the selection criteria are empty, the repository verification fails.

The common skills, JSON Schemas, MCP tools, and the runtime use host-neutral contracts. `host` is an extensible identifier, not an enum closed to Codex and Claude Code, and product-specific hook events, inbox, wake transport, and execution observation are converted into the common contract by an adapter or overlay. Therefore Grok, Spark, or another local AI runtime can use the same functions by adding an adapter, without changing the common layer. Only functions that are inherently specific to one product, such as the log or installation format of a particular product, are exceptions, and the constraint is stated in the function name and the documentation.

The public contracts are divided into `TaskEnvelope.v1`, `SkillDescriptor.v2`, `ProviderResult.v1`, `WorkflowPlan.v1`, `StageResult.v1`, `WorkflowReceipt.v1`, `ApiResult.v1`, and the transport-only `ResponseModeV1`, `WorkflowStatusSummaryV1`, `ConvergenceRootHandleV1`, and `ConvergenceStatusSummaryV1`. `SkillDescriptor.v2` declares the providers of one skill, their input and output artifacts, result schemas, state mappings, and gates. `plan_workflow` reads the registry and signs the plan, including the schema checksums, with an HMAC, and `start_guarded_workflow` freezes the plan after checking the signature and the single-use lease in the same MCP store. The public `start_workflow` is the minimal start that creates the plan, root, lease, and run in one transaction with the same checks.

`record_stage_result` checks the revision and the execution order, and then validates the provider envelope and the internal output each against its declared schema. An input artifact whose producer is in the plan can be consumed only if that preceding stage has left a verified artifact. For artifacts that enter from outside the plan, such as bootstrap and task inputs, the specialist skill that ran is responsible for checking the content and the origin; MCP checks the structure of the submitted attachment id and digest, compares the digest with the sha256 of the attachment (the file was uploaded by the recording session; the server never reads a path on the caller's computer), and records the result in `artifactChecks` as `SHA256_MATCHED` or `NOT_CHECKED`. `verified` is a declaration by the provider and is not used in gate decisions. Because only the root calls Sennard, the independence of auditors and reviewers, fresh context, and user approval are not observed and remain in `unverifiedClaims`. The optional `receiptPolicy` of the descriptor is copied into the plan stage and bound to the HMAC. The `reference-only` mode allows only a closed output schema and opaque references, and applies canonical UUID and per-run uniqueness to the declared actor pointer. `finalize_workflow` produces a completion result only when all required stages have passed, no unresolved items remain, and the receipt policy of each stage has been checked again.

### Semantic execution assurance

Strict MCP assurance never trusts `executionContext` supplied in tool arguments. A `TrustedExecutionContextProvider` must supply a fresh observation bound to the exact task, run, stage and revision; observation IDs are atomically claimed in the workflow store and remain one-use across server restarts and concurrent connections. Expired, mismatched or replayed observations fail closed. The server does not fabricate host attestation. Each distribution declares its host with the static `Sennard-Host-Label` header (`codex` in `.mcp.json`, `claude` in the Claude plugin manifest, `agy` in `mcp_config.json`), and the server selects the matching host adapter. A missing or unknown label is treated as an unknown host: its trust level is `unavailable`, and the session is named by a `sessionRef` from `open_session`.

The execution observation contract is common to every host. Each host has one caller ingress that the server selects from the `Sennard-Host-Label` header: Codex and Antigravity read the host-written `tools/call` `_meta`, and Claude Code claims, by `claudecode/toolUseId`, the admission row its PreToolUse governance hook recorded. The core caller check returns a verified caller (`host`, `sessionId`, `callId`, `actor` root or child, `parentChain`, `execution`) or rejects; an unobserved caller is never presumed to be a root. Services receive this caller as a separate parameter, and tool arguments that carry `_sessionBinding`, `_continuityBinding`, `_hostAttestation` or `_sessionProof` are rejected. For `plan_workflow`, `record_stage_result`, `classify_skills` and `record_skill_selection`, `HostAttestationProvider` qualifies `caller.execution` (raw model, reasoning effort) through the current trusted adapter; the observation ID is derived from host, session, actor and call ID, and the existing `WorkflowService` task/run/stage/revision binding, freshness, and atomic one-use claim checks remain in force. Sennard has no stage floor: the observed model and reasoning effort are recorded and never reject a stage. If there is no observation, the result is `BINDING_REQUIRED`; a contradiction, qualification, or reuse error is `BINDING_INVALID`. There are no signed tokens; the guarantee is host observation, not isolation from a process running as the same OS user. See [execution-attestation.md](execution-attestation.md).

Where each host's observation comes from (the Claude Code PreToolUse governance hook and transcript, the Codex `tools/call` `_meta`, the Antigravity hook runner's PreToolUse rows) and each host's limits are in the table of [execution-attestation.md](execution-attestation.md). The 2.x signed-token path (`_hostAttestation`, issued by a PreToolUse hook that rewrote the tool input) no longer exists.

The Antigravity package registers the MCP server via `mcp_config.json` (server key `sennard`) with the `Sennard-Host-Label: agy` header; how its observations are collected is in [execution-attestation.md](execution-attestation.md).

Since v1.19.0 a stage result may carry its provider output by attachment reference (`StageResult.outputFile` with the `attachmentId` of an attachment uploaded by the recording session and its SHA-256, `output.output` null); the server reads the attachment (16 MiB limit), checks the digest, validates the parsed JSON exactly like inline output, and stores only the reference. Strict MCP claim, guarded start and semantic stage boundaries do not advance a plan that carries no execution assurance.


The `plan_workflow` boundary of MCP applies execution assurance fail-closed. The stage-level checks of a new plan bound to an ExecutionContext are kept as they are.


Since v1.13, an orchestrated workflow binds the execution capability of semantic-judgment stages to the plan. `plan_workflow` verifies the host observation bound to the current call and sets no lower bound on the model class or reasoning level. The initial admission requirement that is signed has `policyId`, `kind` (`semantic`), and `observationRequired` (`true`). The fact that a plan can be started does not mean that the individual stages are qualified to run. Each stage of a new plan contains an `ExecutionRequirement.v1`. The requirement of a semantic-judgment stage is `semantic` and requires an observation. For a stage to be `semantic` and become `PASSED`, the current trusted observation must be verified. If there is no observation information, it is rejected with `BINDING_REQUIRED`; however, whatever the model class or reasoning level of a verified observation is, and even if it is unobserved, it is not rejected and is recorded as it is. Identity, signature, and binding errors are distinguished as `BINDING_INVALID`. A stage that is decided only by the check of a skill, such as `korean-prose-finalization`, is marked `deterministic` (`observationRequired: false`) and does not require an observation. The contract binds `kind` and `observationRequired` together and allows only `true` for `semantic` and `false` for `deterministic`.

The common contract does not fix a list of product-specific model names, but it does not trust a new ID by default either. The interpretation of model names and the capability descriptors are provided by the trusted host adapter, and an ID outside the default catalog runs with its class unknown if there is no descriptor, and a policy note is left in the observation. The `lightweight < general < deep < frontier` model classes and the abstract reasoning depth order (`depth_order` in `runtime/model-routing-presets.json`) are the recommended order of execution settings. The effort labels follow the order of the list that the host presents for its own models. The same class or effort does not mean that the actual ability of models from different vendors has been measured to be equivalent. The model class is obtained from the capability policy of the trusted adapter, and the actual model ID and effort must be observed from the host runtime or the result of a worker spawn. The `executionContext` JSON that a caller puts in tool arguments is not a trusted observation and is not authenticated by itself. The MCP boundary does not use the caller's `executionContext` as an observation and uses only the host observation of the caller that the server has verified (`caller.execution`). However, this observation does not guarantee isolation between processes running with the permissions of the same OS user. Therefore this layer is not a device that creates model performance or equalizes the quality of outputs from different sessions; it is execution governance that observes and records with which execution settings a semantic stage was passed. The actual quality assurance is the responsibility of a separate evaluation layer that binds frozen corpora, rubrics, thresholds, and independent evaluation evidence.

The MCP server is registered by the installation in the host's copy of the plugin (Claude Code: `.mcp.json` at the plugin root), as the stdio MCP relay (`McpRelayMain` of `sennard-hook-client`), which forwards each message to `/mcp` of the server at the address in `server.properties`. An MCP response can be evidence for observing external state, but acceptance of a call alone does not mean success. A request that can be handled by a standalone specialist skill can continue even when MCP is absent.

`responseMode` of the mutating workflow tools and `detail` of the status tools are transport options at the server boundary. When omitted, the value is `full`, and the existing domain validators and state transitions are used as they are. Only for `compact` is the domain result, after validation and storage are complete, projected into a summary contract. These options are removed at the server boundary, so they do not enter stored contracts such as `StageResultV1` and `WorkflowReceiptV1`. An MCP result uses only one JSON text content block and does not duplicate the same data in `structuredContent`.

When `claim_workflow_attempt` omits both the task envelope and the frame, the server restores the stored values of `rootId`, performs the existing digest and revision checks, and stores the normalized full proposal. When `start_guarded_workflow` omits the plan, it restores the proposal plan bound to `leaseId` and then checks the integrity token, the root revision, the expiry, and the single-use consumption. When the caller passes a copy, the existing complete-match check against the stored root and proposal is kept. Because the lease is a safe plan reference, no separate plan ID or cleanup policy is added.

Runs, revisions, the run ID sequence, the plan signing key, the update state, cleanup claims, and trusted execution observation claims are stored in the schema `sennard` of the store. After a server restart, the single-use consumption state of earlier runs and observations is restored, and conflicts and reuse are rejected by optimistic revision verification and atomic observation claims. An observation claim is kept as an opaque ID tombstone even after expiry and does not allow reuse of the same ID. Compact transport does not change the unit of storage either and keeps the plaintext JSON of the full `WorkflowReceipt`. Therefore, if the provider output, evidence notes, findings, blockers, and errors of a `StageResult` contain original code, logs, secret values, or personal information, that content also remains in the database. The MCP server neither filters the field contents nor expires or deletes them automatically, so callers must not submit sensitive original text and must manage the access permissions and the retention period of the state folder.

## Skill Classification Advisory Layer (JEV)

`providerKind: "jev"` is the place of an advisory layer that helps selection, not of a particular product. The decision is made by the AGENT, and TypeSafe is one implementation of this layer. The `noul_*` score kinds and the `JEV_*` reason codes are values that the TypeSafe adapter produces. The profile configuration rules (reasoning effort, `judgmentPolicy`) are decided by `validateConfiguration` of each wire adapter, and the authentication header is decided by the transport contract of the adapter (default `authorization: Bearer`). The profile, the route JSON, and the request cannot decide the authentication header. `SkillClassificationService` handles the permission for external transmission, budget reservation and settlement (`JevBudget`), usage verification, failure responses, and response verification. The JEV provider definitions are built into the source (`JevProvider`), and on/off, model, permission to send information, budget, preset, and key are read from the admin signed settings. There is no server-side budget ceiling, and the estimated running total of usage is stored in `sennard.jev_usage_daily`. The detailed configuration is in [Admin Signed Records and Reading Settings](admin-log.md).

## Local Task Continuity

Continuity is a separate service inside the resident server and uses its own tables (`continuity_*`), which are separate from the workflow tables. It stores the direct-task current and history, the session epoch, the compact marker, hash-only observations, and the retention lookup index. The ledger of orchestrated state remains the `TaskEnvelope`, the `WorkflowReceipt`, and the convergence root of the workflow tables, and the continuity tables hold only the root binding and the marker.

Direct memory is divided into `continuity_current_memory` and `continuity_memory_history`. The whole current body `JSON(status/core/evidenceRefs)` has a hard limit of 2000 UTF-8 bytes, which is not a target amount to fill. An update is processed in the same transaction that keeps the previous current content in the history and replaces the current. The agent API does not expose the history, but there is no separate permission isolation that blocks direct access to the state folder by the same OS user. The body is plaintext JSON, so secret values, personal information, raw logs and code, and chain-of-thought are excluded, and the access permissions and the retention period of the state folder are managed. `load_context` reads its own current and the `stateToken` by `schemaVersion` alone, and writes and deletions are checked against the returned token as `expectedStateToken`. An explicit `purge_direct_context` deletes only the current and leaves a hash tombstone; it does not delete the private history, the workflow receipts, or the convergence roots.

The host lifecycle hooks are received by the resident server. A host runs the Sennard Java client (`sennard-hook-client`, started with `java -cp`) as a command hook, and the client sends the input to `/hooks/v1/<host>/<event>` of the server at the address that the server announced in `server.properties` (`ContinuityHookHandler`, the host adapters of the `hook` package). This path handles every hook of Claude Code, Gemini CLI and Antigravity, plus the Codex hooks for SessionStart, SessionEnd, UserPromptSubmit, PreCompact, PostCompact, PreToolUse, PostToolUse, PreModelRequest, PostModelRequest and Stop. The Codex SubagentStart and SubagentStop hooks use `mcp_tool` and reach the server through the MCP relay. There are no HTTP hooks, because a host's HTTP hook takes a fixed URL and the server's port is not fixed. See [Host Hook Reception](hooks.md).

`SessionStart(resume)` and the direct-task `SessionStart(compact)` inject the current memory body through the existing hook. Freshness means the current at the atomic read time L, and without a host acceptance ACK it does not guarantee exactly-once delivery across a crash or freshness up to the first action of the model. The ordinary inputs of Codex and Claude Code receive only a short update cue without the body. The AGY turn0 uses the native ephemeral current+cue path so that the injected text does not accumulate in the durable conversation history. The revision and digest verification of the workflow and the restoration of the bounded structure card bound to the marker are kept. Startup does not restore, and clear rotates the epoch. If the server cannot be reached, the `SessionStart` hook prints a notice to check with `sennard status`.

## Session Board

The session board is handled by a service of the resident server (`SessionBoardService`) and the `board_sessions` table, and the MCP tools `update_session_status` and `list_session_status` are its interface. Each row holds a session and a one-line summary, and the board does not hold the original request (the original text is the responsibility of "User Prompt Archive" below). Because the store is shared by all hosts (Claude Code, Codex, Antigravity), the list shows the rows of all hosts together with `host`. The board is a pull method in which a session must read the list again to learn of changes; it is not a real-time communication channel that pushes messages to other running sessions or interrupts their work.

## User Prompt Archive

What the user said to the main session is kept verbatim in the prompt tables (V15). The archive has three purposes: to let the user confirm what was said in the original words, to let an agent refer, as a summary, to what it did after hearing it, and to prompt moving important things into the shared context. The original text of the agent's answers is not stored.

- Tables: `user_prompt` (the original text, size, SHA-256, truncation marker, transcript path), `turn_recap` (one summary line per original text, replaced by `version`), `recap_nudge` (one return record per original text), and `transcript_anchor` (one position in the transcript per original text: the entry identifier and time decided by the host, INSERT only).
- There is one write path, the hook collection path. `PromptCollector` (`@Order(7)`) INSERTs through `PromptArchiveWriter`, and the MCP tools only read and record recaps. The build rule `r-prompt-archive` keeps this boundary.
- `TurnCheckService` checks for a save after each user input. On `UserPromptSubmitted` it records `turn-check:start` in the continuity store when the main agent has a task and restore is enabled. A successful `checkpoint_context` or `checkpoint_role_context` (via `RoleContextSaved`) records `turn-check:saved`, and `mark_turn_unchanged` records `turn-check:unchanged`, each for the calling actor. The check reads across epochs and counts records by the main agent after that input. When `TurnEnded` allows a continuation, `ContinuityHookHandler` combines any workflow stage, work evidence, and save notices into one request. The save check requests a continuation at most once per input (`turn-check:asked`). If a Stop can continue but the host has already continued (`alreadyContinued`) or the check has already asked, the check records `turn-check:closed` as unconfirmed. When `continuable` is false and the save is missing, the check leaves it open. The next user input reports a previous input that still lacks a record. Subagent Stops, suppressed sessions, and wake-up Stops without a new input after the check closed are excluded.
- `RecapNudgeHook` (`@Order(30)`, the last) handles the input recap and the session board summary. If the original user message lacks a recap and no request has been recorded for it (`recap_nudge`), the hook asks for `record_turn_recap` once on a Stop that can continue. It checks the board entry (`BoardService.readEntry`) with `SummaryState`, which is missing, stale (`summaryStale()`, older than the last prompt), or current. `RecapNudgeService.remindNow` requests `update_session_status` while the summary is missing or stale, either in the same continuation or on its own. The hook also requests the summary at `UserPromptSubmitted`, `ModelCallFinished` with `carriesContext`, and `ToolFinished` with `stepBoundary`. Antigravity tool endings do not carry context. On a Stop with `alreadyContinued`, the hook skips the summary request and still applies the one-request rule for the recap. A cancelled or failed Antigravity Stop reports `continuable` as false and skips both requests.
- The tools are `record_turn_recap` (the recap length is at most 500 as a weighted sum: 5 for Hangul, Han characters, and kana, and 2 for all others) and `recall_user_prompts` (`scope` SESSION or ROLE). ROLE reads only the originals of sessions that the signed role binding (`ContextLayerService.signedRoles`) places in the same role. The search is the `PromptSearch` port, and the default implementation is the standard SQL `LOWER(...) LIKE LOWER(?) ESCAPE '\'`. The third tool, `read_prompt_transcript`, goes through the transcript boundary below.
- Transcript boundary: what the agent did after an original text is read by `read_prompt_transcript` from the host's transcript, and the only path for reading is `interface Transcript` (`domain.transcript` of `sennard-domain`). Each host has a different file and format, so the implementation is a per-host `@Component` (currently `ClaudeTranscript`), and `TranscriptHosts` selects it by host name from `List<Transcript>`. A host without an implementation (Codex, Gemini CLI, Antigravity) answers `Unsupported`, and its format will be implemented as a separate task after being measured on the test servers. `locate` and `readAfter` answer with sealed results (`TranscriptLookup`, `TranscriptRead`), and unsupported and unconfirmed are not lumped together as `Optional` or null. Each item carries the host's identifier (`key`, the line's `uuid` in Claude or `uuid/position` when the line has several items). `continueAfter` resumes after that item within the range from the specified user message to the next user message and returns `NotInTurn` if the key is absent from that range.
- A transcript is read only for the same session. `TranscriptAccess` compares the calling session with the (host, session ID) of the original-text row, and the only file read is the `transcript_path` that the hook stored in the original-text row, so the caller cannot supply a path. When the first item is found, only its position (`entry_key`; for Claude, the `uuid` of the line) is INSERTed into `transcript_anchor`, and the next call reads from that position. If two calls find it for the first time at the same moment, they read again after the primary key conflict and use the stored value (`TranscriptAnchorService`). The transcript body is not stored. In the Claude implementation, `ClaudeTranscriptFile` and `ClaudeEntry` read the line format in one place, and `ClaudeTranscriptExecutionReader`, which finds the model of a call, uses the same reading.
- The key of the session that called the tool is the (host, host session ID) that the hook stored. A call that has only a session reference (Gemini CLI) obtains the host session ID with `SessionRegistry.identityOf` (`ArchiveSessionKeys`).

## Session Message Store (No Broker)

Session messages are stored in the messaging tables of the store, and the operations run inside the resident server (the server adapter `SessionMessageService` and `MessagingService` of `sennard-app`). There is no per-session relay process, no separate broker process, and no lock directory. Each operation is one database transaction. `prepare` and `send` use the connection pool's isolation level. The personal edition defaults to `READ_COMMITTED` through `sennard.store.isolation`. The value `DEFAULT` uses the database's own default. `host` is an open string identifier, and the store knows neither product-specific transports nor operating systems.
The message ID is issued by the server at prepare, and the immutable sender, target, body, and TTL are kept in `prepared_messages`. Prepare has no delivery effect, and send accepts only an issued ID and commits the queue insertion and the first receipt in the same transaction. The same ID returns the preserved first result, and an unissued ID, a different sender, an expired ID, a purged ID, and changed content are rejected. A lost response is reconciled with the same known ID, and an unknown outcome is not unconditionally resent as a new prepare. The storage limits and recovery limits follow the [message ID and retry contract](session-messaging.md). The claim of a receiving hook sets a short lease, and without an ACK the message is redelivered with exponential backoff until the TTL. Only the moment at which the model has processed the body and called the MCP ACK is `ACKNOWLEDGED`, and the success of a Codex queue write or a Claude inbox write is not used as evidence of delivery. A message stores the sender and receiver host and session, the body, the creation, expiry, claim, and ACK times, the delivery count, and the first delivery time, and it does not contain private keys, broker tokens, inbox tokens, or socket paths. The limits are a body of 4096 UTF-8 bytes, a TTL of 30 seconds to 24 hours, and a spool of 1000 messages and 4 MiB. A claim selects at most 10 messages, but cuts the batch before the actual UTF-8 response, including JSON escapes and metadata, exceeds 32 KiB. The 2.x broker and client accepted a request or response line only when it was collected as the received bytes and its size including the line break was at most 32 KiB, and decoded the completed line to UTF-8 at once so that a character split across a TLS fragment boundary was not corrupted (since 3.0 there is no broker or TLS connection). The caller can lower `maxMessages` and `maxBodyChars` (in UTF-16 code units) further to the injection limit of the target host, and the bundled hook claims only one message at a time. The final envelope is checked to be within 8192 UTF-8 bytes, and a body that overflows because of JSON escaping is delivered losslessly with an explicit base64-utf8 encoding. The digest of the original text and the BEGIN/END boundary and ACK notice are kept. The distinction between ordinary user input, wake, and the tool boundary follows [Input Sources and Task Boundaries](input-boundaries.md).

In an interactive Claude Code session, the server holds a wait hook without a database connection. When a message is committed, it returns the claimed envelope to the hook (`WakeController`, `WakeWaiters`). For Codex and Antigravity, `IdleWakeService` dispatches a reserved marker through the local worker. The recipient claims the queued message at the host’s input hook using the marker, live generation and current server incarnation. The local worker can register again at the next eligible `Stop` after the server restarts.

A malicious process with the permissions of the same OS user can read or change the state folder and therefore cannot be stopped. A peer message does not replace approval, authority, or the intent to make an external change.

## Attachments

The evidence files of a stage result are kept as attachments, each a bundle of one or more files: the tables (`attachment`, `attachment_file`, `attachment_storage`, `upload_staging`) hold metadata only, and the bodies are encrypted segments in the server's own folder, uploaded with the `artifact_*` tools. See [Attachments and Uploads](attachments.md).

## Plugin Update Notice

The MCP server checks only stable tags in the format `vMAJOR.MINOR.PATCH` in the fixed public repository. A successful result is kept in `sennard.plugin_update_state` for 24 hours, and if it fails, the last successful result is kept and the check is retried after 1 hour. An error in the update check does not change the workflow state or the tool result.

If there is a tag higher than the installed version and the version has not been announced yet, a `plugin-update-notice` content block is appended after the existing MCP tool result. The notice for the same version is claimed only once in the whole database. Passing `force: true` to `check_for_updates` ignores the TTL and checks again. The server does not modify installation files or marketplace settings, and `automaticInstall` is always `false`.

The orchestrator does not decide the completion of a high-risk change. It integrates, as they are, the results of the independent audit skill that checked the final target and the evidence. A pass of `mutation-risk-preflight` does not replace execution approval or an audit pass.

MCP is not a security boundary that authenticates an adversarial caller. `verified`, the declared digests of attachments, and auditor IDs are trusted inputs that a specialist skill submits after checking them directly, and MCP checks the structure of those declarations and the stage invariants. A deployment that needs real identity authentication or integrity of raw data must add an authenticated external identity and evidence service.

A previously signed, unstarted plan can produce `LEASE_CONFLICT` when compared with a new canonical plan, because its initial admission requirement differs. The original plan, the run records, and the state ledger are preserved, and the plan is created again with the new observation of the current call. The stage requirements of a run that has already started follow the stored plan, and this change does not rewrite operational data or recovery records.

## Scope and Limits of Checks

The MCP server reads the `capability`, the execution stages, and the `artifact` dependencies of `SkillDescriptor.v2` to create a plan. The plan includes schema checksums and an HMAC signature, and the server checks the following items.

- That the content has not changed since the plan was started
- That each stage was submitted according to the determined order and `revision`
- That the result of each provider follows the declared schema and state mapping
- That the outputs and verification evidence needed by the next stage are ready
- That the targets of independent deliberation and required audits match the current result and satisfy the determined conditions
- That no unresolved blockers remain
- That a new orchestrated run used a single-use lease bound to the root and kept the budget of attempts per epoch fixed in the frame of the root (3 by default; a value changed on the admin page applies from the next root that is opened) and the frame invariants

The convergence root, epoch, attempt, lease, review, and workflow links are also stored in the workflow tables as append-only history, so the budget and the active attempt are kept even if the server restarts. The installer, `sennard start`, or a session-start hook launches the resident server process. The installation registers a stdio MCP relay in `.mcp.json` for Codex and Claude Code, `mcp_config.json` for Antigravity, and `gemini-extension.json` for Gemini CLI. The host starts `McpRelayMain`, which reads the server address from `server.properties` and relays the host's messages to the resident server's HTTP `/mcp` endpoint. For the admin page port, see [Admin Signed Records](admin-log.md).

The orchestrator selects the needed capability candidates from the skill descriptions exposed at installation and then queries only the execution metadata of the active providers with the orchestrator `query-registry` command of the MCP tool `run_skill_check`. The `--all` compact catalog is used only when the candidates cannot be determined, and the whole `skills/registry.json` is not passed as model input.

If the response options of a public MCP tool are omitted, the full result and the convergence history are returned as before. The normal path of the orchestrator uses `responseMode: "compact"` and `detail: "compact"` and receives only a fixed-size summary that excludes the plan, the accumulated `stageResults`, the provider output, the original task and frame, and the full history. Only when the cause of an error, past results, or audit material is needed is that state queried again as `full`.

The running runs, the current `revision`, the run ID sequence, the plan signing key, and the plugin update check state are in the store, so processing can continue after a server restart. The update state contains only the version, tag, commit, ETag, the check time, the next check time, the last announced version, and the error code. A provider that declares `receiptPolicy.mode: reference-only` in its descriptor is allowed, before storage, only a closed output schema and digests, artifact references, and fixed tokens, and the free text of notes, locators, findings, blockers, and errors is also rejected. If `actorIdPointer` and `uniqueness: run` are declared together, reuse of a canonical lowercase UUID actor ID within a run is also rejected after a server restart. This policy is only a structural storage boundary for not storing original text and does not authenticate identity. If authenticated identity, encrypted long-term retention, or evidence integrity that holds even in an adversarial environment is needed, a separate identity and evidence store must be connected.

## Resident Service

Only one resident Spring Boot server per user and PC opens the state store. Hosts connect through a stdio MCP relay to `/mcp` of the server, hooks send requests through the Sennard Java client (and the MCP tool hooks of Codex), and the plugin contains no executable code. The server's port is chosen by the operating system at each start and announced in `server.properties` in the state folder; one server runs on a state folder (`ServerInstanceLock`).

Settings are stored in a local H2, and the business store is connected separately. The MCP and hook port and the admin page port are two connectors of the same Tomcat and are bound only to `127.0.0.1`. Installation, start, and upgrade are handled by the `sennard` command (`SennardCli` and `Installer` of `java/sennard-personal`) and are not registered as an OS service. The procedure is in [Updates and Migration](../user/update.md).
