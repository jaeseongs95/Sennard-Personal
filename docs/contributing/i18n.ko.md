# Sennard 국제화(i18n) 설계

## 1. 목표와 범위

요구:

- Sennard는 영문도 지원한다.
- i18n 국제화 규격으로 설계한다.
- 이후 MCP에 붙일 관리자 페이지도 고려한다.
- 관리자 페이지뿐 아니라 Sennard가 내보내는 모든 메시지에 i18n을 적용한다.

3.2.1 당시 Sennard에는 언어 설정이 없었다(`mcp-server/src`, `runtime`, `scripts`, `hooks`, `claude-overlay`, `antigravity-connector`에서 locale 처리 0건, `localeCompare`만 있음). 서버 오류와 도구 설명은 영어였고 일부 스킬, 접수 안내, hook 문장에는 한국어를 썼다.

현재 관리자 페이지에서는 한국어와 English 중에서 선택할 수 있다. 페이지는 `sennard-admin-language` 쿠키를 먼저 확인하고, 그다음 브라우저의 `Accept-Language` 헤더를 확인한다. 기본 언어는 영어다.

### 1.1 대상: Sennard가 내보내는 모든 문장

| 표면 | 위치 | 카탈로그 도메인(`locales/catalog.json`) | 받는 쪽 |
|---|---|---|---|
| MCP `instructions` | 서버의 `instructions` 문장 + `skills/orchestrator/references/intake.md` 접수 블록 | `instructions` | 에이전트 |
| 도구 설명·입력 필드 설명 | `@McpTool`의 메시지 키, `contracts/*.schema.json`의 `description` | `tools`, `schema` | 에이전트 |
| 도구 결과·오류 문장 | 서비스가 던지는 오류의 메시지 키와 `params` | `server`, `workflow`, `services`, `continuity`, `peer` | 에이전트, 사용자 |
| 저장 후 다시 보이는 문장 | 저장소에 남는 라벨(키와 `params`로 저장) | `workflowRecord` | 에이전트, 관리자 페이지 |
| hook 문장 | 호스트 hook 어댑터(편집 관문, workflow 단계 점검, 사용자 입력별 저장 점검, 현재 요청의 작업 증거) | `hooks`, `connector` | 사용자 화면, 에이전트 |
| 호스트가 직접 읽는 정적 문장 | `hooks.json` `statusMessage`, 플러그인 manifest의 설명·`suggestedPrompts`, `marketplace.json` | 없음(원문 그대로) | 호스트 UI |
| 스킬 | `skills/*/SKILL.md`(frontmatter `description` 포함), `references/`, `agents/openai.yaml` | 없음(원문 그대로) | 에이전트 |
| 스킬 검사·보고 출력 | 서버의 `SkillCheck` 구현 | `skillScripts`, `skillTools`, `skillReports`, `skillChecks`(`*Ko`는 한국어 원문) | 에이전트, 사용자 |
| 엔지니어링 실무 검사 출력 | 서버의 engineering-practices 검사(`EngineeringPractices`)와 산출물 파일 읽기(`LocalFileFacts`) | `practices` | 에이전트, 사용자 |
| 관리자 페이지 | `admin-page.html`과 서버가 내는 상태 | 9장 | 사용자 |

### 1.2 번역하지 않는 것

- 사람이나 에이전트가 쓴 내용: 세션 메시지 본문, `goal`, `acceptanceCriteria`, 결과 요약, 사용자 원문. Sennard는 이것을 그대로 저장하고 그대로 보여 준다.
- 기계 식별자: 오류 `code`, capability, 스킬 이름, 도구 이름, schema 필드 이름, 상태 값. 모든 locale에서 같다.
- `korean-prose-editor`의 기능 대상 언어. 설명·안내 문장은 번역하지만 편집 대상은 한국어 그대로다.
- 저장소의 `docs/` 문서는 런타임 메시지 카탈로그 밖에서 영문판과 한글판으로 관리한다. 영어 사용자 입구인 `README.md`는 한글판 `README.ko.md`를 링크한다.
- stderr 진단. 지금 code와 JSON만 낸다. 문장을 새로 넣게 되면 카탈로그를 거친다.

## 2. 따르는 규격

| 영역 | 규격 | Sennard에서 쓰는 방식 |
|---|---|---|
| 언어 태그 | BCP 47(RFC 5646) | 모든 locale 값. |
| locale 고르기 | RFC 4647 Lookup | 요청 목록을 앞에서부터, 각 태그는 뒤 subtag를 하나씩 잘라 가며 지원 목록과 맞춘다(`en-US` → `en`). |
| 메시지 문법 | `java.text.MessageFormat` | 자리표시 `{name}`과 `{n,number}`만 쓴다. 따옴표는 JDK 규칙이다(`'` 하나는 `''`, 글자 `{`는 `'{'`). |
| 지역 데이터 | JDK의 로캘 데이터(CLDR) | 숫자 모양은 `MessageFormat`이 로캘로 정한다. |

메시지 실행기는 JDK의 `java.text.MessageFormat`이고 외부 라이브러리는 없다. 문장은 Spring `MessageSource` 빈 하나(`CatalogMessageSource`)와 `MessageSourceAccessor`로만 만든다(`sennard-server`의 `message/Messages`가 그 위에서 `MessageRef`를 문장으로 바꾼다). `MessageFormat`은 번호 인자만 읽으므로 카탈로그의 이름 인자는 `CatalogPattern`이 처음 쓸 때 번호로 바꿔 넘긴다.

값에 따라 문장이 바뀌는 것(ICU의 `select`·`plural`)은 패턴 안에 쓰지 않고 키로 쓴다. 문장 `K`가 `{종류}`를 갖고 있으면 `K#종류=값`이 값마다 문구 하나이고, 인자의 값(enum 상수의 이름, 문자열, 정수의 자릿수)으로 문구를 고른다. 어느 것도 아니면 `K#종류=other`를 쓰며 `other`는 꼭 있어야 한다. 개수는 같은 방식으로 `K#개수=0`과 `K#개수=other`로 쓰고, 영어에 `one` 문구를 따로 두지 않는다. 한국어도 단수형 하나다. 문구는 같은 인자를 받는 패턴이다. 로캘은 `en`과 `ko`이고, 그 밖의 요청 언어는 `en`이다. 언어를 더하려면 `locales/<언어>/`의 파일만 더한다.

## 3. 원칙

1. **기계 계약은 언어와 무관하다.** 문장을 내보내는 모든 응답은 `code`, `messageKey`, `params`를 함께 낸다. `message`는 표시용이다. 에이전트 지침·시험·관리자 페이지는 `code`로 판단하고 문장을 비교하지 않는다.
2. **저장은 key와 params로, 렌더링은 내보낼 때 한다.** 저장하는 오류 본문은 `messageKey`, `params`와 함께 `message`를 근 locale(`en`) 문장으로만 갖는다. 그래서 저장 내용과 digest가 요청한 사람의 언어에 따라 달라지지 않고, 관리자 페이지는 보는 사람의 언어로 key에서 다시 그린다. 응답의 맨 위 `error`는 응답 경계(`toolResult`)에서 요청 locale로 다시 렌더링한다. `data` 안에 든 저장 본문(영수증 등)은 digest를 지키려고 그대로 둔다. 이미 저장된 한국어 문장(`LATE_ADOPTION_LABEL` 등)은 읽을 때 알려진 문장을 key로 대응시킨다.
3. **카탈로그는 한 벌이다.** MCP 도구, hook, 스킬 검사, 패키지 빌드, 관리자 페이지가 같은 `locales/`를 쓴다. 표면마다 사본을 두지 않는다.
4. **출시 locale은 빠진 키가 없어야 한다.** CI가 출시 locale(처음에는 `ko`, `en`)의 키 완비를 강제한다. 실행 중 fallback은 안전망일 뿐 번역 누락을 덮는 수단이 아니다.
5. **번역은 원문 판(版)에 묶인다.** 번역 항목마다 원문 digest를 기록한다. 원문이 바뀌었는데 번역이 그대로면 CI가 실패한다.

## 4. locale 결정

### 4.1 프로세스 단위(MCP 서버, hook, CLI, 스킬 스크립트)

Sennard는 세 위치로 나뉘어 배치된다. 위치마다 같은 기계일 수도, 다른 기계일 수도 있다.

| 배치 위치 | 실행 위치 | 여기서 렌더링하는 문장 |
|---|---|---|
| ① 호스트 PC | 사용자 PC | 정적 패키지 문장 |
| ② Sennard/MCP 서비스 | 사용자 PC | hook 응답, `instructions`, 도구 설명, 도구 결과·오류, 스킬 검사 출력, 관리자 페이지 |
| ③ DBMS | 서비스 안 내장(로컬) 또는 서비스와 다른 원격 서버 | 렌더링하지 않는다 |

한 배치 위치가 다른 위치의 파일을 읽는다고 가정하지 않는다.

#### ①·② 호스트 PC와 서비스의 locale: `MODEL_LOCALE` 하나

모델에 전달하는 카탈로그 문장(hook 안내, MCP `instructions`, 도구 설명, 도구 결과·오류, 스킬 검사 출력)은 `server/message/Messages.java`의 `MODEL_LOCALE`(`en`) 하나로 렌더링한다. 모델이 먼저 읽는 문장이고 세션마다 토큰으로 값을 치르므로, 기준은 언어가 아니라 문구마다의 토큰 수다. 카탈로그 1,526개를 o200k로 하나씩 비교하니 영어가 짧은 것 1,468개, 같은 것 47개, 한국어가 짧은 것 11개였고, 그 11개는 영어를 한국어 이하로 줄였다. 그래서 모델에 전달하는 카탈로그는 `en` 하나로 렌더링한다. 새 문구를 더할 때도 두 형태를 재서 적은 쪽에 맞춘다. 사용자에게 보이는 답은 에이전트가 사용자의 언어로 쓴다. `instructions`의 공통 접수 블록은 렌더링하지 않는 정적 문장(4.2)이라 원문(한국어) 그대로다. 영어가 23% 적은 토큰(1,594 대 2,116)이지만 8,151자라 Claude Code가 instructions를 자르는 4,096자를 넘으므로, 한국어로 두고 겹치는 조항을 다른 곳으로 옮겨 줄였다. 스킬 description도 같은 기준으로 영어다.

- 위치마다 locale을 정하지 않으므로 ①과 ② 사이에 언어를 실어 보낼 것도 없다. 어느 배치 위치, 어느 인스턴스가 렌더링해도 결과가 같다.
- 서비스는 응답의 `_meta["io.modelcontextprotocol/contentLanguage"]`에 `MODEL_LOCALE`을 적는다.
- 모델에 제공하는 문구의 locale은 고정돼 있다. 서명된 `locale.set` 기록은 사슬 검증에만 쓰이며 서버는 새 `locale.set` 기록을 거절한다. [관리자 기록 계약](admin-log.ko.md)을 참고한다.
- 카탈로그는 `ko`도 그대로 유지한다(5장). 다시 언어를 고르게 할 일이 생기면 렌더링 호출이 받는 locale 인자만 바꾸면 된다.

#### ③ DBMS

- DB에는 문장을 저장하지 않는다(원칙 2). key, params, UTC 시각만 저장한다. 그래서 DB가 어느 서버에 있든, 어떤 locale로 설정돼 있든 결과가 같다.
- DB 서버의 오류 문장은 그 서버의 `lc_messages` 언어로 나온다. Sennard는 이 문장을 사용자에게 그대로 내보내지 않는다. SQLSTATE를 Sennard `code`로 대응시켜 카탈로그 문장으로 낸다.
- 식별자 열은 DB 서버 locale에 따라 정렬·비교가 달라지지 않게 `COLLATE "C"`로 둔다. 화면에 보일 문장의 정렬은 렌더링한 쪽에서 한다.

#### 버전이 다른 배치 위치

설치된 호스트 플러그인과 로컬 서비스의 Sennard 버전이 다를 수 있다.

- 출시한 키의 뜻과 params는 바꾸지 않는다. 바꿀 때는 새 키를 만든다.
- 모르는 키를 받은 렌더러는 실패하지 않는다. 받은 `message`를 그대로 쓰고, `message`가 없으면 `code`와 key를 보여 준다.

#### 렌더링 상태

- **무상태 렌더링.** locale은 `MODEL_LOCALE` 하나이고, 렌더링에 필요한 것은 카탈로그와 그 요청뿐이다. 요청마다 달라지는 locale 표를 서버 메모리에 두지 않는다.
- **메모리 상한은 카탈로그 크기다.** 메시지는 처음 쓸 때 한 번 컴파일해 보관한다. 상한은 렌더링에 쓰는 locale 수 × 키 수다. 요청마다 파싱하지 않고, 렌더링 결과는 캐시하지 않는다. 그래서 메모리가 params 종류에 따라 늘지 않는다.
- **기록은 code로 한다.** 로그·지표에는 렌더링한 문장 대신 `code`, `messageKey`, locale을 남긴다. 언어가 달라도 같은 사건으로 집계된다.
- **관리자 페이지는 브라우저에서 문장을 만든다.** 서버는 요청 언어(`Accept-Language`, `en`·`ko`, 그 밖은 `en`)의 `admin.page.*` 패턴을 페이지에 JSON으로 실어 보내고(`AdminTexts`), 화면이 패턴과 인자로 문장을 만든다. HTML 틀이 가진 문장(언어, 제목, 스크립트 전의 안내)만 서버가 그린다. 문장 하나가 키 하나이고, 화면은 문장 조각을 이어 붙이지 않는다.

#### 컴퓨터를 잘 모르는 사용자

MCP 서비스와 DBMS는 로컬 PC에 설치할 수 있어야 하고, 이 경로가 기본이다. 설정을 하나도 건드리지 않은 사용자에게도 맞는 언어가 나와야 한다.

- 패키지는 하나라 설치 단계에서 언어를 고르지 않는다. 환경 변수나 설정 파일은 필수가 아니다.
- 설치·연결 실패 안내(DB 파일 열기 실패, 서비스 미기동, DB 연결 거부 등)도 카탈로그 문장이다. 원인을 짐작하게 하지 않는다. 사용자가 할 다음 행동 하나를 그 언어로 적고, 지원 요청용 `code`를 함께 보여 준다.
- 업무 데이터베이스는 별도로 연결한다. 연결과 상태 화면의 문장도 이 카탈로그를 쓴다.

### 4.2 정적 문장과 실행 중 문장

호스트는 플러그인 폴더의 `skills/`, `hooks.json`, manifest를 그대로 읽는다. 세 호스트(Claude Code, Codex, Antigravity) 모두 이 파일들에 locale별 변형을 고르는 기능이 없다. 그래서 정적 문장의 언어는 하나뿐인 패키지의 원문이 정하고, 실행 중 렌더링하는 문장은 `MODEL_LOCALE`이 정한다. 서버 `instructions`의 접수 블록은 설치된 `skills/orchestrator/references/intake.md`에서 읽으므로 정적 문장에 속한다(스킬과 같은 원본이라는 지금 원칙을 유지한다).

### 4.3 요청 단위

- MCP: 요청의 `acceptLanguage`를 읽지 않는다(4.1). 도구 입력 schema에 locale 인자를 추가하지 않는다.
- 관리자 페이지: 화면은 요청의 언어(`Accept-Language`)로 나온다. 영어와 한국어를 지원하고, 그 밖의 언어와 언어를 밝히지 않은 요청은 영어다. 머리말 전환으로 사용자가 고른 언어(쿠키 `sennard-admin-language`, `SennardLocaleResolver`)가 `Accept-Language`보다 먼저이며 서명하는 설정은 아니다([admin-page.md](../user/admin-page.ko.md#언어)).

## 5. 카탈로그

### 5.1 파일

```text
locales/
  catalog.json            # 출시 locale, 각 domain의 원문 locale
  en/server.json          # domain별 파일, 값은 `MessageFormat` 패턴 문자열(이름 인자, 문구는 `키#인자=값`)
  en/hooks.json
  en/cli.json
  en/manifest.json
  en/skill-scripts.json
  en/admin.json           # 관리자 페이지가 보여 주는 문장(`admin.` 키, `catalog.json`의 admin domain, 원문 en). 화면 문장은 `admin.page.<영역>.<이름>`, 서버가 만드는 화면 문장은 `admin.jvm.*`·`admin.rootRelease.*`
  ko/...                  # 같은 구성
  ko/translations.lock.json   # 번역 키 → 원문 문자열 sha256
  en/translations.lock.json
```

- domain을 나누는 이유는 관리자 페이지가 필요한 domain만 불러오고, 번역 검토를 표면별로 나눌 수 있게 하려는 것이다.
- 원문 locale은 domain별로 `catalog.json`에 적는다. 지금 영어로 쓰인 서버 오류·도구 설명은 원문이 `en`이고, 한국어로 쓰고 다듬은 hook 문장·접수 안내는 원문이 `ko`다. 원문을 억지로 한 언어로 맞추지 않는다. 지금 문장의 뜻과 다듬은 결과를 보존하기 위해서다.

### 5.2 키

- 형식: `<domain>.<영역>.<이름>`. 예: `hooks.editGate.denied`, `server.tool.startWorkflow.description`, `server.error.INVALID_INPUT.startWorkflowRequiredArtifacts`.
- 오류 키는 `code`와 별개다. 한 `code`를 여러 문장이 쓰기 때문이다(예: `INVALID_INPUT`).
- 입력 schema 설명은 파일을 고치지 않고 내보낼 때 바꾼다. 키는 `server.schema.<$id>#<JSON Pointer>`다. 원문은 schema 파일의 영어 `description`이다. 그래서 `CONTENT_LOCK.json`이 잠근 engineering 계약 schema를 건드리지 않는다.

### 5.3 형식 안전

- `sennard-repo-tools`의 `LocaleCatalogsTest`가 출시 locale의 키 완비·번역 검토 상태와 자리표시 형식을 검사한다.
- 문장을 내보내는 함수(오류 생성자, hook 응답, 도구 설명 등록)는 `MessageRef { key, params }`를 받는다.
- CI 검사(프로세스를 띄우지 않음):
  - 출시 locale마다 키 집합이 원문 domain과 같다(빠진 키, 남는 키 0).
  - 모든 값이 `CatalogPattern`(`MessageFormat`)으로 읽히고, 자리표시 이름 집합이 원문과 같다. `키#인자=값`은 문장과 그 인자가 있고 `other`가 있다.
  - `translations.lock.json`의 원문 digest가 지금 원문과 같다(번역 stale 0).
  - 태그가 정규형이다.

## 7. 스킬 번역과 잠금

### 7.1 배치

- `skills/`는 원문 그대로 둔다. 스킬마다 원문 locale을 `skills/registry.json`에 적는다(지금 기준 모든 스킬이 `ko`).
- 번역은 `locales/<tag>/skills/<스킬>/<같은 상대 경로>`에 둔다. 대상은 `SKILL.md`(frontmatter `description` 포함), `README.md`, `references/**/*.md`, `agents/openai.yaml`, 프롬프트 양식 같은 문장 파일이다. 스크립트·JSON 같은 비문장 파일은 복제하지 않는다.
- 패키지는 스킬 본문을 원문 그대로 담는다. 스킬 번역은 행동을 전부 다시 시험해야 하므로 후속 과제로 미뤘다. 번역이 원문보다 오래되면(7.2 `sourceChecksum`) CI가 실패한다.

### 7.2 잠금

| 잠금 | 지금 | 바꾸는 점 |
|---|---|---|
| `skills/source-lock.json` | 스킬 폴더별 `integratedChecksum` | locale별 `translations.<tag>.integratedChecksum`과 번역 기준 `sourceChecksum`을 더한다. 원문이 바뀌면 `sourceChecksum`이 어긋나 CI가 실패한다. |
| `ClaudePlugin`의 `COMMON_POLICY_INVARIANTS` | 한국어 문장 대조 | locale별 불변 문장 집합. |
| `claude-overlay/adaptations/*.json`, `antigravity-connector/adaptations/*.json` | 한국어 `find`/`replace` | locale별 adaptation. 번역 파일에 적용한다. |

### 7.3 의미 검토

스킬과 도구 설명은 에이전트 행동을 바꾸는 프롬프트다. 번역마다 원문과의 의미 대응을 독립 검토자가 확인하고, 검토 결과를 번역 커밋에 남긴다. 해시와 구조 검사는 의미 보존을 증명하지 못한다. 실호스트에서 대표 흐름(편집 관문, workflow 시작·기록, 단계 확인)을 돌려 행동이 같은지 본다.

## 8. 패키지와 배포

- 패키지는 호스트마다 하나다: `claude-plugin/`, 저장소 루트의 Codex 플러그인, agy zip. 플러그인 식별자는 `sennard`다.

## 9. 관리자 페이지와의 연계

- 같은 `locales/`를 쓴다. 화면 문장은 `admin` domain에 둔다(`locales/catalog.json`의 `admin`, `locales/en/admin.json`, `locales/ko/admin.json`).
- API의 모든 메시지 객체는 `{ code, messageKey, params, message, locale }`이다. 화면은 `message`를 그대로 쓰거나 자기 locale로 `messageKey`·`params`를 다시 렌더링한다.
- 저장 데이터는 key·params와 UTC ISO 8601 시각만 갖는다. 날짜·숫자 표시는 협상한 locale로 `Intl`이 한다.
- 관리자 페이지는 헤더에서 선택한 언어를 쿠키에 저장합니다. 선택 기록이 없으면 요청의 언어를 사용합니다.
- 화면 문장은 한 문장이 한 키다. 값에 따라 달라지는 문구는 `키#인자=값`으로 쓰고, 문장 조각을 코드에서 이어 붙이지 않는다. 화면 파일(`admin-page.html`)에는 한글이 없고, `AdminPageTextsTest`가 페이지가 쓰는 키와 카탈로그를 대조한다.
- 처음 출시 locale에 오른쪽→왼쪽 언어는 없다. 화면은 CSS 논리 속성(`margin-inline-start` 등)으로 만들어 나중에 추가할 수 있게 한다.

## 10. 시험

- 카탈로그 검사(5.3)와 형 검사는 CI에서 돈다.
- 지금 한국어 문장을 그대로 비교하는 시험(약 153개 파일)은 `code`·`messageKey` 비교로 바꾼다. 표면마다 대표 문장 하나씩만 locale별로 렌더링 결과를 확인한다.
- locale 고정 시험: `SENNARD_LOCALE`·서명 기록·요청 `_meta`가 있어도 렌더링이 `MODEL_LOCALE`로 나오는지, 새 `locale.set`이 거절되는지.
- 패키지 검사: `:sennard-repo-tools:checkClaudePlugin`, agy 묶음 검사, 스킬 잠금 검사.
- 실호스트: Linux 시험 서버에서 Claude Code, Codex, agy에 패키지를 설치해 `instructions`, 편집 관문 거부, 단계 확인 문장이 `MODEL_LOCALE`(영어)로 나오는지 본다.
