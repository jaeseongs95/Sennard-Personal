# DB and Transactions

This document defines the persistence conventions that apply when an area is migrated to Spring Data JDBC. The reference implementations are the status board (board) and session messaging (messaging); the `file:line` references below point to the actual code of these two areas. Other areas are migrated by following the tables and the order in this document. The user prompt store (the prompt tables, V15) is the third area built under these conventions from the start. The application treats prompt text as append-only. The prompt entity has no `@Version`, and `UserPromptWrites` writes a prompt with a single INSERT statement.

## Starting Points

- The store uses Spring Data JDBC. No business logic is placed in the DBMS, DBMS features such as triggers are not used, and SQL is written in ANSI SQL.
- The business database is the user's choice: the user gives the JDBC URL and the JDBC driver jar (the link on the admin page: its URL and driver path), and no vendor driver is shipped (`JdbcDrivers` finds it with `ServiceLoader`, `DataSourceFactory` builds a Spring `SimpleDriverDataSource` and one Hikari pool from it). The tests run on PostgreSQL only (development principle 7.3). For that reason ANSI SQL is used and no DBMS-specific syntax is. Newly written persistence code is DBMS-neutral. Where a product needs the standard written another way, the difference is held in one place, `ScriptDialect` (`GENERATED BY DEFAULT AS IDENTITY` and `TIMESTAMP` for MariaDB/MySQL); the migration scripts stay ANSI. Rules that follow from MariaDB: no column named with a reserved word (`key`, `change`), no key over 3072 bytes in utf8mb4 (768 characters in all), no `MERGE`/`ON CONFLICT` (`SqlMerge` counts, then updates or inserts), no `CAST(... AS VARCHAR(n))`.
- Values are produced in Java and passed to the database. Java creates each value, and the database holds only common types.
- Spring-side rationale: Boot does not add new functionality; it assembles Spring's features through auto-configuration. The DataSource, the pool, the transaction manager, `NamedParameterJdbcTemplate`, and the repository infrastructure are created by Boot auto-configuration, and Sennard does not create them itself.

## Rule Summary

| Rule | Content |
| --- | --- |
| Repository | A `@Table` entity record and a `Repository<T, ID>` interface. Derived queries come first; `@Query` (ANSI) is used only when necessary. |
| User | The personal edition has one user on one PC. No account, tenant, or namespace appears in keys, columns, or query conditions. Row-level security (RLS) is not used. The build rule `n-no-multi-user-columns` prevents such columns from reappearing. |
| Concurrency | Primary keys and UNIQUE constraints, `@Version` optimistic locking, and the `@Transactional` isolation level. Advisory locks, `FOR UPDATE`, and `SKIP LOCKED` are not used. |
| Retry | A transaction that lost a race is not run again. The winner is told by the number of rows one conditional `UPDATE` changed, and a unique key stops duplicates; the loser reads the winner's result or ends with nothing to do. |
| Origin of values | Identifiers come from the injected `IdGenerator`, and timestamps are the UTC `Instant` of the injected `Clock`. Values are not created with DB functions (`now`, `gen_random_uuid`, `clock_timestamp`, and so on). |
| Column types | A UUID is a Java `UUID` (`CHAR(36)`). A timestamp is, without exception, a `TIMESTAMP` (no time zone, UTC value). There is no `timestamptz`, no `bigint` timestamp, and no text timestamp. A meaningful state is an enum name stored as `VARCHAR` with a `CHECK`. |
| Time | A timestamp is created in one place (one `Clock.systemUTC()` bean, `AppConfiguration`) and converted in one place (`Timestamps` in `sennard-domain`). See the "Time" section below and the build rule `TimeRules`. |
| SQL | Only ANSI SQL is used. `ON CONFLICT`, `RETURNING`, `::`, `SKIP LOCKED`, partial indexes, `ILIKE`, `LEAST`/`GREATEST`, and DB functions are prohibited. |
| Role of the DB | Preserving facts. Only FK, CHECK, and UNIQUE declarations are placed in the database; there are no functions, procedures, triggers, roles, or grants (the business database is one account). |
| Errors | Driver classes (`PSQLException` and similar) are not imported. The Spring `DataAccessException` hierarchy is received and converted to `SennardException` ([Exceptions and Messages](exceptions-and-messages.md)). |
| File I/O | Performed outside a transaction. Files are neither read nor written inside a transaction. The attachments are the example that has no body in the database and no foreign key: see [Attachments and Uploads](attachments.md). |
| Migration | A single set. No DBMS-specific folders are created. Only the type name of the long text column is a single placeholder, `${long_text}`, and the DBMS-specific value is the declaration that `SqlBuilder.generateLongText` gives for the dialect (a fixed table with the vendor's documentation URL for each, not a reading of the driver). One runner of Sennard applies the scripts, with a history table that has one row per attempt; Flyway is not used. A table that already holds rows is changed with `ALTER TABLE` in a new script; an applied script is never edited (see "Migrations" below). |

## How It Works

### Entity: Composite Key and `@Version`

When a key consists of two or more columns, an `@Id @Embedded` record is used as the key (`BoardSession.java:20`). Whether a row is new is decided by `@Version Long version`. If the version is `null`, the statement is an INSERT; otherwise it is `UPDATE ... WHERE ... AND version = ?`, and if another transaction changed the row first, zero rows are updated and an `OptimisticLockingFailureException` results. Because an entity is an immutable record, a change creates a new record and calls `save` (`first`, `seen`, and `summarized` at `BoardSession.java:24-`).

### Repository: Marker Interface

A repository extends only `Repository<T, ID>` and does not extend `CrudRepository`. This exposes only the methods the repository declares; CRUD methods such as `findAll` and `deleteAll` do not exist unless declared.

```java
// BoardSessionRepository.java:15
Optional<BoardSession> findByKeyHostAndKeySessionId(String host, String sessionId);
// A derived delete is also possible
long deleteBySeenAtLessThan(Instant before);
```

`@Query` is used only for what a derived query cannot express (ordering, limits, aggregation). Examples: `MessageRepository.java:24` (`findClaimable`), `:29` (`COUNT(*)`), and `:34` (`COALESCE(MAX(seq), 0)`).

### Service: Transactions

`@Transactional` is placed only on service methods. A method is one use case and one transaction, at the isolation level the edition sets (`sennard.store.isolation`; READ COMMITTED for the personal edition), with no raised isolation level on a method. The time every transaction has is the edition's `spring.transaction.default-timeout`, which Spring Boot's `TransactionManagerCustomizers` sets on the store's transaction manager.

A race over one row is decided by a conditional `UPDATE` and the number of rows it changed (`MessageRepository.claim`, `MessageRepository.acknowledge`, `PreparedMessageRepository.submit`), and the loser reads the winner's result or ends with nothing to do; a limit over the whole queue is a plain read that concurrent writers may pass by a few (`MessagingService` class comment).

A transaction that lost is not run again: the second run would decide again on a state the winner changed and would do its effects twice (new identifiers, times, signatures). No method carries `@Retryable` or an annotation that carries it, and the build rule `u-transaction-boundary` finds one. When several requests create a row for the first time at once, the one use case reads inside its own transaction and inserts when there is no row; the second insert of the same moment is stopped by the unique key and ends with the translated error (an accepted limit). Nobody catches a duplicate key to go on, keeps an insert-only use case of its own, or splits a use case outside the transaction to call the parts in turn.

### Values Are Created by Java

A timestamp is taken from the injected `Clock`, truncated to milliseconds, converted to a UTC `LocalDateTime`, and placed in the entity. Because the column is a `TIMESTAMP` without a time zone, the driver never converts the value to the JVM time zone. The conversion happens in this one place only (`Timestamps.toTimestamp` and `toInstant`; `utc()` and `instant()` in `BoardService.java` are aliases that call them). See the "Time" section below. A test verifies that the same UTC value is stored even when the JVM time zone is changed to `Asia/Seoul` (`aTimeIsStoredAsTheUtcInstantWhateverZoneTheJvmIsIn` in `AbstractBoardServiceTest`, and `AbstractMessagingServiceTest` for messaging).

### Time

Time columns are stored in UTC. When a time is shown to a user, the server sends it unchanged in UTC and the client converts it for display. All time calculation in Java is based on UTC, and everything is unified into a single convention.

- Every time column is a `TIMESTAMP` and its value is UTC, with millisecond precision. The PC time reported by a client (`client_started_at`, `client_ended_at`) and the daily aggregate (`jev_usage_daily.day`, UTC midnight) use the same format.
- Time is read from the single injected `Clock`. Business code does not use `Instant.now()`, `System.currentTimeMillis()`, `LocalDateTime.now()`, `ZoneId.systemDefault()`, `java.util.Date`, `Calendar`, or `java.sql.Timestamp`. A waiting period (a deadline) uses the monotonic clock `System.nanoTime()`. The build reads the compiled product classes with ArchUnit and enforces this (`TimeRules` in `sennard-arch-checks`; the test `TimeRulesTest` confirms that a violating example fails). `Clock.systemUTC()` is created in only two places: the `AppConfiguration` bean of the server and the entry point of the CLI process (`SennardCli`).
- `Timestamps.toTimestamp` and `toInstant` are the only conversions between `Instant` and a `TIMESTAMP` value. The value passes through the driver as a `LocalDateTime`. `java.sql.Timestamp` is read and written in the JVM time zone, so the same instant becomes a different value on each JVM and a time in a daylight saving time gap is shifted. When a `Map` row is read, a `TIMESTAMP` column is also received as a `LocalDateTime` (`UtcRows`).
- The database has no clock. `now()`, `clock_timestamp()`, and `CURRENT_TIMESTAMP` are not used in statements or column defaults. The boundaries of a lease expiry and of a retention period are also computed by Java and passed as values.
- Requirement: the time zone of the DB must be UTC. Because Java computes the values in UTC and inserts them, the statements of this repository do not read the DB clock; however, if the DB server or session time zone is not UTC, the interpretation of the `TIMESTAMP` values that an operator views with a tool is shifted. The time zone is not adjusted through a time zone property or a session `SET TIME ZONE`.
- The server emits timestamps in UTC unchanged (`2026-01-02T03:04:05.006Z`, `Timestamps.format`). Conversion to the user's time zone is performed by the client.
- A test verifies that, when the JVM time zone is changed (`Asia/Seoul`, `America/New_York`, including a time in the daylight saving time gap in March), the same instant is stored as the same value and read back as the same instant (`TimestampsTest`, and `aTimeIsStoredAndReadBackIdenticallyWhateverZoneTheJvmIsIn` in `AbstractModuleStoresTest`).

### Enum Storage

A closed set of values is an enum, and the column holds the enum name. The default mapping of Spring Data JDBC is used as is (reference documentation, Mapping: "Enums get mapped to their names."). No Converter is created, and the permitted values are guarded by a DB `CHECK`.

```sql
-- V9__messaging.sql:30,39
state       VARCHAR(16)      NOT NULL,
CONSTRAINT prepared_messages_state CHECK (state IN ('PREPARED', 'SUBMITTED', 'RECALLED')),
```

`PreparedMessage.state` is a `MessageState` (`sennard-domain`). Which columns must be present for each state is also expressed with a `CHECK` (`V9__messaging.sql:41-`).

### Counters

The per-session limit counters of messaging (some columns of `session_ref`) are in a table of the identity area. They are updated by a small repository that decides by the number of rows affected by a conditional `UPDATE ... WHERE ... < limit` (`SessionRefRepository.java:23-35`). Ownership belongs to identity, and the owner migrating the identity area takes it over. The limits of the whole queue (the number and bytes of unacknowledged messages, the number of drafts and receipts) are counted directly from the tables without a counter and compared with the limits in `MessagingProperties` (a plain read before the write; concurrent writers may pass such a limit by a few, which is accepted).

### Connection: the Boot Default Path and the Personal Server

The Boot default path needs only `spring.datasource.*`. A test verifies that the same service runs through this path (`RewrittenAreasContext.bootDefault`, `BoardServiceBootDefaultTest`). The business DB connection of the personal server may be configured after the listener has started. `LazyJdbcRepositories` and `BusinessJdbcConfiguration` defer dialect resolution until a repository first needs it. Spring Data JDBC resolves it from the connected database product and settings.

### Current State of the Transition

The transaction manager is the single Boot `transactionManager`. No service method takes a lock by hand (the module lock, `ModuleLocks`, and the `sennard.module_lock` table are gone): a use case is one `@Transactional` service method, and the database's transaction at the edition's isolation level, the row lock an `UPDATE` takes by itself, and the constraints decide between callers that meet. Because the stores share the same `transactionManager`, several of them may be used in one transaction.

### Concurrency of the Hook Path (Continuity, Update Notice)

Concurrency is left to the database: the transaction, the row lock that an `UPDATE` takes by itself, and the constraints (PK, UNIQUE, FK). A hook changes state with one statement whose `WHERE` holds the condition (the epoch, the state token, the last notified version), and the changed rows say who won; the one that lost does nothing again and is not run again. What exists once in the whole server (the continuity secret, the signing keys of the workflow and of the state cleanup, the row of the plugin's update state) is made by a start-up use case, and a request only reads it. The continuity task of a session is made by the service method that first needs it (`ContinuityService`), in the same transaction in which it reads and changes the task: it reads the task and inserts it when there is none. The two use cases that refuse with the state token the caller is to name (`checkpoint_context`, `purge_direct_context`) only read it: a refusal rolls its transaction back, so a task made inside it would be gone with the token the refusal showed, and for a session that has no task they refuse without a token (`load_context` or the session's start makes it, and that answer is committed). Of two first requests of one session that overlap, the primary key lets one insert, and the other ends in the translated unique violation (an accepted limit); the entry of a hook or a tool call opens no transaction, calls one service method and does not catch it. A row that refers to a task has a foreign key to it (`V18`), so a cleanup that deletes a task cannot leave a hook's rows behind. The isolation level is the edition's setting (`sennard.store.isolation`, Spring's `Isolation`; the personal edition uses `READ_COMMITTED`), applied to the connections of the pool; a method does not name one. A use case that reads a view, scans files, and then writes (the change journal) holds no transaction during the scan: the read and the write are two use cases of `ChangeJournalService` (each one a service method and one transaction, the judgment inside it), the scan between them is `JournalScanner`'s file I/O done by the caller, and the write is the conditional `UPDATE` of the journal's version and state: when it changes no row the call lost and ends with the conflict, and it is not run again.

### Concurrency of the Workflow Tools, the Root Decisions and the Role Bodies

The same rule holds there: no lock decides. A run changes by the compare-and-set on its revision (`WorkflowStore.updateRun`), a root by the compare-and-set on its revision (`casRoot`, which also issues a lease), a lease is consumed by one `UPDATE ... WHERE state = 'ISSUED'`, and an execution observation is claimed once by its primary key. A request that was waiting for another's commit re-reads the row, finds its condition no longer true, and ends with the stale or conflict code of its call; it is not run again. A waiting root approval is decided by the number of rows its `DELETE` changes (`WorkflowStore.deletePendingRootApproval`), and a role body by its state token (`UPDATE ... WHERE state_token = ?`, or the primary key for a first write). Two roots of the same write surface opened at the same moment are decided by a unique key: an active root holds the digest of its write surface as the primary key of its own row in `convergence_active_surfaces` (the digest is made over the host and the sorted, distinct physical locations of its entries, so the order and the spelling of the entries do not change it, and the same place on another host is another key, as in the check of overlapping roots, which looks at one host only). A root that is not active has no row, because the standard has no partial unique index and a nullable unique column is not portable (SQL Server allows one NULL per column, Db2 requires a unique column to be NOT NULL); a root gives its row up in the transaction that moves it out of the active states. So the second root's `INSERT` of its surface row fails on the key and that transaction, its root `INSERT` with it, is rolled back; `WorkflowStore` ends it with `StoreCode.ROOT_CONFLICT`, `WorkflowService` answers `ROOT_CONFLICT`, and nothing runs again. Accepted limits: the check that no two active roots have overlapping write surfaces is an ordinary check inside the transaction, so two roots that only overlap (a folder and a file of it) and are opened at the same moment may both open; two signed admin records stored at the same instant leave the later one failing the chain head check. The registry files and the evidence files a workflow call needs are read by the entry before the transaction opens and passed to the service method; the service method reads no file.

### Migrations

The scripts are `V<number>__<description>.sql` files in the jar (`db/expand`, and `db/contract` for the changes that delete). One runner applies them: `HistoryMigrator` of the module `sennard-migration`. The business database (`MigrationRunner` of `sennard-store-pg`) and the H2 settings store (`SettingsMigrator` of `sennard-settings`) are two adapters of it. Each adapter opens its own connection and turns the runner's `MigrationException` into its own failure type (`StoreCode`, `SettingsCode`); the history format and the rules are not written twice.

Why Flyway is not used: Flyway keeps a list of the databases it knows and ships a part for each of them (a Flyway 10 or later needs a database-specific module), which ties the product to vendors. The business database is the user's choice and the scripts are ANSI SQL, so the runner needs only the SQL standard (`information_schema`, `CREATE SCHEMA`, the history table) and JDBC. The only difference between databases is the spelling of two phrases and the name of the long text type, and both are chosen by the dialect (`Database`) that the driver's product name gives: `ScriptDialect` for the phrases and `SqlBuilder.generateLongText` for the long text type, as `SqlBuilder.generateLimit` does for the row limit. The long text type is not read from `getTypeInfo()`: its `CREATE_PARAMS` is free text that differs by driver (the MariaDB driver reports the character set and collation options of `LONGTEXT`, not a length).

All tables of the business database are in one schema, `sennard`: the history tables, `sennard.module_schema` (the version of each module) and the tables of every module. There is no schema per module, and no role, grant or function. A table name is used once in the schema; where two modules had the same name the table carries its module as a prefix (`continuity_cleanup_backup`, `workflow_cleanup_backup`). The settings database uses the same schema name, with its history in `sennard.history`.

The history table (`sennard.expand_history`, `sennard.contract_history`; `sennard.history` for the settings store) has one row per attempt:

| Column | Type | Meaning |
| --- | --- | --- |
| `version` | `BIGINT` | the script's number |
| `attempt` | `INTEGER` | which attempt of that number this row is (from 1) |
| `script` | `VARCHAR(255)` | the file name |
| `digest` | `CHAR(64)` | SHA-256 of the original file in the jar, before SQL is prepared for execution |
| `applied_at` | `TIMESTAMP` | UTC, from the injected `Clock` |
| `outcome` | `VARCHAR(10)` | `SUCCEEDED` or `FAILED` (a `CHECK` where the database takes it) |

The primary key is `(version, attempt)`.

- An attempt is one transaction. Its first statement inserts its own row as `FAILED`, which claims the number; its last statement changes that row, and no other, to `SUCCEEDED`. A row is never deleted. A script that fails leaves its `FAILED` row, and the next start inserts `attempt + 1`.
- Two runners that apply the same number at once insert the same key, so the second waits in the database for the first one's transaction and then receives a duplicate key. It reads the history once more: when the number is `SUCCEEDED` with the same digest it skips the script; otherwise the other runner failed and it stops with `MIGRATION_FAILED`. The runner has no sleep, no polling and no retry. On a database whose DDL is not transactional the claim row says `FAILED` until the whole script has run, so a half-applied script is never shown as `SUCCEEDED`.
- The numbers are consecutive from 1 (`MIGRATION_GAP` otherwise). A script that was applied is not read again. A changed file (`MIGRATION_CHANGED`), an applied number whose script is gone (`MIGRATION_MISSING`) and a script that is not applied below the highest applied number (`MIGRATION_OUT_OF_ORDER`) stop the run before anything is applied; a changed file is not an attempt, so no row is added.

Changing a table that already holds rows:

- **An applied script is never edited.** The runner checks the digest and refuses a changed script (`MIGRATION_CHANGED`). A change goes in a new script. A comment in an applied script cannot be corrected either; the rule is written here instead.
- **A database is not recreated to change a table.** `ALTER TABLE` is the way, and the rows are kept. `ALTER TABLE t ADD c <type>` (without the keyword `COLUMN`) is accepted by PostgreSQL, Oracle, SQL Server, MySQL, MariaDB, Db2 and H2, so a script may add a column to an existing table. A `NOT NULL` column added to a table that has rows is written `ADD c <type> DEFAULT <constant> NOT NULL`, with `DEFAULT` before `NOT NULL`, the order Oracle takes. `DROP COLUMN`, `DROP CONSTRAINT` and `ADD CONSTRAINT` are portable too. The earlier sentence in the comment of `V12__session_kind.sql`, that the standard `ALTER TABLE` has no `ADD COLUMN` spelling that Oracle and SQL Server take and so no script adds a column to an existing table, is wrong; that script is not edited because it is applied.
- **Statements that differ by product are avoided:** `SET NOT NULL`, `MODIFY`, `ALTER COLUMN` and `RENAME`. A change that needs one of them makes a new table, copies the rows with `INSERT ... SELECT`, and drops the old table.
- **A released migration is not changed; a business change goes forward only, in a new `V` script (`ALTER TABLE` first, additions preferred).** Only a script that has not been released may be corrected. `V21__attachment.sql` creates the final attachment bundle structure directly (see [Attachments and Uploads](attachments.md)). `V22` (`workflow_runs.kind`, added with `ALTER TABLE ... ADD kind VARCHAR(32) DEFAULT 'CHANGE' NOT NULL`) is an example of the form a change takes after release: it changes a table that already exists and keeps its rows.

When business expand V27 is pending, the runner verifies the released resource path, SHA-256 and lock-row INSERT. It binds the attempt's Java UTC timestamp to that INSERT within the migration transaction. Databases with a successful V27 keep their existing history and lock row. A mismatch stops V27 before recording an attempt. If the DBMS committed part of a failed attempt through nontransactional DDL, recover the pre-attempt schema before retrying and keep the failed history row.

### The operationKey of a Write Tool and Its Receipt

A tool that changes state takes the caller's `operationKey` (required; `^[A-Za-z0-9_.:-]{16,128}$`; the server never makes one), so that a request sent again after a lost response is answered and not done twice. One mechanism serves them: `OperationReceipts` over the table `sennard.operation_receipt` (primary key `(tool, scope, operation_key)`, the digest of the request's content, the response, no foreign key). The key is the caller's own: `scope` is the server-issued reference of the session that called, so two sessions that send one key for one tool are two operations with their own effects and receipts; only `open_session`, which is called before its caller has a session, has the fixed scope `global` (the same key opens the same session whoever sends it, so its key is made at random for each call). The digest leaves out the key, the session reference and the response mode for every tool alike (`OperationKeys.digest`). The use case reads the receipt first; the same key and digest answer the stored response, another digest is `REQUEST_CONFLICT` with the reason `OPERATION_CONFLICT`; a new key does the work and writes the receipt as the last statement of the same service-method transaction, so the effect and its receipt commit or roll back together. **Only a success is stored.** A refusal has no effect and is rolled back with the transaction (a use case that commits what it observed on a refusal returns the refusal as a value, not as an exception, and writes no receipt either, because it reaches the write only on success; the entry answers that failure after the commit), so the same key sent again is judged again and refused again for the same reason. The key is not claimed by an INSERT first: PostgreSQL ends the transaction of a unique violation, so the stored row could not be read afterwards; two first requests of one caller with one key at the same moment end the second in `OPERATION_KEY_IN_PROGRESS` (`OperationReceipts.recordText` is the one place that makes it from the duplicate key of the receipt, so every tool shows it alike: `REQUEST_CONFLICT`, `details.reason` `OPERATION_IN_PROGRESS`, retryable), which rolls its work back and is not run again; the same request sent again with the same key is answered with the first one's result. The ten write tools of `WorkflowService` use it. `checkpoint_context` and `purge_direct_context` keep their answer in `continuity_requests`, because those rows are scoped by task and epoch, refer to the task by a foreign key and are removed with it by the state cleanup (`ContinuityStore`). A receipt answers for `sennard.operations.receipt-retention` (default 24 hours); an older one is not answered from and is removed when the next receipt is written (Sennard has no periodic cleanup job, and none was made for this), so the same key sent again after more than 24 hours is a new request. `classify_skills` and `record_skill_selection` keep their operationKey in the server's memory (`SkillClassificationService`), not in this table: the classification is advice for the session's skill choice and is needed only for the life of the server. Every other write tool is on it, each in the service method that is its one transaction: the board (`BoardService.setSummary`), the message queue (`MessagingService.prepare`, `send`, `acknowledge`, `recall`), the recap (`TurnRecapService.record`), the context layers (`ContextLayerService.proposeGlobal`, `proposeBinding`, `saveRole`), the work-record acknowledgement and the restore suppression (`TurnCheckService.markUnchanged`, `ContinuityService.suppress`), the state cleanup (`StateCleanupService.execute`), `open_session` (`SessionOpening`), and the change plan (`ChangeJournalService.submitPlan` and `revisePlan`, where the file reads and scans stay outside the transaction and the digest of the request is the tool's input only; the receipt written in that transaction holds the plan's revision, and the call completes it with the answer it gave once it has one (`OperationReceipts.complete`), so a request that comes again after the call finished gets the first answer as it was given, not one made again from the run as it is now). `run_skill_check` writes a receipt only in `SkillCheckQueue`, the transaction that queues the job of a background command (`change-scope-guardian compare`, `test-engineering run`); a command that only judges writes nothing and has no receipt. The public entry of each of these use cases is the one method that takes the `OperationKey`; its work is a private method of the same service with no transaction of its own, and nothing calls that work without a key (the hooks write none of these, and the tests call the entry with a key of their own). The one public write left without a key is `ChangeJournalService.submitPlan(workflowId, paths)`, which `WorkflowService.startMinimal` calls inside its own transaction, the one that already holds the receipt of that tool's key (a second receipt for the same operation is not written). `OperationReceipts.once` returns a `Receipted`, `Fresh` for the call that did the work and `Replayed` for a call answered from the receipt, so that what a use case does besides its writes after it commits (the event of `checkpoint_role_context` that notes the save for the work-record check, the wake of `send_session_message`) is done for `Fresh` only: a request that comes again is answered with the first result and rings and notes nothing again. What the answer holds of the time of the call (the advisory `autoWake` of `send_session_message`, and of the status of a refused `recall_session_message`) is made inside the transaction and kept in the receipt (`MessagingService.send` and `recall` take the function that makes the answer), so a request that comes again gets the first answer as it was given, `autoWake.checkedAt` included, and not one made again. The target of that status (`SessionMessageService.QueueOutlook`) is kept with the `autoWake`, so its session id does not turn to null when the target's session row has lapsed. The workflow tools keep their whole answer the same way: the use case writes its result as the receipt, and the call completes the receipt with its answer (the result as published and the lines of the change notice after it) once it has it (`WorkflowReceipts.completeAnswer`, over `OperationReceipts.complete`; the notice scans files, and a file read stays outside every transaction). A request that comes again is answered with that answer and does nothing else: it reads no run, records no scan and makes no notice. Only a call that stopped after the use case committed and before it kept its answer leaves the use case's result alone in the receipt, and the request that comes again makes the answer from it and keeps it.

### Files Are Read Before the Transaction

A transaction holds a connection and the row locks of its writes, and a rollback cannot undo a file read, so a use case of the workflow tools reads no file inside its transaction. What it judges from files (the output file and the files a stage result names, the schemas a plan froze, the check of a review bundle, the physical locations of a root's write surface) is read by the entry. The use case has a read-only planning method (`planStageReads`, `planFinalizeReads`, `planOpenRootReads`, `planStartReads`) that reads the rows and returns the requests; the entry (`WorkflowFileReader`) answers them outside any transaction; the transaction method then takes the answers (`FileReads`) as an argument and judges with them. Each answer keeps the failure of its read and raises it where the use case takes the value, so refusals come in the order the use case's checks give. The answers are made for the revision the use case plans on; a run that has moved since is refused as stale by the revision the use case writes under, and is not read again.

## Cautions

- Do not forget `@Version` on a new entity. Without it, `save` cannot determine whether the row is new.
- The time components of a `record` are of type `LocalDateTime`. If an `Instant` or a `java.sql.Timestamp` is used, it is written in the JVM time zone.
- Using a named parameter such as `:targetRef` in `@Query` requires the `-parameters` compiler option (`sennard-app/build.gradle.kts`).
- The build uses `-Xlint:all -Werror`. `@Embedded.Nullable` of `spring-data-relational` produces a jsr305 warning, so `@Embedded(onEmpty = USE_NULL)` is used.
- Where a single method reads and then writes for a limit over the whole queue, concurrent writers can exceed the limit by a few. That is accepted for these capacity limits (no counter row, no lock); the limits of one session are exact because they are conditional UPDATEs (`theRecordByteLimitIsPassedByNoMoreThanThePreparersInFlightWhenManyThreadsPrepareAtOnce` in `AbstractMessagingServiceTest`).
- To avoid deadlock, a method that writes several rows fixes the order of writing (session rows in value order). The two-way transmission test guards this (`sendsToOneRecipientGetSequenceNumbersWithoutAGapAndSendsBothWaysBetweenTwoSessionsFinish` in `AbstractMessagingServiceTest`).
- A lock timeout (SQLSTATE 55P03) becomes an `UncategorizedSQLException` in Spring's translation and is not a retry target. No custom mapping has been written.
- The name of a key column follows the name of its table (`user_prompt_id` in `user_prompt`). A column such as `prompt_id` that has the same name and type as the key column of another table and has no FK is counted as a referencing column by `ForeignKeyCatalogTest` (rule k) and raises the ceiling. The session ID column supplied by the host is a `VARCHAR` for the same reason: so that it is not paired with `board_sessions.session_id`, which is `text`.

## Remaining Non-Neutral Items (Reported)

- `text COLLATE "C"` columns: the place of long text. The convention is that only the type name of long text is a single placeholder (`${long_text}`) and the DBMS-specific value is the declaration of the SqlBuilder dialect. In this scope the existing type was left in place.
- `now()`, `decode(md5())`, and `string_agg` in test code are used only within tests.
