# Receiving Host Hooks

A host runs the Sennard Java client (`sennard-hook-client`, a jar started with `java -cp`) as a command hook, or calls the MCP server through the Sennard stdio relay (`McpRelayMain`, in the same jar). Both find the Spring Boot server at the address it announces in `server.properties` in the state folder, because the server's port is chosen by the operating system at each start (section 2.3). There is no HTTP hook, because a host's HTTP hook takes a fixed URL. Hook definitions contain no curl, no shell quoting, and no `sh -c`. The plugin packages ship the definitions empty; `sennard install`, `sennard upgrade`, and `sennard hooks` write this PC's definitions, which name the absolute paths of this PC's `java` and jar, into the host's copy of the plugin (section 2).

## 1. Host × Event Tables

An "Sennard collected event" is an event that the server reads as a `HostEvent` (`server/hook/HostEvent.java`). Every event that the host officially provides and that corresponds to such an event is received. For each event that is not received, the reason is stated.

### 1.1 Claude Code (https://code.claude.com/docs/en/hooks)

|---|---|---|

| SessionStart wake, Stop wake | Sennard client (command, `asyncRewake`) | Official: `asyncRewake` is a field of command hooks |
| SubagentStart, SubagentStop, PreCompact, PostCompact, PostModelSwitch, UserPromptSubmit, PreToolUse (governance, continuity, native-peer), PostToolUseFailure, PostToolUse, Stop, SessionEnd | Sennard client (command, exec form) | These were `type: "http"` hooks before the server's port stopped being fixed. Official: an HTTP hook's `url` takes no environment variable (only `headers` substitute them), so no definition can name the address; a command reads it from `server.properties`. All three tool-admission commands use `"onFailure": "block"` (Claude Code 2.1.295 or later) and `--on-failure=block-stderr`. An `mcp_tool` hook (the host's other form) was not taken: it has no `onFailure` and takes its `input` from named fields only, so the gate's failure behavior would be unconfirmed |
| StopFailure, UserPromptExpansion | Not received | No corresponding Sennard collected event exists |
| PermissionRequest, Notification, TaskCreated, and the rest | Not received | No corresponding Sennard collected event exists |

### 1.2 Codex (https://learn.chatgpt.com/docs/hooks)

| Event | How it is received | Basis |
|---|---|---|
| SessionStart | Sennard client (command, host PID passed) | Official: "SessionStart hooks can run before an MCP server is ready" |

| UserPromptSubmit, PreCompact, PostCompact, PreToolUse (peer-wait, continuity, native-peer), PostToolUse, PreModelRequest, PostModelRequest | Sennard client (command; the whole event on standard input) | `agent_id` is optional in these events: the host's source (`codex-rs/hooks/src/schema.rs`, `events/model_request.rs`) skips it unless the event is a subagent's. An `mcp_tool` placeholder of a field the event lacks fails the whole hook, so a command reads the event and tells a subagent from the main session. PreModelRequest and PostModelRequest are newly received; they correspond to `ModelCallStarting` and `ModelCallFinished`, and the response carries no text |
| Stop | Sennard client (command, `--bind-host`) | Receives the main session's full input. An eligible Stop can register a local wake worker with the current server |

The `sennard` MCP server that an mcp_tool hook calls is the Sennard relay that the installation registered in Codex's copy of the plugin (`.mcp.json`), so that hook also reaches the server at the announced address. An mcp_tool hook passes only the fields listed in `input` to the tool, not the whole event (official: "Use `${field.nested}` to read a dotted field from the hook event"). The definition lists those fields as `${…}`. The host fills a placeholder by walking the event's JSON and fails the hook when the field is not there ("hook input placeholder `${agent_id}` was not found", `codex-rs/hooks/src/engine/mcp_runner.rs`); there is no default and no optional form, and a field that is present as `null` is found. So the definition names only fields that the event always has (`HookRegistrationFileTest` checks the two subagent hooks’ placeholders against the required fields, and checks the `Stop` command and its recorded main-session input).

## 2. Sennard Hook Client

The client is the module `java/sennard-hook-client`, a program that depends on nothing but the JDK (`java.base`): no Spring, no Jackson, no SLF4J, and no Logback. Every hook of a host that accepts only a command starts a new JVM, so what that JVM loads is the delay of the hook, and the module exists to keep it at the cost of an empty JVM. The module also holds what the server shares with the client: `HookClientCall` (the arguments of a hook command), `HookEndpoints` (the paths), and `HookHeaders` (the header names). The server uses them from there and writes none of them again.

The installed hook definitions run it directly with the `java` that ran `sennard install` (the user's JDK 25; there is no launcher program and no bundled runtime):

```
<java> -XX:+UseSerialGC -Xmx256m -XX:TieredStopAtLevel=1 -XX:-UsePerfData -Xlog:disable -XX:AOTMode=auto -XX:AOTCache=<version folder>/sennard-hook.aot
    -cp <version folder>/lib/sennard-hook-client-<version>.jar io.github.jaeseongs95.sennard.hookclient.HookClientMain
    --server-file=<state folder>/server.properties --jar=<version folder>/sennard-<version>.jar hook <host> <event> [options]
```

`hook` here is the client's own first word, not a command of `sennard`: the Sennard CLI has no `hook` command.

The version folder is `<installation folder>/versions/<version>/`. The words are written one by one (`HookClientCommand`): a host that takes an argument list (Claude Code's exec form) gets them as they are, and a host that takes a command string gets each word that contains a space in double quotes (`HookInstallation.commandLine`). It is 100% Java; the one program it starts is the installed jar (`java -jar <jar> start --within=<seconds>`), once, when a session start finds no server (section 2.1). The relay is the same command with the main class `McpRelayMain` and the arguments `--host=<label> --server-file=… --jar=… --start-server=30` (section 2.3).

- It sends the hook input (stdin) to the server with `POST http://127.0.0.1:<port>/hooks/v1/<host>/<event>[/<module>]`, where `<port>` is read from the file named by `--server-file` for every call (section 2.3), using the JDK `HttpURLConnection` (`java.base`), and writes the 2xx body to stdout unchanged. Spring `RestClient` and `java.net.http.HttpClient` are not used because every hook starts a new JVM, so the classes loaded and the initialization performed at startup are the latency. `HttpClient` also builds a default SSL context when it is created, which `HttpURLConnection` does not. The cost of each is measured at the pre-release hook connection check (see Measurements below).
- What is sent is not the whole host input but only the fields that the server adapter reads. The client reads the input once with a small JSON reader of its own (`InputReducer`: the strict grammar of RFC 8259, nesting up to 500 levels, which is what the server's reader accepts) and writes it again with only those fields, each copied as the host wrote it. Which fields are the host's file `sennard-hook-input/<host>.fields` in the module. The server's input record (`HostDefinition.inputType()`) is the one definition of what is read; the client cannot load it, so `HostInputFieldsTest` holds every file to its record, field for field, and every host definition to a file. The `llm_request.messages` (the whole conversation) and `config` of Gemini `BeforeModel` are not read by the server, so they are not sent. An input the server would refuse with a 400 (empty, not UTF-8, not a JSON object) is refused by the client for the same reason and sent nowhere; `HostInputReductionTest` gives the same fixed inputs to both readers (the recorded host inputs of `hook-fixtures` and every read case of the adapters' golden) and holds their results equal.
- JDK 25 AOT cache: at installation, the client's run is trained to create `<version folder>/sennard-hook.aot` (`CommandAotCache`, with the same `java`, options and class path as the definition; `sennard install`, `sennard upgrade`, and `sennard hooks` make it with the `java` that the definition names), and the options pass `-XX:AOTMode=auto -XX:AOTCache=<version folder>/sennard-hook.aot -Xlog:disable` (official: with auto, the JVM continues without the cache if it cannot read it). The JVM log is turned off because, in measurement, a missing or corrupted cache made the JVM print a warning to standard output and corrupted the answer that the host reads. The cache is not included in the release jar (it differs by JDK and is created at installation). A JVM records one run, so the training is one `hook gemini BeforeModel` run against a port nothing listens on, and `--warm=agy=<file>` makes that same run first read an Antigravity `PreToolUse` input as that host's input and drop the result. `--warm` is for the training run only and no host definition carries it. The `sennard` command itself (the user's `java -jar`) has no AOT cache; it is run rarely by a person.
- What the client's JVM loads is held by a test, not by a time limit: `HookClientProcessTest` runs the client in a JVM whose class path is the module's own classes and fails when it loads a class of `org.springframework`, `com.fasterxml`, `tools.jackson`, `ch.qos`, or `org.slf4j`.
- Alternatives checked (2026-11-14, official documents): Antigravity (https://antigravity.google/docs/hooks) and Gemini CLI (https://geminicli.com/docs/hooks/reference/) document only `"command"` as the hook handler `type`. Claude Code accepts HTTP hooks, but its `url` cannot name a port that is chosen at each start (section 1.1), so every host starts one JVM per command hook, and what can be reduced is the start cost of that JVM: the classes it loads.
- Measurements: taken at the pre-release hook connection check on an installation of the release candidate, not stated here (the figures of the earlier structure, which ran the client through a launcher program with the whole application's AOT cache, no longer describe the client).
- The header `X-Sennard-Time-Zone` (`HookHeaders.TIME_ZONE`; IANA, from the environment's `TZ`) is sent. An mcp_tool hook, which the host sends through the MCP relay, does not carry this header, so the server treats it as UTC.
- `--bind-host`: sends the processes above the client, from the `ProcessHandle.current().parent()` chain of the JDK (nearest first, at most eight), in the header `X-Sennard-Host-Pids` (`HookHeaders.HOST_PIDS`). The host is among them, and which one it is cannot be read in the client (between the host and the client there may be a shell that the host starts for its hook); the server picks the process that is still running once the hook has returned, watches it with `HostWatch` (`ProcessHandle.onExit()`), and ends the session when it ends. A process ID whose start time is later than the time the hook arrived is rejected.
- `--start-server=<seconds>`: present only in the session start definition (section 2.1). If no live server is announced (or the connection is refused), the installed server is started (`--jar`), the client waits up to this many seconds until it is ready, and then sends the original event once. Without this option, no server is started.
- When the server does not answer (`--on-failure`): `fail` (stderr, exit 1: `Sennard hook failed: <code>`, the code being a `HookNoAnswer.Reason` such as `SERVER_NOT_REACHABLE`, `SERVER_REFUSED`, `SERVER_NOT_STARTED`, or one of the three `HOOK_BODY_` reasons the server uses for the same inputs; the client has no message source, so the sentence for a code is the server's and this document's), `block-stderr` (tool denial with the reason on stderr, exit 2), `deny-pre-tool-use` (nested `PreToolUse` permission denial with the reason on stdout, exit 0), `guidance-stderr` (Claude session-start guidance on stderr, exit 2), `guidance-stdout` (Codex), `guidance-steps` and `allow-decision` (Antigravity's `injectSteps` and `{"decision":"allow"}`), `deny-decision` (`{"decision":"deny","reason":"..."}`, with the failure code), and `guidance-system-message` (Gemini). Option values do not contain a host name (the shared code does not know host names). Each registration chooses its failure answer.
- When the server refuses a gate's call (`--on-refusal`): `as-failure` (the default: a refusal is a failure like any other, and the `--on-failure` answer applies) or `deny-decision` (stdout `{"decision":"deny","reason":"..."}` and exit 0, the one deny that Antigravity's PreToolUse and Gemini CLI's BeforeTool both read). It applies only to a status of 400 or above; a connection that fails, a timeout, a failed server start and a status of 3xx (no redirect is followed) are never a refusal. Only the gate definitions carry it (section 2.2). The reason is a fixed English sentence with `SERVER_REFUSED <status>`, because the client has no message source; the sentence in the user's catalog comes from the server (section 2.2).
- `--wake`: if the server answers with a message, the body is written to stderr and the client exits with 2 (the host wakes the session). Every other ending is a silent exit 0. If `--only-if-env=NAME=VALUE` does not match, the client ends without sending a request (Claude's `CLAUDE_CODE_SESSION_ATTENDED=1`).

An option that cannot be read (a port that is not a number, a failure answer that does not exist, an option twice) ends the client with exit 2 and `Sennard hook failed: HOOK_OPTION_INVALID <problem> <option>=<value>`; a host's definition never produces one.

The hook definition in a plugin package is empty (`{"hooks":{}}`), and so is its MCP registration. A package cannot name the installed `java`, the jar, or the address file, because an exec-form command takes no home-folder variable and the variable for the package's own folder differs by host. `sennard install`, `sennard upgrade`, and `sennard hooks` write the words above, with this PC's absolute paths, into the host's copy of the plugin, as a whole file (Claude Code `hooks/hooks.json` and `.mcp.json`, Codex `hooks/hooks.json` and `.mcp.json`, Antigravity `hooks.json` and `mcp_config.json`, Gemini CLI `hooks/hooks.json`) or as one member of a file that holds other settings (the `mcpServers` member of the Gemini CLI extension's `gemini-extension.json`, the rest of the file is kept). The same on every operating system. A host copies the empty files again when a plugin is installed or updated, so `sennard hooks` runs again after that, and `sennard status` lists the copies that are empty now (`hostCopiesWithoutDefinitions`). Every file written is recorded with its digest in `placed.json`, and `sennard uninstall` puts back only what is still exactly that. The copies are those of Claude Code (found through `installed_plugins.json`), Codex (`~/.codex/plugins/cache/<marketplace>/sennard/<version>/`, `CodexPackageLocation`), Antigravity (`~/.gemini/config/plugins/sennard`) and Gemini CLI (`~/.gemini/extensions/sennard`, `GeminiPackageLocation`; a linked extension is the user's own folder and is not written). Not verified on a machine with the host: the Codex cache's layout and name, whether Codex asks for the hook trust again when a file of the copy changes, the Gemini CLI folder's name and place and the layout of a linked extension, and whether Antigravity and the Gemini CLI accept an empty `mcpServers`.

### 2.1 Starting the Server at Session Start

Because no OS service registration (schtasks, systemctl, launchctl) exists, the places that start the server after a reboot are `sennard start` and the session start hook. The code is `Installer.startForSession`, which reuses `applySavedPreset` and `ServerStarter` of `sennard start` as they are. The client program cannot call it (the installer is Spring and the settings database, which the client must not load, and only the installed jar knows where the installation is), so it runs the installed jar once (`JarServerStart`): `<its own java> -XX:+UseSerialGC -Xmx256m -XX:TieredStopAtLevel=1 -jar <jar> start --within=<seconds>` (`--jar=<path>` in the definition; the process's output is discarded and a deadline above the wait kills it and its children). The server itself is started by that command as `<java> <preset options> -cp <application jar> SennardPersonalApplication` with the installation folder as its working folder. A client started without `--jar` starts nothing and ends with `SERVER_NOT_STARTED`.

- **Scope.** Only the session start definitions of the four hosts (the first Claude command, Codex, Gemini, Antigravity) carry `--start-server=30` (`HookClientCall.START_SERVER_SECONDS`). The wake hooks, SessionEnd, and the other events have no such option, so that they never try to start the server on every model call or tool use; when no server exists they only print guidance, as before (test: `anEventOtherThanTheSessionStartStartsNothingWhenThereIsNoServer`).
- **When.** Only when no live server is announced in `server.properties` (the file is missing, or the process it names is not alive with that start time) or the connection is refused (`java.net.ConnectException`). If the server received the request but did not return 2xx, or did not answer within `--timeout`, the server is running and is not started. If the input has a shape that the server would reject (for example, not a JSON object), the client ends before the request and does not start the server.
- **If it is not installed**, nothing is started. no installed version is found and the hook prints the `--on-failure` guidance (nothing is created in the installation folder).
- **One at a time.** Only the one process that holds `FileChannel.tryLock` (JDK; the OS releases it when the process ends) on `server-start.lock` in the state folder starts the server and waits for readiness. A hook that cannot take the lock only checks readiness and tries the lock again. If a live server is already announced (another party started it first), no server is started and the hook waits for readiness. The lock file remains; the lock does not. This lock only serializes the starts; that one server runs on a state folder is held by a second lock, `server.lock` in the state folder (`ServerInstanceLock`, `FileChannel.tryLock` taken early in the server's start and held until the process ends): a second server ends with `SERVER_ALREADY_RUNNING`.
- **Readiness criterion.** The address file names a live server, its `/actuator/health` returns 2xx and, for an installation that prepares the store, the `phase` of `/actuator/sennard` is `READY` (the same criterion that `sennard install` and `sennard upgrade` wait for). `FAILED` fails immediately. One check takes at most 2 seconds (the response limit of `ServerControl`) and is repeated at 200 ms intervals. Even if the server accepts and does not answer, the hook's time is not used up.
- **Server process.** `ServerStarter.ofProcess()`: standard input is closed and standard output and error go to `Redirect.DISCARD` (the server writes its own log file). Because the process does not hold the hook's stdout pipe, the host does not wait for EOF from the hook (a test confirms this with a pipe). The Spring context that reads the session start settings turns logging off (`InstalledSettings.quietlyAt`), so only the server's answer goes to the stdout of this hook.
- **Failure contract.** No installation, a jar that cannot be run with `java`, a failed store preparation, and exceeding the limit are all "no answer". The hook prints the guidance and exit code that its definition specifies (with `FAIL`, the code `SERVER_NOT_STARTED` and what went wrong, such as the start command's exit code, are written to stderr) and does not block the session. Even when the limit is exceeded, the server being started is not killed. Cutting off a server that is preparing the store would leave a half-built store, and if a slow start were cut off at the limit every time, the server would never come up. The next session start meets that server as an already running server.
- **Time limits.** The default command hook timeouts in the official host documents are 600 seconds for Claude Code (`Defaults: 600 for command, http, and mcp_tool`, https://code.claude.com/docs/en/hooks), 600 seconds for Codex (`If timeout is omitted, Codex uses 600 seconds for most hooks`, https://learn.chatgpt.com/docs/hooks), 60000 ms for Gemini CLI (`Execution timeout in milliseconds (default: 60000)`, https://geminicli.com/docs/hooks/reference/), and 30 seconds for Antigravity (`Optional. Timeout in seconds. Defaults to 30`, https://antigravity.google/docs/hooks) (checked on 2026-11-11). The limit for waiting for startup (`--start-server`) is 30 seconds, and the session start limit that the definition gives to the host (`HookClientCall.SESSION_START_LIMIT_SECONDS`) is twice that, 60 seconds (60000 ms for Gemini). It was 10 seconds before. The limit must be sufficiently longer than the wait limit so that the start command's own JVM startup and the event request fit inside it. Because Antigravity is given a value well above its official default (30 seconds), it must be verified on a real host that the host honors the `timeout` in the definition (section 4).
- **Measurement.** The time from the hook start until the answer to the event, on an installation made with `sennard install` and no server, is measured at the pre-release hook connection check on an installation of the release candidate (`HookStartsServerProcessTest.measuresTheStartUntilTheEventIsAnsweredOnARealInstallation` logs it). No figure is stated here. The 30-second wait is a bound for a process that never becomes ready, not an expected time. It is generous enough that a slow start is not cut off every time and short enough that a session whose server cannot start is not held up for long. The time a start takes is the server's (its start and the store preparation) and differs from computer to computer, and the one more process this structure adds (the JVM of the start command) is a fraction of it.
- **Tests** (`HookStartsServerProcessTest`, real installation of the release jar, process, and port): start, record, answer, and server survival with no server; zero process creations and no lock file when a server already exists; one server for two simultaneous hooks; a damaged application jar; an application jar that is gone; exceeding the readiness limit; no installation; and an event other than session start. `HookClientTest` (`sennard-hook-client`) checks the client's decisions (only on a refused connection, only once, failure leads to guidance) with a real socket.

### 2.2 Failure Policy of Gate Hooks

**A tool-admission hook stops the tool when it cannot obtain a server decision.** This includes connection failures, client timeouts and HTTP refusals. SessionStart, UserPromptSubmit, PostToolUse and Stop have their own failure responses.

A gate can stop a tool at `HostEvent.ToolRequested`. The Codex `continuity` registration runs on every `PreToolUse` event the host emits. On Claude Code, `governance` handles Sennard tools and `continuity` checks the other `PreToolUse` calls. Gemini CLI uses `BeforeTool` and Antigravity uses `PreToolUse`. Codex, Claude Code and Antigravity register a separate `native-peer` gate for the host's own send tools (see "Host Send Tools" in `session-messaging.md`). The Antigravity registration matches `send_message` with or without `default_api:`. Claude Code uses exit 2 with a reason on stderr. Codex uses `hookSpecificOutput.permissionDecision: "deny"` with the reason on stdout and exit 0 because Windows PowerShell can turn a native exit code of 2 into 1. Antigravity and Gemini CLI use `decision: "deny"` with a reason on stdout. The Codex `peer-wait` registration supplies bounded-wait guidance.

| Situation | Gate | Other hooks |
|---|---|---|
| No server (connection refused, no start) | The client emits the host's denial with `SERVER_NOT_REACHABLE` | the failure answer, as before |
| No answer within the client's `--timeout` | The client emits the host's denial with the timeout reason | the failure answer, as before |
| The server refuses after it has read the hook's input (a failure of the domain: 409 lost first creation, another 4xx, 503, 500) | **stops the tool**: the server answers 200 in the host's own deny form (`HookPipeline`, through the adapter's `respond` of a `HookVerdict.Refuse`) with the sentence of the catalog key `hooks.gateRefused` (`locales/en` and `locales/ko`; the text a model reads is English) and the error code of the refusal | the status as before (a failed hook; the host goes on) |
| The server refuses before it has read the input (a malformed body, an unknown host or event, a missing session identifier; filters before the controller, such as a server that is still preparing its store, 503) | The client emits the host's denial with `SERVER_REFUSED <status>` | the failure answer, as before |
| A 3xx status | the failure answer (no redirect is followed) | the failure answer |
| A 2xx body that is not the host's JSON | the client does not read the body: it writes it to stdout unchanged and the host decides (unchanged by this decision) | the same |

The user sees the sentence of `hooks.gateRefused` with the error code (for example `HOOK_HANDLER_CONFLICT:STORE_UNIQUE_VIOLATION`) as the reason of the host's refusal. The user retries the same call; if it keeps failing, the code is looked up on the admin page or in the server log (`HOOK_GATE_REFUSED <code>` is logged with its cause). Nothing retries by itself: the client does not retry, and neither does the server.

Claude Code 2.1.295 and later also apply `"onFailure": "block"` when a tool-admission command fails to launch or exceeds the host’s deadline. The client’s failure response applies once the command runs. Tool coverage depends on the events the host emits.

### 2.3 Server Address and the MCP Relay

The server has no port of its own choosing: it binds the port the operating system gives it at each start (`server.port: 0`, as the admin page's connector does), so neither a host's definition nor a client can name the port beforehand. Port conflicts do not exist, and a program that holds a port cannot keep the server from starting.

- **Announcement.** When the server is ready (`ApplicationReadyEvent`, `ServerAddressPublisher`), it writes `<state folder>/server.properties`, a JDK `Properties` file with `port` (the port of the hooks, the MCP endpoint and Actuator), `pid`, and `processStart` (ISO-8601 instant). The file is written to a file of its own and moved over the old one in one step (`ATOMIC_MOVE`), so a client never reads half of it. When the server ends (`ContextClosedEvent`), it deletes the file only when the pid in it is its own. A server whose own start time the operating system does not report does not start.
- **Reading.** `ServerAddress` (`sennard-hook-client`, `java.base` only; the server uses the same class) reads the file for every call: `ServerAddress.read(file)` is empty for a missing or broken file, and `live()` is true only when the process of that pid is alive and started at `processStart` (an id that was given to another process later does not match). A client that finds no live server does not delete the file; the next server writes over it. The installer's commands (`sennard status`, `stop`, `attachments`, `admin-reset`) read the same file; there is no `--port` option anywhere.
- **One server per state folder.** `ServerInstanceLock` takes `FileChannel.tryLock` on `server.lock` in the state folder early in the server's start and holds it until the process ends. A second server on the same state folder ends with `SERVER_ALREADY_RUNNING` (two state folders each have their own server and address).
- **The relay.** A host registers the MCP server as the relay (`McpRelayMain`; `java.base` only, held to it by `HookClientProcessTest` like the hook client), because no host's configuration can name a port that is not known when it is written: `--host=<label> --server-file=… --jar=… --start-server=30`. It reads one JSON-RPC message per line of stdin, posts it to `/mcp` of the announced address with `Accept: application/json, text/event-stream` and the header `Sennard-Host-Label`, and writes the answer (a JSON message, or the `data` messages of an event stream) as lines of stdout; a message without an `id` is a notification and gets no answer (the server answers 202). The negotiated protocol version of the `initialize` answer is sent as `MCP-Protocol-Version` on every later request. The address file is read again for every request, so a server that was started again at another port is found.
- **Starting the server from the relay.** Only an `initialize` that finds no live server starts it (`--start-server`, once per session, the same start as a session-start hook, section 2.1). Any other request with no live server is answered with a JSON-RPC error that carries the request's own id and the code of the reason; the relay neither starts a server for every request nor waits for one. This widens the rule of section 2.1 (only the session start starts a server) by one place, the first request of a session that uses the MCP server.

## 3. Contract Tests

- `hook-command-not-java-client` (limit 0): the plugin packages of the repository ship their definitions empty: a hook of any type, or an MCP server, in a definition of the repository is a violation (`RepositoryRules` of `sennard-arch-checks`). The definition that the installer writes runs the user's `java` with the client's jar, which the rule does not read because it is not a file of the repository; `HookClientCommandTest` and `HookRegistrationFileTest` hold its words.
- `HostInputFieldsTest` and `HostInputReductionTest` (`sennard-personal`): the client's list of the fields of each host equals the server's input record, and the client and the server read the same recorded inputs to the same result and refuse the same inputs for the same reason. `HookClientProcessTest` (`sennard-hook-client`): the client's JVM loads no class of Spring, Jackson, SLF4J, or Logback.
- The failure policy of gates (section 2.2), on recorded host inputs and real processes: `HookLauncherProcessTest` starts the command of the generated Antigravity and Gemini definitions (the user's `java` and the client's jar) against the real server, with the recorded Antigravity `PreToolUse`; `ClaudeHttpHookEndpointTest` posts the recorded Claude bodies to the real endpoint; `CodexHookToolServerTest` calls the real `codex_hook` tool with the recorded Codex fields; `ContinuityHookRaceServerTest` (R7) makes the first edits of a session meet at the creation of its task on a real PostgreSQL database; `HookClientTest` (`sennard-hook-client`) judges the client with real sockets. No Gemini CLI input was ever recorded, so the Gemini cases run on a handwritten `BeforeTool` (section 4).
- `HookCommandPlacesTest` (`sennard-repo-tools`) checks the generated handler types and counts. Claude, Antigravity, and Gemini use command hooks. Codex uses MCP tool hooks for SubagentStart and SubagentStop and command hooks for its other registered events, including Stop.
- `GeneratedFilesTest`: the definition files equal what the adapters produce (`./gradlew hostHookFiles`).

## 4. What Only a Real Host Can Confirm

Starting the server at session start (section 2.1) and the hook client and the relay against the real server were verified without a host, on one Windows PC. Other operating systems (the branches that depend on POSIX permissions in particular) and real hosts are unverified, and the checklist for the real-host verification step is as follows.

1. Whether the host kills the child process that the hook started (the server) when the hook ends (Windows Job Object, process group termination, and so on). The official documents do not state this. If it does, the server is cut off within the first session.
2. Whether the MCP server connects before the SessionStart hook. The Claude Code documentation says "`SessionStart` at launch … fire before the session's MCP servers are available to hooks", and Codex says "SessionStart hooks can run before an MCP server is ready". If the hook starts the server and waits, the MCP connection must come after it for the tools to be visible.
3. Whether the host's hook time limit (`timeout`) is applied as the value in the definition (60 seconds, 60000 ms for Gemini), especially for Antigravity, whose official default is 30 seconds.
4. How the host screen looks while the server is awaited (Claude Code `-p` and interactive, Codex, Gemini, Antigravity), and whether users accept that time (within the measured time).
5. How the host holds the standard input and output pipes of the hook's child: whether the server holds a pipe so that the host waits for EOF from the hook (on Windows on a development machine, a pipe test confirmed that it does not).
6. Whether it is the behavior users expect that the server remains when the host process of the hook that started it has ended (there is one server per computer and other sessions use it).
7. The same behavior on Linux and macOS: `FileChannel.tryLock`, process detachment (`Redirect.DISCARD`), and the start of the jar with `java`.

Also unverified: starting within the 1 second of Codex SessionEnd; the behavior of mcp_tool when `${field}` meets a missing field, and the interpretation of the result text (a JSON object); whether the Claude command hook's `"onFailure": "block"` stops the tool when the client exits with 1, and the delay of the JVM start that every Claude hook now costs (measure both at the connection check); whether the PID that the client chose is actually the host; the field name of Gemini `mcp_context` and the schema of the extension hook file; the Antigravity (Windows `cmd /c`), Codex, and Gemini commands with a `java` path that contains spaces; the start timeout of a stdio MCP server in Codex (its documented default is 10 seconds, which a server start by the relay's `initialize`, section 2.3, may exceed) and whether Codex accepts the registration in the plugin's `.mcp.json`; and `onExit` of a host that has become a zombie (Linux).

## 5. Inputs Without Recorded Samples (Subagents, `--agent`)

The recorded samples in `src/test/resources/hook-fixtures/<os>/<host>/` contain no Claude Code subagent (`agent_id`) and no session started with `--agent` (`agent_type`). The tests that tell the actor apart by the two markers (`@Marker`) of `ClaudeHookInput` (`MainSessionListingServerTest`, `SharedContextHookServerTest.aSubagentGetsTheLayers...`) therefore run with handwritten input (a line such as `"agent_id":"child-1"` inserted into a recorded body). The input format in the official documents does not replace a sample. To obtain samples, record the following on a real host (the Windows and Linux test servers, with the same host versions as the existing samples).

| Host | What to record | How |
|---|---|---|
| Claude Code | Every `SubagentStart`, `PreToolUse`, `PostToolUse`, and `SubagentStop` body while one subagent uses a tool twice (one shell tool call, one Sennard MCP tool call). Which events carry `agent_id` and `agent_type` is the point of the sample | Ask an interactive session to use a subagent (the `Agent` tool). In the recorded bodies, replace sessions, paths, and user names with placeholder values as in the existing samples, and place them in `hook-fixtures/<os>/<host>/` as `Subagent-<event>.json` and `Agent-<event>.json`. The tests are then changed to read these samples instead of the handwritten lines.

Until such a sample shows a field that names a parent, an Antigravity hook cannot say whose child a conversation is (the official hook document lists no parent, root, or agent field). The first hook of a conversation that has no role binding and no recorded root therefore adds the line `hooks.contextLayers.parentUnknown`, which asks a subagent to make one Sennard tool call; that call's `_meta` names the conversation and its root, `HostSessionResolver` links them, and the hooks give the root's role from the next step (`SharedContextHookServerTest`).
