# Admin Signed Records and Reading Settings

How to use the admin page is described in [Admin Page and Contexts](../user/admin-page.md). This document describes the format of the signed records that the page stores, their verification, the behavior of the readers, the JEV configuration, and the error codes.

## Page Server

- The address is `http://localhost:<port>/`, and the port is not fixed. The resident server opens an additional connector of its embedded Tomcat (`AdminPageAddress`) on port 0, so the operating system gives a free port at each start; there is no setting. Every place that states the address (`adminUrl` in hook and tool responses, approval notices, `adminPage` in `sennard status`) and the origin and port checks of requests read it from this one bean. A passkey is bound to the host name `localhost`, not to the port, so it keeps working when the port changes; the `origin` of a signed record holds the port of the start that signed it, and any port is accepted when the log is read.
- The connector is bound only to `127.0.0.1`. `GuardFilter` checks Host and Origin for each port.

## Source of Truth: Passkey-Signed Records

- The source of truth for the items that a person changes is a single signed log. Records are only appended. The log is kept in two places that follow one another in time: the records signed before the business database is linked are in the settings database (`pre_link_admin_records`, see "Before the Business Database Is Linked"), and from the moment the business database is ready they are in `admin_log` of the store. A reader folds the two as one log (`AdminLogSource`): the section before the link first, then the business records. The business records are shifted by the last sequence number of the first section, so there is one sequence, and nothing is copied from one place to the other.
- One record is one canonical JSON string (the intent) signed by a passkey. Its content is `{v, domain:"sennard.admin", rpId:"localhost", target, prevTargetHash, change, issuedAt}`, and the challenge is SHA-256(intent). When reading, `canonicalJson(JSON.parse(s)) === s` is enforced.
- The targets are `keys`, `global`, `roles`, `roleBody:<roleId>` (the role body), `binding:<host>:<sessionId>`, `rootApproval:<approvalId>` (root approval), `rootRelease:<rootId>` (root release), and the setting targets `jev` (on/off, budget, preset), `jevKeys`, `editExempt`, `jvmPreset` (the server JVM preset, `JVM_PRESET_SET {preset}`: only the name of a `JvmPreset` constant is accepted), and `database` (the link of the business database, `DATABASE_LINK {driverPath, jdbcUrl, accountName, passwordRef, tls}`: before first readiness, the settings transaction writes `pre_link_admin_records` and `database_link`. After readiness, the business log takes the signed record and the settings database saves `database_link` after the new connection is prepared. `passwordRef` is a reference to the password. See the database link details below), `convergenceLimits` (the convergence limits, `CONVERGENCE_LIMITS_SET {limits: {maxAttemptsPerEpoch, maxEpochs}}`: both are whole numbers of at least 1 and there is no upper bound. Without a signed value the defaults are 3 and 2. A signed value enters the frame of the roots opened after the signature, and a root that is already open keeps the value in its frame. The rule is the `@Min(1)` of `ConvergenceLimits`, and 0, a negative number, a fraction or a string is refused with `ADMIN_CHANGE_INVALID`. The reader is `ConvergenceLimitSource`, implemented by `SignedConvergenceLimits`). The other signed targets are `resourceLimits` (`RESOURCE_LIMITS_SET`, described below), `attachmentStorage` (`ATTACHMENT_STORAGE_SET {settings}`), and `workflowPlanUnblock:<recordId>` (`WORKFLOW_PLAN_UNBLOCK {workspaceId, kind, planDigest, recordId}`, which identifies the blocked plan to release). Each target is a chain that links the hash of its previous record, so unrelated targets do not contend with each other.
- The signed `resourceLimits` target accepts `RESOURCE_LIMITS_SET {limits: {csArtifactMaxBytes, maxOpenWorkflowsPerSession}}` after the business database is ready. Both are integers. File size accepts 1,048,576–67,108,864 bytes, default 8,388,608 (8 MiB). Open workflows per session accept 1–2,147,483,647, default 5. New checks and openings use the saved values; paused or review-gated workflows count, completed/cancelled work does not. Lowering the limit preserves existing work. Opening reports current and remaining capacity. Continue related follow-up instructions in the existing workflow and revise its file plan with `submit_change_plan`. Restore defaults by saving 8,388,608 and 5 with a passkey. Verified signed-log replay preserves these values without a schema migration. Older binaries do not recognize this new signed operation; use forward updates after saving it.
- Verification items: the client data type (`webauthn.get`), the challenge, the origin (`http://localhost[:port]`), the rpIdHash (`localhost`), the user presence and user verification flags (UP and UV), and the signature (ES256, RS256, EdDSA, verified with the JDK cryptography API, `AdminWebAuthn`). signCount is only recorded and is not used in the decision. When storing, the page server accepts a record only if the origin equals its own address (`http://localhost:<port of this start>`). A signature obtained by a similar page opened on another localhost port cannot be stored. When reading records that are already stored, any localhost port is accepted, because the port changes at each start.
- The first key is registered by self-signature (TOFU). After that, adding or revoking a key requires the signature of a valid key. The last key cannot be revoked. A record signed by a revoked key after its revocation is invalid.
- A passkey's public key is never in the business database. A signed `KEY_ADD` is `{credentialId, fingerprint, alg, label}`, where the fingerprint is `sha256:` and the lower-case hex of the SHA-256 of the key's bytes (the SPKI the browser exposes), in the form a JEV key's fingerprint has. The key itself travels with the signed commit (`publicKey` of the commit request, as a JEV key's value travels as `secret`), and the server checks that it is the key the signed fingerprint names and that it imports as the signed algorithm before it writes anything. The key is kept in the passkey registry of the settings database (see "Passkey Registry").
- Storing does the check and the append in one transaction (no lock of its own). If two signatures are stored at the same instant, the later record fails the chain head check when the log is next read and is shown as a failed record; the user signs again. Sending again with the same request ID returns the record that is already stored. A page that did not receive the response does not send again and only checks the result with `GET /api/request/:id`.

## Passkey Registry

The log decides the order: when a key was added or revoked, and the chain of each target. The passkey registry (`PasskeyRegistry`, the settings database: an H2 file under the state folder that only its owner reads) decides the bytes of the public key and its state. A person who can write only the business database cannot forge a signature, because the keys that verify it are not there.

- A signature is checked with the key the registry holds for the credential, whatever its state, because a record signed before its key was revoked is checked again at every fold. The registry is read once per fold.
- The key must be the one the log names. A key a `KEY_ADD` record names (the signer of a record, and the key a record registers) that the registry does not hold fails the record with `ADMIN_RECORD_ALTERED` (`details.reason: KEY_NOT_IN_REGISTRY`), and a key whose fingerprint or algorithm is not the one in the signed record fails it the same way (`details.reason: KEY_FINGERPRINT_MISMATCH`), so changing or losing the settings database does not change which key signs.
- While the folded log has such a failure it takes no new signature and no first key (`ADMIN_RECORD_ALTERED`, `details.reason: LOG_INTEGRITY_FAILED`; `AdminLog.requireIntact`): any failed record stops the first key (a log with failed records and no key is not a new log), and an integrity failure stops a signature of a listed key (another failed record, a stale chain head, is one the user signs again). Without this a log whose first key record fails would fold to "no key", the state in which the first key registers itself. `sennard admin-reset` is the only way out.
- A new signature needs a key that the log lists and that the registry holds as active (`requireActive`); the page offers only such keys to sign with. A log that lists keys the registry cannot vouch for (the settings database was lost) has no key that can sign; `sennard admin-reset` starts it again.
- The registry's writes (`register`, `revoke`, `clear`) are service methods of the settings database, each with its one `@Transactional(settingsTransactionManager)`, and idempotent: `register` inserts and, when the unique key is violated, reads the held row and answers with it if it is the same key (the same public key and algorithm), or refuses with `PASSKEY_EXISTS` if it is another; `revoke` is one conditional UPDATE (`state = ACTIVE`) and answers a key that is revoked already as revoked (`PASSKEY_NOT_FOUND` only when there is no such key). Two revocations of one key therefore both succeed and write once (the second UPDATE waits for the row of the first). H2 2.4.240 does not make a second INSERT of one unique key wait for the first one's uncommitted row: the unique check of the index throws `CONCURRENT_UPDATE_1` (SQLState 40001) at once (`MVSecondaryIndex.checkUnique`), and only a committed row is a duplicate key. Two registrations of one key therefore both succeed when the first has committed before the second inserts, and a registration that overlaps an uncommitted one is a race with another writer: H2 refuses it at once (`CONCURRENT_UPDATE_1`, 40001) or after a lock wait that ran out (`LOCK_TIMEOUT_1`, 50200), and the settings `JdbcClient` is given Spring's error code translator for H2 (Spring 7's default translator takes the second for a statement timeout, `QueryTimeoutException`), so both are a `ConcurrencyFailureException`; the registry lets it through (no wait, no retry, no lock of ours and no code of the settings store), and the entrances state it by the one translation of data access exceptions (`PersistenceErrors.ofDataAccess`: `SennardExceptionHandler` for a request, `PersistenceErrors.translate` for the tools) as the retryable `409 CONFLICT` with `reasonCode: CONCURRENT_UPDATE` ("repeat the call", the answer of every race, with no `details.reason` of its own); the same call after the other ended is answered with the held key. The settings store is below the application layer, so its `SettingsException` is stated by the one translation (`PersistenceErrors.ofSettings`, with no `default`, so a new code has no answer until it is given one) at the same entrances: `PASSKEY_EXISTS` and `REQUEST_ALREADY_RECORDED` are `CONFLICT` `DUPLICATE`; `PRE_LINK_CLOSED` is `ADMIN_CHANGE_INVALID` (`DATABASE_LINK_CLOSED`); `INVALID_SETTING` and `VALUE_OUTSIDE_SET` are `INVALID_INPUT` (`VALIDATION_FAILED`); `STORED_VALUE_UNKNOWN` and `PASSKEY_NOT_FOUND` are `INTEGRITY_FAILED`; the rest are `STORE_UNAVAILABLE`. None goes out as the unexpected 500. The settings database is H2, where a statement that violates a constraint is undone alone and its transaction goes on, so the read after the violation is in the same transaction; no write follows it.
- The two databases are not one transaction, so each write is ordered to fail towards "nothing can sign", and the registry's write is the settings database's own use case that the business side calls without being bound to its transaction (another DataSource). `KEY_ADD` registers the key first and then appends the record: a record that fails leaves a key that no log lists, with which nothing can be signed. The registration stays inside `ContextLayerService.commit`, after the freshness, the chain and the signature are checked, because a key may be planted under a credential id only by a signed request. `KEY_REVOKE` appends the record first and revokes the registry after the transaction commits (`PasskeyRevoked`, `PasskeyRevocations`); if that fails it is logged (a warning), and the entrance that shows the admin state (`AdminPageData`), after the read of the log has ended, revokes every key the log revoked that the registry still holds as active (`PasskeyRevocations.reconcile`; the read itself, a read-only transaction, writes nothing). Meanwhile the key cannot sign, because the log no longer lists it. Before the link the registration and the revocation are part of the one transaction of the settings database that appends the record.

## Before the Business Database Is Linked

The server starts whether or not a business database is named; without one the store waits (`NOT_CONFIGURED`). The page is then the settings database's (`PreLinkAdminService`): it shows the passkeys and the link of the business database and nothing else.

- The first passkey registers itself there (TOFU), and the user links the business database by signing `DATABASE_LINK` with a passkey: the driver (a jar or a folder of jars), the JDBC URL, the account, the file that holds the account's password and how the link is protected (`LOOPBACK_PLAINTEXT` or `VERIFY_FULL`). The password is never part of the record, of the link settings or of the page state, only the file that holds it; a URL that carries one is refused. The link is checked as the store checks it when it connects (H2 is no business database, the product must be one Sennard has SQL for, the TLS rule), so a link that could never connect is refused before the passkey is asked.
- The records are appended to `pre_link_admin_records` in the settings database with the same record form, the same chain rules and the same checks as the business log. Only the changes the settings database can hold are taken (a key's registration and revocation, and the link); any other is refused with `ADMIN_CHANGE_INVALID` (`details.reason: BUSINESS_DATABASE_NOT_READY`).
- Committing the link writes the link settings (`database_link`) in the same transaction as the record and the key. After the commit the store prepares with it (connecting, migrating, ready); a link signed again while the store has not been ready replaces it.
- The link in the settings database is the one source of the business database: the server, `sennard admin-reset` and `sennard attachments` read it there, and a `sennard.store.database.*` key in `sennard.yaml` is not read, so it neither names a database nor locks the page. The page shows the store's `phase`, the saved link and `link.restartRequired` (see “Changing the business database after it was ready” below).
- The section is open until the business database is ready for the first time, and is then closed (`pre_link_section.closed`): it takes no more records (`SettingsCode.PRE_LINK_CLOSED`) and the page is the business database's. The section has one state row (`pre_link_section`: the last sequence number and whether it is closed), and appending a record and closing the section are both conditional UPDATEs of that row (`H2PreLinkAdminRecords`: `SET last_seq = last_seq + 1 WHERE closed = FALSE` and `SET closed = TRUE WHERE closed = FALSE`, each a service method of the settings database with its one transaction), so the database decides which comes first: a record is before the close, or its append is refused with `PRE_LINK_CLOSED`. No record enters a closed section, and no lock row or `FOR UPDATE` is used. The sequence number of a record is the number its append took, and it goes on counting after the admin reset. The first business record of a chain names the last record before the link of that chain as `prevTargetHash`.
- Changing the business database after it was ready: the page takes `DATABASE_LINK` then too (`ContextLayerService`), with the same shape check, and the signature is a record of the business log (the section before the link is closed). The database the new link names is tried when the signature is committed (`LinkedDatabaseProbe`: the user's driver and account, the start-up checks of the pool, the product the URL names, the migrations of its tables); a failure is the store's own error (`StoreException`) and the record rolls back, so nothing is kept. Then the link settings are written (`database_link`; the settings database is not the business transaction, so the write is the last step, and a failure of the business commit after it leaves a link whose signature was verified in the same request, without its record). The store is prepared once in a process, so the saved link is used by the next start; the page says so (`link.restartRequired`: the store is `READY` and the link was saved after the store started) with the next step, `sennard stop` and `sennard start`. The records of the previous database are not copied to the new one, and the log of the new database starts empty after the section before the link.

## Readers (Hook, MCP, Page)

- On every read, the whole log is verified in order. A record that fails verification is not applied, and its target operates with the last revision whose signature is valid (rN). If there is no valid revision, the defaults are used (no global context, no role, no binding). This is the direction in which permissions decrease.
- The hook inserts one line for each failed target: "verification failed · rN in use · tell the user · agents cannot fix this".
- The global context and the role context are read separately. If one fails, the other is still injected.
- For each failed target, the page shows a red banner with [Sign and adopt] and [Discard]. [Sign and adopt] signs again the change that the failed record was requesting, and [Discard] signs a confirmation (`ACK`) that the currently valid state is kept as it is.
- The resident MCP server keeps in memory the largest seq it has seen for each target. If the records become fewer than that, it reports `ADMIN_LOG_REGRESSED`.

## Where Settings Are Read

Setting items are also read through the same verification path as the other signed items (`AdminLog.fold`). On every read, the whole log is verified, and a record that fails verification is not applied. That item operates with the last valid revision, or with the defaults if there is none.

| Item | Where it is read | When the changed value takes effect |
| --- | --- | --- |
| Attachment folder and resource limits | `SignedAttachmentSettings`: verified current values and all earlier folders, shared with offline maintenance | From the next request; existing files retain their location |
| Edit gate exception paths | The edit gate decision (`ProductEditTargets`) | From the next edit |
| JEV on/off, model, permission to send information, preset | The classification runtime read of the server (on every `classify_skills` call, selection record, and automatic classification started by a user prompt hook) | From the next call |
| JEV budget | The budget reservation of the server (on every reservation) | From the next reservation |
| JEV key | Reading the key at a JEV call and at a model list refresh (name `JEV_API_KEY`) | From the next call |
| Server JVM preset | `PersonalJvmInstallation`, which receives the `JvmPresetSigned` event after the commit, writes `sennard-jvm.yaml`. When the store is ready, it aligns the file with the signed value | When the server is restarted |

- If the exception path record cannot be read, no exception is added. A read failure does not open the gate. There are at most 50 exception paths (`EDIT_EXEMPT_MAX_PATHS`).
- If the JEV settings cannot be read, JEV is off. If the budget cannot be read, no JEV reservation is made.
- Cost: one hook verifies the signed records once or twice (as many signature verifications as there are records). The records are small because only those that a person saved accumulate. If they grow to thousands, the method will be changed to store the verified leading part (`ceiling:`).

### Environment Variables

Environment variables are not used for the following settings.

- **Display language:** There is no setting for choosing the language. This fact is stated in the user document ([admin-page.md](../user/admin-page.md)).
- **Edit gate exception paths:** Only the signed list is used. Environment variables and server settings do not add exception paths.
- **JEV:** The server manages everything. Installation configuration files and environment variables are not used for JEV. See "JEV Configuration" below.
- **Vendor path classification:** It does not operate, because the installation configuration is not read.

## JEV Configuration

The role of JEV (an advisory layer, not a gate), the conditions for using it, and the items sent are described in the JEV section of the [user document](../user/admin-page.md). The implementation facts are as follows.

- **The providers are built into the Sennard source** (`JevProvider`). The only provider in this release is TypeSafe. The call address is `https://api.typesafe.ai/v1/systemone`, the model list address is `https://api.typesafe.ai/v1/models`, the wire format is `jev-skill-selection-choice-r01`, and the key name is `JEV_API_KEY`. To add a provider, add one definition to the list in this file.
- **Model check for the conditions of use:** The provider and model name must be in a format that Sennard knows.
- **Model list:** It is kept in server memory and fetched again every 24 hours (1 hour later if it fails), and refresh requests that arrive at the same time are merged into one.
- **No qualification:** JEV has no prior qualification gate. The JEV profile that Sennard creates records the qualification as `NOT_RUN`, and `adviceQualification` in the `classify_skills` response is also `NOT_RUN` for JEV advice. The qualification rules of the vendor path (PASS, inventory binding, expiry) remain as they are.
- **Permission to send information:** The signed permission replaces `externalClassificationAllowed` of the installation configuration for JEV (the vendor path keeps using the installation configuration). "View details of sent information" on the page shows the items that the wire format actually produces.
- **Budget:** Only the signed limit is used. For each call, the maximum cost is reserved in advance (about 0.0110 USD, calculated with the input limit of 256 KiB at 1 byte = 1 token and an input price of USD 0.042/M), and it is settled with the estimated amount calculated from the token count of the response. The reservation is released when the call ends, including when usage is unknown.
- **Evaluation attempts.** JEV retries communication failures at the same evaluator, honoring a valid `Retry-After` value or using an increasing delay. The deadline runs from the start of the request (`sennard.jev.retry.deadline`, 60 seconds by default). It limits further retries along with the budget for each attempt and whether the request is still current. A call already in progress is allowed to finish. JEV may switch once to the configured fallback evaluator on an eligible failure. The same retry rules apply at that evaluator. If JEV has no advice, the agent makes the selection.
- **Status wording:** The page and the workflow change notices say "in use" for JEV only when JEV can actually be called, and otherwise state what is missing.

### Storing the JEV Key

- The JEV key (`JEV_API_KEY`) uses only the value registered on this page. An environment variable of the same name is not used for JEV.
- The page creates a SHA-256 fingerprint of the key value (`sha256:<hex>`) and then signs with a passkey the change that contains that fingerprint (`JEV_KEY_SET {name, fingerprint}`). Only the fingerprint remains in the signed record.
- The value is sent only with the signed commit request (`secret`). The server checks that the fingerprint of the value equals the signed fingerprint, encrypts the value with the sealer (`SecretSealer`), and stores it in `jev_keys` within the transaction that appends the signed record. The authenticated data are the name and the fingerprint, so a stored value that is moved to another name or replaced with another value cannot be decrypted.
- The data key is placed in the state folder by the local sealer (`LocalFileSealer`) (readable by the owner only, where the platform supports it). It is created at the first registration.
- The reader uses the value only when the fingerprint of the last valid signed record matches the stored value. If a later record fails verification, the stored value belongs to that record, so the fingerprint does not match and the key is not used (it operates as if there were no key).
- The value is not put in responses, page state, or diagnostics. The reset (`admin-reset`) also deletes the stored key.
- The fingerprint is an unsalted SHA-256. A randomly generated API key cannot be recovered from the fingerprint, but a short or guessable value can be guessed by comparing against the fingerprint.
- The operating system key store (Windows DPAPI and the like) is not used in this release. What the encryption protects against is the case in which only the content of the store is copied or read separately (a backup, a support bundle).

### Usage Amount

The JEV usage amount shows only values that have already been aggregated: the estimated running total in `sennard.jev_usage_daily` (the number of calls and the estimated amount in USD) and the amount currently reserved in the memory of the resident server (`JevBudget`). Because the responses contain no billed amount, it is not displayed as actual spending. The estimated running total continues across server restarts, and the reservations disappear on restart. The page only displays these values.

## Agent Requests

- `checkpoint_global_context` and `bind_session_role` store only an unsigned request (a proposal) and return `pending`, `proposalId`, and `adminUrl`. When the same session makes a new request for the same target, it replaces the previous request.
- A binding can be requested only for a role in the role registry. Otherwise the result is `ROLE_NOT_REGISTERED`.
- A binding applies per root session. A subagent inherits the binding of its root session. A binding expires after 30 days from its last use.
- Root approval (`replace-root`, `release-root`) is an item of this signed log (`ROOT_APPROVE`). Before approval, the tool returns `USER_APPROVAL_REQUIRED`, `adminPage`, and `scopeDigest`; after the user approves with a passkey on the page and repeats the same call, that approval is reused (`kind: admin-page`, `RootApprovalService`).
- Root release (`ROOT_RELEASE`) is a signed item with which the user releases an open root even when there is no owning session. The target chain is `rootRelease:<rootId>` and the content is `rootId`, `expectedRevision`, and `reason`. Both `/api/intent` and the commit refuse the request if the root does not exist (`ADMIN_ROOT_NOT_FOUND`, 404), if it is no longer open (`ADMIN_ROOT_NOT_ACTIVE`, 409), or if its revision has changed (`ADMIN_ROOT_STALE`, 409). If the commit is refused, no signed record is left either. The release is in one transaction with the signed record (`RootReleaseService`); `releasedBy` of the release record is `admin-page`, and `userApprovalRefs` points to the approval record (`kind: admin-page`) that contains the hash of the signed record. The release that a session performs with `release_convergence_root` and the closing code are the same (`WorkflowService.closeRoot`).

## Unauthenticated View

`GET /` and `GET /api/state` are open without a passkey. So that other web pages cannot read or write, the Host header (only `localhost:<port>` and `127.0.0.1:<port>`) and, for POST, Origin, `Sec-Fetch-Site`, `Content-Type: application/json`, and a body limit of 64 KiB are checked (blocking DNS rebinding and cross-site requests). The page blocks external scripts and styles with a nonce CSP.

## Reset

`sennard admin-reset` (`AdminResetCommand`, `AdminReset`) empties the passkey registry, moves the records before the link to `pre_link_admin_records_archive` in the settings database, moves the business log to `admin_log_archive`, and leaves `resetOf` (the hash of the previous last record) in `admin_resets`, in this order: the databases are not one transaction, so a run that stops half way is the one that leaves no key to sign with, and running it again gives the same result. The link settings are not a signed record and stay. The first key after the reset is registered by self-signature again. Which reset runs is decided by one state, whether the section of the log before the link is still open (`PreLinkAdminRecords.closed()`, read by the entrance `AdminResetConfiguration`, not a question of an edition): while it is open the business database was never ready, so the log is in the settings database alone and the reset (`AdminResetBeforeLink`, one transaction of the settings database) empties the registry and archives the section's records without touching the business database, which may not be set at all (the authority is the owner's settings file; this is the way out for a passkey lost after the first registration, or after a link that failed); once it is closed the reset above runs and needs the business database, and ends with `ADMIN_RESET_DATABASE_UNREACHABLE` when it cannot be reached. The command's context starts lazily, so the business database's pool exists only in that second case. The command starts its own Spring Boot context without a web server and reaches the business database through the same settings (the installation's, else the link the page saved), driver, pool and isolation level as the server, and the settings database for the registry. The settings database is an H2 file that one process opens at a time, so the command stops the installation's server first when one is up (`AdminResetCommand`, through `ServerControl.shutdown()`, before the context opens the file, for the preview as well as for `--yes`), and a file that a restarted server holds again ends with `ADMIN_RESET_SETTINGS_LOCKED` (translated in one place, `AdminResetContext`, and not retried); the reset is one `@Transactional` method of the `AdminReset` service. Pending requests are rejected. The MCP confirmation window (elicitation) is not used for the first registration proof, because the same OS user could accept it automatically with a fake MCP client. The list of attacks that are not prevented is in the [user document](../user/admin-page.md).

## Error Codes

`ADMIN_KEY_NOT_REGISTERED`, `ADMIN_ALREADY_BOOTSTRAPPED`, `ADMIN_KEY_UNKNOWN`, `ADMIN_KEY_REVOKED`, `ADMIN_LAST_KEY_REVOKE_REFUSED`, `ADMIN_ALGORITHM_UNSUPPORTED`, `WEBAUTHN_PUBLIC_KEY_UNAVAILABLE`, `ADMIN_SIGNATURE_INVALID`, `ADMIN_CHALLENGE_MISMATCH`, `ADMIN_ORIGIN_REJECTED`, `ADMIN_RPID_MISMATCH`, `ADMIN_USER_VERIFICATION_MISSING`, `ADMIN_INTENT_NONCANONICAL`, `ADMIN_INTENT_EXPIRED` (10 minutes after the intent is issued), `ADMIN_INTENT_BEFORE_START` (the intent was issued before this server process started; the page's port changes at each start), `ADMIN_INTENT_NOT_ISSUED` (a commit is accepted only for an intent this server process prepared and no record has used yet; the signature proves what the user signed, not that this server asked for it), `ADMIN_TARGET_STALE`, `ADMIN_LOG_REGRESSED`, `ADMIN_PROPOSAL_NOT_FOUND`, `ADMIN_ROOT_NOT_FOUND`, `ADMIN_ROOT_NOT_ACTIVE`, `ADMIN_ROOT_STALE`, `ADMIN_CHANGE_INVALID` (details.reason: `ROLE_NAME_TAKEN` and others; for settings, `JEV_PRESET_UNKNOWN`, `JEV_KEY_NOT_FOUND`, `JEV_KEY_FINGERPRINT_MISMATCH`, `SECRET_UNEXPECTED`, `JEV_KEY_VAULT_UNAVAILABLE`; for keys, `KEY_FINGERPRINT_MISMATCH` and `PUBLIC_KEY_UNEXPECTED`; for the link, `DATABASE_LINK_INVALID`, `DATABASE_LINK_CLOSED` and `BUSINESS_DATABASE_NOT_READY`), `ADMIN_RECORD_ALTERED` (a record that was edited in the file, or whose key in the passkey registry is missing or not the one the record names: `details.reason: KEY_NOT_IN_REGISTRY` or `KEY_FINGERPRINT_MISMATCH`; and the refusal of a signature or of the first key while the log has such a failure: `LOG_INTEGRITY_FAILED`). HTTP boundary: `HOST_REJECTED`, `CONTENT_TYPE_REJECTED`, `REQUEST_TOO_LARGE`, `REQUEST_INVALID`; a store that cannot answer is `MCP_UNAVAILABLE` with `reasonCode: STORE_UNAVAILABLE`, which the page shows with its own sentence.
