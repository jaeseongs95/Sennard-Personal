# DB와 트랜잭션

이 문서는 영역을 Spring Data JDBC로 옮길 때 지키는 저장 규약입니다. 기준 구현은 현황판(board)과 세션 메시징(messaging)이며, 아래 `파일:행`은 이 두 영역의 실제 코드입니다. 다른 영역은 이 문서의 표와 순서대로 옮기면 됩니다. 사용자 원문 보관소(프롬프트 표, V15)는 처음부터 이 규약으로 만든 세 번째 영역입니다. 애플리케이션은 원문을 추가만 할 수 있도록 다룹니다. 원문 엔티티에는 `@Version`이 없고 `UserPromptWrites`의 INSERT 한 문장으로 원문을 기록합니다.

## 출발점

- 저장소는 Spring Data JDBC를 씁니다. 업무 로직을 DBMS에 넣지 않으며, 트리거 같은 DBMS 기능을 쓰지 않고 SQL은 ANSI SQL로 작성합니다.
- 업무 DB는 사용자가 고릅니다. 사용자가 JDBC URL과 JDBC 드라이버 jar를 줍니다(관리 페이지의 연결: URL과 드라이버 경로). 제조사 드라이버는 동봉하지 않습니다(`JdbcDrivers`가 `ServiceLoader`로 찾고, `DataSourceFactory`가 Spring `SimpleDriverDataSource`와 Hikari 풀 하나를 만듭니다). 시험은 PostgreSQL에서만 돕니다(개발 원칙 7.3). 그래서 ANSI SQL을 쓰고 DBMS 전용 문법은 쓰지 않습니다. 새로 쓰는 저장 코드는 DBMS 중립입니다. 어떤 제품이 표준을 다른 모양으로 적어야 하면 그 차이는 한 곳 `ScriptDialect`에 둡니다(MariaDB·MySQL의 `GENERATED BY DEFAULT AS IDENTITY`와 `TIMESTAMP`). 마이그레이션 스크립트는 ANSI로 남습니다. MariaDB 때문에 생긴 규칙은 다음과 같습니다. 예약어(`key`, `change`)를 열 이름으로 쓰지 않습니다. utf8mb4에서 3072바이트(전체 768자)를 넘는 키를 만들지 않습니다. `MERGE`와 `ON CONFLICT`를 쓰지 않습니다(`SqlMerge`는 개수를 센 뒤 갱신하거나 삽입합니다). `CAST(... AS VARCHAR(n))`를 쓰지 않습니다.
- 값은 Java에서 만들어 DB에 넘깁니다. 값은 Java가 만들고 DB에는 공통 타입만 둡니다.
- Spring 쪽 이유: Boot는 새 기능을 더하지 않고 Spring의 기능을 자동 설정으로 조립합니다. DataSource·풀·트랜잭션 관리자·`NamedParameterJdbcTemplate`·리포지토리 기반은 Boot 자동 설정이 만들고, Sennard는 직접 만들지 않습니다.

## 규칙 요약

| 규칙 | 내용 |
| --- | --- |
| 저장소 | `@Table` 엔티티 record + `Repository<T, ID>` 인터페이스. 파생 쿼리를 먼저 쓰고, 꼭 필요할 때만 `@Query`(ANSI)를 씁니다. |
| 사용자 | 개인판은 한 PC의 한 사용자입니다. 키·열·쿼리 조건에 계정·테넌트·네임스페이스를 두지 않습니다. 행 수준 보안(RLS)은 쓰지 않습니다. 빌드 규칙 `n-no-multi-user-columns`가 그런 열이 다시 생기는 것을 막습니다. |
| 동시성 | 기본키·UNIQUE, `@Version` 낙관적 잠금, `@Transactional` 격리 수준입니다. advisory lock·`FOR UPDATE`·`SKIP LOCKED`는 쓰지 않습니다. |
| 재시도 | 경쟁에서 진 트랜잭션은 다시 실행하지 않습니다. 조건부 `UPDATE` 한 문장이 바꾼 행 수가 승자를 정하고 유일 키가 중복을 막으며, 진 쪽은 이긴 쪽의 결과를 읽거나 할 일 없이 끝납니다. |
| 값의 출처 | 식별자는 주입한 `IdGenerator`, 시각은 주입한 `Clock`의 UTC `Instant`입니다. DB 함수(`now`·`gen_random_uuid`·`clock_timestamp` 등)로 값을 만들지 않습니다. |
| 열 타입 | UUID는 Java `UUID`(`CHAR(36)`), 시각은 예외 없이 `TIMESTAMP`(시간대 없음, UTC 값)입니다. `timestamptz`·`bigint` 시각·텍스트 시각은 없습니다. 의미 있는 상태는 enum 이름 `VARCHAR` + `CHECK`입니다. |
| 시간 | 시각은 한 곳에서 만들고(`Clock.systemUTC()` 빈 하나, `AppConfiguration`) 한 곳에서 바꿉니다(`sennard-domain`의 `Timestamps`). 아래 「시간」 절과 빌드 규칙 `TimeRules`를 봅니다. |
| SQL | ANSI만 씁니다. `ON CONFLICT`·`RETURNING`·`::`·`SKIP LOCKED`·부분 인덱스·`ILIKE`·`LEAST`/`GREATEST`·DB 함수는 금지입니다. |
| DB의 일 | 사실 보존입니다. FK·CHECK·UNIQUE 선언만 두고 함수·프로시저·트리거·ROLE·GRANT는 두지 않습니다(업무 DB는 한 계정입니다). |
| 오류 | 드라이버 클래스(`PSQLException` 등)를 import하지 않습니다. Spring의 `DataAccessException` 계층을 받아 `SennardException`으로 바꿉니다([예외와 메시지](exceptions-and-messages.ko.md)). |
| 파일 I/O | 트랜잭션 밖에서 합니다. 트랜잭션 안에서 파일을 읽고 쓰지 않습니다. 본문을 DB에 두지 않고 FK도 두지 않는 예는 첨부입니다([첨부와 업로드](attachments.ko.md)). |
| 마이그레이션 | 한 벌입니다. DBMS별 폴더를 만들지 않습니다. 긴 텍스트 열의 타입 이름만 자리표시자 `${long_text}` 한 개로 두고, DBMS별 값은 `SqlBuilder.generateLongText`가 방언마다 돌려주는 선언입니다(DBMS마다 공식 문서 URL을 단 고정 표이며, 드라이버를 읽어 정하지 않습니다). Sennard의 적용기 하나가 스크립트를 적용하고 이력 표에는 시도마다 행이 하나 있습니다. Flyway는 쓰지 않습니다. 행이 이미 있는 표는 새 스크립트의 `ALTER TABLE`로 바꾸며, 적용된 스크립트는 고치지 않습니다(아래 「마이그레이션」). |

## 동작 방식

### 엔티티: 복합 키와 `@Version`

키가 둘 이상의 열이면 `@Id @Embedded` record를 키로 둡니다(`BoardSession.java:20`). 새 행인지 판정은 `@Version Long version`이 합니다. 버전이 `null`이면 INSERT, 아니면 `UPDATE ... WHERE ... AND version = ?`이고, 다른 트랜잭션이 먼저 바꿨다면 갱신된 행이 0이라 `OptimisticLockingFailureException`입니다. 엔티티는 불변 record라서 변경은 새 record를 만들어 `save`합니다(`BoardSession.java:24-` 의 `first`·`seen`·`summarized`).

### 리포지토리: 마커 인터페이스

`CrudRepository`를 상속하지 않고 `Repository<T, ID>`만 상속합니다. 리포지토리가 선언한 메서드만 드러내려는 것이며, `findAll`·`deleteAll` 같은 CRUD 메서드는 선언하지 않으면 없습니다.

```java
// BoardSessionRepository.java:15
Optional<BoardSession> findByKeyHostAndKeySessionId(String host, String sessionId);
// 파생 delete도 됩니다
long deleteBySeenAtLessThan(Instant before);
```

파생 쿼리로 안 되는 것(정렬·한도·집계)만 `@Query`로 씁니다. 예: `MessageRepository.java:24`(`findClaimable`), `:29`(`COUNT(*)`), `:34`(`COALESCE(MAX(seq), 0)`).

### 서비스: 트랜잭션

`@Transactional`은 서비스 메서드에만 둡니다. 메서드 하나는 유스케이스 하나이자 트랜잭션 하나이며, 격리 수준은 판이 정합니다(`sennard.store.isolation`, 개인판은 READ COMMITTED). 메서드마다 격리 수준을 올리지 않습니다. 모든 트랜잭션이 갖는 시간은 판의 `spring.transaction.default-timeout`이며, Spring Boot의 `TransactionManagerCustomizers`가 store의 트랜잭션 매니저에 설정합니다.

한 행을 두고 벌이는 경쟁은 조건부 `UPDATE`와 그 영향 행 수가 정하고(`MessageRepository.claim`, `MessageRepository.acknowledge`, `PreparedMessageRepository.submit`), 진 쪽은 이긴 쪽의 결과를 읽거나 할 일 없이 끝납니다. 큐 전체의 한도는 평범한 읽기라서 동시에 쓰는 쪽이 몇 건 넘길 수 있습니다(`MessagingService` 클래스 주석).

진 트랜잭션은 다시 실행하지 않습니다. 두 번째 실행은 이긴 쪽이 바꾼 상태 위에서 판단을 다시 내리고, 그 효과(새 식별자·시각·서명)를 두 번 만들기 때문입니다. `@Retryable`이나 그것이 붙은 주석을 단 메서드는 없고, 빌드 규칙 `u-transaction-boundary`가 있으면 찾아냅니다. 여러 요청이 동시에 행을 처음 만드는 경우는 그 유스케이스 하나의 트랜잭션 안에서 읽고 없으면 INSERT하며, 같은 순간의 두 번째 INSERT는 유일 키가 막아 번역된 오류로 끝납니다(받아들이는 한계). 중복 키를 잡아 이어 가거나, INSERT만 하는 유스케이스를 따로 두거나, 트랜잭션 밖에서 유스케이스를 쪼개 이어 부르지 않습니다.

### 값은 Java가 만든다

시각은 주입한 `Clock`에서 밀리초로 자르고, UTC `LocalDateTime`으로 바꿔 엔티티에 넣습니다. 열이 시간대 없는 `TIMESTAMP`이므로 드라이버가 JVM 시간대로 바꾸는 일이 없습니다. 이 한 곳에서만 바꿉니다(`Timestamps.toTimestamp`·`toInstant`, `BoardService.java`의 `utc()`·`instant()`는 이를 부르는 별칭입니다). 아래 「시간」 절을 봅니다. JVM 시간대를 `Asia/Seoul`로 바꿔도 같은 UTC 값이 저장되는지 시험이 확인합니다(`AbstractBoardServiceTest`의 `aTimeIsStoredAsTheUtcInstantWhateverZoneTheJvmIsIn`, 메시징은 `AbstractMessagingServiceTest`).

### 시간

시간 열은 UTC로 저장합니다. 사용자에게 보여 줄 때는 서버가 UTC 그대로 보내고 클라이언트가 변환해 표시합니다. Java의 시간 계산도 모두 UTC 기준으로 하며, 한 방식으로 통일합니다.

- 모든 시간 열은 `TIMESTAMP`이고 값은 UTC입니다. 밀리초까지 둡니다. 클라이언트가 보고한 PC 시각(`client_started_at`·`client_ended_at`)과 하루 단위 집계(`jev_usage_daily.day`, UTC 0시)도 같은 형식입니다.
- 시각은 주입한 `Clock` 하나에서 읽습니다. 업무 코드에서 `Instant.now()`·`System.currentTimeMillis()`·`LocalDateTime.now()`·`ZoneId.systemDefault()`·`java.util.Date`·`Calendar`·`java.sql.Timestamp`를 쓰지 않습니다. 기다리는 시간(마감)은 단조 시계 `System.nanoTime()`을 씁니다. 빌드가 컴파일된 제품 클래스를 ArchUnit으로 읽어 막습니다(`sennard-arch-checks`의 `TimeRules`, 시험 `TimeRulesTest`가 어긴 예를 빨갛게 확인합니다). `Clock.systemUTC()`를 만드는 곳은 서버의 `AppConfiguration` 빈과 CLI 프로세스의 진입점(`SennardCli`) 둘뿐입니다.
- `Instant`와 `TIMESTAMP` 값 사이는 `Timestamps.toTimestamp`·`toInstant`가 유일한 변환입니다. 값은 `LocalDateTime`으로 드라이버를 지납니다. `java.sql.Timestamp`는 JVM 시간대로 읽고 쓰므로 같은 순간이 JVM마다 다른 값이 되고 서머타임 공백의 시각은 움직입니다. `Map` 행을 읽을 때도 `TIMESTAMP` 열은 `LocalDateTime`으로 받습니다(`UtcRows`).
- DB에는 시계가 없습니다. `now()`·`clock_timestamp()`·`CURRENT_TIMESTAMP`를 문장이나 열 기본값에 쓰지 않습니다. 임대 만료·보존 기간의 경계도 Java가 계산해서 값으로 넘깁니다.
- 요건: DB의 시간대는 UTC여야 합니다. 값은 Java가 UTC로 계산해 넣으므로 이 저장소의 문장은 DB 시계를 읽지 않지만, DB 서버·세션 시간대가 UTC가 아니면 운영자가 도구로 보는 `TIMESTAMP` 값의 해석이 어긋나기 때문입니다. 시간대 속성이나 세션 `SET TIME ZONE`으로 맞추지 않습니다.
- 서버는 시각을 UTC 그대로 내보냅니다(`2026-01-02T03:04:05.006Z`, `Timestamps.format`). 사용자 시간대로의 변환은 클라이언트가 합니다.
- JVM 시간대(`Asia/Seoul`·`America/New_York`, 3월의 서머타임 공백 시각 포함)를 바꿔도 같은 순간이 같은 값으로 저장되고 같은 순간으로 읽히는지 시험이 확인합니다(`TimestampsTest`, `AbstractModuleStoresTest`의 `aTimeIsStoredAndReadBackIdenticallyWhateverZoneTheJvmIsIn`).

### enum 저장

닫힌 값 집합은 enum이고 열은 enum 이름입니다. Spring Data JDBC의 기본 매핑을 그대로 씁니다(참조 문서 Mapping: 「Enums get mapped to their names.」). Converter를 만들지 않고, 허용 값은 DB `CHECK`로 지킵니다.

```sql
-- V9__messaging.sql:30,39
state       VARCHAR(16)      NOT NULL,
CONSTRAINT prepared_messages_state CHECK (state IN ('PREPARED', 'SUBMITTED', 'RECALLED')),
```

`PreparedMessage.state`가 `MessageState`(`sennard-domain`)입니다. 상태별로 어떤 열이 있어야 하는지도 `CHECK`로 둡니다(`V9__messaging.sql:41-`).

### 계수기

메시징의 세션별 한도 계수기(`session_ref`의 일부 열)는 identity 영역의 표에 있습니다. 조건부 `UPDATE ... WHERE ... < 한도`의 영향 행 수로 판정하는 작은 리포지토리가 갱신합니다(`SessionRefRepository.java:23-35`). 소유는 identity이고, identity 영역을 옮기는 담당이 넘겨받습니다. 큐 전체의 한도(미확인 메시지 수·바이트, 초안·영수증 수)는 계수기 없이 표에서 직접 세어 `MessagingProperties`의 한도와 비교합니다(쓰기 전의 평범한 읽기이며, 동시에 쓰는 쪽이 이 한도를 몇 건 넘길 수 있고 이를 받아들입니다).

### 연결: Boot 기본 경로와 개인 서버

Boot 기본 경로는 `spring.datasource.*`만 주면 됩니다. 이 경로로 같은 서비스가 도는지 시험합니다(`RewrittenAreasContext.bootDefault`, `BoardServiceBootDefaultTest`). 개인 서버의 업무 DB 연결은 리스너가 뜬 뒤 설정될 수 있습니다. `LazyJdbcRepositories`와 `BusinessJdbcConfiguration`은 저장소에 방언이 처음 필요할 때까지 방언 해석을 미룹니다. Spring Data JDBC는 연결된 데이터베이스 제품과 설정에서 방언을 해석합니다.

### 현재의 전환 상태

트랜잭션 관리자는 Boot의 `transactionManager` 하나입니다. 서비스 메서드는 손으로 잠금을 잡지 않습니다(모듈 잠금, `ModuleLocks`, `sennard.module_lock` 표는 없앴습니다). 유스케이스는 `@Transactional` 서비스 메서드 하나이고, 호출이 만났을 때는 판의 격리 수준의 트랜잭션, `UPDATE`가 스스로 잡는 행 잠금, 제약이 가릅니다. 저장소들이 같은 `transactionManager`를 공유하므로 한 트랜잭션에서 여러 저장소를 써도 됩니다.

### 훅 경로의 동시성(continuity, 갱신 알림)

동시성은 DB에 맡깁니다. 트랜잭션, UPDATE가 스스로 잡는 행 잠금, 제약(PK·UNIQUE·FK)이 수단입니다. 훅은 조건(epoch, 상태 토큰, 마지막 알림 버전)을 `WHERE`에 둔 SQL 한 문장으로 상태를 바꾸고, 영향 행 수가 이긴 쪽을 가릅니다. 진 쪽은 아무것도 다시 하지 않고 다시 실행되지도 않습니다. 서버 전체에 하나뿐인 것(continuity 비밀값, workflow·상태 정리의 서명키, 플러그인 갱신 상태 행)은 서버 시작 유스케이스가 만들고 요청은 읽기만 합니다. 세션의 continuity task는 task를 읽고 바꾸는 서비스 메서드가 없으면 같은 트랜잭션에서 만듭니다(`ContinuityStore.ensureTask`). 다만 호출자가 이어서 써야 할 상태 토큰을 알려 주며 거절하는 두 유스케이스(`checkpoint_context`, `purge_direct_context`)는 task를 읽기만 합니다. 거절은 트랜잭션을 되돌리므로 그 안에서 만든 task는 거절이 보여 준 토큰과 함께 사라지기 때문입니다. task가 없는 세션은 토큰 없이 거절하며, task는 `load_context`나 세션 시작이 만들고 그 답은 커밋된 값입니다. 같은 세션의 첫 요청 둘이 겹치면 진 쪽은 유일 키가 막아 번역된 오류로 끝나며, 잡아서 이어 가지 않고 다시 실행하지도 않습니다. task를 가리키는 행은 task로 FK(`V18`)를 가지므로 정리가 task를 지워도 훅의 행이 남지 않습니다. 격리 수준은 판의 설정(`sennard.store.isolation`, Spring `Isolation`, 개인판은 `READ_COMMITTED`)이고 풀의 연결에 적용합니다. 메서드가 직접 지정하지 않습니다. 보기를 읽고 파일을 검사한 뒤 쓰는 유스케이스(변경 journal)는 검사 동안 트랜잭션을 쥐지 않습니다. 읽기와 쓰기는 `ChangeJournalService`의 두 유스케이스(각각 서비스 메서드 하나, 트랜잭션 하나이고 판단은 그 안에 있습니다)이고, 그 사이의 검사는 호출자가 하는 `JournalScanner`의 파일 I/O이며, 쓰기는 journal 버전과 상태를 조건으로 한 조건부 UPDATE입니다. 영향 행이 0이면 진 호출이므로 충돌 오류로 끝나고 다시 실행하지 않습니다.

### workflow 도구·root 결정·역할 본문의 동시성

여기서도 규칙은 같습니다. 잠금이 판가름하지 않습니다. run은 revision 비교 후 설정(`WorkflowStore.updateRun`), root는 revision 비교 후 설정(`casRoot`, 임대 발급도 같음)으로 바뀌고, 임대는 `UPDATE ... WHERE state = 'ISSUED'` 한 문장으로 소비되며, 실행 관측은 기본키로 한 번만 사용됩니다. 다른 요청의 커밋을 기다린 요청은 행을 다시 읽어 조건이 더는 참이 아님을 알고, 그 호출의 stale·conflict 코드로 끝납니다. 다시 실행하지 않습니다. 대기 중인 root 승인은 `DELETE`가 바꾼 행 수로(`WorkflowStore.deletePendingRootApproval`), 역할 본문은 상태 토큰으로(`UPDATE ... WHERE state_token = ?`, 첫 저장은 기본키) 결정합니다. 같은 쓰기 면의 root 둘을 같은 순간에 열면 유일 키가 하나만 통과시킵니다. 활성 root는 쓰기 면 digest(host와 항목들의 물리 경로를 정렬하고 중복을 없앤 값으로 만들어, 항목의 순서와 표기가 달라도 같고, 겹침 확인이 한 host만 보는 것처럼, 다른 host의 같은 경로는 다른 키입니다)를 `convergence_active_surfaces`의 자기 행 기본 키로 담습니다. 활성이 아닌 root에는 행이 없습니다(표준 SQL에는 부분 유일 인덱스가 없고, NULL을 허용하는 유일 열은 이식되지 않습니다. SQL Server는 열마다 NULL을 하나만 허용하고 Db2는 유일 열이 NOT NULL이어야 합니다). root는 활성 상태에서 벗어나는 트랜잭션에서 그 행을 내놓습니다. 그래서 뒤 root의 표면 행 `INSERT`는 그 키에 걸리고, 그 트랜잭션은 root `INSERT`와 함께 되돌려집니다. `WorkflowStore`는 이를 `StoreCode.ROOT_CONFLICT`로 끝내고 `WorkflowService`는 `ROOT_CONFLICT`로 답하며, 다시 실행하지 않습니다. 받아들이는 한계가 둘 있습니다. 활성 root들의 쓰기 면이 겹치지 않는지는 트랜잭션 안의 평범한 확인이라, 겹치기만 하고 같지 않은 면(폴더와 그 안의 파일)의 두 root를 같은 순간에 열면 둘 다 열릴 수 있습니다. 서명된 관리 기록 둘을 같은 순간에 저장하면 나중 기록이 사슬 머리 검사에 실패합니다. workflow 호출이 필요로 하는 registry 파일과 증거 파일은 진입 쪽이 트랜잭션을 열기 전에 읽어 서비스 메서드에 넘기며, 서비스 메서드는 파일을 읽지 않습니다.

### 마이그레이션

스크립트는 jar 안의 `V<번호>__<설명>.sql` 파일입니다(`db/expand`, 지우는 변경은 `db/contract`). 적용기는 `sennard-migration` 모듈의 `HistoryMigrator` 하나입니다. 업무 DB(`sennard-store-pg`의 `MigrationRunner`)와 H2 설정 저장소(`sennard-settings`의 `SettingsMigrator`)는 이 적용기의 어댑터 둘입니다. 어댑터는 각자 연결을 열고, 적용기의 `MigrationException`을 자기 실패 타입(`StoreCode`, `SettingsCode`)으로 바꿉니다. 이력 형식과 판정 규칙은 두 번 쓰지 않습니다.

Flyway를 쓰지 않는 이유: Flyway는 아는 DB 목록을 갖고 DB마다 부품을 따로 받습니다(Flyway 10 이상은 DB별 모듈이 필요합니다). 그러면 제품이 특정 벤더에 묶입니다. 업무 DB는 사용자가 고르고 스크립트는 ANSI SQL이므로, 적용기에 필요한 것은 SQL 표준(`information_schema`, `CREATE SCHEMA`, 이력 표)과 JDBC뿐입니다. DB마다 다른 것은 두 구절의 철자와 긴 텍스트 타입 이름이고, 둘 다 적용기 안의 벤더 목록이 아니라 드라이버의 제품 이름이 주는 방언(`Database`)이 정합니다. 두 구절은 `ScriptDialect`가, 긴 텍스트 타입은 행 제한(`SqlBuilder.generateLimit`)처럼 `SqlBuilder.generateLongText`가 정합니다. 긴 텍스트 타입을 `getTypeInfo()`에서 읽지 않는 이유는 `CREATE_PARAMS`가 드라이버마다 다른 자유 문자열이기 때문입니다(MariaDB 드라이버는 `LONGTEXT`에 길이가 아니라 문자셋·정렬 옵션을 알려 줍니다).

업무 DB의 표는 모두 하나의 스키마 `sennard`에 둡니다. 이력 표, 모듈 버전을 적는 `sennard.module_schema`, 모든 모듈의 표가 그 안에 있습니다. 모듈별 스키마와 역할·GRANT·함수는 없습니다. 표 이름은 스키마 안에서 한 번만 씁니다. 두 모듈이 같은 이름을 썼던 표에는 모듈 접두를 붙입니다(`continuity_cleanup_backup`, `workflow_cleanup_backup`). 설정 DB도 스키마 이름은 `sennard`이고 이력 표는 `sennard.history`입니다.

이력 표(`sennard.expand_history`, `sennard.contract_history`, 설정 저장소는 `sennard.history`)는 시도마다 행이 하나입니다.

| 열 | 타입 | 뜻 |
| --- | --- | --- |
| `version` | `BIGINT` | 스크립트 번호 |
| `attempt` | `INTEGER` | 그 번호의 몇 번째 시도인지(1부터) |
| `script` | `VARCHAR(255)` | 파일 이름 |
| `digest` | `CHAR(64)` | jar 안 파일의 SHA-256(자리표시자를 바꾸기 전) |
| `applied_at` | `TIMESTAMP` | UTC, 주입된 `Clock` |
| `outcome` | `VARCHAR(10)` | `SUCCEEDED` 또는 `FAILED`(DB가 받으면 `CHECK`로 제한) |

기본키는 `(version, attempt)`입니다.

- 시도 한 번은 트랜잭션 하나입니다. 첫 문장은 자기 행을 `FAILED`로 넣는 것으로, 번호를 차지합니다. 마지막 문장은 그 행 하나만 `SUCCEEDED`로 바꿉니다. 행은 지우지 않습니다. 스크립트가 실패하면 `FAILED` 행이 남고, 다음 시작은 `attempt + 1`로 새 행을 넣습니다.
- 두 적용기가 같은 번호를 동시에 적용하면 같은 키를 넣게 되므로, 둘째는 DB 안에서 첫째의 트랜잭션을 기다린 뒤 중복 키를 받습니다. 그러면 이력을 한 번 다시 읽습니다. 그 번호가 같은 digest로 `SUCCEEDED`이면 건너뛰고, 아니면 상대가 실패한 것이므로 `MIGRATION_FAILED`로 멈춥니다. 적용기에는 sleep·폴링·재시도가 없습니다. DDL이 트랜잭션이 아닌 DB에서는 스크립트 전체가 끝나기 전까지 차지한 행이 `FAILED`로 보이므로, 반쯤 적용된 스크립트가 `SUCCEEDED`로 보이지 않습니다.
- 번호는 1부터 연속이어야 합니다(아니면 `MIGRATION_GAP`). 적용된 스크립트는 다시 읽지 않습니다. 바뀐 파일(`MIGRATION_CHANGED`), 적용된 번호의 스크립트가 없는 경우(`MIGRATION_MISSING`), 가장 높게 적용된 번호보다 낮은데 적용되지 않은 스크립트(`MIGRATION_OUT_OF_ORDER`)는 아무것도 적용하기 전에 실행을 멈춥니다. 바뀐 파일은 시도가 아니므로 행을 더하지 않습니다.

행이 이미 있는 표를 바꾸는 규칙입니다.

- **적용된 스크립트는 고치지 않습니다.** 적용기가 digest를 확인해 바뀐 스크립트를 거절합니다(`MIGRATION_CHANGED`). 변경은 새 스크립트에 넣습니다. 적용된 스크립트의 주석도 고칠 수 없으므로, 규칙은 이 문서에 적습니다.
- **표를 바꾸려고 DB를 다시 만들지 않습니다.** 방법은 `ALTER TABLE`이며 행은 그대로 보존합니다. `ALTER TABLE t ADD c <type>`(키워드 `COLUMN` 없음)은 PostgreSQL, Oracle, SQL Server, MySQL, MariaDB, Db2, H2가 모두 받으므로 스크립트가 이미 있는 표에 열을 더할 수 있습니다. 행이 있는 표에 `NOT NULL` 열을 더할 때는 `ADD c <type> DEFAULT <상수> NOT NULL`로 쓰며, Oracle이 받는 순서인 `DEFAULT`가 `NOT NULL` 앞입니다. `DROP COLUMN`, `DROP CONSTRAINT`, `ADD CONSTRAINT`도 이식할 수 있습니다. `V12__session_kind.sql`의 주석에는 앞선 문장이 있습니다. 곧 표준 `ALTER TABLE`에는 Oracle과 SQL Server가 받는 `ADD COLUMN` 철자가 없어서 기존 표에 열을 더하는 스크립트는 없다는 말인데, 틀렸습니다. 그 스크립트는 이미 적용되었으므로 고치지 않습니다.
- **제품마다 다른 문장은 쓰지 않습니다.** `SET NOT NULL`, `MODIFY`, `ALTER COLUMN`, `RENAME`입니다. 이 가운데 하나가 필요한 변경은 새 표를 만들고, `INSERT ... SELECT`로 행을 옮기고, 옛 표를 `DROP`합니다.
- **배포된 마이그레이션은 바꾸지 않습니다. 업무 변경은 새 `V` 스크립트로 앞으로만 갑니다(`ALTER TABLE` 위주, 추가 우선).** 배포 전 스크립트만 고칠 수 있습니다. `V21__attachment.sql`이 최종 첨부 묶음 구조를 처음부터 만듭니다([첨부와 업로드](attachments.ko.md) 참조). `V22`(`workflow_runs.kind`를 `ALTER TABLE ... ADD kind VARCHAR(32) DEFAULT 'CHANGE' NOT NULL`로 더함)는 배포 뒤 변경이 취하는 형태의 예이며, 이미 있는 표를 바꾸고 행을 보존합니다.

### 쓰기 도구의 operationKey와 영수증

상태를 바꾸는 도구는 호출자가 만든 `operationKey`(필수, `^[A-Za-z0-9_.:-]{16,128}$`, 서버는 만들지 않음)를 받습니다. 응답을 잃어 같은 요청을 다시 보내도 작업을 두 번 하지 않고 처음 응답을 돌려주기 위해서입니다. 하나의 장치가 이를 맡습니다. `OperationReceipts`가 `sennard.operation_receipt` 표(기본키 `(tool, scope, operation_key)`, 요청 내용의 digest, 응답, 외래 키 없음)를 씁니다. 키는 호출자 자신의 것입니다. `scope`는 호출한 세션의 서버 발급 참조라서, 한 도구에 같은 키를 보낸 두 세션은 각자의 효과와 영수증을 가진 두 작업입니다. 호출자가 세션을 갖기 전에 불리는 `open_session`만 고정 scope `global`을 쓰며(누가 보내든 같은 키는 같은 세션을 엽니다), 그래서 그 키는 호출마다 무작위로 만듭니다. digest는 모든 도구에서 같게 키·세션 참조·응답 모드를 뺍니다(`OperationKeys.digest`). 유스케이스는 영수증을 먼저 읽습니다. 같은 키와 같은 digest면 저장된 응답을 돌려주고, digest가 다르면 `REQUEST_CONFLICT`(reason `OPERATION_CONFLICT`)입니다. 처음 보는 키면 일을 하고, 같은 서비스 메서드 트랜잭션의 마지막 문장으로 영수증을 씁니다. 그래서 효과와 영수증은 함께 커밋되거나 함께 되돌려집니다. **성공만 저장합니다.** 거절은 효과가 없고 트랜잭션과 함께 되돌려지므로(거절하면서 관측한 것을 커밋해야 하는 유스케이스는 거절을 예외가 아니라 값으로 돌려주며, 이 유스케이스는 성공했을 때만 쓰기에 이르므로 영수증도 쓰지 않습니다. 그 실패는 진입 쪽이 커밋 뒤에 답합니다), 같은 키로 다시 보내면 다시 판정해 같은 이유로 거절합니다. 키를 INSERT로 먼저 차지하지 않는 이유는 PostgreSQL이 유일 키 위반이 난 트랜잭션을 끝내 버려 저장된 행을 읽을 수 없기 때문입니다. 같은 호출자가 같은 키로 보낸 첫 요청 둘이 동시에 오면 뒤의 것이 `OPERATION_KEY_IN_PROGRESS`로 끝납니다. 영수증의 중복 키에서 이것을 만드는 곳은 `OperationReceipts.recordText` 하나라서 모든 도구가 같게 보입니다(`REQUEST_CONFLICT`, `details.reason` `OPERATION_IN_PROGRESS`, 다시 시도 가능). 그 작업은 되돌려지고 다시 실행하지 않으며, 같은 요청을 같은 키로 다시 보내면 먼저 된 요청의 결과를 받습니다. `WorkflowService`의 쓰기 도구 열 개가 이를 씁니다. `checkpoint_context`와 `purge_direct_context`는 답을 `continuity_requests`에 둡니다. 그 행은 task·epoch 범위이고 task에 외래 키가 있으며 상태 정리가 task와 함께 지우기 때문입니다(`ContinuityStore`). 영수증은 `sennard.operations.receipt-retention`(기본 24시간) 동안 답하며, 더 오래된 것은 답하지 않고 다음 영수증을 쓸 때 지웁니다(Sennard에는 주기 정리 작업이 없고 이를 위해 만들지도 않았습니다). 그래서 24시간이 넘어 같은 키를 다시 보내면 새 요청입니다. `classify_skills`와 `record_skill_selection`은 operationKey를 이 표가 아니라 서버 메모리(`SkillClassificationService`)에 둡니다. 분류는 세션의 스킬 선택을 위한 조언이라 서버가 떠 있는 동안만 필요하기 때문입니다. 그 밖의 쓰기 도구도 모두 이 장치를 쓰며, 각자 자기 트랜잭션인 서비스 메서드 안에서 씁니다. 보드(`BoardService.setSummary`), 메시지 큐(`MessagingService.prepare`·`send`·`acknowledge`·`recall`), 리캡(`TurnRecapService.record`), 컨텍스트 층(`ContextLayerService.proposeGlobal`·`proposeBinding`·`saveRole`), 작업 기록 확인 표시와 복원 억제(`TurnCheckService.markUnchanged`, `ContinuityService.suppress`), 상태 정리(`StateCleanupService.execute`), `open_session`(`SessionOpening`), 변경계획서(`ChangeJournalService.submitPlan`·`revisePlan`, 파일 읽기·스캔은 트랜잭션 밖에 두고 요청 digest에는 도구 입력만 넣습니다. 그 트랜잭션에서 쓰는 영수증은 계획의 revision을 담고, 호출이 답을 얻으면 그 답으로 영수증을 마무리하므로(`OperationReceipts.complete`), 호출이 끝난 뒤 다시 온 요청은 지금의 run으로 다시 만든 답이 아니라 처음 낸 답을 그대로 받습니다)입니다. `run_skill_check`는 배경 작업을 큐에 넣는 트랜잭션(`SkillCheckQueue`)에서만 영수증을 씁니다(`change-scope-guardian compare`, `test-engineering run`). 판정만 하는 명령은 쓰기가 없어 영수증이 없습니다. 이 유스케이스들의 공개 진입점은 `OperationKey`를 받는 메서드 하나입니다. 일 자체는 같은 서비스의 private 메서드이고 자기 트랜잭션이 없으며, 그 일을 키 없이 부르는 곳은 없습니다(훅은 이 유스케이스로 쓰지 않고, 시험은 자기 키로 진입점을 부릅니다). 키 없이 남은 공개 쓰기는 `ChangeJournalService.submitPlan(workflowId, paths)` 하나입니다. `WorkflowService.startMinimal`이 그 도구 키의 영수증을 이미 쥔 자기 트랜잭션 안에서 부르므로, 같은 작업의 영수증을 한 번 더 쓰지 않습니다. `OperationReceipts.once`는 `Receipted`를 돌려줍니다. 일을 한 호출은 `Fresh`, 영수증으로 답한 호출은 `Replayed`입니다. 그래서 유스케이스가 커밋 뒤에 쓰기 말고 하는 일(작업 기록 점검에 저장을 알리는 `checkpoint_role_context`의 이벤트, `send_session_message`의 깨우기)은 `Fresh`일 때만 합니다. 다시 온 요청은 처음 결과로 답하고, 다시 알리거나 깨우지 않습니다. 답에 담긴 호출 시점의 값(`send_session_message`의 조언용 `autoWake`, 거절된 `recall_session_message`의 상태에 붙는 `autoWake`)은 트랜잭션 안에서 만들어 영수증에 함께 저장합니다(`MessagingService.send`와 `recall`이 답을 만드는 함수를 받습니다). 그래서 다시 온 요청은 `autoWake.checkedAt`까지 처음 답 그대로 받고, 새로 만든 답을 받지 않습니다. 그 상태의 대상(`SessionMessageService.QueueOutlook`)도 `autoWake`와 함께 저장하므로, 대상 세션 행이 정리되어도 그 안의 세션 ID가 null로 바뀌지 않습니다. workflow 도구도 전체 응답을 같은 방식으로 저장합니다. 유스케이스가 자기 결과를 영수증으로 쓰고, 호출이 응답(공개한 결과와 그 뒤에 붙이는 변경 알림 줄)을 얻으면 영수증을 그 응답으로 마무리합니다(`WorkflowReceipts.completeAnswer`, 안쪽은 `OperationReceipts.complete`. 알림은 파일을 훑고, 파일 읽기는 어떤 트랜잭션 안에도 두지 않기 때문입니다). 다시 온 요청은 그 응답을 돌려줄 뿐 다른 일을 하지 않습니다. run을 다시 읽지 않고, 훑은 기록을 쓰지 않고, 알림을 새로 만들지 않습니다. 유스케이스가 커밋한 뒤 응답을 저장하기 전에 멈춘 호출만 영수증에 유스케이스의 결과만 남기며, 그 뒤 다시 온 요청이 그 결과로 응답을 만들어 저장합니다.

### 파일은 트랜잭션 앞에서 읽습니다

트랜잭션은 연결과 쓰기의 행 잠금을 쥐고 있고, 롤백은 파일 읽기를 되돌리지 못합니다. 그래서 워크플로 도구의 유스케이스는 트랜잭션 안에서 파일을 읽지 않습니다. 유스케이스가 파일로 판단하는 것(출력 파일과 단계 결과가 가리키는 파일, 계획이 고정한 스키마, 검토 번들의 검사, root 쓰기 범위의 물리 위치)은 진입점이 읽습니다. 유스케이스에는 행만 읽는 계획 메서드(`planStageReads`, `planFinalizeReads`, `planOpenRootReads`, `planStartReads`)가 있어 필요한 읽기를 요청으로 돌려주고, 진입점(`WorkflowFileReader`)이 트랜잭션 밖에서 답합니다. 그 뒤 트랜잭션 메서드가 답(`FileReads`)을 인자로 받아 판단합니다. 각 답은 읽기가 실패했으면 그 실패를 간직했다가 유스케이스가 값을 꺼내는 자리에서 던지므로, 거절은 유스케이스의 확인 순서대로 나옵니다. 답은 유스케이스가 계획한 revision에 대해 만들어지며, 그 뒤 run이 움직였으면 유스케이스가 쓰는 revision 조건에서 낡은 요청으로 거절되고 다시 읽지 않습니다.

## 주의사항

- 새 엔티티는 `@Version`을 잊지 마십시오. 없으면 `save`가 새 행인지 판정하지 못합니다.
- `record`의 시각 성분 이름은 `LocalDateTime`입니다. `Instant`나 `java.sql.Timestamp`를 넣으면 JVM 시간대로 쓰입니다.
- `@Query`에서 `:targetRef` 같은 이름 인자를 쓰려면 `-parameters` 컴파일 옵션이 필요합니다(`sennard-app/build.gradle.kts`).
- `-Xlint:all -Werror`입니다. `spring-data-relational`의 `@Embedded.Nullable`은 jsr305 경고를 내므로 `@Embedded(onEmpty = USE_NULL)`을 씁니다.
- 큐 전체의 한도를 한 메서드에서 읽고 쓰는 곳은 동시에 쓰는 쪽이 한도를 몇 건 넘길 수 있습니다. 이 용량 한도에는 이를 받아들이고(계수기 행도 잠금도 두지 않습니다), 세션 하나의 한도는 조건부 UPDATE라서 정확합니다(`AbstractMessagingServiceTest`의 `theRecordByteLimitIsPassedByNoMoreThanThePreparersInFlightWhenManyThreadsPrepareAtOnce`).
- 교착을 피하려고 여러 행을 쓰는 메서드는 쓰는 순서를 정합니다(세션 행은 값 순서). 양방향 전송 시험이 이를 지킵니다(`AbstractMessagingServiceTest`의 `sendsToOneRecipientGetSequenceNumbersWithoutAGapAndSendsBothWaysBetweenTwoSessionsFinish`).
- lock timeout(SQLSTATE 55P03)은 Spring 번역에서 `UncategorizedSQLException`이 되어 재시도 대상이 아닙니다. 매핑을 자작하지 않았습니다.
- 표의 키 열 이름은 표 이름을 따릅니다(`user_prompt`의 `user_prompt_id`). `prompt_id`처럼 다른 표의 키 열과 이름과 타입이 같고 FK가 없는 열은 `ForeignKeyCatalogTest`(규칙 k)가 참조 열로 세어 천장을 올립니다. 호스트가 주는 세션 ID 열이 `VARCHAR`인 것도 같은 이유로, `text`인 `board_sessions.session_id`와 짝지어지지 않게 한 것입니다.

## 남은 비중립(보고된 것)

- `text COLLATE "C"` 열: 긴 텍스트 자리입니다. 규약은 「긴 텍스트 타입 이름만 자리표시자(`${long_text}`) 한 개로 두고 DBMS별 값은 SqlBuilder 방언의 선언으로 한다」입니다. 이번 범위에서는 기존 타입을 두었습니다.
- 시험 코드의 `now()`·`decode(md5())`·`string_agg`는 시험 안에서만 씁니다.
