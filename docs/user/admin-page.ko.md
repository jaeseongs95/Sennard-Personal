# 관리자 페이지와 컨텍스트

관리자 페이지는 사람이 정하는 Sennard 설정을 사용자가 직접 바꾸는 로컬 웹 페이지입니다. 에이전트는 이 설정을 바꾸지 못하고 요청만 남깁니다. 사용자는 페이지에서 요청 내용을 확인하고 패스키로 서명해 승인합니다. 이 문서는 페이지 사용법과, 페이지가 관리하는 전역·담당·상황 컨텍스트를 설명합니다. 서명 기록의 형식과 검증 절차는 [관리자 서명 기록](../contributing/admin-log.ko.md)에 있습니다.

## 여는 법

- 페이지는 상주 서버의 별도 포트이며 서버가 떠 있는 동안 열 수 있습니다. 포트는 고정이 아니며 설정도 없습니다. 서버가 시작할 때마다 운영체제가 빈 포트를 주므로, 다른 프로그램이 포트를 쥐고 있어도 서버는 시작하며 한 컴퓨터에서 서버를 둘 띄우면 각각 자기 페이지를 가집니다.
- 현재 주소는 `sennard status`가 출력하는 `adminPage` 값입니다. root 승인이나 담당 결속 요청처럼 사용자의 결정이 필요하다고 알리는 메시지에도 같은 주소가 들어 있습니다.
- 패스키는 포트가 아니라 호스트 이름 `localhost`에 묶이므로, 페이지가 다른 포트로 열려도 앞서 등록한 패스키를 그대로 쓸 수 있습니다. 서명 기록에는 서명한 시작의 포트가 남으며 그 기록은 계속 유효합니다.
- 페이지는 `127.0.0.1`에만 묶입니다. 다른 컴퓨터에서는 열 수 없습니다.
- 주소는 반드시 `localhost`로 엽니다. 패스키(WebAuthn)는 IP 주소를 relying party ID로 쓸 수 없습니다. `http://127.0.0.1:<port>/`로 들어오면 이유를 적은 안내를 보여 주고 `http://localhost:<port>/`로 넘깁니다.

호스트마다 따로 뜨는 서버는 없고 한 컴퓨터에 서버가 하나이므로 어느 호스트에서 열어도 같은 페이지입니다.

## 처음 쓸 때: 패스키 등록

처음 페이지를 열면 첫 패스키를 등록합니다. 첫 키 자체로 등록에 서명하므로, 같은 컴퓨터의 다른 프로그램보다 먼저 등록해야 합니다. 개인판은 컴퓨터와 사용자가 한 명이므로 패스키를 하나만 씁니다. 패스키가 있으면 서버가 다른 패스키 등록을 거절하고(`ADMIN_CHANGE_INVALID`, 이유 `SINGLE_PASSKEY`), 하나뿐인 패스키는 폐기할 수 없습니다. 패스키 화면은 그 패스키의 지문과 등록 시각을 보여 줍니다. 패스키를 잃어버렸다면 컴퓨터에서 `sennard admin-reset`을 실행한 뒤 새로 등록합니다(아래 「패스키를 모두 잃었을 때: 재설정」 참고).

## 페이지에서 바꾸는 것과 보기만 하는 것

| 구분 | 항목 |
| --- | --- |
| 바꿈(패스키 서명) | 전역 컨텍스트, 역할 등록표(추가·이름 변경·삭제), 담당 컨텍스트 본문(결속된 세션의 에이전트도 작성), 세션과 역할의 결속·해제 및 결속 제안 승인, 첫 패스키 등록(새 패스키로 서명), JEV 켜기·끄기(기본 꺼짐)·주 모델과 대체 모델·정보 전송 허용·예산·프리셋·공급자 키 등록과 삭제(화면에는 지문을 표시하고 값은 암호화해 저장), 편집 관문 예외 경로(절대 경로만), 서버 JVM 프리셋(다음 시작부터 적용), 리소스 상한(세션당 열린 workflow 상한), 첨부 저장(절대 저장 폴더, 파일당 최대 크기 MiB, 전체 첨부 용량 MiB), [수렴 한도](#수렴-한도)(전체 시도의 epoch당 횟수와 epoch 수는 root를 열 때 고정합니다. 기존 root에서도 계속 진행할 수 있는 Stop마다 현재 epoch당 시도 횟수를 재점검 한도로 읽습니다), [열린 workflow 해제](#열린-workflow-사용자가-해제), workflow의 작업 범위 변경·종료 요청 승인, 서명 기록 검증 실패 시 **서명해서 채택** 또는 **버리기**, [차단된 워크플로 계획 해제](#차단된-워크플로-계획), [업무 데이터베이스 연결](#업무-데이터베이스) |
| 서명 없이 바꿈 | 전역 컨텍스트 변경 제안과 세션의 역할 결속·해제 제안 거절, workflow의 요청 거절, 페이지 언어 선택(한국어 / English) |
| 보기만 함 | 등록된 패스키, JEV 사용액, JEV 모델 목록과 갱신 상태, JEV에 보내는 항목, 세션 현황, 변경 이력, 스킬 통계, workflow 통계 |
| 페이지에 없음 | 도구 스키마 프로필, 호스트 실행 관측 설정, 상태 경로, JEV 공급자 주소·요청 형식(Sennard 소스에 내장), 벤더 경로 런타임·digest, 깨우기 방식 |

업무 데이터베이스가 처음 준비되기 전에는 패스키와 업무 데이터베이스 탭만 나타납니다.

페이지 상단에 서명 기록 검증 실패가 표시되면, **서명해서 채택** 버튼이 있는 경우 기록된 변경에 다시 서명할 수 있습니다. **버리기**를 선택하면 현재 적용 중인 상태를 유지합니다. 두 동작 모두 패스키 서명이 필요합니다.

서명 전에는 바뀌는 내용을 보여 줍니다. 내용을 읽지 않고 패스키를 누르면 Sennard가 막을 수 없습니다.

## 스킬 통계

스킬 통계 화면은 어느 호스트가 어느 Sennard 스킬을 몇 번 호출했는지를 기간별로 보여 줍니다. 호출이 없는 스킬은 0으로 함께 나옵니다. 스킬은 에이전트 교정과 전문분야 두 묶음으로 나뉘어, 묶음마다 제목 줄과 호출이 많은 순의 스킬이 나옵니다. 묶음은 스킬의 `classification.json`에 있는 `category`입니다. 서버는 스킬 호출 기록을 90일간 보관합니다. 스킬 이름과 시각, 호스트, 세션 ID만 저장하고 대화 내용은 저장하지 않습니다.

호스트마다 세는 기준이 다르며, 표의 호스트 이름 아래에 기준을 적었습니다.

| 기준 | 세는 것 |
| --- | --- |
| 스킬 도구 호출 | 호스트의 스킬 호출 도구 사용 |
| SKILL.md 읽기 | Sennard의 `SKILL.md`를 파일 도구나 읽기 명령으로 연 횟수. 설치 폴더의 `skills`와 호스트가 직접 설치한 플러그인 사본(Codex·Antigravity가 읽는 사본)을 셉니다. 그 밖의 사본은 세지 않으며, 설치 사본의 위치를 알 수 없는 호스트도 세지 않습니다. 다시 읽으면 또 셉니다 |

호스트가 훅에 보여 주지 않는 방식으로 연 스킬(사용자가 슬래시나 이름으로 직접 불러 본문이 바로 들어간 경우 등)과 Sennard 밖의 스킬은 세지 않습니다. 서브에이전트 표시를 주지 않는 호스트에서는 서브에이전트 호출도 메인으로 셉니다.

## workflow 통계

**분석 → workflow 통계**에서 에이전트가 선택한 workflow 종류를 기간별로 볼 수 있습니다. 기존 실행 기록을 읽어 아래 순서로 표시합니다.

1. **종류별 시작 건수.** 종류(답변·조사, 변경, 실행·운영)별로 시작한 workflow 수와, 그중 스킬 없이 시작한 수입니다. 종류는 Sennard가 정의한 종류에서 읽으므로, 나중에 종류가 늘면 이 화면에도 저절로 나타납니다.
2. **최근 workflow.** 선택한 기간의 최근 실행을 최대 50건 표시합니다. 목록을 검색하거나 종류·상태·호스트로 필터링할 수 있습니다. 각 실행의 상세 정보를 펼치면 실행 ID와 선언한 스킬이 표시됩니다.
3. **종류별 선언 스킬.** 이 영역을 펼치면 workflow 종류별 선언 스킬과 각 스킬을 선언한 workflow 건수가 표시됩니다. 답변과 조사는 스킬 사용이 선택 사항이므로 종류별로 따로 집계합니다.

기록된 종류가 없는 workflow(다단계 도구로 시작했거나 기록이 정리된 것)는 변경으로 세며, 그렇게 센 건수를 화면에 알려 줍니다. 보기만 하는 화면이라 패스키가 필요 없습니다. 기간은 스킬 통계와 같습니다.

## 전역·담당·상황 컨텍스트

Sennard는 세 가지 컨텍스트를 둡니다. 프로젝트 단위 컨텍스트는 없습니다.

| 컨텍스트 | 받는 대상 | 본문 상한(UTF-8) | 바꾸는 주체 |
| --- | --- | --- | --- |
| 전역 | 이 컴퓨터에서 Sennard에 연결된 모든 세션과 그 서브에이전트 | 4000 byte | 사용자. 관리자 페이지에서 패스키로 서명 |
| 담당 | 그 역할에 결속된 세션과 그 서브에이전트 | 2000 byte | 그 역할에 결속된 세션(에이전트가 쓰며 서명 대상이 아님) |
| 상황 | 그 세션과 그 서브에이전트 | 2000 byte | 그 세션(`checkpoint_context`) |

- 세 컨텍스트 모두 서버의 저장소에 있습니다. 저장한 적이 없으면 주입도 없습니다.
- **주입 시점.** Claude Code와 Codex는 시작·재개·압축 완료를 알립니다. Antigravity는 호스트가 0번으로 알린 모델 첫 호출에서 복원합니다. Antigravity에서는 요청 중 자동 압축 뒤 다음 요청의 해당 훅에서 복원합니다. 서브에이전트가 시작할 때는 부모 세션의 상황 컨텍스트도 전달할 수 있습니다. Antigravity의 서브에이전트는 부모가 확인된 뒤 첫 담당 컨텍스트를 받습니다.
- **역할과 결속:** 담당 컨텍스트에 누가 접근하는지는 서명된 결속으로만 정합니다. 결속은 역할 등록표에 있는 역할에만 요청할 수 있습니다(없으면 `ROLE_NOT_REGISTERED`). 결속은 root 세션 단위이고 서브에이전트는 root 세션의 결속을 이어받습니다. 같은 세션을 재개하면 유지되고, 마지막으로 쓴 뒤 30일이 지나면 없어집니다.
- 세션 현황판(`list_session_status`)은 서명된 결속이 있으면 그 역할을 보여 주고(`roleSource: "signed"`), 없으면 세션이 스스로 적은 역할을 보여 줍니다(`roleSource: "self"`). 세션이 스스로 적은 역할은 표시용이며 접근 키가 아닙니다.
- 세션 결속 화면의 **구분 불가**에는 메인 세션과의 관계가 확인되지 않았고 요약과 역할이 모두 없는 Antigravity 대화가 표시됩니다. Antigravity 자체 서브에이전트도 첫 Sennard 도구 호출을 확인하기 전에는 여기에 표시될 수 있습니다. Sennard가 생성한 관리형 자식은 생성 시 반환된 ID로 식별합니다. 메인 세션임을 확인한 뒤 역할을 정하세요. 세션이 끝나면 **종료**로 옮겨집니다. 관리 페이지는 시작할 때마다 주소가 바뀌므로 브라우저에 정보를 저장하지 않습니다. [세션 협업](collaboration.ko.md)을 참고하세요.
- **담당 컨텍스트 저장:** 결속된 세션은 `load_shared_context`로 최신 본문과 `stateToken`을 읽고, 본문 전체를 다시 구성해 `checkpoint_role_context`에 `expectedStateToken`과 함께 보냅니다. 그 사이 같은 역할의 다른 세션이 저장했으면 `STALE_REVISION`으로 거절되고 아무것도 쓰지 않습니다. 역할마다 최근 이력 50개를 남깁니다.
- **검증 실패:** 서명 검증에 실패한 대상은 마지막으로 유효했던 판(없으면 기본값)으로 동작합니다. hook은 「검증 실패 · rN 적용 중 · 사용자에게 알릴 것 · 에이전트가 고칠 수 없음」 한 줄을 넣고, 페이지는 그 대상에 빨간 띠와 [서명해서 채택]·[버리기]를 보여 줍니다. 전역·담당 컨텍스트는 따로 읽으므로 하나를 읽지 못해도 다른 하나는 넣습니다.

## 에이전트의 요청과 승인

에이전트는 다음 도구로 요청만 남깁니다.

| 도구 | 하는 일 |
| --- | --- |
| `load_shared_context` | 전역·담당 컨텍스트를 읽습니다. |
| `checkpoint_global_context` | 전역 컨텍스트 변경을 요청합니다. |
| `bind_session_role` | 이 세션을 역할에 결속해 달라고 요청합니다. |
| `checkpoint_role_context` | 결속된 세션이 담당 컨텍스트를 저장합니다(요청이 아니라 바로 저장). |

요청 도구는 `pending`·`proposalId`·`adminUrl`을 돌려줍니다. 같은 세션이 같은 대상에 새 요청을 내면 이전 요청을 대신합니다. 사용자가 페이지에서 차이를 보고 패스키로 승인해야 적용됩니다. 요청 거절에는 서명이 필요 없으며, 결정된 요청은 30일 뒤 지웁니다.

### root 승인

`open_convergence_root`로 기존 root를 교체하거나(`replace-root`) `release_convergence_root`로 해제할 때(`release-root`) 사용자 승인이 필요하면, 승인이 없는 동안 도구가 `details.reason=USER_APPROVAL_REQUIRED`와 페이지 주소(`adminPage`), 승인 범위의 `scopeDigest`를 돌려줍니다. 페이지에서 표시된 행위·root·실행 주체·범위를 확인하고 패스키로 승인하면 같은 호출을 다시 했을 때 그 승인을 재사용해 실행합니다. 승인은 같은 행위·root·실행 주체·범위에만 쓰이고, 모델이 넘긴 인자만으로는 승인되지 않습니다.

## 열린 workflow: 사용자가 해제

열린 workflow는 해제될 때까지 다른 workflow가 같은 파일을 다루지 못하도록 막습니다. workflow를 연 세션이 갑자기 끝나면 **작업 → Workflow 관리**에서 직접 해제할 수 있습니다. 이 화면은 일시 중지되거나 검토 또는 사용자 확인을 기다리는 workflow를 포함해 열린 workflow를 보여 줍니다. 목록을 검색하고 상태나 소유자로 필터링하거나 마지막 활동 시각으로 정렬할 수 있습니다. 각 항목에는 상태, 목표, 소유 세션의 접속 상태와 마지막 활동 시각이 표시됩니다. 상세 정보를 펼치면 root ID, 가장 최근 실행 ID와 생성 시각을 볼 수 있습니다. 시각은 브라우저 시간대를 따릅니다. 소유 세션은 짧은 불투명 참조로 표시되며, 온라인이면 호스트도 함께 표시됩니다.

- **해제에는 패스키가 필요합니다.** 서명은 workflow, 화면이 본 판(revision), 사유를 묶습니다. workflow가 이미 없거나 닫혔거나 화면을 불러온 뒤 바뀌었으면 패스키를 묻기 전에 거절합니다. 서명이 도착하기 전에 바뀐 경우에도 거절하며, 이때는 아무것도 기록하지 않습니다.
- **해제하면 일어나는 일.** workflow가 닫히고 다시 이어갈 수 없으며, 그 workflow에서 실행 중인 run은 blocked로 닫힙니다. 이후 새 workflow가 같은 파일을 다룰 수 있습니다.
- **소유 세션이 살아 있을 때.** 화면이 먼저 경고합니다. 작업을 멈춰도 되는지는 사용자만 알 수 있으므로 해제는 그래도 할 수 있고, 소유 세션이 살아 있었다는 사실이 기록에 남습니다.
- **기록되는 것.** 해제 주체(관리자 페이지), 사유, 시각, 읽은 시점의 소유 세션 생존 상태, 서명한 기록과 패스키를 가리키는 승인 기록을 남깁니다. 같은 내용을 `get_convergence_status`로도 볼 수 있습니다.
- **workflow가 저절로 해제되는 일은 없습니다.** 시간 제한이 없고, 세션은 자기 workflow만 직접 해제할 수 있습니다. 자기 workflow가 아닌 workflow를 사용자의 결정 없이 해제하는 도구는 없습니다.

## JEV: 스킬 선택 조언

JEV는 에이전트의 판단을 돕습니다. 이 버전에서는 작업에 맞는 스킬을 자동으로 추천합니다. 사용할 스킬은 에이전트가 선택합니다.

JEV를 호출할 수 있는 상태(아래 조건을 모두 만족)이면 에이전트가 조언을 요청하지 않아도 됩니다. 사용자 프롬프트가 들어오는 순간 서버가 직접 분류를 시작하고, 서명한 정보 전송 허용에 따라 프롬프트와 스킬 목록을 JEV에 보내며, 훅은 응답을 기다리지 않습니다. 응답이 준비되면 같은 세션의 다음 훅(모델 응답 뒤나 도구 실행 뒤)이 짧은 몇 줄을 한 번 붙입니다. JEV가 필요하다고 판단한 스킬과 그 신뢰도이며, 최대 8개이고 프롬프트나 전체 목록은 담지 않습니다. 에이전트가 `classify_skills`를 직접 불러도 되며, 같은 프롬프트면 이미 받은 응답을 돌려주고 JEV를 다시 부르지도(과금하지도) 않습니다. JEV가 꺼져 있거나 조건이 맞지 않거나 예산이 다했으면 아무것도 보내지 않고 붙이지도 기록하지도 않습니다. 호출을 실제로 했는데 실패한 경우만 서버 로그에 남습니다.

JEV는 서버와 이 페이지가 전부 관리합니다. 공급자 정의(호출 주소, 모델 목록 주소, 요청 형식, key 이름)는 Sennard에 들어 있고, 이 판의 공급자는 TypeSafe 하나입니다. 설치 설정 파일과 환경 변수는 JEV에 쓰지 않습니다.

### JEV를 쓰는 조건

JEV 탭은 저장된 설정을 기준으로 자동 스킬 추천 상태를 표시합니다. **자동 스킬 추천 사용**을 켜고 모델, 공급자 키, 예산을 설정한 뒤 정보 전송을 허용하고 패스키로 저장하십시오. 저장 후 설정이 충분하지 않으면 화면에 빠진 항목이 표시됩니다. 화면과 서버는 다음 조건을 사용합니다.

1. 자동 스킬 추천 켜짐(설정하고 저장하기 전에는 꺼짐)
2. 모델을 고름
3. 「JEV에 정보 전송 허용」 켜짐
4. 이 페이지에 고른 모델의 공급자 key(TypeSafe는 `JEV_API_KEY`)를 등록함
5. 예산 한도가 한 번 호출의 예약액 이상이고 남아 있음

### 항목별 설명

- **모델:** 페이지에서 골라 서명합니다. 목록은 공급자의 모델 목록 주소에서 받아 24시간마다(실패하면 1시간 뒤) 다시 받습니다. key가 없으면 Sennard에 들어 있는 목록을 보여 줍니다. 목록이 바뀌어도 저장한 모델은 자동으로 바뀌지 않으며, 목록에서 빠지면 「(목록에 없음)」으로 그대로 보입니다.
- **JEV에 정보 전송 허용:** 따로 서명하는 항목입니다. 허용하지 않으면 JEV를 부르지 않습니다. 「전송 정보 자세히 보기」에서 실제로 보내는 항목을 확인할 수 있습니다. 작업마다 사용자 요청 원문(`originalPrompt`), 확인된 작업 맥락(`confirmedContext`), 분류 기준의 판·참조·규칙, 모델 이름을 보내고, 설치된 스킬마다 ID·판·설명·사용/설치/호스트 지원 여부·능력·행동·대상·제약·적용/제외 조건·의존·단계를 보냅니다. 스킬 원본 파일 경로·digest(`sourceRefs`)는 보내지 않습니다. key는 본문에 넣지 않고 `Authorization` 머리글로만 보냅니다.
- **예산:** 서명한 한도만 씁니다. 서버 쪽에 따로 둔 상한은 없습니다. 비우면 JEV를 부르지 않습니다. 호출마다(다시 부르는 호출은 시도마다) 최대 비용(약 0.0110 USD)을 미리 잡아 두고, 호출이 끝나면 예약을 풉니다. 답을 받은 호출은 응답의 토큰 수로 계산한 추정액으로 기록하고, 답을 받지 못한 호출은 토큰 수를 알려 주지 않았으므로 세지 않습니다. JEV 응답에는 청구액이 없어 사용액은 추정치입니다. 추정 누계는 저장소에 남아 이 PC의 모든 Sennard 서버가 함께 쓰고 서버를 다시 시작해도 이어지며, 호출마다 이 누계에 지금 보내는 호출들의 예약액을 더해 한도와 비교합니다.
- **자동 스킬 추천 사용:** 이 스위치를 켜면 JEV 사용과 내장 스킬 분류 프리셋이 함께 켜집니다.
- **대체 평가자:** 고르지 않아도 됩니다. 고른 모델과 다른 모델(설치된 어느 공급자의 것이든)을 골라 서명합니다. 고른 모델이 조언하지 못하는데 다시 불러도 나아지지 않는 경우(key 없음, key 거부(HTTP 401·403), 응답 형식 오류, 그 밖의 HTTP 4xx, 너무 큰 입력·응답)에 JEV가 대체 평가자로 전환할 수 있습니다. 요청당 한 번 전환하며 같은 정보를 보냅니다. 대체 평가자에서 통신 오류가 나면 그 평가자를 다시 부를 수 있습니다. 고른 모델이 있어야 하고 그 모델과 달라야 합니다.
- **JEV가 평가하지 못할 때.** 통신 오류(연결 실패, 끊김, 응답 전 시간 초과, HTTP 429·5xx)가 발생하면 같은 평가자를 다시 부를 수 있습니다. 유효한 `Retry-After` 값이 있으면 그만큼 기다리고, 그 외에는 호출 간격을 늘립니다. 요청 기한(`sennard.jev.retry.deadline`, 기본 60초), 시도마다 적용되는 예산, 요청의 유효성에 따라 재시도를 제한합니다. 이미 시작한 호출은 끝까지 진행합니다. 대체 평가자를 쓸 수 있는 오류라면 설정된 대체 평가자를 부릅니다. 조언을 얻지 못하면 에이전트가 직접 고릅니다.
- **key:** 공급자별 JEV key(TypeSafe는 `JEV_API_KEY`)는 이 페이지에 등록한 값만 씁니다. 같은 이름의 환경 변수는 JEV에 쓰지 않습니다. 페이지에는 지문만 보이고 값은 암호화해 저장합니다.
- **보기만 하는 정보:** JEV 사용액, 모델 목록과 갱신 상태, JEV에 보내는 항목.

## 편집 관문 예외 경로

- **편집 관문 예외 경로:** 이 페이지에서 서명한 목록만 씁니다. 환경 변수나 서버 설정이 예외 경로를 더하지 않습니다. 저장한 목록은 다음 편집부터 적용됩니다. 예외 경로를 읽지 못하면 예외를 하나도 더하지 않습니다.
- **예외 경로는 사용자만 정합니다.** 서명한 목록은 이 페이지에서 패스키로 저장한 것만 쓰며, 에이전트가 MCP 도구로 바꿀 수 있는 도구는 없습니다. 기본값은 빈 목록이라 아무것도 더하지 않습니다.
- **경로 적는 법.** Windows 경로(`D:\work\notes`), POSIX 경로(`/home/me/notes`), Git Bash의 드라이브 경로(`/d/work/notes`)를 적을 수 있습니다. Windows의 Git Bash가 쓰는 `/tmp`처럼 드라이브가 없는 경로는 그 문자열 그대로 적습니다. 이 경로는 Git Bash 셸이 쓴 경로와 문자열로 비교하고, 파일 시스템의 경로로는 비교하지 않습니다.
- **맞추는 방식.** 경로 구분자 단위로 맞추므로 `/tmp`는 `/tmp/a`에 해당하고 `/tmpx`에는 해당하지 않습니다. 비교 전에 `..`을 풀므로 `/tmp/../etc/a`는 `/etc/a`로 판정하고, 루트를 넘는 `..`은 루트에서 멈춥니다.

## 수렴 한도

- **두 값이 같은 작업을 몇 번까지 반복할 수 있는지 정합니다.** workflow마다 epoch당 전체 시도 횟수와 열 수 있는 epoch 수가 정해져 있습니다. 한 epoch의 시도를 모두 쓰면 다음 전체 시도 전에 독립 검토가 필요하고, 마지막 epoch 뒤에는 검토만으로는 한도가 다시 채워지지 않습니다.
- **기본값은 epoch당 3회, epoch 2개입니다.** 이 페이지에서 서명한 값이 없는 동안 적용됩니다.
- **각 값은 1 이상의 정수이고 상한은 없습니다.** 0, 음수, 소수, 문자열은 서명을 요청하기 전에 거절합니다.
- **전체 시도 한도는 workflow의 수렴 root를 열 때 고정됩니다.** 서버는 저장한 epoch당 시도 횟수와 epoch 수를 새 root의 frame에 넣고, 에이전트가 적은 값은 대체합니다. 고정된 값은 workflow 상태에서 볼 수 있습니다.
- **Stop 재점검에는 현재 설정의 epoch당 시도 횟수를 적용합니다.** 호스트가 계속 진행할 수 있는 Stop마다 서버는 현재 설정을 읽어 점검을 통과하지 못한 workflow 또는 관문이 선택되지 않은 입력을 확인합니다. 두 경우의 재점검 횟수는 각각 집계하며, workflow의 전체 시도 횟수와는 별도입니다.
- **한도는 사용자만 정합니다.** 이 페이지에서 패스키로 서명한 설정만 쓰며, 에이전트가 MCP 도구로 바꿀 수 있는 도구는 없습니다.

Sennard가 Claude Code 훅을 등록할 때 Claude Code 사용자 `settings.json`의 `env.CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`을 문자열 `"0"`으로 설정합니다. 이 설정은 Claude Code 자체의 연속 Stop 훅 차단 횟수 제한을 끕니다. 이미 다른 값이 있으면 확인 창에 현재 값을 표시합니다. 창을 열 수 없으면 터미널에서 확인합니다. 거절하거나 응답을 받을 수 없으면 파일을 쓰기 전에 설정을 중단합니다. Claude Code 사용자 `settings.json`이 Sennard 설치 루트 바깥에 있으면 제거 후에도 이 설정값이 남습니다. 파일이 설치 루트에 직접 있거나 그 하위 폴더에 있으면 제거할 때 설치 루트와 함께 삭제됩니다. 파일이 남아 있으면 `env`의 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` 항목을 지우거나 값을 바꿔 설정을 되돌릴 수 있습니다.

## 차단된 워크플로 계획

**일반 설정**의 수렴 한도 아래에 이 목록이 있습니다. 화면에는 「해제 전까지 같은 작업 폴더에서 같은 종류의 워크플로에 동일한 계획을 다시 제출할 수 없습니다.」라고 표시됩니다.

각 항목에 **작업 폴더**, **워크플로 종류**, **계획 SHA-256**, **차단된 워크플로**, **이유**, **차단 시각**이 표시됩니다. 계획을 다시 제출할 수 있게 하려면 해당 항목의 **패스키로 해제**를 눌러 패스키로 확인합니다.

## 서버 JVM 프리셋

- **한 값이 가비지 컬렉터와 힙을 정합니다.** 서버 JVM은 프리셋으로 설정합니다: 힙이 224MB·512MB·1GB·2GB·4GB인 G1, 힙이 4GB인 ZGC, 힙이 메모리의 약 6%인 ZGC. JVM 옵션을 적는 칸은 없습니다. 페이지는 이 값만 내놓고, 서명한 변경도 다른 값은 가리킬 수 없습니다.
- **처음 값은 설치 프로그램이 한 번 정합니다.** `sennard install`은 JVM에서 이 컴퓨터의 전체 메모리를 한 번 읽어 가장 가까운 표준 크기(4, 8, 12, 16, 24, 32, 48, 64, 96, 128, 192, 256GB …)로 올림한 뒤, 그 크기 이하에서 가장 큰 등급의 프리셋을 고릅니다: 4GB 이하 G1 224MB, 8GB G1 512MB, 16GB G1 1GB, 32GB G1 2GB, 64GB G1 4GB(ZGC 4GB를 고를 수 있음), 128GB 이상 ZGC 메모리의 약 6%. 두 등급 사이 크기(12·24·48·96GB)는 아래 등급을 따릅니다. 서버는 기동할 때 메모리를 재지 않습니다.
- **메모리는 항상 추정으로 보입니다.** JVM이 알려 주는 값은 운영체제가 JVM에 주는 값이라 실제 장착된 RAM보다 작으므로, 페이지에는 예를 들어 「추정 메모리 32GB (JVM에서 확인된 용량 29.7GB 기준으로 산정되었습니다. 실제 장착된 RAM 용량과 다를 수 있습니다.)」로 보입니다.
- **저장한 값은 다음 시작부터 적용됩니다.** 서명이 기록된 뒤 서버 옆의 `sennard-jvm.yaml`에 씁니다. 적용하려면 서버를 다시 시작합니다(`sennard stop`, `sennard start`). 업그레이드는 이 파일을 가져갑니다. 다시 설치한 직후의 첫 기동은 설치 프로그램이 고른 값을 쓰고, 서버는 저장소가 준비되면 서명한 프리셋을 파일에 다시 써서 다음 기동부터 쓰게 합니다.
- **서버 JVM은 UTC로 돌고 GC 로그를 남깁니다.** 설치 폴더에 `jvm-gc.log`(JVM이 회전, 10MB 5개)와 AOT 캐시 로그 `jvm-aot.log`를 씁니다. AOT 캐시는 설치 때 고른 컬렉터용으로 만들어, 컬렉터를 바꾸면 다음 업그레이드가 캐시를 만들 때까지 캐시 없이 기동하고 `jvm-aot.log`에 그 사실이 남습니다. `sennard` 명령은 사용자가 직접 실행하는 `java -jar`이며 프리셋을 따르지 않습니다.

## 업무 데이터베이스

**업무 데이터베이스** 화면은 저장소의 상태(데이터베이스 대기 중, 접속 중, 테이블 준비 중, 준비 완료, 실패), 마지막 실패의 사유, 저장된 연결을 보여 줍니다. 데이터베이스를 연결하는 곳도 이 화면입니다. JDBC 드라이버, URL, 계정, 비밀번호 파일, 보호 방식을 적습니다(항목별 설명은 상태 문서의 [업무 데이터베이스](state.ko.md#업무-데이터베이스) 참고). 연결은 업무 데이터베이스를 지정하는 유일한 곳이며 상태 폴더의 설정 데이터베이스에 저장됩니다. `sennard.yaml`은 업무 데이터베이스를 지정하지 않습니다.

- **처음 연결.** 첫 패스키를 등록한 뒤 그 패스키로 연결을 저장합니다. Sennard가 백그라운드에서 접속해 테이블을 준비하며, 저장소가 준비되거나 실패할 때까지 화면이 따라갑니다. 실패한 연결은 같은 화면에서 다른 연결로 바꿀 수 있습니다.
- **연결 바꾸기.** 데이터베이스가 준비된 상태에서도 언제든, 새 연결을 패스키로 저장해 바꿀 수 있습니다. 저장하기 전에 Sennard가 새 연결이 가리키는 데이터베이스에 접속해 보고 그곳에 테이블을 준비합니다. 이것이 실패하면 아무것도 저장하지 않고 이전 연결이 남습니다. 실행 중인 저장소는 바꿔 끼우지 않습니다. 저장한 연결은 Sennard 서버를 다시 시작한 뒤부터 쓰이며(`sennard stop` 다음 `sennard start`), 그때까지 화면이 그 사실과 다음 행동을 알려 줍니다. 이전 데이터베이스의 기록은 새 데이터베이스로 옮겨지지 않습니다.

## 언어

모델이 읽는 Sennard 문구는 언어 설정 없이 문구마다 토큰이 적은 형태 하나로 고정됩니다. hook 안내, MCP 도구 설명·결과, 스킬 검사 출력, 스킬 description은 영어입니다. MCP instructions의 공통 접수 기준은 한국어입니다(영어가 토큰은 적지만 호스트가 instructions를 자르는 길이를 넘습니다). 사용자에게 보이는 답은 에이전트가 사용자의 언어로 씁니다. 관리자 페이지는 요청의 언어를 따릅니다. 브라우저의 언어 설정에 따라 영어 또는 한국어로 표시되고, 그 밖의 언어이거나 브라우저가 언어를 밝히지 않으면 영어로 표시됩니다. 모든 화면과 루프백 주소로 접속한 방문을 localhost로 옮기는 페이지, 페이지 제목에 적용됩니다.
- 페이지 머리말의 언어 전환(한국어 / English)으로 페이지의 언어를 고릅니다. 고른 값은 페이지의 쿠키(`sennard-admin-language`, `en` 또는 `ko`, `SameSite=Strict`, 스크립트에서 읽을 수 없고 다른 값은 담지 않음)에 저장되어 브라우저 언어보다 먼저 적용되며, 고른 적이 없으면 브라우저 언어를 따릅니다. 바꾸면 페이지를 다시 그리며, 저장하지 않은 편집이 있으면 먼저 확인을 받고 거절하면 아무것도 바꾸지 않습니다. 서버의 서명하는 설정이 아닙니다.
- 표시 언어 설정은 없습니다.

## 패스키를 모두 잃었을 때: 재설정

HTTP나 MCP로는 재설정할 수 없습니다. 같은 컴퓨터에서 Sennard를 설치한 OS 사용자로 `sennard admin-reset`을 실행합니다. `--yes` 없이 실행하면 무엇이 보관되는지만 보여 주고 아무것도 쓰지 않으며, `sennard admin-reset --yes`가 실제로 재설정합니다. 두 방식 모두 실행 중인 서버가 쥐고 있는 설정 데이터베이스를 열므로, 명령은 먼저 이 설치본의 서버가 실행 중이면 멈추고 출력에 그 사실을 알립니다(서버가 실행 중이 아니면 아무것도 멈추지 않습니다). 서버는 다음 hook 호출 때 다시 시작됩니다. 명령이 데이터베이스를 여는 시점에 서버가 아직 종료 중이거나(포트가 닫힌 뒤에도 서버가 설정 데이터베이스를 놓기까지 시간이 걸립니다) 이미 다시 시작되어 있으면 `ADMIN_RESET_SETTINGS_LOCKED`로 끝나며 아무것도 바꾸지 않습니다. 명령을 다시 실행합니다.

경우는 둘이며, 명령은 사실 하나로 어느 쪽인지 가립니다. 업무 데이터베이스가 한 번이라도 준비된 적이 있는지입니다.

- **업무 데이터베이스가 한 번도 준비된 적이 없을 때**(패스키를 처음 등록한 뒤 첫 연결이 성공하기 전에 잃은 경우, 연결이 실패한 채로 잃은 경우 포함): 서명된 기록은 상태 폴더 아래 설정 데이터베이스에만 있고 업무 로그는 아직 없습니다. 이때 `sennard admin-reset`은 업무 데이터베이스가 필요 없고, 업무 데이터베이스가 아예 지정되지 않았어도 됩니다. 패스키 등록부를 비우고 연결 전에 만든 기록을 설정 데이터베이스의 보관 표로 옮깁니다. 권한은 설정 데이터베이스가 Sennard를 설치한 OS 사용자의 파일이라는 점에서 나옵니다. 페이지에서 저장한 연결 설정은 서명된 기록이 아니므로 그대로 남고, 새 첫 키를 등록한 뒤 다시 연결할 수 있습니다.
- **업무 데이터베이스가 한 번이라도 준비된 뒤:** 로그가 업무 데이터베이스에도 있어 그것까지 보관해야 하므로, 명령에는 업무 데이터베이스와 그 계정의 비밀번호 파일이 필요합니다. 데이터베이스에 닿지 않으면 명령은 `ADMIN_RESET_DATABASE_UNREACHABLE`로 끝나며, 데이터베이스에 닿게 한 뒤 다시 실행합니다.

- 기록 전체를 보관 표로 옮기고 재설정 사실을 남깁니다. 대기 중인 요청은 거절 처리합니다. 페이지에서 등록한 JEV key도 지웁니다.
- 사람이 정한 항목은 모두 기본값으로 돌아갑니다. 재설정으로 권한을 얻을 수는 없으며, 다시 첫 패스키를 등록해야 저장할 수 있습니다.
- 재설정 사실은 페이지 상단에 계속 보입니다.

## 막지 못하는 것

다음은 같은 OS 사용자로 도는 프로그램(에이전트 포함)의 의도적 공격입니다. 이 설계는 이런 시도를 막지 못하고 드러나게만 합니다.

- **첫 패스키 선점:** 키가 하나도 없을 때 같은 컴퓨터의 프로그램이 먼저 등록하면 그 키가 첫 키가 됩니다. 키가 이미 있으면 새 첫 등록은 `ADMIN_ALREADY_BOOTSTRAPPED`로 거절됩니다.
- **재설정 뒤 첫 키 등록:** 같은 OS 사용자로 도는 프로그램은 패스키 없이 `sennard admin-reset --yes`를 실행할 수 있습니다. 서명 기록이 보관되고 서명된 항목은 모두 기본값으로 돌아가며, 대기 중인 요청은 거절 처리되고 JEV key는 지워집니다. 그 뒤 그 프로그램이 자기 키를 첫 키로 등록할 수 있습니다. 재설정 사실은 페이지 상단에 계속 보입니다.
- **설치 파일 패치:** Sennard 설치 파일을 고치면 검증 자체를 건너뛸 수 있습니다.
- **기록 전체 교체:** 같은 OS 사용자는 DB 자격 증명을 읽어 서명 기록을 통째로 바꾸고 자기 키를 첫 키로 심을 수 있습니다. 최초 등록 시각·지문이 바뀌므로 페이지에서 드러납니다.
- **꼬리 자르기:** 마지막 기록 몇 개를 지우면 이전 판이 유효해 보입니다. 상주 MCP 서버는 자기가 본 기록보다 줄면 `ADMIN_LOG_REGRESSED`로 알리지만, 그 서버가 다시 시작된 뒤에는 알 수 없습니다.
- **같은 OS 사용자의 JEV key 읽기:** key는 암호화해 두지만 데이터 키 파일도 같은 사용자 폴더에 있어, 함께 읽으면 값을 풀 수 있습니다. 암호화가 막는 것은 저장소 내용만 따로 복사되거나 읽힌 경우입니다.
- **요청 거절:** 같은 컴퓨터의 프로그램이 대기 중인 요청을 거절할 수 있습니다. 그것으로 바뀌는 설정은 없습니다.
- 담당 컨텍스트 본문은 에이전트가 쓰므로 서명 대상이 아닙니다.

보기(`GET /`, `GET /api/state`)는 패스키 없이 열립니다. 같은 컴퓨터의 사용자와 에이전트는 저장소를 직접 읽을 수 있으므로 보기를 막아도 얻는 것이 없습니다. 다른 웹 페이지가 읽거나 쓰는 것은 Host·Origin 검사 등으로 막습니다.
