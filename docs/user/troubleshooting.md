# Troubleshooting

| Symptom | What to check |
| --- | --- |
| Skills or MCP tools are not visible | Check with `sennard status` whether the server is installed. Check that you started a new session after installation or after the server came up, and that the plugin and MCP are enabled in the host. If the server was not running when a session started, that session is not connected to it later. |
| The MCP server does not start | See [Resident server](#resident-server) below. |
| `sennard install` ends with `INSTALL_ROOT_NOT_REPRESENTABLE` or `STATE_DIR_NOT_REPRESENTABLE` | The folder has a letter that the system's file name encoding (`native.encoding`) cannot write. Set `SENNARD_INSTALL_ROOT` or `SENNARD_STATE_DIR` to a folder it can write. See [Folder the system encoding cannot write](#folder-the-system-encoding-cannot-write) below. |
| `sennard` ends with `NOT_A_RELEASE_JAR` or `JAVA_EXECUTABLE_UNKNOWN` | `NOT_A_RELEASE_JAR`: run the command as `java -jar sennard-<version>.jar <command>` from the release jar, not from a folder of classes. `JAVA_EXECUTABLE_UNKNOWN`: the JVM did not report the `java` program it runs from; start `java` by its full path. |
| Guidance, the status board, or messages do not work in Codex | Check in `/hooks` that you have reviewed and trusted the Sennard hooks. After updating to a release that changes the hook definitions, you must trust them again. |
| Antigravity installation fails | Close the app and install the installation package attached to the release. Do not install the entire repository. |
| The Sennard hooks and MCP tools are gone after a plugin was installed or updated | The plugin ships empty definitions, and the host replaces this PC's definitions with them whenever it copies the plugin. Once the plugin packages and installed server match exactly, run `sennard hooks` and start a new session. `hostCopiesWithoutDefinitions` of `sennard status` names the copies that are empty. If you removed Sennard, also remove the Sennard plugin from the host. [Plugin updates and `sennard hooks`](update.md#plugin-updates-and-sennard-hooks) |
| A file edit is rejected because a workflow is required | Open the workflow the refusal names: for a change, give `start_workflow` the objective, stages, `skills`, acceptance criteria and `writeTargets` (and `changePlan` with the file), or resume an open change workflow whose plan has the file with `resume_workflow`. A request with no workflow at all is held before tool use or when the agent attempts to stop until it opens or resumes one (`start_inquiry_workflow` for an answer, `start_operation_workflow` for a run). If the work differs from the workflow in progress, start another one with a non-overlapping scope. [Edit gate](usage.md#workflows-and-the-edit-gate) |
| Cannot start because of `ROOT_CONFLICT` | Check the existing workflow, its status, and the next action in the error `details`. Call `release_convergence_root` to release your own workflow. Use the tool to release another session's workflow only when its owner is offline and the user has made a decision. The user can release an open workflow on the admin page under **Work → Workflow management**. |
| An execution attestation error such as `BINDING_REQUIRED` occurs | Check the host-specific causes in [Execution attestation and host connection](../contributing/execution-attestation.md). Model selection advice and execution attestation are separate. |
| The model selection in `coordinate-subagents` withholds a call because of insufficient support information | Check the evidence for the model and reasoning support of the current host. Do not infer the actual application from the catalog or from requested values. |
| The admin page does not open | Check with `sennard status` that the server is running, that you opened the page with `localhost`, and that you opened the current address. The page's port changes each time the server starts; the address is the `adminPage` value of `sennard status`, and it is also in the guidance the agent received and in `adminUrl` in a request response. [Admin page and context](admin-page.md#opening-the-page) |
| I lost my passkey and the admin page shows an integrity failure, or I lost the passkey before the business database was linked | Run `sennard admin-reset` as the OS user who installed Sennard (add `--yes` to perform it). Before the business database has ever been ready it needs no business database; afterwards it needs the database, and ends with `ADMIN_RESET_DATABASE_UNREACHABLE` if it cannot be reached. It stops the running server first (the next hook call starts it again); if the server is still shutting down or has come back when the command opens the settings database, it ends with `ADMIN_RESET_SETTINGS_LOCKED` and you run it again. [Resetting when all passkeys are lost](admin-page.md#resetting-when-all-passkeys-are-lost) |
| JEV is not shown as "On" | Fill in the missing conditions that the page lists (JEV use turned on, model, permission to send information, key, budget, preset). [JEV](admin-page.md#jev-skill-selection-advice) |
| A hook reports "verification failed · rN in use" | On the admin page, check the target marked with a red band and choose [Sign and adopt] or [Discard]. Agents cannot fix this. |
| Other sessions are not visible, or a message receives only an ACK | Check hook trust and the wake method of each host, and query the status with the same `messageId`. Request the actual work result separately. [Session collaboration](collaboration.md) |
| Old behavior remains after an update | Check that `versions` in `sennard status` shows the new release and that the plugin was updated as well, and connect through a new session as described in the [update procedure](update.md#update-procedure). |
| Two Sennard MCP servers appear in Antigravity after an update | Restart the app and open a new conversation. |

## Resident server

MCP and hooks share one resident server per user and PC (Spring Boot, `127.0.0.1`). Neither its port nor the admin page's is fixed: the operating system assigns a free port to each at every start, so there is no port conflict to resolve. The server announces its address in `server.properties` in the state folder (`port`, `pid`, `processStart`) and removes the file when it ends; the hook client and the MCP relay read it at each call, and ignore it when the process it names is not alive with that start time. Only one server runs on a state folder: a second one ends with `SERVER_ALREADY_RUNNING`. Sennard does not register an OS service; the installer, `sennard start`, or a session-start hook starts the server.

`sennard status` shows the installation folder, version, command path, port, `healthy`, store readiness (`store`), and the current address of the admin page (`adminPage`) as JSON. The server log is at `logs/sennard-server.log` under the state folder (default `~/.sennard/logs/sennard-server.log`). It records warnings and startup failures. By default, it rolls over daily or at the 10 MB size threshold. The archive policy retains up to 7 daily periods and caps archived logs at 100 MB in total, excluding the active log. Check the separately configured business database's logs with its administrator.

| Symptom | Check and action |
| --- | --- |
| `Sennard server is not reachable.` appears at session start, or Sennard tools end with a call error | The session-start hook tried to start the installed server and could not: Sennard is not installed, the installed jar could not be started with `java`, the store could not be prepared (`FAILED`), or the server was not ready within 30 seconds. Check the server with `sennard status` and the log under the state folder. If it is stopped, run `sennard start`; if Sennard is not installed, run `sennard install`. Restart the session after the server is up (a server that was still starting when the hook gave up is usually ready by then). |
| A tool call is refused with `The Sennard server refused to check this tool call (...)` | The server is running but refused the call that checks the tool (for example, two requests tried to create the session's first record at the same moment, or the store could not answer). The tool did not run and nothing was changed. Try the same call again. If it keeps being refused, look up the error code on the admin page or in the server log (the line `HOOK_GATE_REFUSED <code>`). |
| A tool call is blocked with `The Sennard hook could not verify this tool call (...)` | The hook client could not obtain a decision. The reason includes the failure code. For `SERVER_NOT_REACHABLE`, check the server with `sennard status` and retry after it is running and responsive. If the error recurs, check the admin page or the server log. |
| `sennard install` or `sennard start` ends with `START_FAILED` | The message names the cause: another start of the server was not done within the wait (`otherStartPending`), the server was not ready within the wait or did not become healthy (it names the address file), or the program could not be started. Check the log under the state folder and `sennard status`, then run `sennard start`. A port cannot be the cause, because the operating system assigns a free one at each start. If another server already holds the state folder, the start ends with `SERVER_ALREADY_RUNNING`. If the first installation stopped this way, then run `sennard hooks`. |
| `sennard install` is rejected with `ALREADY_INSTALLED` | Sennard is already installed. To switch to a new release, update the installed host plugins to the target version before running the new JAR's `upgrade` command. [Update procedure](update.md#update-procedure) |
| A tool returns `STORE_PREPARING` | The configured store is being prepared. Check the stage in `store` of `sennard status` and wait. If the stage is `NOT_CONFIGURED`, no business database is linked: link it on the admin page ([Business Database](state.md#business-database)). |
| The `store` stage is `FAILED`, or `STORE_PREPARATION_FAILED` occurs | Check `reason`, fix the cause, and run `sennard prepare --retry`. If the link itself is wrong, save a corrected one on the admin page (before the database has ever been ready, the store prepares with it at once). |
| `STORE_POOL_EXHAUSTED` | DB connections are temporarily insufficient. The request is processed when retried. |

## Folder the system encoding cannot write

The installer passes the installation folder, the state folder, and the jar to `java` on its command line. The `java` launcher of Windows reads its command line in the system's file name encoding (the JDK's standard property `native.encoding`; on Windows the ANSI code page, the "Language for non-Unicode programs" setting), so a folder with a letter that encoding cannot write would reach the program as another folder. Sennard decides this by asking the JVM, not by the name of the operating system: the path is accepted when the encoder of `native.encoding` can write all of it.

- `sennard install` ends with `INSTALL_ROOT_NOT_REPRESENTABLE` when the installation folder (`~/.sennard/install`, or `SENNARD_INSTALL_ROOT`) cannot be written in that encoding. Sennard installs nowhere else: set `SENNARD_INSTALL_ROOT` to a folder that can be written in it (an ASCII-only folder always can) and run the command again.
- A state folder that cannot be written in it ends with `STATE_DIR_NOT_REPRESENTABLE`: set `SENNARD_STATE_DIR` (or `sennard.state-dir` in `sennard.yaml`) to a folder that can be written in it. See [Storage Location](state.md#storage-location).
- The folder that holds the downloaded jar is not checked by this rule. The installation passes the jar's path to a child `java` when it extracts the jar, so a jar folder with a letter that the encoding cannot write may make `sennard install` end with `INSTALL_FAILED` (`Could not extract ...`). This was not measured; if it happens, copy the jar to a folder the encoding can write.

The release jar test (`jarRun`) runs `install`, `status`, `start`, `stop`, `upgrade`, and `uninstall` in a folder whose name is outside ASCII, made from letters that the encoding of the test PC can write. It was run on Windows only.
