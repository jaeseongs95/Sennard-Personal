# 세션 협업

같은 컴퓨터에서 같은 OS 사용자로 실행한 Sennard 세션끼리 현황판으로 서로를 찾고 PEER 메시지를 주고받습니다. 호스트가 달라도(Claude Code·Codex·Antigravity) 같은 상주 서버를 쓰므로 함께 협업할 수 있습니다. 메시지 상태와 저장 한도의 기술 계약은 [세션 메시지 계약](../contributing/session-messaging.ko.md)에 있습니다.

## 현황판

- `update_session_status`로 이 세션이 지금 하는 일을 한 줄로 적고, `list_session_status`로 다른 세션의 호스트·세션 ID·작업 폴더·한 줄 요약·역할을 봅니다.
- Sennard는 `launch_managed_child`로 만든 Antigravity 대화를 호스트가 생성 시 반환한 대화 ID로 식별합니다. Antigravity 자체 서브에이전트는 Sennard 도구를 처음 호출해 훅과 MCP 요청이 일치하면 하위 대화로 식별합니다. 그전에는 요약과 역할이 없는 대화가 관리 페이지의 "구분 불가"에 표시될 수 있습니다. Claude Code는 훅 입력에서 서브에이전트(`agent_id`)와 `--agent` 세션(`agent_type`)을 식별합니다.
- 현황판 자체에는 요청 원문이 없습니다. 사용자의 메시지는 아래 「사용자가 한 말」의 원문 보관소에 따로 둡니다. 세션 ID와 작업 폴더는 hook 입력에서 채웁니다.
- 역할은 관리자 페이지에서 서명한 결속이 있으면 그 역할(`roleSource: "signed"`), 없으면 세션이 스스로 적은 역할(`roleSource: "self"`)을 보여 줍니다. 현황판의 역할은 접근 권한이나 실행 승인이 아닙니다.
- 현황판은 다시 읽어야 변경을 알 수 있는 pull 방식입니다. 실행 중인 다른 세션의 작업을 멈추게 하는 채널이 아닙니다.
- 끝난 세션은 요약이 있어도 현황판에 나오지 않습니다.

## 사용자가 한 말

- 사용자가 주 세션에 한 메시지는 hook이 이 컴퓨터의 Sennard 데이터베이스에 원문 그대로 보관합니다. 서브에이전트의 입력과 에이전트의 답변은 보관하지 않습니다. 1 MiB를 넘는 메시지는 글자 경계에서 잘라 보관하고 잘렸다고 표시하며, 전체 크기와 전체의 SHA-256 요약값을 함께 적습니다. 서비스는 보관된 원문을 바꾸거나 지울 수 없습니다. 서비스의 데이터베이스 역할은 읽기와 추가만 할 수 있습니다.
- Antigravity의 첫 Sennard MCP 호출이 같은 대화의 최근 도구 훅과 일치하면 주 세션임을 확인할 수 있습니다. 그 전까지 서버는 입력을 최장 30분 동안 전체 64 MiB 한도의 메모리에 보류합니다. 주 세션으로 확인되면 보류한 입력을 훅에서 받은 시각과 함께 보관합니다. 확인 전에 서버가 재시작되거나 보류 한도에 도달하거나 보류 시간이 지나면 원문이 유실될 수 있습니다. 하위 대화로 확인된 입력은 원문 보관소에 넣지 않습니다.
- 턴이 끝나면 에이전트가 `record_turn_recap`으로 한 일을 짧은 요약 한 줄로 기록합니다(한글·한자·가나는 100자, 그 밖의 글자는 250자 이하, 섞이면 가중 합계로 셈). 기록하지 않았으면 메시지마다 한 번, 턴을 이어 가며 기록을 요청합니다. 세션 현황판의 한 줄 요약도 필수입니다. 사람이 세션 목록으로 각 세션이 지금 무엇을 하는지 알아야 하기 때문입니다. 메인 세션의 요약이 없거나 마지막 메시지보다 오래됐으면, hook이 요청을 실을 수 있는 때마다 `update_session_status`로 요약을 쓰라고 요청합니다. 메시지가 들어올 때, 도구 실행이 끝날 때, 모델 호출이 끝날 때, 턴이 끝날 때(리캡 요청과 같은 이어 가기에서 하며, 호스트가 이미 한 번 이어 간 턴의 끝에서는 하지 않습니다)입니다. 요약이 마지막 메시지보다 새로워지면 요청이 멈춥니다. 요청 원문이나 비밀을 적으라고는 하지 않습니다. 서브에이전트는 메인 세션의 요약을 따릅니다. 같은 메시지에 다시 기록하면 앞의 요약을 바꿉니다. 기록은 메인 에이전트만 하며, 서브에이전트가 부르면 거절합니다. 요약은 에이전트의 주장이며 사용자의 말이 아닙니다.
- `recall_user_prompts`는 메시지를 최신 순으로 읽고, 메시지마다 기록된 요약을 함께 줍니다. `query`는 메시지의 일부를 영문 A–Z의 대소문자는 구분하지 않고(다른 글자는 정확히 맞아야 합니다) 찾고, `limit`은 기본 20, 최대 100입니다. `scope: "SESSION"`(기본)은 이 세션의 메시지를, `scope: "ROLE"`은 관리자 페이지에서 사용자가 이 세션과 같은 역할에 묶은 모든 세션의 메시지를 읽습니다. 세션이 스스로 적은 역할은 인정하지 않고, 서명된 결속이 없는 세션은 거절합니다.
- `read_prompt_transcript`는 이 세션이 받은 메시지 하나 뒤에 에이전트가 한 일을 호스트가 직접 기록한 트랜스크립트에서 읽어 줍니다. 에이전트의 글, 도구 호출, 도구가 돌려준 결과를 사용자의 다음 메시지까지 보여 줍니다. `promptId`는 `recall_user_prompts`가 돌려준 값이고, `limit`은 기본 20, 최대 100이며, 각 텍스트는 2000자에서 잘라 잘렸다고 표시합니다. 메시지 뒤의 트랜스크립트는 그 메시지를 받은 세션만 읽을 수 있습니다. 다른 세션에서 한 말은 역할 결속과 관계없이 거절합니다. Sennard는 트랜스크립트 안에서 그 메시지가 있는 위치만 저장하고 트랜스크립트의 복사본은 저장하지 않으며, 호스트가 메시지를 전달할 때 알려 준 파일에서 읽습니다. `status`는 `LOCATED`(항목이 따르며, 턴이 항목 뒤로 이어지면 `more`가 true), `NOT_YET_WRITTEN`(트랜스크립트에 이 메시지의 항목이 아직 없으니 나중에 다시 요청), `UNSUPPORTED`, `UNREADABLE`(`reason`과 함께) 중 하나입니다. 각 항목에는 `key`가 있으며, `more`가 true이면 마지막 항목의 `key`를 `after`로 넘겨 그다음 항목부터 이어 읽을 수 있습니다(그 메시지의 턴에 없는 키는 거절합니다). 6.0.0은 Claude Code의 트랜스크립트만 읽으며, Codex·Gemini CLI·Antigravity는 `UNSUPPORTED`입니다.
- 턴의 내용에 이후 세션이 알아야 할 결정이나 교정이 있으면 에이전트가 `checkpoint_context` 또는 `checkpoint_role_context`로 저장하도록 안내합니다. 원문 보관소는 한 말의 기록이며 공유 컨텍스트를 대신하지 않습니다.

## 메시지 보내기

에이전트에게 「현황판에서 ○○ 담당 세션을 찾아 PEER 메시지로 검토를 요청해 줘」처럼 요청하면, 에이전트가 다음 도구를 씁니다.

| 도구 | 하는 일 |
| --- | --- |
| `prepare_session_message` | 대상·본문·TTL을 고정하고 시스템이 발급한 `messageId`를 받습니다. 전달 효과는 없습니다. |
| `send_session_message` | 발급받은 `messageId`만 넘겨 전송합니다. |
| `get_session_message_status` | 같은 `messageId`로 전달·ACK 상태를 봅니다. |
| `acknowledge_session_messages` | 받은 쪽이 메시지를 처리했다고 확인합니다. |
| `recall_session_message` | 받는 쪽이 아직 가져가지 않은 자기 메시지를 회수합니다(메일 발송 취소와 같습니다). |

이 도구들은 호스트가 현재 세션의 신원을 확인한 뒤에 사용할 수 있습니다. `BINDING_REQUIRED`가 반환되면 호스트 훅이 실행된 현재 세션에서 다시 시도하세요.

- 메시지는 전송, 본문 전달, 처리 확인(ACK)을 따로 기록합니다. **ACK는 메시지를 처리했다는 확인일 뿐, 작업 완료나 실행 승인이 아닙니다.** 검토 결과와 근거는 별도 메시지로 받습니다.
- 받는 세션이 오프라인이면 보낸 세션은 기다리며 멈추지 않고 답이 필요 없는 일을 계속합니다.
- 결과가 불분명한 메시지를 새 ID로 다시 보내지 않습니다. 같은 `messageId`로 상태를 조회하거나 send를 다시 시도합니다. 새 ID로 보내면 한 의도가 두 메시지로 전달될 수 있습니다.
- 본문은 UTF-8 4096 byte까지입니다. TTL은 30초~24시간이며 기본 1시간입니다.
- 받는 쪽에서 메시지는 도구 경계나 턴이 끝날 때 전달됩니다. 사용자 입력 직후에는 다음 도구 경계 한 번을 미룹니다.

## 관리형 자식 대화 만들기

실행 중인 메인 세션에서 호스트가 지원하는 모델과 추론 수준으로 `launch_managed_child`를 호출합니다. 연결된 호스트 워커가 요청을 수락하면 `CREATED` 결과에 새 `childId`가 담깁니다. 생성된 대화는 대기합니다. 작업을 보낼 때는 메인 세션의 호스트와 세션 ID를 PEER 목적지로 지정하고 반환된 `childId`를 `targetActorId`에 넣습니다. 자식은 PEER로 메인 세션에 답하고 자신이 처리한 메시지에 ACK를 보냅니다.

Antigravity 관리형 대화에는 호스트의 기존 `agy` 로그인과 권한 규칙이 적용됩니다. 워커는 같은 ACP 연결에서 그 대화를 재개합니다. 사용자 확인이 필요한 도구 호출은 취소됩니다. 사용자 확인 없이 PEER 도구를 호출하려면 Antigravity에서 해당 도구 사용을 허용해야 합니다. [Antigravity MCP 권한](https://antigravity.google/docs/cli/mcp/#mcp-permissions-and-access-control)을 참고하세요.

호스트가 선택값을 지원하지 않으면 `SELECTION_UNSUPPORTED`, 워커가 생성 요청을 보내지 못하면 `NOT_SENT`가 반환됩니다. 결과가 `UNKNOWN`이거나 응답을 받지 못했으면 같은 `operationKey`와 입력으로 저장된 결과를 조회합니다. 새 키는 별도의 대화를 만들 수 있습니다.

## 쉬고 있는 세션 깨우기

메시지를 넣은 뒤 쉬고 있는 세션을 깨우는 방식은 호스트마다 다릅니다.

| 호스트 | 기본 동작 |
| --- | --- |
| Claude Code | 대기 hook은 세션 시작과 턴 종료에 하나씩 두 개입니다. 세션이 시작된 때와 턴이 끝난 때부터 그 이벤트의 hook이 서버에서 메시지를 기다립니다. 메시지가 오면 그 메시지를 전달하면서 쉬는 세션을 깨웁니다. 세션이 다시 일을 시작하면 대기는 끝나고 메시지는 아래의 경계에서 전달됩니다. 한 번의 대기는 최대 24시간입니다. 그보다 오래 쉬었거나 그 사이에 Sennard 서버가 다시 시작됐다면, 다음 턴이 끝난 뒤부터 다시 깨울 수 있습니다. 이 동작은 사람이 붙어 있는 대화형 세션에서만 하며, `-p`로 띄운 세션은 깨우지 않습니다. SDK로 띄운 세션은 측정하지 않았습니다. 이 구분은 Claude Code가 훅에 넘기는 `CLAUDE_CODE_SESSION_ATTENDED` 값에 의존하며, 이 변수는 Claude Code 공식 문서에 없습니다(Claude Code 2.1.319에서 측정. 별도로 Windows의 Claude Code 2.1.316에서 측정한 값은 `-p` 세션 `0`, 사람이 붙은 대화형 세션 `1`). |
| Codex | 사용자가 선택한 native queue 깨우기입니다. 대상의 새 SessionStart 환경, native 실행 파일, 이 서버가 소유한 live 세대가 필요합니다. 준비되지 않으면 메시지는 일반 hook 경계를 기다립니다. |
| Antigravity | 대화형 메인 세션은 자체 훅의 연결값으로 `agentapi`를 사용합니다. 워커는 관리형 자식을 ACP로 깨웁니다. 호스트를 깨울 수 없으면 일반 전달 경계에서 메시지를 받습니다. |

`send_session_message` 결과와 `get_session_message_status`에는 조언용 `autoWake`가 붙습니다. 현황판의 세션에는 붙지 않습니다. 받는 세션의 깨우기 경로를 지금 쓸 수 있는지에 대한 사실만 알려 주며, 전달·처리·완료의 증거가 아닙니다.

- `available`: 대기 hook이 붙어 있거나 native 대상 연결과 live 세대가 준비되었습니다.
- `degraded`: 대상이 작업 중이거나 사전 조건이 없거나 이전 알림이 미관측 상태이거나 재시도 유예 중입니다. 전달 증거가 아닙니다.
- `unsupported`: native queue 선택이 꺼져 있습니다.
- `no-live-relay`: 사용할 대상 연결이나 소유한 live 세대를 알 수 없습니다. 본문은 일반 경계를 기다리며 세션이 꺼졌다는 증거는 아닙니다.

Codex의 이전 설정을 유지합니다. `AGENT_GOVERNANCE_CODEX_QUEUE_WAKE=1`은 활성화, `=0`은 비활성화입니다. 변수가 빈 값이거나 잘못된 값으로 존재하면 파일 설정으로 넘어가지 않습니다. 변수가 없으면 대상의 절대 `PLUGIN_DATA/session-messaging.json`에서 `{"schemaVersion":"1.0.0","codex":{"queueWake":true}}`를 읽을 수 있습니다(4096바이트 제한). 기본은 꺼짐입니다. 설정 변경이나 Sennard 서버 재시작 뒤에는 대상 세션을 다시 열어 hook이 새 연결을 넘기게 합니다.

대화형 AGY 메인 세션을 깨우려면 해당 훅이 `ANTIGRAVITY_PROJECT_ID`, 루프백 주소인 `ANTIGRAVITY_LS_ADDRESS`, `ANTIGRAVITY_CSRF_TOKEN`, 절대 경로인 `ANTIGRAVITY_AGENTAPI_EXE` 또는 노출된 PATH의 native `agy`를 제공해야 합니다. `ANTIGRAVITY_CONVERSATION_ID`가 있으면 대상과 일치해야 합니다. Sennard는 해당 훅이 제공한 값을 사용하며, 명령 인수·데이터베이스·진단 로그에 토큰을 남기지 않습니다. 이전 설치에서 자동 탐색을 사용했다면 호스트가 이 값을 제공해야 합니다. 표식 도착, 본문 인수와 ACK는 CLI 인계와 별도로 확인합니다. [native wake 상세와 복구](../contributing/native-idle-wake.ko.md)를 참고하세요.

`status.wake`는 항상 `null`입니다.

## 두 세션으로 확인해 보기

같은 프로젝트를 연 세션 두 개에 다음처럼 요청합니다. 코드는 바꾸지 않습니다.

```text
[검토 세션]
Sennard 현황판의 현재 작업을 "Sennard-DEMO-REVIEW · 테스트 실행 방법 검토"로 기록해 줘.
```

## 로컬 프로세스

세션 메시지는 사용자·PC당 하나인 상주 서버가 처리하고 서버의 저장소에 저장합니다. 메시지 전용 프로세스나 세션별 상주 프로세스는 없습니다. 세션의 생존 확인은 서버가 호스트 프로세스를 지켜보는 임대(lease)로 합니다. 호스트 자체나 외부 모델 서비스의 네트워크 사용은 이 메시징 구조와 별개입니다.

## 한계

- 같은 OS 사용자 권한의 프로그램은 서버의 DB 자격 증명을 읽어 DB를 읽거나 바꿀 수 있습니다. 세션 식별자는 인증된 사용자가 아닙니다.
- PEER 메시지는 승인·권한·외부 변경 의사를 대신하지 않습니다.
- 받는 모델이 메시지 업무를 정확히 한 번 실행한다는 보장은 없습니다.
