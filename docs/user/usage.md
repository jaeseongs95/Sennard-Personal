# Usage

After installing Sennard, assign work to your agent as usual. This document describes how to make requests, the behavior that changes after installation, workflows and the edit gate, work records, model selection for subtasks, and what Sennard does not do. For installation, see the [README](../../README.md#installation).

## How to Make Requests

State the result you want, the conditions to check, and the targets to preserve. The agent selects a workflow procedure for each request and chooses the skills the work needs.

```text
Revise this notice so that a first-time visitor can proceed through to a reservation.
Preserve the reservation conditions and contact details, and list the cases to check before making changes.
Report separately what was actually verified and what still requires human confirmation.
```

```text
Implement and verify this feature. First define the scope of changes and the completion criteria,
and in the final result include the checks that were actually run and any problems that remain unresolved.
```

To name a skill directly, write its name using the host's skill invocation syntax. For example, use `$orchestrator` in Codex and `/sennard:orchestrator` in Claude Code.

## What Changes After Installation

Sennard operates through a resident server (MCP tools), one per user on this computer, and host hooks (guidance and observation at specific points). A host runs a small Sennard Java client as a command hook (Codex delivers most of its hooks as MCP tool calls), and the client sends the input to the server. The presence of guidance alone does not mean that the agent followed the instructions or that the result was verified.

| Point | Sennard behavior |
| --- | --- |
| Session start, resume, and compaction | Provides guidance on skill selection and workflow use, and injects the global, role, and situational context. After a resume or compaction, injects the body of the current work record; when the body is needed, the agent reads it with `load_context`. |
| Each user message | Prompts the agent to review skill selection again through a turn check notice and a list of targets for each installed skill. It also includes guidance to save corrections, decisions, approvals, prohibitions, and remaining work with `checkpoint_context`. |
| End of each user turn | The server records every user turn start. When the turn ends with no successful `checkpoint_context` or `checkpoint_role_context` since that start and no `mark_turn_unchanged` (which says there is nothing to save), the turn is continued once and the agent is told what is missing. A turn that ends without either, because the host cannot continue it, already continued it or sends no turn end, is named in the next prompt's turn check. Subagents and sessions whose restore is suppressed are not checked. |
| Subagent start | Injects the list of skill targets, guidance to respect the assigned scope, forbidden areas, and write ownership, the global and role context, and the situational context of the parent session. Claude Code and Codex inject these through the subagent start hook. Antigravity does not have this start hook, so an agy subagent receives the role context from the step after its first call to a Sennard tool. |
| When a workflow changes | Appends the next step and skill-matching guidance to Sennard tool responses. |
| Work step boundaries | If the global, role, or situational context changed during the session, injects it once into each actor that has not yet received that revision. |
| When files change | Compares the edit target path with the workflow scope (see "Edit Gate" below). |
| Turn and subagent end | If product files were changed and workflow stages that have not passed remain, provides guidance on the work to continue. The check is performed per actor that did the work. Edits made by a subagent and workflows started by that subagent are checked when that subagent ends (Claude Code and Codex `SubagentStop`, Stop in an agy subagent conversation), not at the end of the parent's turn. |

**Starting the server.** Sennard registers nothing with the operating system, so nothing starts the server when the computer starts. The first session that starts after that starts it: the session-start hook of each host (Claude Code, Codex, Gemini CLI, Antigravity) finds that no server is listening, starts the installed server, waits until it is ready (its store included), and then sends the session start as usual. The session therefore starts later than usual, by the time the server needs to start. Only the session start does this; no other hook starts the server. When Sennard is not installed, when the server cannot be started, or when it is not ready within 30 seconds, the hook shows the guidance that begins with `Sennard server is not reachable.` and the session starts without Sennard; a server that was still starting continues and is there for the next session. The server keeps running after the session that started it ends, because it serves every session of the user. Whether each host lets the server that its hook started live on after the hook ends, and whether a host connects its MCP tools after the session-start hook, has not been verified in the hosts themselves.

**Tray icon.** The server's ports are chosen by the operating system at each start, so the address of the admin page changes with each start. When the computer has a desktop with a system tray, the server shows an icon there once it is ready. Its tooltip names the Sennard version and the current address of the admin page; a double click on the icon or the menu entry "Open admin page" opens that address in the default browser (the entry is disabled when the desktop cannot open a browser), and the entry "Stop server" stops the server through the same graceful shutdown as `sennard stop`. The menu and the tooltip are shown in English or Korean according to the default language of the JVM, and in English for any other language. When the JVM has no desktop (a headless JVM) or the desktop has no system tray, no icon is shown, the log records why in one line, and the server runs as before; `sennard status` still prints the address.

## Workflow Kinds and the Workflow Gate

Every request requires a workflow procedure, including an answer without tool calls. The agent selects the procedure by choosing the appropriate MCP tool. Sennard records the workflow or applied transition that serves the request. A start only declares the skills.

| Procedure | MCP entry point | `skills` | Edits | Commands | Ends |
|---|---|---|---|---|---|
| INQUIRY | `start_inquiry_workflow` (`goal`) for an answer or investigation | optional | refused (reads only) | allowed | the server closes it when the turn of the request that opened it ends |
| CHANGE | `start_workflow` (`goal`, `stages`, `acceptanceCriteria`, `writeTargets`, optional `changePlan`) | required | the files of the change plan | allowed | Explicit disposition (below) |
| EXECUTION | `start_operation_workflow` (`goal`, `target` such as a repository, branch or install location). The stored kind is `OPERATION`. | required | refused | allowed | Explicit disposition (below) |
| TRANSITION | Find the existing run or root with `list_session_workflows`, read its revision, then use the applicable lifecycle tool below. | per tool | refused | refused | the server commits the requested lifecycle change |

Each kind carries its own process (its phases, what each phase allows, and what moves it on); a change has a planning phase that only reads and an executing phase that edits the files of its plan, an answer has one phase that reads, and an operation has one phase that runs commands. A start that leaves out required `skills` is refused with `SKILLS_REQUIRED`; where the kind does not require them, a start may leave them out. A kind that owns no files stands on a place of its own that nothing is written to, so any number of answers and operations can be open at once, in any workspace, without a `ROOT_CONFLICT`; the changes keep the existing refusal of overlapping `writeTargets`.

**The gate.**

- **At each prompt**, the hook offers the four procedures and lists the session's open workflows (id, kind, phase and goal). Use `resume_workflow` (`runId`) to continue suitable unpaused work. A PAUSED workflow requires an explicit revision-checked resume. An active inquiry closes at the end of the request that opened it.
- **Before each tool**, a request that no workflow serves has its tools refused, except the Sennard tools, the host's skill tool and the host's tool that loads another tool; the refusal gives the exact call to make next. An edit is refused unless the file is in the change plan of a change workflow that the request took; a workflow of a kind that does not change files refuses it with the reason, and a command is allowed only to a workflow whose kind allows commands.
- If a workflow start fails, the request still needs a procedure. Resolve the reported error and retry the selection.
- **At the end of the turn**, if the request still needs a procedure, the hook asks the agent to choose one. The hold is given at most three times for one request, and not at a turn end that the host has continued already (the same loop guard as the session summary's question). A RUNNING workflow attributed to the current request whose root is OPEN also requires an explicit disposition on every Stop: complete, deliberately pause, or cancel. This check still applies when the host has already continued the turn. A committed transition can serve the current request. Editing and command execution require an applicable workflow with those permissions.
- **Subagents** are held to the same rule. A workflow a subagent opened can be resumed and worked on by the session's own agent, and not the other way round: a subagent opens a workflow of its own.

**Completion, pause and cancellation.** The MCP status and change responses say what to call next with the current run ID and revision.

- Complete passed work with `finalize_workflow` (`runId`, `expectedRevision`, `operationKey`). Every planned stage must have passed and no blocker or unresolved item may remain. A stage-free operation still needs this explicit finish. The run becomes PASSED, the root becomes COMPLETED, and its scope is released.
- Hold unfinished work with `pause_workflow` (`runId`, `expectedRevision`, `reason`, `resumeCondition`, `operationKey`). PAUSED retains stage progress, the current attempt and its scope; it records neither a pass nor an attempt outcome. Status includes the reason, resume condition and pause time. Only an explicit `resume_workflow` with both the current `expectedRevision` and a fresh `operationKey` restores RUNNING. A gated or finished root cannot be resumed this way.
- Cancel the whole work with `release_convergence_root` (`rootId`, the root's `expectedRevision`, `reason`, `operationKey` and any required approval references). The root becomes ABANDONED, its unfinished run is BLOCKED and the scope is released. It cannot be resumed.
- `abort_workflow` stops only the current attempt; it does not cancel the root or release an OPEN root's scope. A FAILED or BLOCKED attempt cannot resume. Read `get_convergence_status`; if the root remains OPEN and the retry requirements are met, claim and start a new attempt. NEEDS_REVIEW and NEEDS_USER require their review or user decision first.

**V24 upgrade and recovery.** The forward migration adds PAUSED to the existing run-state constraint without rewriting old receipts or the V8 migration. Back up the database before upgrading. After V24, do not start an older server that cannot read PAUSED. There is no down migration; recovery requires a matching server version and the database backup taken before the upgrade.

**JEV before the start.** For a kind that requires `skills` (a change, an operation), when JEV is on, the server first runs its classification for the request, or reuses the one the prompt hook already ran, and gives the advice with the start. A start that left the skills out is refused with the advice in the refusal, so the next call can declare them. The run records which advised skills were adopted, added or not adopted. The agent is not asked to call `classify_skills` first, and the server does not check whether a declared skill was used. When JEV is off, this step is skipped.

## Workflows and the Edit Gate

Changes that span multiple stages start with a workflow. When the agent passes a goal, stages, skills to use (`skills`), acceptance criteria, and paths to change (`writeTargets`) to `start_workflow`, the server creates the plan, root, lease, and run in a single call. At least one skill must be submitted with a reason, and skills are submitted separately for each attempt, so when the work is restarted because the situation changed, the skills are chosen again. If advice such as JEV was received, its task ID is submitted as well so that the difference between the advice and the actual selection is recorded in the run; the start is not blocked when there is no advice. A single session can run multiple workflows at the same time on non-overlapping paths. The result of each stage is recorded with `record_stage_result`, and `finalize_workflow` produces a completion result only when all planned stages have passed and no unresolved items remain. Completion in the record is not proof that the submitted content is true.

**Change plan and change record.** A workflow run has two phases. In the *planning* phase, the agent may read and investigate, but a write inside the run's `writeTargets` is refused by the edit gate. The run leaves the planning phase when the agent submits the files it will change (the change plan): either as `changePlan` in `start_workflow`, in which case the run starts in the *executing* phase, or afterwards with `submit_change_plan` (`runId`, `expectedRevision`, `files`). Every file must be inside `writeTargets`. A valid plan opens the executing phase without a user approval; the usual approvals for merging, publishing and deleting are unchanged. In the executing phase the plan can be revised with `submit_change_plan`, and each revision is recorded.

When the executing phase opens, Sennard records the path, size and modification time of the files under `writeTargets`, and a SHA-256 hash of the planned files. File contents are not stored. Afterwards, the edit hooks of the host record each file an edit tool changed (path, hash after the change, time and workflow), and `record_stage_result` and `finalize_workflow` compare the write targets again by size and modification time and hash only the files that changed, so a change made by a shell command that the hook could not read is also found. The result of `record_stage_result` lists the files that changed outside the plan ("changes outside the plan") as a report. `finalize_workflow` refuses: while any change is outside the plan it fails with `GATE_FAILED` (`details.reason` `UNPLANNED_CHANGES`, `details.unplanned` lists every path) and the run stays open. Add the file to the plan with `submit_change_plan` (a later plan that names the file answers for the earlier change) or undo the change, then call `finalize_workflow` again; it then reports `passed` and its unverified claims as before. `abort_workflow` is not refused for it. **Frame artifacts are declared, not read.** `open_convergence_root` and `claim_workflow_attempt` keep the `workspace`, and the `locator` and `digest` of each control and target artifact of the frame, as the caller wrote them. The server never reads a path on the caller's computer, so it does not check that a digest is the digest of the file at its locator; it compares the digests with those of the root to tell whether a later frame changed (a change to a control artifact needs an independent frame review). Files that a stage result cites are uploaded as attachments, and for those the server compares the sha256 it holds with the declared digest. The record is kept by Sennard itself and does not depend on a version control system; it is a record of what was observed, not a way to restore files.

The **edit gate** compares the edit target path reported by the host with the scope of the workflows in progress.

- A product file belongs to the change workflow, taken by the request, whose change plan has the file. A call that changes a file that no such workflow owns is refused at once, whatever the folder's version control: the refusal says whether the request has no workflow, has one of a kind that does not change files, or has none whose plan has the file. Only the OS temporary folder, the host's agent memo folder, and exempt paths set on the admin page are not product files. (The earlier allowance of two files changed without a workflow is gone.)
- A separate refusal applies to targets of a root that is waiting for review or a user decision.
- A write inside the `writeTargets` of a run that is still in its planning phase is refused until the change plan is submitted (see "Change plan and change record").
- **The `operationKey` of write tools.** The tools that change state are the workflow tools (`plan_workflow`, `open_convergence_root`, `claim_workflow_attempt`, `start_guarded_workflow`, `start_workflow`, `resolve_convergence_gate`, `record_stage_result`, `finalize_workflow`, `abort_workflow`, `pause_workflow`, `release_convergence_root`, `submit_change_plan`), the context tools (`checkpoint_context`, `purge_direct_context`, `checkpoint_global_context`, `checkpoint_role_context`, `bind_session_role`, `suppress_context_restore`, `mark_turn_unchanged`, `execute_state_cleanup`), the session tools (`open_session`, `update_session_status`, `record_turn_recap`, `prepare_session_message`, `send_session_message`, `acknowledge_session_messages`, `recall_session_message`), the skill tools (`classify_skills`, `record_skill_selection`) and `run_skill_check`. An explicit PAUSED-to-RUNNING `resume_workflow` also requires the key together with `expectedRevision`; runId-only selection of an already unpaused workflow remains compatible. Each requires an `operationKey` that the caller makes: 16 to 128 characters of `A-Z a-z 0-9 _ . : -`. Make a new random key (a UUID, for example) for each operation, and send the same key only to repeat that same operation. The server never makes one, and a missing or malformed key is refused as `INVALID_INPUT`. Sending the same key with the same content again, for example after a response was lost, returns the first successful answer without doing the work twice. The key belongs to the calling session: another session that sends the same key for the same tool is another operation, with its own effect and answer (only `open_session`, which is called before the caller has a session, has a key shared by every caller, so a key that was used before, by anyone, opens that same session again and never a new one; `run_skill_check` and `execute_state_cleanup` settle no caller either and share their keys the same way). The same key with different content is refused as `REQUEST_CONFLICT` (`details.reason` is `OPERATION_CONFLICT`). Every write tool answers it in this one shape (the code `REQUEST_CONFLICT`, `details.reason` and `details.field` `operationKey`). Two requests of one caller with one key at the same moment do the work once: the one that finishes second is refused as `REQUEST_CONFLICT` with `details.reason` `OPERATION_IN_PROGRESS`, which is retryable; send the same request again with the same key to get the first one's result. Only a success is stored: a refused request has no effect, so the same key sent again is judged again. A stored answer is kept for 24 hours (the setting `sennard.operations.receipt-retention`); the same key sent after that is a new request. `classify_skills` and `record_skill_selection` keep the key only for the life of the server. `run_skill_check` stores a receipt only for the commands that queue a background job (`change-scope-guardian compare` and `test-engineering run`): the same key answers the same `jobRef`; a command that only judges writes nothing, so it needs the key but has no stored answer.
- When a change is refused, call `start_workflow` as shown in the example in the refusal message. If the work differs from the work in progress, start another workflow with non-overlapping `writeTargets`.
- **Known limit: overlapping write scopes opened at the same moment.** A root whose write scope overlaps that of an active root is refused with `ROOT_CONFLICT`; for example, while `a` is open, `a/b` does not open. Two roots with exactly the same scope opened at the same moment are decided by the primary key of the active-surface table (`convergence_active_surfaces`), and the second is refused with `ROOT_CONFLICT`. Two roots that only overlap (`a` and `a/b`) and are opened at the same moment may both open, because at the isolation level `READ COMMITTED` neither request sees the other's uncommitted row. Sennard keeps `READ COMMITTED` and does not close this gap. If it happens, release one of the roots with `release_convergence_root` or close it.
- The gate does not monitor the entire file system. It covers supported edit tools, explicit output redirection in shells, and some PowerShell write paths. It cannot detect every write made through arbitrary scripts, aliases, or dynamic paths. A shell write whose path cannot be determined is itself counted as one file. A command that runs a script file (`node`, `python`, `ruby` or `bun` given a script file) is counted the same way, because what that file writes is not known. The exception is a running workflow that covers the whole workspace (`writeTargets` of `.`): such a write is taken to be inside its scope and is not counted, unless the same call also names a file outside it. When only a workflow with narrower `writeTargets` is running, the write is outside it and no other workflow can cover it, so the refusal tells you to write the file's path literally in the command or to use a file tool.
- If the check cannot be performed because of an internal Sennard failure, the edit is not unconditionally blocked; the condition is recorded and reported. If the server cannot be reached, decisions for tools other than Sennard tools pass without a decision on all three hosts. If the server answers but refuses the call (an HTTP 4xx or 5xx answer, including losing a first creation to a concurrent request), the gate stops the tool and names the error code; try the same call again.

## Work Records (Situational Context)

The agent saves corrections, decisions, and remaining work in the work record, and on resume compares the original text with the current state. Work records are handled by MCP tools and hooks, not by a skill.

| Tool | Function |
| --- | --- |
| `checkpoint_context` | Saves the current state to continue after compaction or resume (goal, latest decisions, permissions, and constraints, incomplete work and next actions, and necessary failures and evidence). The entire body is at most 2000 bytes in UTF-8. |
| `inspect_context`, `load_context` | Read the session's own current record and its `stateToken`. When saving or deleting, that token is compared through `expectedStateToken`. |
| `suppress_context_restore` | Suppresses automatic restoration. |
| `purge_direct_context` | Deletes only the current record when the user explicitly requests deletion. |

- The work record does not duplicate the workflow's stage ledger. Even when a saved summary exists, the actual files, environment, and test results must be checked again.
- To read its own current record, the agent sends only `{"schemaVersion":"1.0.0"}` to `load_context`. If a save conflicts because the state changed, the agent reads the latest record again and rebuilds it. Signed fork and workflow candidates are selected with the provided `candidateToken`, but arbitrary past revisions, records of other sessions, and history cannot be retrieved.
- The body injected at session start, resume, and compaction is the content at the time it was read. Because there is no acknowledgment that the host received it, there is no assurance that it is delivered exactly once across failures or that it is still the latest content at the model's first action.
- Do not put secrets, personal information, or raw logs or code in the work record. For storage locations and cleanup, see [State Storage and Cleanup](state.md).
- For the global and role context shared by multiple sessions, see [Admin Page and Context](admin-page.md#global-role-and-situational-contexts).

## When to Use Skills

Each skill is reviewed or invoked depending on the work situation. The list below is not an order in which to run every item from the top. Choose only the skills that fit the risk of the request and the current state, and when connecting two or more, `orchestrator` determines the order. The list of skills is in the [skill table in the README](../../README.md#skills).

- **Before starting:** when checking the applicable instructions and repository conventions before changing files or running commands, and when defining the goal, scope, and completion conditions
- **During the work:** when the work needs to be divided into independent units, or when a decision with a high cost of failure needs to be reviewed from multiple perspectives
- **Convergence review:** when the allowed number of repeated attempts has been used up, or the goal, evaluation criteria, or inputs may change, and you need to confirm, before opening a new attempt interval (`epoch`), that the meaning of the changed proposal is the same as the existing contract
- **Before and after changes:** when taking the baseline from the run's change record before a change, and after the change comparing the changes recorded since with that baseline to confirm that there are no files outside the scope
- **Immediately before changes that are hard to reverse:** when checking the target, permissions, and recovery conditions of high-impact actions such as deletion, deployment, and migration
- **Before completion:** when checking the evidence for each acceptance criterion before declaring completion, and for high-risk work, confirming that it has also passed an independent audit
- **When problems repeat:** when the same failure repeats or the cause is unclear, separating observations from hypotheses and deciding the next discriminating check
- **When choosing a recovery:** when comparing two or three recovery options for a failure whose cause has been confirmed, and preparing handoff material to bind to a new task contract
- **Before and after evaluation:** when checking the feasibility of the design before running an evaluation, or auditing the validity of the results, judgments, and aggregation evidence after running it
- **Specialist work:** the items above are agent correction skills. Use a specialist skill only when the work really deals with its field: `cs-engineering` for concurrency, databases, algorithms, and performance; `solid-design` for module and contract boundaries; `test-engineering` for writing tests; `code-review` for reviewing a fixed diff or PR; `software-security-auditor` for attack-path audits; `ui-ux-design` for what people see, such as screens, documents, and signage; `korean-prose-editor` for Korean prose; and `prompt-engineering` for prompts and instructions. The split into two groups only decides how skills are listed in the README and on the admin page; how a skill is selected is the same.

For example, a high-risk deployment proceeds as follows.

1. Before the work, check the applicable instructions and repository conventions, and define the allowed scope and completion conditions.
2. If the change is hard to reverse, first check the permissions, targets, scope of impact, and recovery method.
3. If multiple agents work together, divide the areas of responsibility and separate the implementer from the auditor.
4. When the change is finished, compare the initially defined scope with the actual changes and check the test results.
5. If the auditor and the implementer are the same, the audit target differs from the current result, or unresolved problems remain, completion is refused.

The MCP server checks plan signatures, stage order, the format of stage results, required artifacts, the match of audit targets, and unresolved items. However, it does not authenticate the truthfulness of the submitted evidence or the actual identity of the worker.

## Skill Selection Advice (JEV)

Where skill classification advice is configured, the server asks JEV by itself when a user prompt arrives and a hook gives the agent the short result as context; the agent does not have to call anything. `classify_skills` remains for an agent that wants the full response, and for the same prompt it returns the answer already obtained without calling JEV again. The server reads the installed skills itself, so the agent sends no skill list, and the answer does not repeat it: it holds the request as digests and a skill count, each skill's judgment beside the evaluator's confidence in it (`advice`), and the evaluator's tries. A score is the confidence in the judgment the evaluator gave for that skill, whatever the judgment is: 0.98 on `not-needed` means almost surely not needed, and 0.19 on `needed` means a weak `needed`; it is not how much the skill is needed. The hook shows the same number for the skills it names, and only the needed ones. `get_skill_inventory` answers with a summary of every installed skill (its size does not grow with the lines each skill applies by); the applicability, exclusions and phases of the skills the agent is considering come with `skillIds` (at most 6 per call, `view` is then `detail`). JEV is an advisory layer, and the agent makes the final selection. For how to enable and configure JEV, see the [JEV section of the admin page](admin-page.md#jev-skill-selection-advice).

## Models and Reasoning Levels for Subtasks

Choosing a model and reasoning level is a section of the delegation decision in `coordinate-subagents`. **Before invoking a subagent task that has already been approved**, the agent judges, from the role, difficulty, risk, and verifiability of the task, the model class and reasoning depth it needs, and then takes the actual model and effort from the list the host exposes. The product names no model and no host effort label, and it keeps no per-role table or floor. If you want a particular model or reasoning level, state it and it takes precedence when the host supports it. The choice does not decide whether to delegate, how many agents to use, or which permissions and audits to grant. It is also not a consultation feature that observes the current main model or changes UI settings.

- The common selection contract is separated from vendors. A model or effort label is usable only if the current host lists it, so the agent first reads the support information and invocation fields the actual host provides. A model or label seen for the first time needs no change here.
- The selected value, the value actually sent in the invocation, and the effective setting observed on the host are recorded separately. If an inherited setting cannot be observed, it is left as unconfirmed.
- Delegation, result recording, and closure are not refused because of the model class or reasoning level. A model seen for the first time is recorded with an unknown class and is not refused.
- Removed in 6.0.0: the `economy`, `balanced`, and `quality` preference, the risk-based floor on model class and reasoning level, the `support-guard` command and its `ModelEffortAdvice.v1` contract, and the `complex-reasoning` role. Use the `judgment` path (the delegating agent's own class and depth judgment) instead; there is no compatibility layer.
- Details are in [Model Routing and Per-Host Application](../../skills/coordinate-subagents/references/model-routing.md).

## Attaching a Local File

The agent runs `sennard attachments upload --session-ref <current sessionRef> "<file path>"` once. The client reads the file and automatically prepares, sends and finishes the attachment, returning its ID and metadata. Obtain the current reference with `open_session`; do not ask the user to split or encode the file. A repeated invocation recovers the same attachment. Multi-file bundles and recovery details are in [Attachments and Uploads](../contributing/attachments.md#the-upload-client).

The administrator can set the storage folder, maximum file size and total attachment capacity under **General settings → Attachment storage** and save with a passkey. Existing attachments remain readable from their previous locations. Include those locations and the encryption keys in backups.

## Choosing a Workflow for Execution

Use `CHANGE` for edits to named source or configuration files and revise its file plan with `submit_change_plan`. Use `OPERATION` for test/build execution such as `python tools/check.py`, `./gradlew test`, `node check.mjs` or `java -jar verifier.jar`. The hook does not inspect an external script's internal file effects. Planning the script and result files in `CHANGE` therefore does not authorize that execution. Generated test outputs belong to the operation. Explicit redirections, deletions and observed inline writes remain subject to the change plan.

Resume an existing operation for the same work with `resume_workflow`. Only if none fits, call `start_operation_workflow` with `goal`, `target`, nonempty `skills` (`skillId` and `reason`) and a fresh `operationKey`. Keep the existing change workflow for source edits. Selecting a workflow preserves its kind; `target` is descriptive and does not grant a path exemption or approval to publish, install or deploy. Record the actual execution result and finish the operation with `finalize_workflow`. A refused command has not run.

## What Sennard Does Not Do

- **It is not a security boundary against the same OS user's permissions.** A program running with those permissions can read the server's DB credentials and modify the state DB, or call the MCP server directly. Although it checks the format and consistency of submitted evidence, auditor identities, and user approval references, it does not authenticate their truthfulness. [Security Policy](../../SECURITY.md)
- **The edit gate does not monitor the entire file system.** It covers only the scope described in "Edit Gate" above.
- **Guidance, skill invocations, and tool success are different from completed actions.** The turn check notice does not confirm compliance with instructions, and it cannot remove a previously read skill body from the conversation. Delegation rules are provided as guidance; not every delegation call is checked.
- **Message ACKs and wake-ups are not work results or approvals.** See [Session Collaboration](collaboration.md).

The verification that was run and not run for each version is described in the verification section of the [release notes](../release-notes/).
