# 사용하기

Sennard를 설치한 뒤 평소처럼 에이전트에게 일을 맡기면 됩니다. 이 문서는 요청하는 법, 설치하면 달라지는 동작, workflow와 편집 관문, 작업 기록, 하위 작업의 모델 선택, Sennard가 하지 않는 일을 설명합니다. 설치는 [README](../../README.ko.md#설치)를 봅니다.

## 요청하는 법

원하는 결과와 확인할 조건, 보존할 대상을 함께 알려 주십시오. 에이전트가 요청마다 워크플로 절차를 고르고 작업에 필요한 스킬을 선택합니다.

```text
이 안내문을 처음 방문하는 사람이 예약까지 진행할 수 있게 고쳐 줘.
예약 조건과 연락처는 보존하고, 바꾸기 전에 확인할 사례를 적어 줘.
실제로 확인한 것과 사람의 확인이 남은 것을 나눠 알려 줘.
```

```text
이 기능을 구현하고 검증해 줘. 수정 범위와 완료 기준을 먼저 정리하고,
최종 결과에는 실제로 실행한 검사와 아직 해결하지 못한 문제를 함께 적어 줘.
```

스킬을 직접 지정하려면 호스트의 스킬 호출 방식으로 이름을 적습니다. 예를 들어 Codex에서는 `$orchestrator`, Claude Code에서는 `/sennard:orchestrator`입니다.

## 설치하면 달라지는 것

Sennard는 이 컴퓨터의 사용자당 하나인 상주 서버(MCP 도구)와 호스트 hook(시점별 안내와 관측)으로 동작합니다. 호스트가 작은 Sennard Java 클라이언트를 command hook으로 실행하고(Codex는 hook 대부분을 MCP 도구 호출로 전달합니다), 클라이언트가 서버에 입력을 보냅니다. 안내가 있다는 사실만으로 에이전트가 지시를 따랐거나 결과가 검증됐다고 볼 수는 없습니다.

| 시점 | Sennard의 동작 |
| --- | --- |
| 세션 시작·재개·압축 | 스킬 선택과 workflow 사용 기준을 안내하고, 전역·담당·상황 컨텍스트를 넣습니다. 재개·압축 뒤에는 현재 작업 기록 본문을 넣으며, 본문이 필요하면 에이전트가 `load_context`로 읽습니다. |
| 사용자 메시지마다 | 턴 확인 안내와 설치된 스킬별 대상 목록으로 스킬 선택을 다시 살피게 합니다. 교정·결정·승인·금지·남은 일을 `checkpoint_context`에 저장하라는 안내도 들어 있습니다. |
| 사용자 턴이 끝날 때 | 서버는 모든 사용자 턴의 시작을 기록합니다. 턴이 끝날 때 그 시작 뒤에 성공한 `checkpoint_context`나 `checkpoint_role_context`도, 저장할 것이 없다는 `mark_turn_unchanged` 표시도 없으면 턴을 한 번 이어 가며 무엇이 없는지 알립니다. 호스트가 이어 갈 수 없거나 이미 이어 갔거나 턴 끝을 보내지 않아 둘 다 없이 끝난 턴은 다음 프롬프트의 턴 확인에 알립니다. 서브에이전트와 복원을 억제한 세션은 확인하지 않습니다. |
| 서브에이전트 시작 | 스킬 대상 목록과 맡은 범위·금지 구역·쓰기 소유를 지키라는 안내, 전역·담당 컨텍스트, 부모 세션의 상황 컨텍스트를 넣습니다. Claude Code·Codex는 서브에이전트 시작 hook으로 넣습니다. Antigravity에는 이 시작 hook이 없어, agy 서브에이전트는 Sennard 도구를 처음 호출한 다음 단계부터 담당 컨텍스트를 받습니다. |
| workflow가 바뀔 때 | Sennard 도구 응답에 다음 단계와 스킬 대조 안내를 붙입니다. |
| 작업 단계 경계 | 세션 도중 바뀐 전역·담당·상황 컨텍스트가 있으면, 그 판을 아직 받지 않은 실행 주체에게 한 번 넣습니다. |
| 파일을 바꿀 때 | 편집 대상 경로를 workflow 범위와 대조합니다(아래 「편집 관문」). |
| 턴·서브에이전트 종료 | 제품 파일을 고친 뒤 통과하지 못한 workflow 단계가 남으면 이어 갈 일을 안내합니다. 확인은 일한 실행 주체별로 합니다. 서브에이전트의 편집과 그 서브에이전트가 시작한 workflow는 그 서브에이전트가 끝날 때(Claude Code·Codex `SubagentStop`, agy 서브에이전트 대화의 Stop) 확인하고, 부모의 턴 종료에서는 확인하지 않습니다. |

**서버 시작.** Sennard는 운영체제에 아무것도 등록하지 않으므로 컴퓨터가 켜질 때 서버를 띄우는 것은 없습니다. 그 뒤 처음 시작하는 세션이 서버를 띄웁니다. 각 호스트(Claude Code·Codex·Gemini CLI·Antigravity)의 세션 시작 hook이 듣고 있는 서버가 없음을 보면 설치된 서버를 띄우고, 저장소를 포함해 준비될 때까지 기다린 뒤 평소처럼 세션 시작을 보냅니다. 그래서 세션은 서버가 뜨는 시간만큼 늦게 시작합니다. 이렇게 하는 것은 세션 시작뿐이고 다른 hook은 서버를 띄우지 않습니다. Sennard가 설치되어 있지 않거나 서버를 띄울 수 없거나 30초 안에 준비되지 않으면 hook은 `Sennard server is not reachable.`로 시작하는 안내를 내고 세션은 Sennard 없이 시작합니다. 아직 뜨는 중이던 서버는 계속 떠서 다음 세션이 씁니다. 서버는 사용자의 모든 세션이 함께 쓰므로 띄운 세션이 끝나도 계속 실행됩니다. 호스트가 hook이 끝난 뒤에도 hook이 띄운 서버를 살려 두는지, 호스트가 세션 시작 hook 뒤에 MCP 도구를 연결하는지는 호스트에서 확인하지 않았습니다.

**트레이 아이콘.** 서버의 포트는 시작할 때마다 운영체제가 고르므로 관리 페이지 주소도 시작할 때마다 바뀝니다. 컴퓨터에 시스템 트레이를 갖춘 데스크톱이 있으면 서버는 준비를 마친 뒤 트레이에 아이콘을 띄웁니다. 아이콘의 툴팁에는 Sennard 버전과 관리 페이지의 현재 주소가 표시됩니다. 아이콘을 더블클릭하거나 메뉴의 「관리 페이지 열기」를 고르면 그 주소를 기본 브라우저로 엽니다(데스크톱이 브라우저를 열 수 없으면 이 항목은 비활성입니다). 「서버 끄기」는 `sennard stop`과 같은 정상 종료 경로로 서버를 끕니다. 메뉴와 툴팁은 JVM의 기본 언어가 한국어이면 한국어로, 영어이면 영어로 표시하고, 그 밖의 언어는 영어로 표시합니다. JVM에 데스크톱이 없거나(headless) 데스크톱에 시스템 트레이가 없으면 아이콘을 띄우지 않고 그 이유를 로그 한 줄로 남기며, 서버는 그대로 동작합니다. 주소는 `sennard status`로도 확인할 수 있습니다.

## workflow 종류와 관문

도구 없이 답하는 경우를 포함해 모든 요청에는 워크플로 절차가 필요합니다. 에이전트는 해당 MCP 도구를 호출해 절차를 선택합니다. Sennard는 요청을 처리한 워크플로 또는 적용된 전이를 기록합니다. 시작할 때는 사용할 스킬을 선언합니다.

| 절차 | MCP 진입점 | `skills` | 편집 | 명령 실행 | 끝 |
|---|---|---|---|---|---|
| INQUIRY | 답변·조사에는 `start_inquiry_workflow`(`goal`) | 옵션 | 거절(읽기만) | 허용 | 연 요청의 턴이 끝나면 서버가 닫음 |
| CHANGE | `start_workflow`(`goal`, `stages`, `acceptanceCriteria`, `writeTargets`, 선택 `changePlan`) | 필수 | 변경 계획의 파일 | 허용 | 명시적 완료·보류·취소(아래 설명) |
| EXECUTION | `start_operation_workflow`(`goal`, 저장소·브랜치·설치 위치 등 `target`). 저장되는 종류는 `OPERATION`입니다. | 필수 | 거절 | 허용 | 명시적 완료·보류·취소(아래 설명) |
| TRANSITION | `list_session_workflows`로 기존 실행이나 루트를 찾고 리비전을 읽은 뒤 아래의 해당 상태 변경 도구를 호출합니다. | 도구별 계약 | 거절 | 거절 | 서버가 요청된 상태 변경을 확정 |

종류마다 자기 프로세스(단계, 단계별 허용 행동, 다음 단계로 가는 조건)를 갖습니다. 변경은 읽기만 하는 계획 단계와 계획한 파일을 편집하는 구현 단계가 있고, 답변은 읽는 단계 하나, 실행·운영은 명령을 실행하는 단계 하나입니다. 필수인 `skills`를 빠뜨린 시작은 `SKILLS_REQUIRED`로 거절하고, 필수가 아닌 종류는 빠뜨려도 됩니다. 파일을 갖지 않는 종류는 아무것도 쓰지 않는 자기만의 자리에 서므로 답변과 실행·운영 workflow는 몇 개든 어느 작업공간에서든 `ROOT_CONFLICT` 없이 함께 열 수 있습니다. 변경은 `writeTargets`가 겹치면 거절하는 기존 규칙을 그대로 따릅니다.

**관문.**

- **요청마다** 훅이 네 절차와 세션의 열린 워크플로(id, 종류, 단계, 목표)를 보여 줍니다. 이어서 진행할 작업은 `resume_workflow`(`runId`)로 선택합니다. PAUSED 워크플로는 리비전을 확인한 뒤 명시적으로 재개해야 합니다. 진행 중인 답변·조사는 워크플로를 연 요청의 턴 끝에 닫힙니다.
- **도구마다**, 어떤 workflow도 처리하지 않는 요청에서는 Sennard 도구, 호스트의 스킬 도구, 다른 도구를 불러오는 호스트 도구를 뺀 도구를 거절하고, 거절 문구에 다음에 부를 정확한 호출을 담습니다. 편집은 그 요청이 잡은 변경 workflow의 변경 계획에 파일이 있을 때만 허용합니다. 파일을 바꾸지 않는 종류의 workflow는 이유를 알리며 거절하고, 명령 실행은 명령을 허용하는 종류의 workflow가 있을 때만 허용합니다.
- 워크플로 시작에 실패하면 요청을 처리할 절차를 선택해야 합니다. 표시된 오류를 해결하고 다시 선택하십시오.
- **턴 끝에** 요청에 필요한 절차가 선택되지 않았다면 훅이 네 절차를 다시 안내합니다. 한 요청에 최대 세 번까지만 붙잡고, 호스트가 이미 이은 턴 끝에는 붙잡지 않습니다. 현재 요청에 귀속된 RUNNING 워크플로의 루트가 OPEN이면 매 Stop마다 완료·명시 보류·취소 중 하나를 기록해야 합니다. 호스트가 이미 턴을 이었어도 이 확인은 계속 적용됩니다. 확정된 전이는 현재 요청을 처리한 근거가 됩니다. 편집과 명령 실행에는 해당 행동을 허용하는 워크플로가 필요합니다.
- **서브에이전트**도 같은 규칙을 받습니다. 서브에이전트가 연 workflow는 세션의 에이전트가 재개해 작업할 수 있지만 반대는 안 됩니다. 서브에이전트는 자기 workflow를 엽니다.

**완료·보류·취소.** MCP 상태 조회와 변경 응답은 현재 run ID와 revision을 넣어 다음 호출을 안내합니다.

- 통과한 작업은 `finalize_workflow`(`runId`, `expectedRevision`, `operationKey`)로 완료합니다. 계획한 단계가 모두 통과하고 blocker와 미해결 항목이 없어야 합니다. 단계 없는 실행·운영도 명시적으로 완료해야 합니다. run은 PASSED, root는 COMPLETED가 되고 작업 범위가 해제됩니다.
- 미완료 작업은 `pause_workflow`(`runId`, `expectedRevision`, `reason`, `resumeCondition`, `operationKey`)로 보류합니다. PAUSED는 단계 진행·현재 시도·작업 범위를 유지하며 통과나 시도 결과를 기록하지 않습니다. 상태에는 사유·재개 조건·보류 시각이 표시됩니다. 현재 `expectedRevision`과 새 `operationKey`를 함께 넣은 명시적 `resume_workflow`만 RUNNING으로 되돌립니다. 검토·사용자 결정을 기다리거나 끝난 root는 이 방법으로 재개할 수 없습니다.
- 작업 전체를 취소하려면 `release_convergence_root`(`rootId`, root의 `expectedRevision`, `reason`, `operationKey`, 필요한 승인 참조)를 호출합니다. root는 ABANDONED, 아직 끝나지 않은 run은 BLOCKED가 되고 작업 범위가 해제됩니다. 재개할 수 없습니다.
- `abort_workflow`는 현재 시도만 중단합니다. root 전체를 취소하거나 OPEN root의 작업 범위를 해제하지 않습니다. FAILED·BLOCKED 시도는 재개할 수 없습니다. `get_convergence_status`를 읽고 root가 OPEN이며 재시도 요건을 충족할 때 새 시도를 claim하고 시작합니다. NEEDS_REVIEW·NEEDS_USER는 먼저 검토나 사용자 결정을 거쳐야 합니다.

**시작 전 JEV.** `skills`가 필수인 종류(변경, 실행·운영)는 JEV가 켜져 있으면 서버가 먼저 그 요청을 분류하거나 프롬프트 훅이 이미 돌린 분류를 재사용해 조언을 시작 결과에 담습니다. 스킬을 빠뜨린 시작은 거절 응답에 조언을 담아, 다음 호출에서 채울 수 있게 합니다. run에는 조언한 스킬 중 채택한 것, 더한 것, 채택하지 않은 것을 기록합니다. 에이전트에게 `classify_skills`를 먼저 부르라고 요구하지 않고, 서버는 선언한 스킬을 썼는지 검사하지 않습니다. JEV가 꺼져 있으면 이 단계를 건너뜁니다.

## workflow와 편집 관문

단계가 이어지는 변경 작업은 workflow로 시작합니다. 에이전트가 `start_workflow`에 목표·단계·쓸 스킬(`skills`)·수용 기준·바꿀 경로(`writeTargets`)를 주면, 서버가 계획·root·lease·run을 한 번에 만듭니다. 스킬은 하나 이상 이유와 함께 내야 하고, 시도마다 따로 내므로 상황이 바뀌어 다시 시작할 때 스킬도 다시 정합니다. JEV 같은 조언을 받았으면 그 작업 ID를 함께 내어 조언과 실제 선택의 차이를 run에 남기며, 조언이 없어도 시작은 막히지 않습니다. 한 세션은 겹치지 않는 경로로 workflow를 여러 개 함께 진행할 수 있습니다. 각 단계 결과는 `record_stage_result`로 기록하고, 모든 계획 단계가 통과하고 미해결 항목이 없을 때만 `finalize_workflow`가 완료 결과를 만듭니다. 기록상 완료는 제출 내용이 사실이라는 증명이 아닙니다.

**변경계획서와 변경 기록.** workflow run에는 두 단계가 있습니다. *계획 단계*에서는 읽기와 조사만 할 수 있고, run의 `writeTargets` 안에 쓰면 편집 관문이 거부합니다. 에이전트가 바꿀 파일 목록(변경계획서)을 내면 계획 단계가 끝납니다. `start_workflow`의 `changePlan`으로 내면 run이 바로 *실행 단계*로 시작하고, 나중에 `submit_change_plan`(`runId`, `expectedRevision`, `files`)으로 낼 수도 있습니다. 모든 파일은 `writeTargets` 안에 있어야 합니다. 형식에 맞는 계획서는 사용자 승인 없이 실행 단계를 엽니다. 병합·발행·삭제 같은 기존 승인 규칙은 그대로입니다. 실행 단계에서 `submit_change_plan`을 다시 내면 계획을 고치며, 고칠 때마다 판으로 기록합니다.

실행 단계가 열릴 때 Sennard는 `writeTargets` 아래 파일의 경로·크기·수정시각과 계획한 파일의 SHA-256 해시를 기록합니다. 파일 내용은 저장하지 않습니다. 이후 호스트의 편집 hook이 편집 도구가 바꾼 파일(경로, 변경 뒤 해시, 시각, workflow)을 기록하고, `record_stage_result`와 `finalize_workflow`가 쓰기 범위를 크기·수정시각으로 다시 대조해 바뀐 파일만 해시합니다. 그래서 hook이 읽지 못한 셸 명령의 변경도 찾아냅니다. `record_stage_result`의 결과는 계획 밖에서 바뀐 파일(「계획 밖 변경」)을 보고로 알려 줍니다. `finalize_workflow`는 거절합니다. 계획 밖 변경이 하나라도 있는 동안에는 `GATE_FAILED`(`details.reason` `UNPLANNED_CHANGES`, `details.unplanned`에 모든 경로)로 실패하고 run은 열린 채 남습니다. `submit_change_plan`으로 그 파일을 계획에 더하거나(그 파일을 이름으로 든 뒤의 계획이 앞선 변경을 책임집니다) 변경을 되돌린 뒤 `finalize_workflow`를 다시 호출하면 그때 `passed`와 미검증 주장을 보고합니다. `abort_workflow`는 이 이유로 거절하지 않습니다. **frame 산출물은 선언일 뿐 읽지 않습니다.** `open_convergence_root`와 `claim_workflow_attempt`는 frame의 `workspace`와 control·target 산출물 각각의 `locator`·`digest`를 호출자가 쓴 그대로 보관합니다. 서버는 호출자 컴퓨터의 경로를 읽지 않으므로 digest가 그 locator의 파일 digest인지 확인하지 않고, root의 digest와 견주어 뒤의 frame이 바뀌었는지만 가립니다(control 산출물의 변경은 독립 frame 검토가 필요합니다). stage 결과가 인용하는 파일은 첨부로 올리며, 그 파일은 서버가 가진 sha256과 선언된 digest를 대조합니다. 이 기록은 Sennard가 직접 보관하므로 버전 관리 시스템에 의존하지 않으며, 관측한 내용의 기록일 뿐 파일을 되돌리는 수단이 아닙니다.

**편집 관문**은 호스트가 알려 준 편집 대상 경로를 진행 중인 workflow 범위와 대조합니다.

- 제품 파일은 그 파일을 변경 계획에 담은, 요청이 잡은 변경 workflow에 속합니다. 그런 workflow가 없는 파일을 바꾸는 호출은 폴더의 버전 관리와 상관없이 바로 거부합니다. 거부 문구는 요청에 workflow가 없는지, 파일을 바꾸지 않는 종류만 있는지, 계획에 그 파일이 있는 workflow가 없는지를 알립니다. OS 임시 폴더, 호스트의 에이전트 메모 폴더, 관리자 페이지에서 정한 예외 경로만 제품 파일이 아닙니다. (workflow 없이 두 파일까지 바꾸게 두던 이전 허용은 없어졌습니다.)
- 검토·사용자 판단을 기다리는 root의 대상에는 별도 거부가 적용됩니다.
- 아직 계획 단계인 run의 `writeTargets` 안에 쓰는 호출은 변경계획서를 낼 때까지 거부됩니다(위 「변경계획서와 변경 기록」).
- **쓰기 도구의 `operationKey`.** 상태를 바꾸는 도구는 workflow 도구(`plan_workflow`, `open_convergence_root`, `claim_workflow_attempt`, `start_guarded_workflow`, `start_workflow`, `resolve_convergence_gate`, `record_stage_result`, `finalize_workflow`, `abort_workflow`, `pause_workflow`, `release_convergence_root`, `submit_change_plan`), 컨텍스트 도구(`checkpoint_context`, `purge_direct_context`, `checkpoint_global_context`, `checkpoint_role_context`, `bind_session_role`, `suppress_context_restore`, `mark_turn_unchanged`, `execute_state_cleanup`), 세션 도구(`open_session`, `update_session_status`, `record_turn_recap`, `prepare_session_message`, `send_session_message`, `acknowledge_session_messages`, `recall_session_message`), 스킬 도구(`classify_skills`, `record_skill_selection`), `run_skill_check`입니다. PAUSED를 RUNNING으로 바꾸는 명시적 `resume_workflow`도 `expectedRevision`과 함께 키를 받으며, 이미 보류되지 않은 workflow를 `runId`만으로 선택하는 기존 호출은 그대로 쓸 수 있습니다. 모두 호출자가 만든 `operationKey`를 필수로 받습니다. `A-Z a-z 0-9 _ . : -`로 된 16자 이상 128자 이하 문자열입니다. 작업마다 새 무작위 키(예: UUID)를 만들고, 같은 키는 같은 작업을 다시 보낼 때만 보냅니다. 서버는 키를 만들지 않으며, 빠지거나 형식이 틀리면 `INVALID_INPUT`으로 거부합니다. 응답을 받지 못한 경우처럼 같은 키와 같은 내용을 다시 보내면 작업을 두 번 하지 않고 처음 성공한 응답을 돌려줍니다. 키는 호출한 세션의 것입니다. 같은 도구에 같은 키를 보낸 다른 세션은 효과도 응답도 따로 가진 다른 작업입니다(호출자가 세션을 갖기 전에 불리는 `open_session`만 모든 호출자가 키를 공유하며, 그래서 이전에 누가 썼든 쓰인 키는 새 세션이 아니라 그 세션을 다시 엽니다. 호출자를 정하지 않는 `run_skill_check`와 `execute_state_cleanup`도 같은 식으로 키를 공유합니다). 같은 키에 다른 내용을 보내면 `REQUEST_CONFLICT`(`details.reason`은 `OPERATION_CONFLICT`)로 거부합니다. 모든 쓰기 도구가 이 한 가지 모양(코드 `REQUEST_CONFLICT`, `details.reason`, `details.field` `operationKey`)으로 답합니다. 같은 호출자가 같은 키로 보낸 요청 둘이 같은 때 오면 일은 한 번만 하고, 나중에 끝나는 쪽은 `REQUEST_CONFLICT`(`details.reason`은 `OPERATION_IN_PROGRESS`)로 거부합니다. 이는 다시 시도할 수 있는 오류이며, 같은 요청을 같은 키로 다시 보내면 먼저 된 요청의 결과를 받습니다. 성공만 저장하므로, 거부된 요청은 효과가 없어 같은 키로 다시 보내면 다시 판정합니다. 저장된 응답은 24시간(설정 `sennard.operations.receipt-retention`) 동안만 보관하며, 그 뒤에 같은 키를 보내면 새 요청입니다. `classify_skills`와 `record_skill_selection`은 키를 서버가 떠 있는 동안만 보관합니다. `run_skill_check`는 배경 작업을 만드는 명령(`change-scope-guardian compare`, `test-engineering run`)에서만 영수증을 저장합니다. 같은 키는 같은 `jobRef`를 돌려줍니다. 판정만 하는 명령은 쓰기가 없어 키는 필수로 받지만 저장된 응답은 없습니다.
- 거부되면 거부 문구의 예대로 `start_workflow`를 호출합니다. 진행 중인 작업과 다른 일이면 겹치지 않는 `writeTargets`로 workflow를 하나 더 시작합니다.
- **알려진 한계: 겹치는 쓰기 범위를 같은 순간에 여는 경우.** 쓰기 범위가 활성 root와 겹치는 root는 `ROOT_CONFLICT`로 거절합니다. 예를 들어 `a`가 열려 있으면 `a/b`는 열리지 않습니다. 범위가 완전히 같은 두 root를 같은 순간에 열면 활성 표면 표(`convergence_active_surfaces`)의 기본 키가 가려, 둘째를 `ROOT_CONFLICT`로 거절합니다. 범위가 겹치기만 하는 두 root(`a`와 `a/b`)를 같은 순간에 열면 둘 다 열릴 수 있습니다. 격리 수준 `READ COMMITTED`에서는 두 요청이 서로의 미커밋 행을 보지 못하기 때문입니다. Sennard는 `READ COMMITTED`를 유지하며 이 틈을 막지 않습니다. 이렇게 되면 한쪽 root를 `release_convergence_root`로 해제하거나 닫습니다.
- 관문은 파일시스템 전체를 감시하지 않습니다. 지원 편집 도구와 셸의 명시적 출력 리다이렉션, 일부 PowerShell 쓰기 경로를 다룹니다. 임의 스크립트·별칭·동적 경로로 생긴 쓰기를 모두 알아내지 못합니다. 경로를 알 수 없는 셸 쓰기는 그 자체로 한 파일로 셉니다. 스크립트 파일을 실행하는 명령(`node`, `python`, `ruby`, `bun`에 스크립트 파일을 준 경우)도 그 파일이 무엇을 쓰는지 알 수 없으므로 경로를 알 수 없는 쓰기로 셉니다. 다만 작업 폴더 전체를 덮는 진행 중 workflow(`writeTargets`가 `.`)가 있으면 그 쓰기는 그 범위 안으로 보고 세지 않습니다. 같은 호출이 범위 밖의 파일을 함께 이름 붙이면 그대로 셉니다. 더 좁은 `writeTargets`의 workflow만 있으면 그 쓰기는 범위 밖이며, 다른 workflow로는 덮을 수 없으므로 거부 문구가 명령에 파일 경로를 그대로 쓰거나 파일 도구를 쓰라고 안내합니다.
- Sennard 내부 장애로 검사할 수 없으면 편집을 무조건 막지 않고 그 상태를 기록하고 알립니다. 서버에 닿지 못하면 Sennard 도구가 아닌 도구의 판정은 세 호스트 모두 판정 없이 통과합니다. 서버가 답하되 호출을 거절하면(HTTP 4xx·5xx 응답. 동시 요청이 처음 만들기 경쟁에서 진 경우 포함) 게이트가 도구를 막고 오류 코드를 알려 줍니다. 같은 호출을 다시 시도합니다.

## 작업 기록(상황 컨텍스트)

에이전트는 교정·결정·남은 일을 작업 기록에 저장하고, 재개할 때 원문과 현재 상태를 대조합니다. 작업 기록은 스킬이 아니라 MCP 도구와 hook이 맡습니다.

| 도구 | 하는 일 |
| --- | --- |
| `checkpoint_context` | 압축·재개 뒤 이어 갈 현재 상태(목표, 최신 결정·권한·제약, 미완료·다음 행동, 필요한 실패·근거)를 저장합니다. 본문 전체는 UTF-8 2000 byte 이하입니다. |
| `inspect_context`, `load_context` | 자기 현재 기록과 `stateToken`을 읽습니다. 저장·삭제 때 `expectedStateToken`으로 그 토큰을 대조합니다. |
| `suppress_context_restore` | 자동 복원을 억제합니다. |
| `purge_direct_context` | 사용자가 명시적으로 삭제를 요청할 때 현재 기록만 지웁니다. |

- 작업 기록은 workflow의 단계 원장을 복제하지 않습니다. 저장된 요약이 있어도 실제 파일·환경·시험 결과를 다시 확인해야 합니다.
- 자기 현재 기록은 `load_context`에 `{"schemaVersion":"1.0.0"}`만 보내 읽습니다. 상태가 바뀌어 저장이 충돌하면 최신 기록을 다시 읽어 재구성합니다. 서명된 fork·workflow 후보는 제공받은 `candidateToken`으로 고르지만, 임의의 과거 판·다른 세션의 기록·이력은 조회하지 못합니다.
- 세션 시작·재개·압축 때 넣는 본문은 읽은 시점의 내용입니다. 호스트가 받았다는 확인이 없으므로, 장애 뒤까지 정확히 한 번 전달된다거나 모델의 첫 행동까지 최신이라는 보장은 없습니다.
- 비밀값, 개인정보, 원시 로그·코드를 작업 기록에 넣지 마십시오. 저장 위치와 정리는 [상태 저장과 정리](state.ko.md)를 봅니다.
- 여러 세션이 함께 쓰는 전역·담당 컨텍스트는 [관리자 페이지와 컨텍스트](admin-page.ko.md#전역담당상황-컨텍스트)를 봅니다.

## 스킬을 쓰는 시점

각 스킬은 작업 상황에 따라 검토하거나 호출합니다. 아래 목록은 위에서부터 모두 실행하라는 순서가 아닙니다. 요청의 위험도와 현재 상태에 맞는 스킬만 고르고, 둘 이상을 이을 때는 `orchestrator`가 순서를 정합니다. 스킬 목록은 [README의 스킬 표](../../README.ko.md#스킬)에 있습니다.

- **시작 전:** 파일을 바꾸거나 명령을 실행하기 전에 적용 지침과 저장소 관례를 확인하고, 목표·범위·완료 조건을 정할 때
- **진행 중:** 작업을 독립 단위로 나눌 필요가 생기거나, 실패 비용이 큰 결정을 여러 관점에서 검토할 때
- **수렴 검토:** 반복 시도의 허용 횟수를 다 썼거나 목표·평가 기준·입력이 달라질 수 있어, 새 시도 구간(`epoch`)을 열기 전에 기존 계약과 바뀐 제안의 의미가 같은지 확인할 때
- **변경 전후:** 변경 전에 run의 변경 기록에서 기준 상태를 받고, 변경 뒤 그 뒤로 기록된 변경을 기준과 비교해 범위 밖 파일이 없는지 확인할 때
- **되돌리기 어려운 변경 직전:** 삭제, 배포, 마이그레이션처럼 영향이 큰 동작의 대상·권한·복구 조건을 점검할 때
- **완료 전:** 완료를 선언하기 전에 수용 기준별 근거를 확인하고, 고위험 작업은 독립 감사까지 통과했는지 확인할 때
- **문제가 반복될 때:** 같은 실패가 반복되거나 원인이 불분명할 때 관측과 가설을 나누고 다음 판별 검사를 정할 때
- **복구를 고를 때:** 원인이 확정된 실패의 복구안 2~3개를 비교하고, 새 작업 계약에 결속할 인계 자료를 만들 때
- **평가 전후:** 평가 실행 전에 설계의 실행 가능성을 확인하거나, 실행 뒤 결과·판정·집계 근거의 타당성을 감사할 때
- **전문분야 작업:** 위 목록은 에이전트 교정 스킬입니다. 전문분야 스킬은 작업이 그 분야를 실제로 다룰 때만 씁니다. 동시성·DB·알고리즘·성능은 `cs-engineering`, 모듈과 계약 경계는 `solid-design`, 시험 작성은 `test-engineering`, 고정된 diff·PR 리뷰는 `code-review`, 공격 경로 감사는 `software-security-auditor`, 화면·문서·안내물 같은 사람이 보는 결과물은 `ui-ux-design`, 한국어 산문은 `korean-prose-editor`, 프롬프트·지침은 `prompt-engineering`입니다. 스킬을 두 묶음으로 나눈 것은 목록과 관리자 페이지에 나누어 보이는 데만 쓰이며, 스킬이 고르는 방식은 같습니다.

예를 들어 위험도가 높은 배포 작업은 다음처럼 진행합니다.

1. 작업 전에 적용 지침과 저장소 관례를 확인하고, 허용 범위와 완료 조건을 정합니다.
2. 되돌리기 어려운 변경이면 권한, 대상, 영향 범위, 복구 방법을 먼저 점검합니다.
3. 여러 에이전트가 함께 일하면 담당 영역을 나누고 구현자와 감사자를 분리합니다.
4. 변경이 끝나면 처음 정한 범위와 실제 변경을 비교하고 시험 결과를 확인합니다.
5. 감사자와 구현자가 같거나, 감사 대상이 현재 결과와 다르거나, 해결되지 않은 문제가 남아 있으면 완료를 거절합니다.

MCP 서버는 계획 서명, 단계 순서, 단계 결과 형식, 필수 산출물, 감사 대상의 일치, 미해결 항목을 검사합니다. 다만 제출된 근거의 진실성이나 작업자의 실제 신원은 인증하지 않습니다.

## 스킬 선택 조언(JEV)

스킬 분류 조언이 설정된 환경에서는 사용자 프롬프트가 들어올 때 서버가 스스로 JEV에 묻고, 훅이 그 짧은 결과를 맥락으로 에이전트에게 줍니다. 에이전트가 따로 부를 필요는 없습니다. `classify_skills`는 전체 응답이 필요한 에이전트를 위해 남아 있으며, 같은 프롬프트면 JEV를 다시 부르지 않고 이미 받은 응답을 돌려줍니다. 서버가 설치된 스킬을 직접 읽으므로 에이전트는 스킬 목록을 보내지 않고, 응답도 그 목록을 되풀이하지 않습니다. 응답에는 요청의 digest와 스킬 수, 스킬마다 평가자의 판정과 그 판정에 대한 확신도(`advice`), 평가자의 시도가 담깁니다. 점수는 평가자가 그 스킬에 내린 판정에 대한 확신도이며 판정이 무엇이든 같습니다. `not-needed`에 0.98이면 거의 확실히 필요 없다는 뜻이고 `needed`에 0.19이면 약한 `needed`라는 뜻이며, 스킬이 얼마나 필요한지를 나타내지 않습니다. 훅은 자신이 이름 붙이는 스킬(필요하다고 판단한 것만)에 같은 수치를 보여 줍니다. `get_skill_inventory`는 설치된 모든 스킬의 요약을 돌려주며(스킬이 적용되는 줄이 늘어도 크기는 늘지 않습니다), 검토 중인 스킬의 적용·제외·단계는 `skillIds`(한 번에 최대 6개, 이때 `view`는 `detail`)로 읽습니다. JEV는 조언 계층이며, 최종 선택은 에이전트가 합니다. JEV를 켜고 설정하는 방법은 [관리자 페이지의 JEV 절](admin-page.ko.md#jev-스킬-선택-조언)을 봅니다.

## 하위 작업의 모델과 추론 수준

모델과 추론 수준을 고르는 일은 `coordinate-subagents`의 위임 판단에 들어 있는 한 절입니다. **이미 승인된 서브에이전트 작업을 호출하기 전에** 에이전트가 역할·난도·위험·검증 가능성으로 그 일에 필요한 모델 등급과 추론 깊이를 판단하고, 실제 모델과 추론 수준은 호스트가 제시한 목록에서 고릅니다. 제품은 모델 이름과 호스트 고유 추론 수준 라벨을 두지 않고, 역할별 고정 표나 바닥도 두지 않습니다. 특정 모델이나 추론 수준을 원하면 직접 지정하면 되고, 호스트가 지원하는 한 그 지정이 우선합니다. 이 선택은 위임할지, 몇 명을 쓸지, 어떤 권한과 감사를 줄지를 정하지 않습니다. 현재 메인 모델을 관측하거나 UI 설정을 바꾸는 상담 기능도 아닙니다.

- 공통 선택 계약은 벤더와 분리되어 있습니다. 모델과 추론 수준 라벨은 현재 호스트가 목록에 올린 것만 쓸 수 있으므로, 에이전트가 실제 호스트가 제공한 지원 정보와 호출 필드를 먼저 읽습니다. 처음 보는 모델이나 라벨도 여기를 고칠 필요가 없습니다.
- 선택한 값, 실제 호출에 보낸 값, 호스트에서 관측한 유효 설정을 따로 기록합니다. 상속 설정을 볼 수 없으면 미확인으로 남깁니다.
- 모델 등급·추론 수준 때문에 위임·결과 기록·종결이 거부되지 않습니다. 처음 보는 모델은 등급 미상으로 기록하며 거부하지 않습니다.
- 위임하는 에이전트가 모델과 추론 수준을 판단할 때 `judgment` 경로를 사용합니다.
- 자세한 내용은 [모델 라우팅과 호스트별 적용](../../skills/coordinate-subagents/references/model-routing.md)에 있습니다.

## 로컬 파일 첨부

에이전트는 `sennard attachments upload --session-ref <현재 sessionRef> "<파일 경로>"`를 한 번 실행합니다. 클라이언트가 파일을 읽고 준비·전송·완료를 자동 처리해 첨부 ID와 메타데이터를 반환합니다. 현재 참조는 `open_session`에서 받으며, 사용자에게 파일 분할이나 인코딩을 요구하지 않습니다. 같은 명령을 다시 실행하면 같은 첨부를 복구합니다. 여러 파일의 묶음과 오류 복구는 [첨부와 업로드](../contributing/attachments.ko.md#업로드-클라이언트)를 봅니다.

관리자는 **일반 설정 → 첨부 저장**에서 저장 폴더, 파일당 최대 크기와 전체 첨부 용량을 정하고 패스키로 저장합니다. 기존 파일은 이전 위치에서 계속 읽습니다. 이전 위치와 암호화 키도 백업에 포함합니다.

## 실행에 맞는 workflow 선택

경로가 명시된 소스·설정 파일 편집은 `CHANGE`에서 하고 `submit_change_plan`으로 같은 파일 계획을 수정합니다. `python tools/check.py`, `./gradlew test`, `node check.mjs`, `java -jar verifier.jar` 같은 시험·빌드 실행은 `OPERATION`을 사용합니다. 관측기는 외부 스크립트 내부의 파일 효과를 해석하지 않습니다. 따라서 스크립트와 결과 파일을 `CHANGE` 계획에 넣어도 해당 실행이 허용되지는 않습니다. 시험이 생성하는 결과물은 실행에 속하지만 명시적 리다이렉션·삭제·관측된 인라인 쓰기에는 변경 계획이 계속 적용됩니다.

같은 작업의 기존 실행 workflow가 있으면 `resume_workflow`로 선택합니다. 맞는 것이 없을 때만 `start_operation_workflow`에 `goal`, `target`, `skillId`와 `reason`을 담은 비어 있지 않은 `skills`, 새 `operationKey`를 보냅니다. 소스 편집은 기존 변경 workflow에서 이어 갑니다. workflow를 선택해도 종류는 바뀌지 않으며 `target`은 설명일 뿐 경로 예외나 공개·설치·배포 승인을 부여하지 않습니다. 실제 실행 결과를 기록하고 `finalize_workflow`로 실행 workflow를 끝냅니다. 거절된 명령은 실행되지 않은 것입니다.

## Sennard가 하지 않는 일

- **같은 OS 사용자 권한에 대한 보안 경계가 아닙니다.** 그 권한으로 도는 프로그램은 서버의 DB 자격 증명을 읽어 상태 DB를 고치거나 MCP 서버를 직접 호출할 수 있습니다. 제출된 근거·감사자 신원·사용자 승인 참조의 형식과 일관성을 검사해도 진실성을 인증하지는 않습니다. [보안 정책](../../SECURITY.ko.md)
- **편집 관문은 파일시스템 전체를 감시하지 않습니다.** 위 「편집 관문」의 범위만 다룹니다.
- **안내·스킬 호출·도구 성공은 행동 완료와 다릅니다.** 턴 확인 안내는 지시 준수를 확인하지 않으며, 앞서 읽은 스킬 본문을 대화에서 지우지도 못합니다. 위임 규칙은 안내하고, 위임 호출 전체를 검사하지 않습니다.
- **메시지 ACK와 깨우기는 업무 결과나 승인이 아닙니다.** [세션 협업](collaboration.ko.md)을 봅니다.
- **검증 결과는 판·호스트·CLI 버전별로 따로 읽습니다.** hook 출력, MCP 성공 응답, 모델에 실제로 전달된 입력, 실제 준수는 각각 확인해야 합니다. 각 판에서 실행한 검증과 실행하지 않은 검증은 [릴리스 노트](../release-notes/)의 검증 절에 적습니다.
