# Sennard 6.0.0 Release Notes

Sennard 6.0.0 is a foundational release. It replaces the Node processes that each host started (MCP server, relay, hooks) with a single Java server per user and PC. Settings use a local H2 database and business state uses a separately configured database. The installation method and some public contracts change, so the major version has been incremented.

## Before Upgrading

- **A server installation step has been added.** The host plugins contain the skills and empty hook and MCP definitions; the installation writes this PC's definitions into the host's copy of each plugin. If the server is not installed, MCP tools do not connect. Follow the [README](../../README.md#installation) for installation.
- **The release is one jar, and you need JDK 25.** The assets are `sennard-<version>.jar` and `sennard-<version>.jar.sha256`, and the Antigravity package `sennard-antigravity-v<version>.zip`; you run `java -jar sennard-<version>.jar install` with your own JDK 25. There are no per-OS archives and no bundled Java runtime. Node.js is not required. Provide a separate business database for business state and link it on the admin page after installation.
- **6.0.0 does not read data stored by an earlier version.** The state store, stored documents and signed admin records have a new format. This server has no import command. Do not point 6.0.0 at the state files of an earlier version.
- **A database used by a 6.0.0 trial build must be deleted and linked again.** In the release, every table of the business database is in one schema, `sennard`. Trial builds of 6.0.0 placed each module's tables in its own `sennard_*` schema (the local settings database had its own schema as well). There is no migration from those schemas. If you ran such a trial build, delete its business database (or its `sennard_*` schemas) and the `settings/sennard-settings` database in the state folder, then link a database again on the admin page. This does not apply to an upgrade from 5.x.
- **Stop an earlier Sennard server first.** The 6.0.0 server has no fixed port, neither for MCP and hooks nor for the admin page: the operating system assigns a free port at each start, and the server announces its address in `server.properties` in the state folder. A port held by another program, including an earlier Sennard server, does not block the 6.0.0 server. An earlier server that keeps running is not part of 6.0.0, so end it.

## Upgrading from an earlier major version

1. Close all Sennard sessions in Claude Code, Codex, and Antigravity, so that the earlier server and relay exit. Confirm that the earlier server has ended: nothing listens on the admin page port it used, 47615. The following command must produce no output.

   ```powershell
   netstat -ano | findstr LISTENING | findstr :47615
   ```

   ```bash
   lsof -nP -iTCP:47615 -sTCP:LISTEN
   ```

2. Download `sennard-<version>.jar` and its `.sha256`, check the jar, and run `java -jar sennard-<version>.jar install` with your JDK 25. It extracts the jar into `~/.sennard/install`, starts the server, waits for readiness and writes the hook and MCP definitions. It does not register an OS service.
3. Upgrade the plugins of all three hosts to 6.0.0 together, following the [README](../../README.md#installation). In Codex, review and trust the Sennard hook again in `/hooks`. After installing each plugin, run `sennard hooks` (on every operating system). This command writes this PC's hook and MCP definitions into the plugin copies that the hosts read ([Plugin updates and `sennard hooks`](../user/update.md#plugin-updates-and-sennard-hooks)).
4. Open a new session and confirm that `healthy` in `sennard status` is `true` and that the Sennard tools are visible.
5. The admin page address is the `adminPage` value of `sennard status`. Its port is assigned by the operating system each time the server starts and has no setting.

**If `sennard install` ends with `START_FAILED`,** hook file placement is not run, and running `sennard install` again is rejected with `ALREADY_INSTALLED`. Remove the cause described in [Troubleshooting](../user/troubleshooting.md), then run `sennard start` and `sennard hooks` in that order.

There is no `sennard` program and nothing is added to PATH: `sennard <command>` stands for `java -jar <installation folder>/versions/<version>/sennard-<version>.jar <command>`. Use the command printed by installation or upgrade (`Run Sennard commands with: ...`), or the `command` field of `sennard status`. The path changes on upgrade. If the installation folder (`~/.sennard/install`) cannot be written in the system's file name encoding, `sennard install` ends with `INSTALL_ROOT_NOT_REPRESENTABLE`: set `SENNARD_INSTALL_ROOT` to a folder that can be written in it.

### Names changed with the product name

Starting with 6.0.0 the product is named Sennard. Earlier versions were named Agent Governance Suite (AGS). 6.0.0 does not read the earlier names, and nothing renames them automatically. Replace the earlier names wherever you use them:

| Item | Earlier name | 6.0.0 |
| --- | --- | --- |
| Command | `ags` | `sennard` |
| State folder | `~/.agent-governance-suite` | `~/.sennard` |
| Environment variables | `AGS_*`, `AGENT_GOVERNANCE_*` | `SENNARD_*` |
| Server settings and command-line options | prefix `ags.` | prefix `sennard.` |
| MCP server and plugin name | `agent-governance-suite` | `sennard` |
| Plugin and marketplace (Claude Code, Codex) | `agent-governance-suite@agent-governance-claude`, `agent-governance-suite@agent-governance` | `sennard@sennard-claude`, `sennard@sennard` |
| Public repository | `github.com/jaeseongs95/agent-governance-suite` | `github.com/jaeseongs95/sennard` |

Uninstall the earlier plugin of each host before installing the 6.0.0 plugin, because the plugin and MCP server names differ. Scripts and settings that call `ags`, set an `AGS_*` or `AGENT_GOVERNANCE_*` variable, pass an `ags.` option, or use the earlier repository address must be updated to the names above.

### Earlier data

6.0.0 neither reads nor changes the state files of an earlier version, and it has no import command. If you need to go back, stop the 6.0.0 server with `sennard stop`, remove the installation with `sennard uninstall` (the state folder of 6.0.0 remains) and reinstall the earlier plugin; the earlier state files are as they were.

## Changes

- **Every request is handled inside a workflow, by kind.** A workflow has a kind, set by the tool that opens it: `start_inquiry_workflow` (answer or investigation: reads only, `skills` optional, closed by the server when the turn ends), `start_workflow` (change: `skills` required, edits the files of its change plan) and `start_operation_workflow` (execution or operation, such as a test run, a push, an install or a deployment: `target` and `skills` required, commands allowed, file edits refused). The kinds are one enum, and each constant carries its tool, whether `skills` is required, its process, when it closes and its message keys. Until a request has a workflow, the hooks refuse its tools (the Sennard tools, the host's skill tool and the host's tool-loading tool excepted), hold the end of its turn (at most three times per request), and give at each prompt the list of the open workflows with `resume_workflow` and the ways to open a new one. Skills are declared, not forced: nothing checks that a declared skill was used. When JEV is on, a kind that requires `skills` runs the classification before it starts (reusing the one the prompt hook ran) and the advice comes with the start or with the refusal of a start that left the skills out. A file edit belongs to the change workflow whose change plan has the file; the earlier allowance of two files changed without a workflow is gone. See [Usage](../user/usage.md#workflow-kinds-and-the-workflow-gate).
- **One server per PC.** A single Spring Boot 4.1 embedded web server is the MCP server and the receiver for hooks. Its MCP endpoint is `POST /mcp` on `127.0.0.1`. The port is not fixed: the operating system assigns a free port at each start, as it does for the admin page, which is on a separate port of the same server, and the server announces its address in `server.properties` in the state folder. Only one server runs on a state folder (`SERVER_ALREADY_RUNNING`). A host reaches `/mcp` through a stdio relay that the installation registers, which finds the server through that file. The per-session shim processes and the named pipe transport have been removed.
- **Server startup.** The installer, `sennard start`, or a session-start hook starts the server. Sennard does not register an OS service.
- **State storage.** Settings use local H2; business state uses a separately configured database. The default local state folder is `~/.sennard`. All tables of the business database are in one schema, `sennard`, created and migrated by Sennard with one account; the per-module schemas have been removed.
- **The business database is linked on the admin page only.** The link (JDBC driver, URL, account, password file path, protection) is saved with your passkey in the settings database of the state folder, and the server, `sennard admin-reset` and `sennard attachments` read it there. `sennard.store.database.*` in `sennard.yaml` is not read; if an earlier installation had one, link the database again on the admin page. The link stays in the state folder after `sennard uninstall` and is found by a later install. You can change the link at any time, also while the database is ready: Sennard connects to the new database and prepares its tables before saving, and saves nothing if that fails. The saved link is used after you restart the server (`sennard stop`, then `sennard start`), and the screen says so until then. The records of the previous database are not copied to the new one. See [Business Database](../user/state.md#business-database).
- **One passkey on the admin page.** The personal edition registers one passkey: the server refuses to register another while one exists (`ADMIN_CHANGE_INVALID`, reason `SINGLE_PASSKEY`), and the only passkey cannot be revoked. If it is lost, run `sennard admin-reset`. The admin page layout has been reorganized (lists, panels, JEV conditions, session rows that show the summary first), and the page no longer uses any browser storage; the "Remove from list" function of the undetermined sessions group is gone, because a session leaves that group when it is given a role or ends.
- **JEV advice without a request from the agent.** When JEV can be called, the server starts the skill classification itself when a user prompt arrives, without making the hook wait, and the next hook of the same session adds a short result once (at most 8 skills, with the judgment and confidence). When JEV is off or a condition is not met, nothing is sent, added or logged; only a call that was made and failed is logged. `classify_skills` remains, and for the same prompt it returns the answer already obtained. The JEV key is kept sealed (AES-256-GCM) in the `jev_keys` table of the business database. See [JEV: skill selection advice](../user/admin-page.md#jev-skill-selection-advice).
- **Session summary requests.** While a main session's summary on the session board is missing or older than its last message, every hook that can carry the request asks the agent to write it with `update_session_status`; the request stops once the summary is newer. See [Session collaboration](../user/collaboration.md).
- **Tray icon.** When the computer has a desktop with a system tray, the server shows an icon there. The menu opens the admin page and stops the server; the tooltip shows the version and the current admin page address. Without a desktop or a tray, no icon is shown, one line is logged, and the server runs as before. See [Usage](../user/usage.md).
- **Hooks reach the server through a Java client.** Every hook of Claude Code, Gemini CLI and Antigravity, and the Codex session start and end, is a command that runs the small Sennard Java client (`sennard-hook-client`, started with the installed `java`); the other Codex hooks are MCP tool hooks that go through the relay. The client reads the server's address from `server.properties` for each call, starts no other program (except the installed jar at a session start that finds no server), and at a session start it tells the server which host process the session belongs to, so the server ends the session as soon as that process exits. There are no HTTP hooks, because the server's port is not fixed. No `curl`, shell, or Node process is involved.
- **Gemini CLI hooks.** A Gemini CLI extension (`gemini-extension/`) now receives the session, prompt, turn-end, model-request, tool, and compression events. Codex model-request events are received as well.
- **Skill scripts have been replaced by server checks.** Instead of the executable scripts in the skill folders, the MCP tool `run_skill_check` is called. Skill instructions remain as files.
- **Skills are in two groups.** Each skill's `classification.json` names its `category`: `agent-correction` (15 skills) or `specialist` (8 skills: `cs-engineering`, `code-review`, `test-engineering`, `solid-design`, `ui-ux-design`, `korean-prose-editor`, `software-security-auditor`, `prompt-engineering`). The README and the admin page list the skills in these two groups; how a skill is selected, checked, or hooked does not change. The seven specialist skills that were removed earlier in the 6.0.0 work are back (23 skills in all); the test-engineering check runs a command for you: `run_skill_check` with the `run` command of `test-engineering` starts the program with the privileges of the user who started the server and records a run receipt.
- **Only programs on the same PC can connect; OS users are not told apart.** The server binds only to `127.0.0.1`, so only programs on the same PC can connect. The personal edition assumes one person's PC, so it does not distinguish other OS accounts on the same PC. For the trust boundary, see the [security policy](../../SECURITY.md).
- **The user sets the edit gate exception paths.** The list that the user signs with a passkey on the admin page decides which directories the edit gate does not count; no environment variable or server setting adds one (`AGENT_GOVERNANCE_PHASE_EXEMPT_PATHS` is not read). No MCP tool changes it, and the default is an empty list. A path may be a Windows path, a POSIX path or a Git Bash drive path; a path with no drive, such as `/tmp` of Git Bash on Windows, is written as that string. The match is on whole path segments after `..` is resolved. See [Edit Gate Exception Paths](../user/admin-page.md#edit-gate-exception-paths).
- **Evidence files are kept as attachments.** Five new tools, `artifact_begin`, `artifact_chunk`, `artifact_finish`, `artifact_status` and `artifact_read`, upload files in chunks of at most 262144 bytes. An attachment is a bundle of 1 to 64 files that is uploaded together, checked file by file and kept under one ID, so a caller never compresses files only to attach them as one. The server stores each file encrypted (AES-256-GCM segments, random file names, keys in a separate owner-only folder) in the `attachments` folder of the state folder, and the database holds metadata only (`upload_staging` for the uploads in progress; `attachment`, `attachment_file` and `attachment_storage` for the kept attachments, which are only ever inserted into so that they stay auditable; no foreign keys; migration V21). The new settings `sennard.attachments.*` set the limits, and `sennard attachments` (`check`, `rekey --from <keyId>`, `keygen --id <keyId>`, `purge-orphans [--yes]`) checks the folder against the rows, replaces a key and empties the quarantine folder. The new commands `sennard attachments prepare` and `sennard attachments send` are the upload client for large files; `sennard attachments send` sends the chunks of one file and does not finish; the model calls `artifact_finish` once with the `attachmentId`, and the attachment is made only when all its files pass the check. `artifact_chunk` and `artifact_status` by `uploadId`, and `artifact_finish` by `attachmentId`, need no session (the random `uploadId` or `attachmentId` alone binds them to the upload; the attachment's author is still the session that called `artifact_begin`). A stage result names its files by attachment id and file number (`seq`): the server never reads a path on the caller's computer, so the evidence, artifacts and output file of `record_stage_result` must be attachments uploaded first by the session that records the result. See [Attachments and Uploads](../contributing/attachments.md).
- **Workflow statistics on the admin page.** A new screen shows, by period, how many workflows of each kind started (and how many without skills), the skills each kind declared, and the newest 50 workflows with kind, goal, state, declared skills, start time and host. The screen is view-only and needs no passkey. A workflow with no recorded kind is counted as a change, and the screen says how many were counted that way. The counts come from migration V22, which adds the column `workflow_runs.kind` (every existing row is given `CHANGE`) with an index on the period, and the table `workflow_run_skills` (one row per skill a start declared). The skills of a workflow started before V22 are not written back, so such a workflow is counted under its kind with no skills. See [Workflow Statistics](../user/admin-page.md#workflow-statistics).
- **Declarative column sealing (contributors).** A record component marked `@Encrypted` is sealed when the common row path of the business database store writes it and opened when it reads it, so a module no longer seals a value by hand. The JEV key now uses it. The sealer, its context data (scope, name, fingerprint) and the stored form are the same as before, so nothing visible changes and no stored value has to be migrated; a stored value still opens only under its own name and fingerprint.
- **`finalize_workflow` refuses a change outside the plan.** While the change journal finds a file changed outside the submitted change plan, the finish is refused with `GATE_FAILED` (`details.reason=UNPLANNED_CHANGES`, `details.unplanned` lists the files). Add the files with `submit_change_plan`, or undo the changes, and call the tool again. This check runs before the check of the stages. `abort_workflow` is not refused for it.
- **Every MCP tool except `codex_hook` answers with the common envelope.** The answer carries `schemaVersion`, `ok`, `data` and `error`, and `isError` is the negation of `ok` (true exactly when `ok` is false). The error of `run_skill_check` uses the same envelope (`ok` false, `isError` true) and has no `exitCode`; on success, `exitCode` is in `data`. `codex_hook` is the only exception, because the Codex hook runner reads its answer as the hook's own JSON.
- **A skill with no registry entry can be named in a workflow start.** A skill that is installed as a folder `skills/<name>/SKILL.md` can be named in `skills` of a workflow start by its name alone, even if the registry has no entry for it (for example `session-board` or `orchestrator`).
- **Why the host could not observe the model.** The `BINDING_REQUIRED` answer carries in `details.observation.transcriptReason` (with `waitedMs` and `linesSeen`) why the Claude Code transcript gave no model: `TRANSCRIPT_UNREADABLE`, `CALL_LINE_NOT_FOUND`, `OTHER_THREAD` or `MODEL_FIELD_MISSING`.
- **A file that a check names but the root lacks is `NOT_FOUND`.** When `run_skill_check` or an engineering check is given a bundle that names a file the root does not contain, the answer is `NOT_FOUND` (`practices.io.fileNotFound`) instead of `INVALID_INPUT`. A path that names something that is not a regular file keeps `INVALID_INPUT`.

### Fixed Defects

These defects were observed in 5.1.0 or earlier. Defects found and fixed during the development of 6.0.0 were never released and are not listed, except the first two entries, which change what you observe or must do.

- **The edit gate judges a shell write by the wrong folder (AGS3-D-0303):** A write that Sennard cannot read from the command (a script file, a build run by path, `git pull`) counted as inside a running workflow only when the session's working directory was covered, so `cd B && ./gradlew build` was refused when the session ran in folder A and the workflow was over folder B. The shell scan now records the folder the shell was in at each such write (`cd`, `pushd`, `Set-Location`, `cmd cd /d`, `git -C`, nested shells, and the Git Bash `/d/...` and `D:/...` spellings), and the gate covers the write only when every one of those folders is inside a running workflow's write surface. A folder the scan cannot follow (a variable, a glob, `popd`, `cd -`) opens nothing. Claude Code, Codex and Antigravity use the same path.
- **The business database was split into one schema per module (AGS3-D-0304):** This was a design mistake of the 6.0.0 trial builds: with one account and no role or grant, there was no reason to separate the schemas. All tables are now in the schema `sennard`; see "Before Upgrading" for a database that a trial build used.

- **Agents do not call subagents (follow-up):** In addition to the description change in 5.0.0, the delegation condition in `coordinate-subagents` has been reworded. The sentence that said delegation is "allowed only when" the user requests it or every net-benefit condition is satisfied now says to delegate an independent unit in those cases, and the cost condition changed from "still cost less than direct execution" to "do not clearly cost more than direct execution", so a unit whose cost is about equal to direct execution is no longer excluded by that condition. Only the wording has changed; its effect on agent behavior has not been measured on the three hosts.
- **Agents stop to ask whether to recover from their own problems or rework their own rejected results:** The intake guidance now states that recovering from a change the agent made and reworking its own result that was found below the criteria start without asking, and that only steps needing separate approval are asked about. Only the wording has changed; its effect on agent behavior has not been measured on the three hosts.
- **JEV skill classification answers are always discarded as `OUTPUT_TOO_LONG`:** The output ceiling of a classification answer was 1000 tokens, which an answer for 25 skills exceeded. The ceiling is now 4000 tokens.
- **A missing context source in `classify_skills` is reported as a runtime failure:** It was returned as `MCP_UNAVAILABLE`. It is now returned as an input error, `INVALID_INPUT` with `details.category=request-state` and `details.reasonCode=CONTEXT_SOURCE_MISSING`.
- **JEV usage is always 0 and reservations accumulate:** A JEV response carries no billed amount, so each sent call is now recorded as an estimate from its input tokens, and its reservation is released once the estimate is recorded. A sent call whose usage is unknown keeps its reservation.
- **JEV usage and budget are held per MCP server process:** Usage is stored in the server's database, and the admin page and the budget check read the same totals. Because 6.0.0 runs one server per user and PC, the budget applies to every session connected to that server.
- **A subagent that only invokes a skill without following its procedure is not noticed:** The subagent start message states that invoking a skill is not applying it and asks for each skill's procedure, required outputs and checks (the common behavior standard is in the intake block the server sends, so there is no file whose reading the hook could check at the end of a turn). Only the guidance has been added; its effect on agent behavior has not been measured on the three hosts.
- **A delegating parent starts subagents at once without planning a shared test server:** The `coordinate-subagents` reference now asks the parent to name the skills chosen for each unit in its brief, and to set the capacity, the order, and the owner of each run on a shared execution resource before dispatching. Only the wording has changed; its effect on agent behavior has not been measured on the three hosts.

## Public Contract Changes

If you have code that calls MCP tools directly or parses their responses, check the following.

| Item | 5.x | 6.0.0 |
| --- | --- | --- |
| Root approval (`replace-root`, `release-root`) | The host's MCP confirmation dialog (elicitation) or approval via a model argument | Approved with a passkey on the local admin page. The tool returns `details.reason=USER_APPROVAL_REQUIRED` together with `adminPage` and `scopeDigest`. The approval record is `kind: admin-page`, and repeating the same call reuses that approval. `USER_APPROVAL_PRODUCER_UNSUPPORTED` has been removed. The approval of 5.1.2 was bound to the reason the user saw and could be used once within 30 minutes; in 6.0.0 the user approves with a passkey on the admin page, and an approval is bound to the action, root, actor and scope, not to a reason, and can be used again until it is revoked |
| MCP transport | A stdio server started per session | The host starts the Sennard stdio relay, which forwards each message to the server's HTTP endpoint (`STATELESS`: no `Mcp-Session-Id`, and no requests sent by the server to the host first) |
| Hook definition format | Runs a Node script | The Sennard Java client as a command hook, or the host's MCP tool hook (Codex) through the relay; the plugin packages ship empty definitions that the installation fills |
| `stageValidator` | File path | Skill ID (`^[a-z][a-z0-9-]*$`, for example `"cs-engineering"`) |
| Session tools | Host observation only | Optional argument `sessionRef`. When the host cannot attach the session to a call, pass the value issued by `open_session` |
| Undeclared arguments | `RESERVED_CALLER_FIELD` | `INVALID_INPUT`, `details.reasonCode=UNDECLARED_ARGUMENT` |
| External `Host` header | 403 | 421. `Origin` rejection remains 403 |
| Input schema | The contract file as is | Generated by the server. Fewer `const` and length constraints are included than in 5.x, and the schema error messages have changed. Determine errors by `error.code`, not by message text |
| digest pattern | Accepts a trailing newline | Rejects a trailing newline |
| `prepare_session_message` for a target unknown to the server | Queued | `NOT_FOUND`, `details.reasonCode=SESSION_NOT_FOUND` |
| Refusals of the session message tools | `INVALID_INPUT` for a body that is blank or too long (message key `services.sessionMessage.prepare.bodyInvalid`); every other refusal `MCP_UNAVAILABLE` with `details` null | The category names the cause: `INVALID_INPUT` (body, time to live, an acknowledgement's shape; `details.reasonCode` is the rule, for example `MESSAGE_BODY_SIZE`), `NOT_FOUND`, `CONFLICT`, and `MCP_UNAVAILABLE` for a full store (`details` has `reasonCode`, `scope`, `earliestReleaseAt`) or a send the queue refused (`details.reasonCode=SEND_REJECTED`, `error.params.reason` is the sentence) |
| `status.wake` in message status | Wake status | Always `null`. Check the wake outlook with `autoWake` |
| State cleanup result | `partial` possible | The two stores are processed in one transaction. There is no `partial` status, and the result is `completed` or `no-op`. Deleted rows remain in the per-module backup table (`continuity_cleanup_backup`, `workflow_cleanup_backup`) under the plan ID (`backupPath` is `null`) |
| Lost passkey reset | None | `sennard admin-reset` (preview without `--yes`). Keeps the records and returns the signed items to their defaults |
| MCP `instructions` | Delivered by the per-session server | The resident server includes the common intake criteria and the session message guidance in the `initialize` response |
| Skill scripts | `node <script>` | `run_skill_check` `{skill, command, arguments}` |
| Model and reasoning effort of a workflow stage | `executionRequirement` carries `minimumModelClass` and `minimumReasoningEffort`. A reasoning effort outside the eight values `none` to `ultra` is recorded as `null` with the note `REASONING_EFFORT_UNRECOGNIZED` | `executionRequirement` has only `policyId`, `kind` and `observationRequired`; the two minimum fields are removed from `plan_workflow`, `start_guarded_workflow` and `claim_workflow_attempt` plans and their input schemas. The `reasoningEffort` and `modelClass` of an execution context are any non-empty string, or `null`, and are recorded as the host reported them. `REASONING_EFFORT_UNRECOGNIZED` is no longer returned; `HOST_EFFORT_UNREPORTED` and `MODEL_NOT_IN_CATALOG` remain. No model or effort is required or refused, so a new host, model or effort needs no change to Sennard |
| Starting a workflow | `start_workflow` only | One tool per kind: `start_inquiry_workflow` (`goal`, optional `skills`), `start_workflow` (unchanged input), `start_operation_workflow` (`goal`, `target`, `skills`); each takes a required `operationKey`. `resume_workflow` (`runId`) takes an open workflow for the request. The start answer carries `advice` (the skills JEV advised) when JEV ran first, and a refusal of a start that left out required `skills` carries it in `details.advice` |
| Hooks of a request with no workflow | Guidance | The prompt hook gives the gate, the list of open workflows and how to open each kind; the tool hook refuses every tool except the Sennard tools, the host's skill tool and its tool-loading tool; the turn end is held up to three times per request |
| Product file edit without a workflow | Allowed for two files, refused from the third | Refused at once unless a change workflow taken by the request has the file in its change plan |
| Uploading files | None | New tools `artifact_begin` (takes `files`, 1 to 64 items, and answers `attachmentId` and an `uploadId` per file), `artifact_chunk` (by `uploadId`), `artifact_finish` (by `attachmentId`; makes the attachment only when all files verify), `artifact_status` (by `uploadId` or by `attachmentId`), `artifact_read` (takes `seq`, the file; default 0) (`purpose` is `evidence` only; `sha256` is written `sha256:<64 hex>`). New error codes, each with `details.retryable`: `ARTIFACT_OPERATION_CONFLICT`, `ARTIFACT_CHUNK_CONFLICT`, `CHUNK_HASH_MISMATCH`, `ARTIFACT_BUSY`, `ARTIFACT_INCOMPLETE`, `ARTIFACT_HASH_MISMATCH`, `ARTIFACT_CORRUPTED`, `ARTIFACT_LIMIT` (`details.limit`), `ARTIFACT_STORAGE_UNSAFE`, `ARTIFACT_STORAGE_IO_ERROR`, `ARTIFACT_KEY_MISSING`, `ARTIFACT_STORAGE_FULL`, `ARTIFACT_UNSUPPORTED_PURPOSE`, `ARTIFACT_EXPIRED`, `ARTIFACT_NOT_FOUND` |
| `evidence[]` of `record_stage_result` | `locator`, `digest` and `note`; a local file was only hashed | `attachmentId` and `digest` are required, `seq` (the file of the attachment; 0 when left out) names the file the `digest` belongs to, and `locator` is removed (a missing `digest` is a contract error, `INVALID_INPUT`). The attachment must exist and have been made by the recording session, or recording fails with `BINDING_INVALID` (`details.reason` `ATTACHMENT_NOT_FOUND` or `ATTACHMENT_AUTHOR_MISMATCH`). When the attachment's sha256 differs from `digest`, a passing stage is refused with `BINDING_INVALID` (`details.reason` `ARTIFACT_DIGEST_MISMATCH`) and any other stage records `NOT_CHECKED`; when it is equal the server records `SHA256_MATCHED`. Two evidence items may name the same attachment. The server no longer keeps a copy of a local file |
| `output.artifacts[]`, `outputFile` and `artifactChecks[]` of `record_stage_result` | `locator` (a path or a label); `outputFile` was `{locator, digest}`, an absolute path of a local JSON file read by the server | `locator` is replaced by `attachmentId` and `seq` in all three: `output.artifacts[]` carries `attachmentId`, `seq` and `digest`, `outputFile` is `{attachmentId, seq, digest}` (a file of an attachment holding the JSON object of `output.output`, at most 16 MiB), and the server-owned `artifactChecks[]` entries carry `attachmentId` and `seq`. `seq` is 0 when left out, and `digest` is that of the file. They are judged by the same rules as `evidence[]`. In `claim_workflow_attempt`, `priorFailure.evidenceRefs` are attachment ids of the calling session; a missing or another session's attachment fails with `MISSING_EVIDENCE` (`details.reason` `ATTACHMENT_NOT_FOUND` or `ATTACHMENT_AUTHOR_MISMATCH`) |
| Checking audited files at `finalize_workflow` | The server read the audited local file again and failed with `AUDIT_TARGET_CHANGED` when it had changed | The server does not read the caller's files again. For a mandatory audit it checks that each audited attachment is still there with the recorded sha256 and can be read whole, and otherwise fails with `GATE_FAILED` (`details.reason` `AUDIT_TARGET_UNAVAILABLE`, which replaces `AUDIT_TARGET_CHANGED`). Attachments are never deleted as evidence, so changing or deleting the original file after the upload does not make finalize fail |
| `finalize_workflow` with a change outside the change plan | Not checked | Refused with `GATE_FAILED` (`details.reason=UNPLANNED_CHANGES`) before the stages are checked; `abort_workflow` is not refused |
| Answer of an MCP tool | The answer of each tool in its own shape | Every tool except `codex_hook` answers with the envelope `schemaVersion`, `ok`, `data`, `error`; `isError` is the negation of `ok`. The error of `run_skill_check` is the same envelope and has no `exitCode` |

Migration of stage results: a caller that recorded stage results with a `locator` in 5.x must upload the content first. Call `artifact_begin` once with all the files, then `artifact_chunk` for each file and `artifact_finish` once with the `attachmentId`, as the session that records the result (small contents go directly through the tools in base64 chunks of at most 256 KiB), then put the returned `attachmentId`, the `seq` of the file and the `sha256` of that file into `evidence[]`, `output.artifacts[]` and `outputFile`, and the `attachmentId` into `priorFailure.evidenceRefs`. Large files are uploaded with the upload client: `sennard attachments prepare <file>` for each file (prints `fileName`, `size`, `sha256` and `mediaType`), then `artifact_begin` once with those values (it answers `attachmentId` and an `uploadId` per file), then `sennard attachments send --upload-id <id> <file>` for each file (prints `uploadId`, `attachmentId`, `seq` and `received`; it does not finish), then `artifact_finish` once.

Migration of bundle review stages (`cs-implementation-review`, `test-sensitivity-review`, `change-code-review`): upload every file of the bundle first, as the session that records the result: the manifest, the report and every raw file the manifest or the check reads. The file name an attachment is uploaded under is its path under the bundle's folder (a portable relative path, `/`-separated). Then list the manifest and the report in `output.artifacts[]` and the raw files in `evidence[]`, each by `attachmentId`, `seq` and `digest`. The server rebuilds the folder in a private temporary place, runs the unchanged `check-stage-bundle` there and removes the folder.

Environment variables have also changed. The host-side `AGENT_GOVERNANCE_*` variables of 5.x are not read. `AGENT_GOVERNANCE_HOST_ATTESTATION` has been replaced by the static header `Sennard-Host-Label`, `AGENT_GOVERNANCE_ADMIN_PORT` has been removed (the admin page port is assigned by the operating system at each start), and `AGENT_GOVERNANCE_TOOL_SCHEMA_PROFILE` has been removed. `AGENT_GOVERNANCE_PHASE_EXEMPT_PATHS` is not read; edit gate exception paths are set on the admin page only. `AGENT_GOVERNANCE_CLASSIFICATION_CONFIG` (vendor path installation setting) is not read.

## Behavior When the Server Is Unavailable

- Sennard tools themselves end with a call error when the server is unavailable.
- Continuity decisions for tools other than Sennard tools (such as edit phase checks) pass without a decision on all three hosts when the server is unavailable (no connection or no answer in time). This is the same scope as the 5.x fail-open behavior.
- The workflow gate is open in the same way when Sennard itself fails. If the start of a workflow for a request failed for a Sennard reason (an unavailable server or store, a binding or integrity failure), or the state that tells whether a workflow serves the request cannot be read, the hooks do not refuse the request's tools and do not hold the end of its turn. The edit gate lets an edit through after a failed start as well, and records the file, so a start that succeeds later is marked as begun after product files had changed. A start refused for the agent's own mistake (for example, `skills` left out) is not a Sennard failure and keeps the gate closed.
- A server that is running but refuses a call is not the same as a server that is unavailable. A gate, a tool-call hook whose refusal stops the tool (the edit gate and the Sennard tool admission check on Claude Code; the continuity check on Codex; BeforeTool on Gemini CLI; PreToolUse on Antigravity), stops the tool when the server answers it with an HTTP status of 400 or above, including the loss of a first creation to a concurrent request (409). The refusal names the error code, and the user retries the call or looks the code up on the admin page or in the server log. Hooks that are not gates (session start, prompt submission, tool results, turn end and the others) continue as before: a refusal is a failed hook, and the host goes on. A refusal that is raised before the server has read the hook's input (a malformed body, an unknown host or event, a missing session identifier) is not turned into a refusal of the tool by the server; Antigravity and Gemini CLI still deny the tool for it, and Claude Code and Codex go on.
- If no server is listening when a session starts, the session-start hook starts the installed server and waits for it (up to 30 seconds), then sends the event; Sennard registers nothing with the operating system. If Sennard is not installed, the server cannot be started, or it is not ready in time, Sennard tools do not appear in that session, and the session does not reconnect even if the server starts later. The hook emits guidance that begins with `Sennard server is not reachable.`. Start the server, then restart the session. Whether each host keeps the server that its hook started alive after the hook ends, and whether MCP tools attach after the session-start hook, is not verified in the hosts yet.
- If the server restarts during a session, calls work as before from the next call onward. Calls that were running in the meantime end with an error and are not retried automatically.

## Supported Platforms

- Supported: any environment on which JDK 25 runs. The release assets are `sennard-<version>.jar` and `sennard-<version>.jar.sha256`; the jar is the same file on every operating system.
- Verified on one Windows PC only; see Verification and Known Limitations.
- Paths that use the Node.js runtime have been removed from the product. If you called scripts that ran with Node in 5.x directly, move to `run_skill_check`.

## Known Limitations

- **Waking idle sessions.** Claude Code wakes sessions with two wait hooks, one registered at session start and one at turn end. A single wait lasts up to 24 hours, and a session that has been idle longer than that, or whose Sennard server restarted in the meantime, can be woken again after the next turn ends. This works only in an interactive Claude Code session with a person attached; a session started with `-p` is not woken, and sessions started through the SDK have not been measured. The distinction relies on the value of `CLAUDE_CODE_SESSION_ATTENDED` that Claude Code passes to hooks, a variable that is not in Claude Code's official documentation (measured with Claude Code 2.1.319; in a separate measurement with Claude Code 2.1.316 on Windows, the value was `0` in a `-p` session and `1` in an interactive session with a person attached). Codex and Antigravity do not wake idle sessions in 6.0.0, and messages are delivered at the next hook boundary (prompt submission, tool boundary, turn end). The Codex `session-messaging.json` setting, `AGENT_GOVERNANCE_CODEX_QUEUE_WAKE`, and `AGENT_GOVERNANCE_ANTIGRAVITY_QUEUE_WAKE` are not read.
- **Convergence roots with overlapping write scopes opened at the same moment.** A root whose write scope overlaps an active root's is refused with `ROOT_CONFLICT` (while `a` is open, `a/b` does not open), and two roots with exactly the same scope opened at the same moment are decided by the primary key of `convergence_active_surfaces`. Two roots that only overlap (`a` and `a/b`) and are opened at the same moment may both open, because at the isolation level `READ COMMITTED` neither request sees the other's uncommitted row. 6.0.0 keeps `READ COMMITTED` and does not close this gap; if it happens, release or close one of the roots. See [Workflows and the Edit Gate](../user/usage.md#workflows-and-the-edit-gate).
- **Antigravity child conversations that have not called a Sennard tool.** The Antigravity hook input does not say whose child a conversation is (only `conversationId`). After a child conversation calls a Sennard tool once, the MCP `_meta` of that call marks it as a child and it leaves `list_session_status` and the admin page; before that it is listed like a main session, and on the admin page it goes to the "Undetermined" group when it has no summary and no role. Claude Code subagents (`agent_id`) and `--agent` sessions (`agent_type`) are told apart by the hook input. See [Session collaboration](../user/collaboration.md).
- **`read_prompt_transcript` reads Claude Code transcripts only.** In 6.0.0 the server has one transcript reader, for Claude Code. For Codex, Gemini CLI and Antigravity the tool answers `status: UNSUPPORTED` (the host's transcript format has not been measured, so none is guessed); to read what the user said in those sessions, use `recall_user_prompts`. See [Session collaboration](../user/collaboration.md).
- **Multiple OS users on the same PC.** There is one server per state folder and the default state folder is in the user's home, so two users each have their own server and address. The server accepts any program on this computer, so it does not tell the users apart (see the security policy).
- **Operating systems other than Windows.** The release was tested on one Windows PC only. The code does not choose a branch by the name of the operating system, but the branches that depend on the file-system permission model (POSIX permissions) have not been run on Linux or macOS. The Codex plugin cache layout and the Gemini CLI extension folder, where the installation writes the host definitions, have not been confirmed on a machine that has those hosts.
- **Plugin updates empty the definitions.** A host copies the plugin's empty definitions again when it installs or updates a plugin, so run `sennard hooks` after that (`sennard status` lists the copies that are empty).
- **Programs of the same OS user.** Programs running with the same user's privileges can call the server. For the trust boundary, see the [security policy](../../SECURITY.md).
- **Background notifications count as new requests (AGS3-D-0311).** In Claude Code, a background-task notification, and a turn that a Stop hook continues, reach the prompt-submission hook like a user prompt, so the workflow gate asks for a workflow again and the session board asks for a new summary. Resume the open workflow to continue.
- **Parallel Sennard tool calls in one turn of Claude Code (AGS3-D-0312).** When Claude Code calls Sennard tools in parallel in the same turn, the model observation can be empty and the call is refused with `BINDING_REQUIRED`. 6.0.0 only adds the reason to the answer (`details.observation.transcriptReason`); the cause is fixed in the next version. Calling the failed tool once more observes it anew.
- **A command whose target cannot be determined, inside an operation workflow.** In a workflow opened with `start_operation_workflow`, a command whose written files Sennard cannot determine (for example running a build tool such as Gradle) is treated as a file change and refused. Run such a command inside the change workflow that planned those files. This is fixed in the next version.
- **Claude Code plugin from a local folder.** When the Claude Code plugin is installed from a marketplace added with a local folder path, Claude Code loads the plugin from that folder, which `sennard hooks` does not write to, so the plugin keeps its empty definitions and the hooks and MCP tools of Sennard do not run. `sennard hooks` ends with an error that names the file Claude Code reads and the definition to copy over it. A plugin installed from the git marketplace works. See [Plugin updates and `sennard hooks`](../user/update.md#plugin-updates-and-sennard-hooks).

# Sennard 6.0.0 릴리스 노트

Sennard 6.0.0은 기반을 다지는 판입니다. 호스트마다 띄우던 Node 프로세스(MCP 서버, relay, 훅)를 사용자·PC당 Java 서버 하나로 바꿨습니다. 설정은 로컬 H2에, 업무 상태는 별도로 연결한 데이터베이스에 저장합니다. 설치 방법과 일부 공개 계약이 바뀌므로 주 버전을 올렸습니다.

## 업그레이드 전 확인

- **서버 설치 단계가 생겼습니다.** 호스트 플러그인은 스킬과 빈 훅·MCP 정의를 담고, 설치가 이 PC의 정의를 호스트의 플러그인 사본마다 씁니다. 서버를 설치하지 않으면 MCP 도구가 연결되지 않습니다. 설치는 [README](../../README.ko.md#설치)를 따릅니다.
- **릴리스는 jar 하나이며 JDK 25가 필요합니다.** 자산은 `sennard-<판>.jar`와 `sennard-<판>.jar.sha256`, Antigravity 패키지 `sennard-antigravity-v<판>.zip`이고, 사용자의 JDK 25로 `java -jar sennard-<판>.jar install`을 실행합니다. OS별 압축 파일과 동봉 Java 런타임은 없습니다. Node.js는 필요 없습니다. 업무 상태를 위해 별도의 데이터베이스를 준비하고, 설치한 뒤 관리자 페이지에서 연결합니다.
- **6.0.0은 이전 판이 저장한 데이터를 읽지 않습니다.** 상태 저장소, 저장된 문서, 서명한 관리 기록의 형식이 새로 정해졌습니다. 이 서버에는 가져오기 명령이 없습니다. 이전 판의 상태 파일을 6.0.0에 연결하지 않습니다.
- **6.0.0 시험판이 쓰던 데이터베이스는 지우고 다시 연결해야 합니다.** 릴리스는 업무 데이터베이스의 모든 표를 스키마 `sennard` 하나에 둡니다. 6.0.0 시험판은 모듈마다 `sennard_*` 스키마를 따로 썼고, 로컬 설정 데이터베이스도 별도 스키마를 썼습니다. 그 스키마에서 옮기는 마이그레이션은 없습니다. 시험판을 실행한 적이 있으면 그 업무 데이터베이스(또는 `sennard_*` 스키마)와 상태 폴더의 `settings/sennard-settings` 데이터베이스를 지우고, 관리자 페이지에서 데이터베이스를 다시 연결합니다. 5.x에서 올리는 경우에는 해당하지 않습니다.
- **이전 Sennard 서버를 먼저 멈춥니다.** 6.0.0 서버에는 MCP·훅용 포트에도 관리자 페이지용 포트에도 고정 포트가 없습니다. 서버가 시작할 때마다 운영체제가 빈 포트를 주고, 서버는 상태 폴더의 `server.properties`에 주소를 알립니다. 이전 Sennard 서버를 포함해 다른 프로그램이 포트를 쥐고 있어도 6.0.0 서버는 막히지 않습니다. 계속 떠 있는 이전 서버는 6.0.0의 일부가 아니므로 끝냅니다.

## 이전 주 판에서 올리는 순서

1. Claude Code, Codex, Antigravity의 Sennard 세션을 모두 닫아 이전 서버와 relay를 끝냅니다. 이전 서버가 끝났는지, 곧 이전 서버가 쓰던 관리자 페이지 포트 47615에서 아무것도 듣지 않는지 다음 명령으로 확인합니다. 아무것도 나오지 않아야 합니다.

   ```powershell
   netstat -ano | findstr LISTENING | findstr :47615
   ```

   ```bash
   lsof -nP -iTCP:47615 -sTCP:LISTEN
   ```

2. `sennard-<판>.jar`와 `.sha256`을 받아 jar를 대조한 뒤 JDK 25로 `java -jar sennard-<판>.jar install`을 실행합니다. jar를 `~/.sennard/install`에 풀고 서버를 시작해 준비를 기다린 뒤 훅·MCP 정의를 씁니다. OS 서비스에는 등록하지 않습니다.
3. 세 호스트의 플러그인을 [README](../../README.ko.md#설치)대로 6.0.0으로 함께 올립니다. Codex는 `/hooks`에서 Sennard hook을 다시 검토하고 신뢰합니다. 각 플러그인을 설치한 뒤 `sennard hooks`를 실행합니다(모든 운영체제 공통). 이 명령이 호스트가 읽는 플러그인 사본에 이 PC의 훅·MCP 정의를 씁니다([플러그인 업데이트와 `sennard hooks`](../user/update.ko.md#플러그인-업데이트와-sennard-hooks)).
4. 새 세션을 열어 `sennard status`의 `healthy`가 `true`인지, Sennard 도구가 보이는지 확인합니다.
5. 관리자 페이지 주소는 `sennard status`의 `adminPage` 값입니다. 포트는 서버가 시작할 때마다 운영체제가 정하며 설정이 없습니다.

**`sennard install`이 `START_FAILED`로 끝난 경우.** 훅 파일 배치는 실행되지 않고, `sennard install`을 다시 실행하면 `ALREADY_INSTALLED`로 거절됩니다. [문제 해결](../user/troubleshooting.ko.md)에 적힌 원인을 없앤 뒤 `sennard start`, `sennard hooks`를 차례로 실행합니다.

`sennard`라는 프로그램은 없고 PATH에 등록하는 것도 없습니다. `sennard <명령>`은 `java -jar <설치 폴더>/versions/<판>/sennard-<판>.jar <명령>`을 뜻합니다. 설치·업그레이드 출력(`Run Sennard commands with: ...`)이나 `sennard status`의 `command` 필드에 표시된 명령을 사용합니다. 업그레이드하면 경로가 바뀝니다. 설치 폴더(`~/.sennard/install`)를 시스템의 파일 이름 인코딩으로 쓸 수 없으면 `sennard install`이 `INSTALL_ROOT_NOT_REPRESENTABLE`로 끝납니다. `SENNARD_INSTALL_ROOT`를 그 인코딩으로 쓸 수 있는 폴더로 지정합니다.

플러그인 이름과 MCP 서버 이름이 다르므로 6.0.0 플러그인을 설치하기 전에 각 호스트의 이전 플러그인을 먼저 제거합니다. `ags`를 호출하거나, `AGS_*`·`AGENT_GOVERNANCE_*` 변수를 설정하거나, `ags.` 옵션을 넘기거나, 이전 저장소 주소를 쓰는 스크립트와 설정은 위 이름으로 고쳐야 합니다.

### 이전 데이터

6.0.0은 이전 판의 상태 파일을 읽지도 바꾸지도 않으며 가져오기 명령도 없습니다. 돌아가야 하면 `sennard stop`으로 6.0.0 서버를 멈추고 `sennard uninstall`로 설치를 지운 뒤(6.0.0의 상태 폴더는 남습니다) 이전 플러그인을 다시 설치합니다. 이전 상태 파일은 그대로입니다.

## 바뀐 점

- **모든 요청은 종류별 workflow 안에서 처리합니다.** workflow에는 종류가 있고, 여는 도구가 종류를 정합니다. `start_inquiry_workflow`(답변·조사: 읽기만, `skills` 옵션, 턴이 끝나면 서버가 닫음), `start_workflow`(변경: `skills` 필수, 변경 계획의 파일을 편집), `start_operation_workflow`(시험 실행·push·설치·배포 같은 실행·운영: `target`과 `skills` 필수, 명령 허용, 파일 편집 거절)입니다. 종류는 enum 하나이고, 각 상수가 도구, `skills` 필수 여부, 프로세스, 닫히는 때, 메시지 키를 갖습니다. 요청에 workflow가 생길 때까지 훅이 그 요청의 도구(Sennard 도구, 호스트의 스킬 도구, 도구 불러오기 도구는 제외)를 거절하고 턴 끝을 붙잡아 두며(한 요청에 최대 세 번), 요청마다 열린 workflow의 목록과 `resume_workflow`, 새로 여는 방법을 보여 줍니다. 스킬은 선언할 뿐 강제하지 않으며, 선언한 스킬을 썼는지는 검사하지 않습니다. JEV가 켜져 있으면 `skills`가 필수인 종류는 시작 전에 분류를 돌려(프롬프트 훅이 돌린 것을 재사용) 그 조언을 시작 결과나, 스킬을 빠뜨린 시작의 거절에 담습니다. 파일 편집은 그 파일을 변경 계획에 담은 변경 workflow에 속하고, workflow 없이 두 파일까지 바꾸게 두던 이전 허용은 없어졌습니다. [사용법](../user/usage.ko.md#workflow-종류와-관문)을 봅니다.
- **PC당 서버 하나.** Spring Boot 4.1 내장 웹 서버 하나가 MCP 서버이고 훅의 수신처입니다. MCP 엔드포인트는 `127.0.0.1`의 `POST /mcp`입니다. 포트는 고정이 아닙니다. 관리자 페이지와 마찬가지로 시작할 때마다 운영체제가 빈 포트를 주며(관리자 페이지는 같은 서버의 별도 포트), 서버가 상태 폴더의 `server.properties`에 주소를 알립니다. 상태 폴더 하나에는 서버가 하나만 실행됩니다(`SERVER_ALREADY_RUNNING`). 호스트는 설치가 등록한 stdio 중계를 거쳐 `/mcp`에 닿으며, 중계는 그 파일로 서버를 찾습니다. 세션별 shim 프로세스와 이름 있는 파이프 전송이 없어졌습니다.
- **서버 시작.** 설치 명령, `sennard start` 또는 세션 시작 훅이 서버를 띄웁니다. OS 서비스에는 등록하지 않습니다.
- **상태 저장.** 설정은 로컬 H2에, 업무 상태는 별도로 연결한 데이터베이스에 저장합니다. 로컬 상태 폴더 기본값은 `~/.sennard`입니다. 업무 데이터베이스의 모든 표는 스키마 `sennard` 하나에 있으며, Sennard가 계정 하나로 만들고 마이그레이션합니다. 모듈별 스키마는 없어졌습니다.
- **업무 데이터베이스는 관리자 페이지에서만 연결합니다.** 연결 정보(JDBC 드라이버, URL, 계정, 비밀번호 파일 경로, 보호 방식)는 패스키로 서명해 상태 폴더의 설정 데이터베이스에 저장하며, 서버·`sennard admin-reset`·`sennard attachments`가 그곳에서 읽습니다. `sennard.yaml`의 `sennard.store.database.*`는 읽지 않습니다. 이전 설치에 그 키가 있었다면 관리자 페이지에서 데이터베이스를 다시 연결합니다. 연결 정보는 `sennard uninstall` 뒤에도 상태 폴더에 남고 이후 설치가 찾습니다. 연결은 데이터베이스가 준비된 뒤에도 언제든 바꿀 수 있습니다. 저장하기 전에 새 데이터베이스에 접속해 표를 준비해 보고, 실패하면 아무것도 저장하지 않습니다. 저장한 연결은 서버를 다시 시작한(`sennard stop` 다음 `sennard start`) 뒤에 쓰이며, 그때까지 화면이 이를 알립니다. 이전 데이터베이스의 기록은 새 데이터베이스로 옮겨지지 않습니다. [업무 데이터베이스](../user/state.ko.md#업무-데이터베이스)를 봅니다.
- **관리자 페이지의 패스키는 하나.** 개인용은 패스키를 하나만 등록합니다. 패스키가 있는 동안 서버는 다른 패스키의 등록을 거절하고(`ADMIN_CHANGE_INVALID`, 사유 `SINGLE_PASSKEY`), 하나뿐인 패스키는 폐기할 수 없습니다. 잃어버리면 `sennard admin-reset`을 실행합니다. 관리자 페이지 레이아웃을 정비했고(목록, 패널, JEV 조건, 요약을 먼저 보여 주는 세션 행), 페이지는 브라우저 저장소를 쓰지 않습니다. 판별되지 않은 세션 묶음의 「목록에서 제거」는 없어졌습니다. 세션은 역할을 받거나 끝나면 그 묶음에서 나가기 때문입니다.
- **에이전트의 요청 없이 JEV 조언.** JEV를 부를 수 있으면 사용자 프롬프트가 도착할 때 서버가 스스로 스킬 분류를 시작하고(훅은 기다리지 않습니다), 같은 세션의 다음 훅이 짧은 결과를 한 번 붙입니다(스킬 최대 8개, 판정과 신뢰도). JEV가 꺼져 있거나 조건이 맞지 않으면 아무것도 보내거나 붙이거나 기록하지 않으며, 호출했다가 실패한 경우만 로그를 남깁니다. `classify_skills`는 그대로 있고, 같은 프롬프트에는 이미 얻은 답을 돌려줍니다. JEV 키는 봉인(AES-256-GCM)해 업무 데이터베이스의 `jev_keys` 표에 저장합니다. [JEV 스킬 선택 조언](../user/admin-page.ko.md#jev-스킬-선택-조언)을 봅니다.
- **세션 요약 요청.** 메인 세션의 세션 게시판 요약이 비었거나 마지막 메시지보다 오래되었으면, 요청을 실을 수 있는 모든 훅이 에이전트에게 `update_session_status`로 요약을 쓰라고 안내합니다. 요약이 마지막 메시지보다 새로워지면 안내가 멈춥니다. [세션 협업](../user/collaboration.ko.md)을 봅니다.
- **트레이 아이콘.** 컴퓨터에 시스템 트레이가 있는 데스크톱이 있으면 서버가 그곳에 아이콘을 보입니다. 메뉴로 관리자 페이지를 열고 서버를 멈출 수 있으며, 툴팁에 버전과 현재 관리자 페이지 주소가 나옵니다. 데스크톱이나 트레이가 없으면 아이콘을 보이지 않고 로그 한 줄을 남기며 서버는 그대로 동작합니다. [사용법](../user/usage.ko.md)을 봅니다.
- **훅은 Java 클라이언트를 거쳐 서버에 닿습니다.** Claude Code, Gemini CLI, Antigravity의 모든 훅과 Codex의 세션 시작·종료는 작은 Sennard Java 클라이언트(`sennard-hook-client`, 설치된 `java`로 시작)를 실행하는 command이고, Codex의 나머지 훅은 중계를 거치는 MCP 도구 훅입니다. 클라이언트는 호출마다 `server.properties`에서 서버 주소를 읽고, 다른 프로그램을 띄우지 않으며(서버를 찾지 못한 세션 시작에서 설치된 jar를 띄우는 경우만 예외), 세션 시작 때 세션이 속한 호스트 프로세스를 서버에 알려 그 프로세스가 끝나면 서버가 바로 세션을 끝냅니다. 서버의 포트가 고정이 아니므로 HTTP 훅은 없습니다. `curl`·셸·Node 프로세스는 없습니다.
- **Gemini CLI 훅.** Gemini CLI 확장(`gemini-extension/`)이 세션·프롬프트·턴 끝·모델 요청·도구·압축 이벤트를 받습니다. Codex의 모델 요청 이벤트도 받습니다.
- **스킬 스크립트가 서버의 검사로 바뀌었습니다.** 스킬 폴더의 실행 스크립트 대신 MCP 도구 `run_skill_check`를 호출합니다. 스킬 지시문은 파일 그대로입니다.
- **스킬이 두 묶음으로 나뉩니다.** 스킬마다 `classification.json`의 `category`가 `agent-correction`(15개) 또는 `specialist`(8개: `cs-engineering`, `code-review`, `test-engineering`, `solid-design`, `ui-ux-design`, `korean-prose-editor`, `software-security-auditor`, `prompt-engineering`)입니다. README와 관리자 페이지가 이 두 묶음으로 스킬을 나누어 보여 주며, 스킬을 고르고 검사하고 hook으로 다루는 방식은 바뀌지 않습니다. 6.0.0 작업 중에 먼저 지웠던 전문분야 스킬 7개를 되살려 스킬은 모두 23개입니다. test-engineering 검사는 명령을 대신 실행합니다. `run_skill_check`로 `test-engineering`의 `run` 명령을 호출하면 서버를 시작한 사용자의 권한으로 프로그램을 실행하고 실행 영수증을 기록합니다.
- **같은 PC의 프로그램만 연결할 수 있으며 OS 사용자는 구분하지 않습니다.** 서버는 `127.0.0.1`에만 묶이므로 같은 PC의 프로그램만 연결할 수 있습니다. 개인용은 한 사람의 PC를 전제로 하므로 같은 PC의 다른 OS 계정은 구분하지 않습니다. 신뢰 범위는 [보안 정책](../../SECURITY.ko.md)을 봅니다.
- **편집 관문 예외 경로는 사용자가 정합니다.** 사용자가 관리자 페이지에서 패스키로 서명한 목록이 편집 관문이 세지 않는 폴더를 정합니다. 환경 변수나 서버 설정은 예외 경로를 더하지 않습니다(`AGENT_GOVERNANCE_PHASE_EXEMPT_PATHS`는 읽지 않습니다). 이 목록을 바꾸는 MCP 도구는 없고 기본값은 빈 목록입니다. 경로는 Windows 경로, POSIX 경로, Git Bash의 드라이브 경로를 쓸 수 있고, Windows의 Git Bash `/tmp`처럼 드라이브가 없는 경로는 그 문자열 그대로 적습니다. 경로 구분자 단위로 맞추며 `..`을 푼 뒤 판정합니다. [편집 관문 예외 경로](../user/admin-page.ko.md#편집-관문-예외-경로)를 봅니다.
- **근거 파일을 첨부로 보관합니다.** 새 도구 다섯 개 `artifact_begin`, `artifact_chunk`, `artifact_finish`, `artifact_status`, `artifact_read`가 파일을 최대 262144바이트의 청크로 업로드합니다. 첨부는 파일 1~64개의 묶음이며 함께 업로드하고 파일마다 검증해 ID 하나로 보관하므로, 호출자가 파일을 하나로 첨부하려고 압축할 필요가 없습니다. 서버는 상태 폴더의 `attachments` 폴더에 파일을 암호화해 저장하고(AES-256-GCM 세그먼트, 무작위 파일 이름, 소유자 전용 별도 폴더의 키), DB에는 메타데이터만 둡니다(진행 중인 업로드는 `upload_staging`, 보관된 첨부는 `attachment`, `attachment_file`, `attachment_storage`이며 감사할 수 있도록 넣기만 하고 바꾸지 않습니다. FK 없음. 마이그레이션 V21). 새 설정 `sennard.attachments.*`가 한도를 정하고, `sennard attachments`(`check`, `rekey --from <keyId>`, `keygen --id <keyId>`, `purge-orphans [--yes]`)가 폴더와 행을 대조하고 키를 바꾸고 격리 폴더를 비웁니다. 새 명령 `sennard attachments prepare`와 `sennard attachments send`는 큰 파일을 올리는 업로드 클라이언트입니다. `sennard attachments send`는 파일 하나의 청크를 보낼 뿐 마무리하지 않으며, 모델이 `attachmentId`로 `artifact_finish`를 한 번 호출하고 첨부는 모든 파일이 검증을 통과했을 때만 만들어집니다. `artifact_chunk`, `uploadId`로 조회하는 `artifact_status`, `attachmentId`로 하는 `artifact_finish`는 세션이 필요 없으며(무작위 `uploadId` 또는 `attachmentId` 하나로 업로드에 묶입니다), 첨부의 작성자는 계속 `artifact_begin`을 호출한 세션입니다. stage 결과는 파일을 첨부 id와 파일 번호(`seq`)로 가리킵니다. 서버는 호출자 컴퓨터의 경로를 읽지 않으므로, `record_stage_result`의 근거·산출물·출력 파일은 결과를 기록하는 세션이 먼저 업로드한 첨부여야 합니다. [첨부와 업로드](../contributing/attachments.ko.md)를 봅니다.
- **관리자 페이지의 workflow 통계.** 새 화면이 기간별로 종류마다 시작한 workflow 수(스킬 없이 시작한 수 포함), 종류별로 선언한 스킬, 최근 workflow 50건(종류, 목표, 상태, 선언한 스킬, 시작 시각, 호스트)을 보여 줍니다. 보기만 하는 화면이라 패스키가 필요 없습니다. 기록된 종류가 없는 workflow는 변경으로 세며, 그렇게 센 건수를 화면에 알려 줍니다. 집계는 마이그레이션 V22가 뒷받침합니다. V22는 `workflow_runs.kind` 열(기존 행은 모두 `CHANGE`)과 기간 색인, 시작이 선언한 스킬마다 한 행을 두는 `workflow_run_skills` 표를 추가합니다. V22 이전에 시작한 workflow의 스킬은 다시 채우지 않으므로, 그런 workflow는 종류별로만 세고 스킬은 없는 것으로 셉니다. [workflow 통계](../user/admin-page.ko.md#workflow-통계)를 봅니다.
- **선언형 열 암호화(기여자용).** record 구성요소에 `@Encrypted`를 붙이면 업무 데이터베이스 저장소의 공통 행 경로가 쓸 때 봉인하고 읽을 때 엽니다. 모듈이 값을 손으로 봉인하지 않아도 됩니다. JEV 키가 이를 씁니다. 봉인기, 결속 데이터(scope, 이름, 지문), 저장 형식은 전과 같으므로 보이는 변화가 없고 저장된 값을 이전할 필요도 없습니다. 저장된 값은 자기 이름과 지문으로만 열립니다.
- **`finalize_workflow`는 계획 밖 변경을 거절합니다.** 변경 기록이 제출한 변경 계획 밖에서 바뀐 파일을 찾으면, 마무리는 `GATE_FAILED`(`details.reason=UNPLANNED_CHANGES`, `details.unplanned`에 파일 목록)로 거절됩니다. `submit_change_plan`으로 그 파일을 계획에 더하거나 변경을 되돌린 뒤 다시 호출합니다. 이 검사는 단계 검사보다 먼저 합니다. `abort_workflow`는 이 때문에 거절하지 않습니다.
- **`codex_hook`을 뺀 모든 MCP 도구가 공통 응답 봉투로 답합니다.** 응답은 `schemaVersion`, `ok`, `data`, `error`를 담고 `isError`는 `ok`의 반대 값입니다(`ok`가 false일 때만 true). `run_skill_check`의 오류도 같은 봉투(`ok` false, `isError` true)이고 `exitCode`가 없습니다. 성공했을 때 `exitCode`는 `data` 안에 있습니다. `codex_hook`만 예외인데, Codex의 훅 실행기가 그 응답을 훅 자신의 JSON으로 읽기 때문입니다.
- **레지스트리 항목이 없는 스킬도 workflow 시작에 쓸 수 있습니다.** 설치된 스킬 폴더(`skills/<이름>/SKILL.md`)의 스킬은 레지스트리에 항목이 없어도(예: `session-board`, `orchestrator`) workflow 시작의 `skills`에 이름만으로 적을 수 있습니다.
- **호스트가 모델을 관측하지 못한 이유.** `BINDING_REQUIRED` 응답의 `details.observation.transcriptReason`(`waitedMs`, `linesSeen` 함께)에 Claude Code 트랜스크립트에서 모델을 얻지 못한 이유가 `TRANSCRIPT_UNREADABLE`, `CALL_LINE_NOT_FOUND`, `OTHER_THREAD`, `MODEL_FIELD_MISSING` 중 하나로 담깁니다.
- **검사가 이름 댄 파일이 루트에 없으면 `NOT_FOUND`입니다.** `run_skill_check`나 엔지니어링 검사에 준 묶음이 루트에 없는 파일을 이름으로 대면 `INVALID_INPUT` 대신 `NOT_FOUND`(`practices.io.fileNotFound`)로 답합니다. 일반 파일이 아닌 것을 가리키는 경로는 그대로 `INVALID_INPUT`입니다.

### 고친 결함

5.1.0 이하에서 관찰된 결함입니다. 6.0.0 개발 중에 찾아 고친 결함은 발행된 적이 없으므로 적지 않되, 처음 두 항목은 관찰되는 동작이나 해야 할 일이 바뀌므로 적습니다.

- **편집 관문이 셸 쓰기를 엉뚱한 폴더로 판정함(AGS3-D-0303):** 명령에서 읽어 낼 수 없는 쓰기(스크립트 파일, 경로로 실행하는 빌드, `git pull`)는 세션의 작업 폴더가 실행 중인 workflow의 범위에 들어 있을 때만 그 안의 쓰기로 셌습니다. 그래서 세션이 폴더 A에서 돌고 workflow가 폴더 B에 대한 것이면 `cd B && ./gradlew build`가 거절되었습니다. 이제 셸 검사가 그런 쓰기마다 셸이 있던 폴더(`cd`, `pushd`, `Set-Location`, `cmd cd /d`, `git -C`, 중첩 셸, Git Bash의 `/d/...`·`D:/...` 표기)를 기록하고, 그 폴더가 모두 실행 중인 workflow의 쓰기 범위 안에 있을 때만 관문이 그 쓰기를 포함합니다. 검사가 따라갈 수 없는 폴더(변수, glob, `popd`, `cd -`)는 아무것도 열지 않습니다. Claude Code, Codex, Antigravity가 같은 경로를 씁니다.
- **업무 데이터베이스를 모듈마다 스키마로 나눔(AGS3-D-0304):** 6.0.0 시험판의 설계 실수였습니다. 계정이 하나이고 ROLE·GRANT가 없으므로 스키마를 나눌 이유가 없었습니다. 모든 표를 스키마 `sennard` 하나에 둡니다. 시험판이 쓰던 데이터베이스는 「업그레이드 전 확인」을 봅니다.

- **에이전트들이 서브에이전트를 호출하지 않음(후속):** 5.0.0의 설명 수정에 이어 `coordinate-subagents`의 위임 조건 문구를 고쳤습니다. 사용자가 요청하거나 순이익 조건을 모두 충족할 때만 위임을 "허용"한다던 문장은 그 경우에 독립 단위를 위임하라는 문장으로 바꿨고, 비용 조건은 "직접 실행보다 여전히 적게 든다"에서 "직접 실행보다 분명히 더 들지 않는다"로 바꿨습니다. 그래서 비용이 직접 실행과 비슷한 단위는 이 조건 때문에 제외되지 않습니다. 문구만 바꿨으며 에이전트 행동에 미치는 효과는 세 호스트에서 측정하지 않았습니다.
- **자기가 일으킨 문제의 복구와 불합격 판정을 받은 자기 결과물의 재작업을 할지 묻고 멈춤:** 접수 안내에 자기가 일으킨 변경의 복구와 미달로 확인된 자기 결과물의 재작업은 묻지 않고 시작하며, 별도 승인 대상에 닿는 단계만 묻는다는 문구를 넣었습니다. 문구만 바꿨으며 에이전트 행동에 미치는 효과는 세 호스트에서 측정하지 않았습니다.
- **JEV 스킬 분류 응답이 항상 `OUTPUT_TOO_LONG`으로 버려짐:** 분류 응답의 출력 상한이 1000토큰이어서 스킬 25개에 대한 응답이 이를 넘었습니다. 상한을 4000토큰으로 올렸습니다.
- **`classify_skills`의 입력 누락이 런타임 실패로 나감:** `MCP_UNAVAILABLE`로 돌려주던 것을 입력 오류인 `INVALID_INPUT`(`details.category=request-state`, `details.reasonCode=CONTEXT_SOURCE_MISSING`)으로 돌려줍니다.
- **JEV 사용액이 항상 0이고 예약액이 쌓임:** JEV 응답에는 청구 금액이 없으므로, 보낸 호출을 입력 토큰으로 계산한 추정액으로 기록하고 기록하면 그 예약을 해제합니다. 보냈지만 사용량을 알 수 없는 호출은 예약을 유지합니다.
- **JEV 사용액과 예산이 MCP 서버 프로세스마다 따로 있음:** 사용액을 서버의 데이터베이스에 저장하고, 관리자 페이지와 예산 확인이 같은 합계를 읽습니다. 6.0.0은 사용자·PC당 서버 하나이므로 예산은 그 서버에 연결된 모든 세션에 적용됩니다.
- **서브에이전트가 스킬을 호출만 하고 절차를 지키지 않아도 감지하지 않음:** 서브에이전트 시작 안내가 호출은 적용이 아님을 알리고 스킬별 절차·필수 산출물·검사를 요구합니다(공통 행동 기준은 서버가 보내는 접수 블록에 있으므로 턴이 끝날 때 훅이 읽은 기록을 확인할 파일이 없습니다). 안내만 추가했으며 에이전트 행동에 미치는 효과는 세 호스트에서 측정하지 않았습니다.
- **위임 부모가 공유 시험 서버의 계획 없이 서브에이전트를 한꺼번에 띄움:** `coordinate-subagents` 참고 문서에, 브리프에 단위마다 고른 스킬을 적고 공유 실행 자원은 위임 전에 수용량·실행 순서·실행마다의 담당을 정하라는 문구를 넣었습니다. 문구만 바꿨으며 에이전트 행동에 미치는 효과는 세 호스트에서 측정하지 않았습니다.

| workflow 없이 제품 파일 편집 | 두 파일까지 허용, 세 번째부터 거절 | 요청이 잡은 변경 workflow가 그 파일을 변경 계획에 담지 않으면 바로 거절 |
| 파일 업로드 | 없음 | 새 도구 `artifact_begin`(`files` 1~64개 항목을 받고 `attachmentId`와 파일마다의 `uploadId`를 답함), `artifact_chunk`(`uploadId`로), `artifact_finish`(`attachmentId`로. 모든 파일이 검증을 통과했을 때만 첨부를 만듦), `artifact_status`(`uploadId` 또는 `attachmentId`로), `artifact_read`(파일인 `seq`를 받음. 기본 0)(`purpose`는 `evidence`만, `sha256`은 `sha256:<16진수 64자>`로 씀). 새 오류 코드는 모두 `details.retryable`을 싣습니다: `ARTIFACT_OPERATION_CONFLICT`, `ARTIFACT_CHUNK_CONFLICT`, `CHUNK_HASH_MISMATCH`, `ARTIFACT_BUSY`, `ARTIFACT_INCOMPLETE`, `ARTIFACT_HASH_MISMATCH`, `ARTIFACT_CORRUPTED`, `ARTIFACT_LIMIT`(`details.limit`), `ARTIFACT_STORAGE_UNSAFE`, `ARTIFACT_STORAGE_IO_ERROR`, `ARTIFACT_KEY_MISSING`, `ARTIFACT_STORAGE_FULL`, `ARTIFACT_UNSUPPORTED_PURPOSE`, `ARTIFACT_EXPIRED`, `ARTIFACT_NOT_FOUND` |
| `record_stage_result`의 `evidence[]` | `locator`, `digest`, `note`. 로컬 파일은 해시만 확인 | `attachmentId`와 `digest`가 필수이고, `seq`(첨부의 파일. 생략하면 0)가 `digest`가 속한 파일을 가리키며, `locator`는 없어집니다(`digest`가 없으면 계약 오류 `INVALID_INPUT`). 첨부가 있어야 하고 기록하는 세션이 만든 것이어야 하며, 아니면 기록이 `BINDING_INVALID`(`details.reason` `ATTACHMENT_NOT_FOUND` 또는 `ATTACHMENT_AUTHOR_MISMATCH`)로 실패합니다. 첨부의 sha256이 `digest`와 다르면 통과하는 단계는 `BINDING_INVALID`(`details.reason` `ARTIFACT_DIGEST_MISMATCH`)로 거절하고 다른 단계는 `NOT_CHECKED`로 기록하며, 같으면 `SHA256_MATCHED`로 기록합니다. 근거 두 항목이 같은 첨부를 가리킬 수 있습니다. 서버는 로컬 파일의 사본을 더 이상 보관하지 않습니다 |
| `record_stage_result`의 `output.artifacts[]`, `outputFile`, `artifactChecks[]` | `locator`(경로 또는 라벨). `outputFile`은 서버가 읽는 로컬 JSON 파일의 절대 경로를 담은 `{locator, digest}` | 세 곳 모두 `locator`가 `attachmentId`와 `seq`로 바뀝니다. `output.artifacts[]`는 `attachmentId`, `seq`, `digest`를, `outputFile`은 `{attachmentId, seq, digest}`(`output.output`의 JSON 객체를 담은 첨부의 파일, 16 MiB 이하)를, 서버가 채우는 `artifactChecks[]` 항목은 `attachmentId`와 `seq`를 가집니다. `seq`는 생략하면 0이고, `digest`는 그 파일의 것입니다. `evidence[]`와 같은 규칙으로 판정합니다. `claim_workflow_attempt`의 `priorFailure.evidenceRefs`는 호출한 세션의 첨부 id이며, 없거나 다른 세션의 첨부이면 `MISSING_EVIDENCE`(`details.reason` `ATTACHMENT_NOT_FOUND` 또는 `ATTACHMENT_AUTHOR_MISMATCH`)로 실패합니다 |
| `finalize_workflow`의 감사 대상 파일 확인 | 서버가 감사한 로컬 파일을 다시 읽고, 바뀌었으면 `AUDIT_TARGET_CHANGED`로 실패 | 서버는 호출자의 파일을 다시 읽지 않습니다. 필수 감사는 감사한 첨부가 기록된 sha256 그대로 남아 있고 전체를 읽을 수 있는지 확인하며, 아니면 `GATE_FAILED`(`details.reason` `AUDIT_TARGET_UNAVAILABLE`, `AUDIT_TARGET_CHANGED`를 대체)로 실패합니다. 첨부는 지우지 않으므로, 업로드한 뒤 원본 파일을 바꾸거나 지워도 finalize는 실패하지 않습니다 |
| 변경 계획 밖 변경이 있는 `finalize_workflow` | 검사하지 않음 | 단계를 검사하기 전에 `GATE_FAILED`(`details.reason=UNPLANNED_CHANGES`)로 거절합니다. `abort_workflow`는 거절하지 않습니다 |
| MCP 도구의 응답 | 도구마다 각자의 모양 | `codex_hook`을 뺀 모든 도구가 봉투 `schemaVersion`, `ok`, `data`, `error`로 답하고 `isError`는 `ok`의 반대 값입니다. `run_skill_check`의 오류도 같은 봉투이며 `exitCode`가 없습니다 |

stage 결과 이전: 5.x에서 `locator`로 stage 결과를 기록하던 호출자는 내용을 먼저 업로드해야 합니다. 결과를 기록하는 세션으로 모든 파일을 담아 `artifact_begin`을 한 번, 파일마다 `artifact_chunk`를, `attachmentId`로 `artifact_finish`를 한 번 호출한 뒤(작은 내용은 base64 청크(최대 256 KiB)로 도구에 바로 싣습니다) 돌려받은 `attachmentId`, 파일의 `seq`, 그 파일의 `sha256`을 `evidence[]`, `output.artifacts[]`, `outputFile`에, `attachmentId`를 `priorFailure.evidenceRefs`에 넣습니다. 큰 파일은 업로드 클라이언트로 올립니다. `sennard attachments prepare <file>`(`fileName`, `size`, `sha256`, `mediaType`을 출력)을 파일마다 실행하고, 그 값으로 `artifact_begin`을 한 번 호출한 뒤(`attachmentId`와 파일마다의 `uploadId`를 답함), `sennard attachments send --upload-id <id> <file>`(`uploadId`, `attachmentId`, `seq`, `received`를 출력하며 마무리하지 않음)을 파일마다 실행하고, `artifact_finish`를 한 번 호출합니다.

번들 검토 단계(`cs-implementation-review`, `test-sensitivity-review`, `change-code-review`) 이전: 번들의 모든 파일, 곧 manifest, 보고서, manifest나 검사가 읽는 모든 원파일을 결과를 기록하는 세션으로 먼저 업로드합니다. 첨부를 올릴 때의 파일 이름이 번들 폴더 아래의 경로입니다(`/`로 구분한 이식 가능한 상대 경로). 그 뒤 manifest와 보고서는 `output.artifacts[]`에, 원파일은 `evidence[]`에 각각 `attachmentId`, `seq`, `digest`로 적습니다. 서버가 비공개 임시 위치에 폴더를 다시 만들어 그 안에서 바뀌지 않은 `check-stage-bundle`을 실행하고 폴더를 지웁니다.

환경 변수도 바뀌었습니다. 5.x의 호스트 쪽 `AGENT_GOVERNANCE_*` 변수는 읽지 않습니다. `AGENT_GOVERNANCE_HOST_ATTESTATION`은 정적 헤더 `Sennard-Host-Label`로, `AGENT_GOVERNANCE_ADMIN_PORT`는 없어졌고(관리자 페이지 포트는 시작할 때마다 운영체제가 정합니다), `AGENT_GOVERNANCE_TOOL_SCHEMA_PROFILE`도 없어졌습니다. `AGENT_GOVERNANCE_PHASE_EXEMPT_PATHS`는 읽지 않으며, 편집 관문 예외 경로는 관리자 페이지에서만 정합니다. `AGENT_GOVERNANCE_CLASSIFICATION_CONFIG`(벤더 경로 설치 설정)는 읽지 않습니다.

## 서버가 없을 때의 동작

- Sennard 도구 자체는 서버가 없으면 호출 오류로 끝납니다.
- Sennard 도구가 아닌 도구에 대한 continuity 판정(편집 단계 확인 등)은 서버가 없으면(연결이 안 되거나 제때 답이 없으면) 세 호스트 모두 판정 없이 통과합니다. 5.x의 fail-open과 같은 범위입니다.
- workflow 관문도 Sennard 자체가 실패하면 같은 방식으로 열려 있습니다. 요청의 workflow 시작이 Sennard 사유(서버나 저장소를 쓸 수 없음, 연결·무결성 실패)로 실패했거나, workflow가 요청을 맡고 있는지 알려 주는 상태를 읽지 못하면 훅은 그 요청의 도구를 거절하지 않고 턴 끝도 붙잡지 않습니다. 편집 관문도 시작이 실패한 뒤의 편집을 통과시키고 그 파일을 기록하므로, 나중에 성공한 시작은 제품 파일이 이미 바뀐 뒤에 시작한 것으로 표시됩니다. 에이전트 자신의 실수(예: `skills` 누락)로 거절된 시작은 Sennard의 실패가 아니며 관문을 닫아 둡니다.
- 떠 있는 서버가 호출을 거절하는 것은 서버가 없는 것과 다릅니다. 게이트(거절하면 도구를 막는 도구 호출 훅: Claude Code의 편집 게이트와 Sennard 도구 허용 확인, Codex의 continuity 확인, Gemini CLI의 BeforeTool, Antigravity의 PreToolUse)는 서버가 HTTP 400 이상으로 답하면 도구를 막습니다. 동시 요청이 처음 만들기 경쟁에서 진 경우(409)도 같습니다. 거절 사유에 오류 코드가 들어가며, 사용자는 같은 호출을 다시 시도하거나 관리 페이지나 서버 로그에서 코드를 확인합니다. 게이트가 아닌 훅(세션 시작, 프롬프트 제출, 도구 결과, 턴 종료 등)은 전과 같아서, 거절은 실패한 훅이고 호스트는 그대로 진행합니다. 서버가 훅 입력을 읽기 전에 낸 거절(깨진 본문, 모르는 호스트·이벤트, 세션 식별자 없음)은 서버가 도구 거절로 바꾸지 않습니다. Antigravity와 Gemini CLI는 이 경우에도 도구를 막고, Claude Code와 Codex는 그대로 진행합니다.
- 세션을 시작할 때 듣고 있는 서버가 없으면 세션 시작 훅이 설치된 서버를 띄우고 준비될 때까지(최대 30초) 기다린 뒤 사건을 보냅니다. Sennard는 운영체제에 아무것도 등록하지 않습니다. Sennard가 설치되어 있지 않거나 서버를 띄울 수 없거나 제때 준비되지 않으면 그 세션에서는 Sennard 도구가 나타나지 않고, 서버가 나중에 떠도 다시 연결되지 않습니다. 훅이 `Sennard server is not reachable.`로 시작하는 안내를 냅니다. 서버를 띄운 뒤 세션을 다시 시작합니다. 호스트가 훅이 끝난 뒤에도 훅이 띄운 서버를 살려 두는지, 세션 시작 훅 뒤에 MCP 도구가 붙는지는 호스트에서 아직 확인하지 않았습니다.
- 세션 도중 서버가 다시 시작되면 다음 호출부터 그대로 동작합니다. 그 사이에 실행 중이던 호출은 오류로 끝나며 자동으로 재시도되지 않습니다.

## 지원 범위

- 지원: JDK 25가 도는 모든 환경. 릴리스 자산은 `sennard-<판>.jar`와 `sennard-<판>.jar.sha256`이며 jar는 모든 운영체제에서 같은 파일입니다.
- Windows PC 한 대에서만 검증했습니다. 검증과 알려진 한계를 봅니다.
- Node.js 런타임을 쓰는 경로는 제품에서 없어졌습니다. 5.x에서 Node로 실행하던 스크립트를 직접 호출하던 경우 `run_skill_check`로 옮깁니다.

## 알려진 한계

- **쉬고 있는 세션 깨우기.** Claude Code는 세션 시작과 턴 종료에 하나씩 둔 대기 훅 두 개로 깨웁니다. 한 번의 대기는 최대 24시간이며, 그보다 오래 쉬었거나 그 사이 Sennard 서버가 다시 시작된 세션은 다음 턴이 끝난 뒤부터 다시 깨울 수 있습니다. 이 동작은 사람이 붙어 있는 Claude Code 대화형 세션에서만 하며, `-p`로 띄운 세션은 깨우지 않습니다. SDK로 띄운 세션은 측정하지 않았습니다. 이 구분은 Claude Code가 훅에 넘기는 `CLAUDE_CODE_SESSION_ATTENDED` 값에 의존하며, 이 변수는 Claude Code 공식 문서에 없습니다(Claude Code 2.1.319에서 측정. 별도로 Windows의 Claude Code 2.1.316에서 측정한 값은 `-p` 세션 `0`, 사람이 붙은 대화형 세션 `1`). Codex와 Antigravity는 6.0.0에서 쉬는 세션을 깨우지 않으며, 메시지는 다음 훅 경계(프롬프트 제출, 도구 경계, 턴 종료)에서 전달됩니다. Codex의 `session-messaging.json` 설정과 `AGENT_GOVERNANCE_CODEX_QUEUE_WAKE`, `AGENT_GOVERNANCE_ANTIGRAVITY_QUEUE_WAKE`는 읽지 않습니다.
- **겹치는 쓰기 범위의 수렴 root를 같은 순간에 여는 경우.** 쓰기 범위가 활성 root와 겹치는 root는 `ROOT_CONFLICT`로 거절하며(`a`가 열려 있으면 `a/b`는 열리지 않습니다), 범위가 완전히 같은 두 root를 같은 순간에 열면 `convergence_active_surfaces`의 기본 키가 가립니다. 범위가 겹치기만 하는 두 root(`a`와 `a/b`)를 같은 순간에 열면 둘 다 열릴 수 있습니다. 격리 수준 `READ COMMITTED`에서는 두 요청이 서로의 미커밋 행을 보지 못하기 때문입니다. 6.0.0은 `READ COMMITTED`를 유지하며 이 틈을 막지 않습니다. 이렇게 되면 한쪽 root를 해제하거나 닫습니다. [Workflow와 편집 관문](../user/usage.ko.md)을 봅니다.
- **Sennard 도구를 부르지 않은 Antigravity 하위 대화.** Antigravity 훅 입력에는 대화가 누구의 하위 대화인지 알려 주는 값이 없습니다(`conversationId`만 있습니다). 하위 대화가 Sennard 도구를 한 번 부르면 그 호출의 MCP `_meta`로 하위 대화로 표시되어 `list_session_status`와 관리 페이지에서 빠지고, 그 전에는 메인 세션처럼 목록에 나옵니다. 관리 페이지에서는 요약·역할이 없으면 "구분 불가" 묶음에 들어갑니다. Claude Code 서브에이전트(`agent_id`)와 `--agent` 세션(`agent_type`)은 훅 입력으로 가려집니다. [세션 협업](../user/collaboration.ko.md)을 봅니다.
- **`read_prompt_transcript`는 Claude Code의 트랜스크립트만 읽습니다.** 6.0.0의 서버에는 Claude Code용 트랜스크립트 리더 하나만 있습니다. Codex·Gemini CLI·Antigravity에서는 이 도구가 `status: UNSUPPORTED`로 답합니다(호스트의 트랜스크립트 형식을 측정하지 않았으므로 추측하지 않습니다). 이 세션들에서 사용자가 한 말은 `recall_user_prompts`로 읽습니다. [세션 협업](../user/collaboration.ko.md)을 봅니다.
- **같은 PC의 여러 OS 사용자.** 서버는 상태 폴더마다 하나이고 기본 상태 폴더는 사용자의 홈에 있으므로 두 사용자는 각자의 서버와 주소를 가집니다. 서버는 이 컴퓨터의 어느 프로그램이든 받아들이므로 사용자를 구분하지 않습니다(보안 정책 참고).
- **Windows 밖의 운영체제.** 릴리스는 Windows PC 한 대에서만 시험했습니다. 코드는 운영체제의 이름으로 갈라지지 않지만, 파일 시스템 권한 모델(POSIX 권한)에 따라 갈라지는 분기는 Linux와 macOS에서 실행하지 않았습니다. 설치가 호스트 정의를 쓰는 Codex 플러그인 캐시의 구조와 Gemini CLI 확장 폴더는 해당 호스트가 있는 컴퓨터에서 확인하지 못했습니다.
- **플러그인 업데이트가 정의를 비웁니다.** 호스트는 플러그인을 설치하거나 업데이트할 때 플러그인의 빈 정의를 다시 복사하므로 그 뒤 `sennard hooks`를 실행합니다(`sennard status`가 비어 있는 사본을 알려 줍니다).
- **같은 OS 사용자의 프로그램.** 같은 사용자 권한의 프로그램은 서버를 호출할 수 있습니다. 신뢰 경계는 [보안 정책](../../SECURITY.ko.md)을 봅니다.
- **백그라운드 알림이 새 요청으로 셈해집니다(AGS3-D-0311).** Claude Code에서 백그라운드 작업의 알림과 Stop 훅이 이어 가게 한 턴은 사용자 프롬프트처럼 프롬프트 제출 훅에 닿습니다. 그래서 workflow 관문이 workflow를 다시 요구하고 세션 게시판이 새 요약을 요구합니다. 계속하려면 열린 workflow를 다시 이어 갑니다(`resume_workflow`).
- **Claude Code에서 같은 턴의 Sennard 도구 병렬 호출(AGS3-D-0312).** Claude Code가 같은 턴에 Sennard 도구를 병렬로 부르면 모델 관측이 비어 호출이 `BINDING_REQUIRED`로 거절될 수 있습니다. 6.0.0은 응답에 이유(`details.observation.transcriptReason`)만 담고, 원인은 다음 판에서 고칩니다. 실패한 도구를 한 번 다시 부르면 새로 관측됩니다.
- **operation workflow 안에서 쓰는 대상을 알 수 없는 명령.** `start_operation_workflow`로 연 workflow 안에서, 쓰는 파일을 Sennard가 판별할 수 없는 명령(예: Gradle 같은 빌드 도구 실행)은 파일 변경으로 보고 거절됩니다. 그런 명령은 그 파일을 계획한 change workflow 안에서 실행합니다. 다음 판에서 고칩니다.
- **로컬 폴더로 설치한 Claude Code 플러그인.** 로컬 폴더 경로로 추가한 마켓플레이스에서 Claude Code 플러그인을 설치하면 Claude Code는 그 폴더에서 플러그인을 읽고 `sennard hooks`는 그 폴더에 쓰지 않으므로, 플러그인은 빈 정의를 유지해 Sennard의 훅과 MCP 도구가 실행되지 않습니다. `sennard hooks`는 Claude Code가 읽는 파일과 덮어쓸 정의를 알리는 오류로 끝납니다. git 마켓플레이스로 설치한 플러그인은 정상입니다. [플러그인 업데이트와 `sennard hooks`](../user/update.ko.md#플러그인-업데이트와-sennard-hooks)를 봅니다.
